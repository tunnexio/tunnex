Tunnex gateway "{{ .Release.Name }}" rendered as ONE connector identity.

INSTALL CONTRACT
  Use `tunnex k8s install` for the customer flow. It creates the one-time token
  Secret outside Helm with create-only semantics, rechecks the plan fingerprint,
  runs `helm install --atomic --wait`, verifies
  /readyz, and deletes the consumed Secret only after success.

  This chart requires hostNetwork, NET_ADMIN + NET_BIND_SERVICE on the ordinary
  gateway, /dev/net/tun, and the separate cluster-singleton tunnex-host-posture
  manager. The manager owns privileged host preparation. The unprivileged
  gateway admission init only reads its heartbeat and receives NO
  service-account token, join token, or identity state volume.

Security posture (for your security team's review):
  - Capabilities: the pod drops the ENTIRE default set and adds back ONLY NET_ADMIN and
    NET_BIND_SERVICE (not privileged:true; allowPrivilegeEscalation:false; seccompProfile
    RuntimeDefault).
  - Kubernetes API: the gateway reads Service ENDPOINTS to DNAT a VIP to a ready pod. Its
    ServiceAccount token IS mounted and bound to a READ-ONLY ClusterRole over EXACTLY two
    resource types — `services` and `discovery.k8s.io/endpointslices` (get/list/watch). It
    CANNOT read Secrets, CANNOT write anything, CANNOT escalate. It talks to the control
    plane over mTLS. (A VIP→ClusterIP DNAT cannot complete — kube-proxy will not re-DNAT it
    — so the gateway resolves ready pod IPs itself; hence the minimal read grant.)
  - Access-event collection uses NFLOG group {{ .Values.flowLog.group }} in the
    Kubernetes node's HOST network namespace. Confirm it does not collide with
    another host workload's NFLOG consumer before rollout. Canary one gateway/node
    at a time: the required pod restart briefly interrupts that gateway's datapath.
    `helm upgrade ... --set flowLog.group=0 --wait` is the observation-only rollback;
    it removes future Tunnex log clauses without changing allow/drop policy semantics
    or deleting access events already retained by the control plane.

STATE AND LIFECYCLE
  Claim: {{ include "tunnex-gateway.stateClaimName" . }}
{{- if and .Values.persistence.enabled .Values.persistence.retain }}
  RETAINED: `helm uninstall` does not delete this claim. It contains the node
  certificate, WireGuard key, HA fences, leases, and authority evidence.
{{- end }}
  Never share a Secret, release name, or claim between HA A and B. Install each
  connector as its own release and let Tunnex own pool promotion/drain.

  Upgrade with immutable image.digest and `--atomic --wait`. Change only the
  non-secret rolloutRevision when an intentional pod recreation is required.
  Rollback/reinstall must preserve or explicitly reuse the exact retained claim.

  Identity rotation and state deletion are NOT Helm side effects. Safely detach
  and revoke the old node first, then use a distinct release and new claim.
  Deleting the retained claim destroys recovery material and is irreversible.

READINESS
  kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "tunnex-gateway.fullname" . }}
  kubectl -n {{ .Release.Namespace }} get svc {{ include "tunnex-gateway.fullname" . }}-wg
  Kubernetes readiness is the agent's real /readyz result, not pod process state.
