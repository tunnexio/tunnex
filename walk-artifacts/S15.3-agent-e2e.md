**The founder's requirement, tested verbatim:** *"once ai-agent is enrolled against the gateway it should give
cli command so that user can run that in ai-agent server and connect to gateway now agent can access to all
other destination services as per access rule"*.

⛔ **The command under test is the one the product generated — copied off the enrolment modal, not written for
the test.** A command composed by hand proves the tunnel; only the generated one proves the feature.

## 1. THE ALLOWED REQUEST — on the wire, end to end

```
16:53:23.567459 wg0   In  IP 10.99.0.2.53830   > 172.18.0.11.8931: Flags [S]
16:53:23.567527 eth0  Out IP 172.18.0.12.53830 > 172.18.0.11.8931: Flags [S]     ← gateway, masqueraded
16:53:23.567620 eth0  In  IP 172.18.0.11.8931  > 172.18.0.12.53830: Flags [S.]
16:53:23.567627 wg0   Out IP 172.18.0.11.8931  > 10.99.0.2.53830:   Flags [S.]   ← back down the tunnel
```

`{"mcp":"ok","tools":["search","fetch"]}` — **the agent read the MCP server's response through the VPN.**

## 2. ⭐ AND IT WAS THE GRANT THAT ALLOWED IT — the step that makes step 1 mean anything

A request that succeeds proves reachability. It does **not** prove enforcement: an absent policy and a
satisfied policy produce **the same successful request.** The counter delta separates them.

```
before:     grant=packets 0   default_drop=packets 0
  → GET 172.18.0.11:8931  →  {"mcp":"ok",...}
after:      grant=packets 1   default_drop=packets 0     ← the GRANT rule counted it
  → GET 172.18.0.11:8932  →  timed out
after8932:  grant=packets 1   default_drop=packets 4     ← the adjacent port hit tunnex_default_drop
```

⛔ **Same source, same host, one port apart: one counted by the grant, the other by the default drop.** Port
scope is enforced, not merely configured.

### ⚠ And the drop is MEASURED, not inferred

`tunnex_default_drop` is a **global** counter on a gateway carrying nine other devices. `0 → 4` is equally
consistent with the agent's SYN retries **and** with any other dropped forward packet in that window — so on
its own it attributes nothing. Captured directly instead:

```
wg0 In IP 10.99.0.2.48940 > 172.18.0.11.8932    ← ×5, SYN retries
eth0 …                                           ← ZERO packets on 8932
```

**Five in, none forwarded.** The gateway received the denied flow and did not pass it.

⚠ **The first attempt at this capture was invalid and is recorded rather than quietly re-run:** the filter was
`host 10.99.0.2`, which cannot match the **post-masquerade** packet (`172.18.0.12`). "No `eth0` output" under
that filter is a property of the filter, not of the gateway. Re-run port-only.

⚠ **The counters had to be read inside one window.** The agent's full-sweep reconcile rewrites the table
periodically, which **zeroes them** — a counter read a minute late reads `0` on a rule that had fired, and
looks exactly like a rule that never matched. That misread cost this walk an hour and is the reason the
measurement is a *delta*, never an absolute.

## 3. THE PER-RULE TOGGLE — and the control

⛔ **THIS SECTION IS NOT A REVOKE, AND WAS TITLED AS ONE.** *Disable ≠ revoke* is a standing founder ruling;
`PATCH enabled=false` turns a grant off and leaves the credential alive. The real revoke is §3b.

| step | on the wire | the request |
| --- | --- | --- |
| grant enabled | `ip saddr 10.99.0.2 … daddr 172.18.0.11 tcp dport 8931 accept` | `{"mcp":"ok",…}` |
| **`PATCH enabled=false`** → reconcile | **rule GONE** — nothing pairs the agent with the resource | **timed out** |
| **`PATCH enabled=true`** → reconcile | rule back | `{"mcp":"ok",…}` |

⛔ **The restore is not a courtesy, it is the control.** Access that dies after a toggle is consistent with
the toggle *and* with the rig breaking at that moment. Only its return on re-enable rules the second out.

Driven through the **product's own API**, not SQL — an enforcement proof taken by writing to the database
would be proving the compiler, not the product.

## 3b. THE ACTUAL REVOKE — the full sweep, on the wire

`POST /organizations/{org}/devices/{device}/revoke` → **204**.

| what | after |
| --- | --- |
| device row | `status = revoked` |
| **WireGuard peer on `wg0`** | **GONE from the interface** |
| **nft rule** | **GONE** |
| the request | **timed out** |

⛔ **The peer disappearing is the half a policy toggle cannot prove.** A disabled grant leaves the agent
connected and merely unauthorised; a revoke removes it from the interface, so the credential itself is dead.

⚠ **What this did NOT exercise:** the `policy_rules.src_device_id` `ON DELETE CASCADE` from 0070. Revoke does
not delete the device row — **the grant row survives, still pointing at a revoked device** (verified: 1 rule
remaining). So the cascade that D26 holds open is *still untested on a wire*, and this walk must not be read
as having closed it.

## 4. ⛔ THE DEFECTS THIS FOUND — none of which any test could have

### 4.1 The generated command pointed at documentation space

`Endpoint = 198.51.100.10:51820` — **RFC 5737**, an address reserved for examples. The Node DTO did not serve
`endpoint`, so the UI had nothing real to put there. **Fixed**: `endpoint` is served, and the gateway picker
**only offers gateways that have one** — the product now refuses to issue a config it knows is undialable
rather than issuing one that fails at the user's terminal.

### 4.2 ⭐ AllowedIPs carried the pool and nothing else — and my own earlier test concealed it

An agent runs `wg-quick`. It cannot poll for routes the way the desktop client does, so **every destination it
will ever reach must be in the config at mint time.** It was not.

⛔ **This defect was invisible in my first test because I had added the destination route by hand.** A test
that repairs the thing it is testing reports success about a product that does not work.

**Fixed** at the one line that decides it:

```go
// ⛔ AN AGENT IS ALWAYS A STATIC EXPORT, AND THIS IS THE LINE THAT MAKES IT REACHABLE AT ALL.
isStatic := in.Provisioning == "static" || in.Kind == "agent"
```

### 4.3 ⭐ The malformed-key guard, second path — the gateway was configuring ZERO peers

A fixture node key reached `wg syncconf` through **`ListSiteGatewaysForOrg`**, which still guarded
`wg_public_key <> ''`. `wg syncconf` is all-or-nothing: the whole interface config was rejected.

> ## **THE S15.2 CENSUS FOUND THIS CLASS AND FIXED THE WRONG MEMBER OF IT.** The device path was corrected;
> ## the **site-link** path had the identical too-narrow predicate and was never enumerated, because the
> ## census's input was *device* queries rather than *every query that yields a key to the data plane.*

**Fixed** with the format predicate, and **all key-yielding queries re-censused by that input** — which is the
census that should have been run the first time.

---

### 4.4 ⛔ ONE AGENT PER GATEWAY — AND A REVOKE BRICKS THE SLOT FOREVER

Found by checking §4.1's fix on a *freshly created* agent, which is the only reason it surfaced at all.

```
devices_agent_node_key :: UNIQUE (node_id) WHERE kind = 'agent' AND deleted_at IS NULL
```

**A gateway can carry exactly one agent, product-wide.** The requirement is *"agent can access all other
destination services as per access rule"* — plural agents, per-agent rules — and the schema permits one.

⛔ **And the index survives a revoke.** Its predicate is `deleted_at IS NULL`; revoke sets
`status='revoked'` and **never sets `deleted_at`**. Verified after §3b: creating a replacement agent on that
same gateway returns **409**. *A revoked agent consumes its gateway's only agent slot permanently, and the
gateway can never host another agent.*

⚠ **The 409 also says the wrong thing** — `"this public key is already registered on the node"`. The
constraint violated is one-agent-per-node; the public key is not duplicated and the operator cannot act on
what they are told.

> ## **THE INDEX WAS CORRECT FOR THE MODEL IT WAS WRITTEN UNDER, AND THE MODEL CHANGED UNDER IT.** In S15.2 an
> ## agent *was* the node, so one agent row per node was a tautology with a DoS guard attached (a re-enrolment
> ## loop exhausting the org pool through a door the device cap deliberately does not watch). Under the peer
> ## model an agent is an operator-created device — **the enrolment loop it defends against no longer exists,
> ## and the limit it imposes is now the product's ceiling.**

⛔ **NOT FIXED — HALT-AND-SURFACE.** Dropping the index re-opens a real question the index was answering:
agent devices are **cap-exempt** (0067), so with no uniqueness there is nothing at all bounding how many pool
addresses agents consume. *Drop the index* and *leave the pool unbounded* are one edit apart, and choosing
silently is exactly what the protocol forbids. Recommendation, for the founder's ruling: **drop the
node-scoped uniqueness, and bound agents by an org-level count** — the limit belongs where the pool is, not on
the gateway.

---

### 4.5 ⭐ `wg-quick` DELETES THE INTERFACE WHEN `resolvconf` IS MISSING — the command silently does nothing

Found while restoring the rig to demonstrate the status surface. The generated config carries `DNS = 10.99.0.1`,
so `wg-quick` shells out to `resolvconf` — and **on any failure there it rolls the whole interface back**:

```
[#] ip link add dev tunnex type wireguard
[#] ip -4 address add 10.99.0.4/32 dev tunnex
[#] ip link set mtu 1420 up dev tunnex          ← four lines that all look like success
[#] resolvconf -a tunnex -m 0 -x
resolvconf: could not detect a useable init system
[#] ip link delete dev tunnex                   ← the tunnel deletes itself
```

⛔ **On a minimal container or slim VM — exactly the host an AI agent runs on — the operator is left with no
interface, no route, and a command that appeared to work.** Alpine, distroless and most slim base images ship
no `resolvconf`.

### ⛔ AND IT CONCEALED ITSELF, BY THE SAME MECHANISM AS §4.2

With no tunnel route, the agent reached `172.18.0.11` **directly over the host network** — same bridge — so
the request still returned `{"mcp":"ok",...}` and I recorded the rig as healthy. The gateway's peer counters
were frozen at `rx=648` the whole time and I read the freeze as *stale telemetry* rather than as *no traffic*.

> ## **A SUCCESSFUL REQUEST IS NOT PROOF THE TUNNEL CARRIED IT.** Only a counter delta on the peer is. This
> ## is the third time in this session that a green result came from a path that bypassed the thing under
> ## test, and the first two were already written down one section above.

`ip route get <dst>` is now the first check after any tunnel bring-up, before any request is believed.
Re-verified properly: `rx 1188 → 1940` across one request.

**Fixed** to the extent it can be without a ruling: `AGENT_PREREQ` now names `openresolv` alongside
`wireguard-tools`. ⚠ **The deeper question is open and is the founder's** — *should an agent's config carry
`DNS =` at all?* It buys tunnel-side name resolution (S8.4) and costs a hard dependency that fails silently
and totally. Dropping it for agents, or emitting `PostUp` fallbacks instead, are both real options.

⚠ **Rig deviation, recorded:** the `DNS =` line was stripped from the config on the agent host to bring the
tunnel up. Everything else is the product's command verbatim.

## 5. WHAT THIS DOES NOT PROVE

- **No MCP protocol was spoken.** A real HTTP server on a known port proved *enforcement*. The `/32`, the
  port, the grant and the drop are all real; the payload's MCP-ness is not.
- **One gateway, one org, containers on one bridge.** No multi-site, no cross-cloud, no NAT traversal from a
  genuinely remote agent — the endpoint here is reachable on the same L2.
- **Reconcile latency is unmeasured.** Revoke took effect within the 25s wait; the actual bound is unknown,
  and *"a revoke lands eventually"* is a weaker claim than the table above reads as.
- **The endpoint fix was never seen on the screen the founder complained about.** §4.1 is verified in the
  served DTO and in a command that dialled successfully — **not** on a freshly-rendered enrolment modal,
  because §4.4's 409 made a fresh agent uncreatable. *Verified at the API, unverified at the surface.*

### ⛔ AND THE RIG WAS CHANGED TO MAKE THE COMMAND WORK

The gateway's approved subnet started as `172.18.0.0/16` and **I narrowed it to `172.18.0.11/32`** because
`wg-quick` failed with `File exists`: the exported range **overlapped the agent host's own `eth0` subnet**, so
the generated config tried to route the agent's local network into the tunnel.

⛔ **I filed that as a test-setup artifact. It is not.** §4.2 states the law that convicts it — *a test that
repairs what it tests reports success about a product that does not work* — and this is the same move one
section later. Overlapping RFC1918 space is the **normal** case: an agent on `10.0.1.0/24` and a gateway
exporting `10.0.0.0/16` reproduces it exactly.

Nothing in the mint path detects this, and **it cannot** — the control plane does not know the agent host's
local subnets. So the generated command either dies at the operator's terminal with `File exists`, or, where
it does not collide outright, **silently pulls the host's own network into the tunnel.** No warning, no
diagnostic, and the operator's only evidence is a command that the product told them to run.

**Open, unfixed, and not a rig quirk.**
