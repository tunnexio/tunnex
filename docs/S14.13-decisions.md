# 10. THE TWO REGISTERED ITEMS, RANKED — and one is sharper than filed

## ⛔ #1 — **`domain_taken` IS ALWAYS A FALSE CROSS-TENANT ACCUSATION ON THE CLAIM PATH**

**NEW, and it outranks both items I registered.** Found by probing the constraints rather than reading them.

`mapClaimErr` (`domain.go:197`) maps **any** `23505` to `domain_taken` —
*"this domain is already captured by another organization"*. **MEASURED** (probe run in a transaction and
rolled back, both halves):

```
same org, same domain      -> ERROR: duplicate key ... "domain_claims_org_domain_key"
                              DETAIL: Key (org_id, domain)=(...) already exists.
second org, CREATE against
a VERIFIED claim elsewhere -> INSERT 0 1     ← SUCCEEDS
then VERIFY it             -> ERROR: duplicate key ... "domain_claims_verified_domain_key"
```

**The global index is `UNIQUE (domain) WHERE verified_at IS NOT NULL`, and a fresh insert has
`verified_at = NULL` — so it is not in that index at all.** A second org can always CREATE. Therefore the only
`23505` reachable from `CreateClaim` is the **same-org duplicate**, and:

> ## **EVERY `domain_taken` AN OPERATOR CAN SEE ON THE CLAIM PATH IS FALSE. It is never another organization.**
> ## **It is always their own previous claim.**

**AND THE TRIGGER IS THE MAIN RECOVERY PATH, NOT A CORNER CASE.** There is no GET, so an admin who reloads
loses the TXT value. Re-claiming is the *only* way back — and it returns "another organization has captured
your domain." **The write-only-state gap does not merely hide state; it manufactures a false cross-tenant
conflict at the one moment the operator is trying to recover.** Two registered findings interacting, which
neither showed alone.

*Fix is small and server-side: branch on the constraint name, and return the existing claim's token on the
same-org path — the recovery this panel cannot otherwise offer.*

## ⛔ #2 — **NO DELETE VERB + A GLOBAL VERIFIED INDEX: A WRONG CLAIM IS DURABLE AND BLOCKS THE REAL OWNER**

**Cross-tenant consequence, ranked above the audit gap** — it denies a capability to a party who has done
nothing wrong, and no surface can undo it.

Once an org **verifies** a domain, the partial unique index locks it globally (proven above). There is **no
delete verb anywhere in the spec**, so no operator, in either org, can release it. The real owner's own
`Verify` returns `domain_taken` — correct, for them — and there is nothing they or we can do about it from a
UI.

**HONEST BOUNDING, because the severity is not "anyone can squat":** verifying requires **both** a verified
account at the domain (`domain.go:100`) **and** DNS TXT control at the apex. That is insider-or-owner access,
not a stranger. The realistic case is an employee or contractor who captures the company domain into a
personal org, or a legitimate org that later needs to move the domain and cannot.

**THE ONLY RELEASE VALVE IS UNDOCUMENTED AND ACCIDENTAL:** `SuspendDomainClaim` clears `verified_at` — freeing
the global index — but it fires only from `capturingOrgTx`, i.e. **only when someone attempts a signup** on
that domain and the TXT record is found missing. So the remedy is *"delete the DNS record, then have someone
try to sign up"*, which nobody could derive from any surface.

## #3 — **A SUSPEND IS A STATE CHANGE WITH NO AUDIT TRAIL, ON AN AUTH-ADJACENT SURFACE**

`claim_created`, `verified` and `verification_failed` all write audit rows (`domain.go:113/136/145`).
**`SuspendDomainClaim` writes none** (`domain.go:167`). So a domain can be **silently un-verified org-wide**,
capture stops for everyone, and **nothing records that it happened or when** — on the surface that decides
which org new accounts join. The panel warns against removing the record; it cannot report a suspend that
already occurred, because that needs the read that does not exist.

**Ranked below #2 only because it is a detection gap rather than a denial of capability** — but it is the one
that makes #2 hard to diagnose when it happens.

## ⛔ THE DIAGNOSIS THAT BEAT THE REPORT

The finding arrived as *"Google is autofilled, Microsoft is not — compare them and find the difference."*
**There is no difference.** `SsoProvider` renders both providers from ONE component; the fields are
byte-identical. Chrome fills the **first** text+password pair on a page and **one pair per page**, and `google`
is first in `PROVIDERS`.

> ## **A DIFFERENCE IN SYMPTOM DOES NOT IMPLY A DIFFERENCE IN CAUSE. Two instances of one component behaved**
> ## **differently because of POSITION — invisible from the markup, and living one file away in the order of**
> ## **a list.**

**This is the difference between a fix and a relocation:** annotating only Google would have handed the defect
to Microsoft on the first reorder of `PROVIDERS`, and the diff would have looked like a fix. Filed in
`laws.md` with its mechanical check — *when two instances of the same component differ, diff the instances
first; if identical, the cause is their context.*

**And one instance is not a scope.** The report named one field on one provider; the census named the real
one — **five password inputs, zero `autocomplete` attributes.**

## ⛔ THE PROCESS FINDING — the sweep caught a test that never ran

A new Go test reported `ok`. **It had SKIPPED** (`set TUNNEX_TEST_DATABASE_URL`), and `go test` prints `ok` for
a skipped package. Caught only because **all five Go mutations survived** — impossible for a test that asserts.

> ## **A WEAK ASSERTION LETS SOME MUTATIONS SURVIVE. A TEST THAT NEVER EXECUTED LETS ALL OF THEM SURVIVE.**
> ## **A 100% survival rate is a verdict about whether the test RAN, not about its assertions.**

*Ran and passed are different claims* was already law; **this is the instance where the mutation sweep, not a
careful reading, was the instrument.** Filed.

empty set.
