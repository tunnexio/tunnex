# AA-5 login and app-session contract

Status: **In progress**. This implements browser login handoff and own-user sessions after AA-4 transport acceptance. Positive native publication remains AA-6. Existing local/SSO login and configured MFA/password/email gates apply; an administrator still needs an explicit grant to consume application content.

My Applications lists only the caller's eligible published applications and uses server-derived `https://<exact-app-host>/__tunnex_app/start` links. The proxy first obtains the current publication route, generates a 32-byte browser nonce and registers a bounded server-side pending launch through the private proxy authority. The record binds the nonce hash, exact serving tuple and safe relative target for ten minutes; this permits a normal SSO/MFA login ceremony without extending the later launch-code lifetime. Only after registration succeeds does it set a host-only Secure/HttpOnly/Lax pending cookie and redirect to the configured trusted console's fixed `/app-access/launch` route. The console destination carries only server-derived organization/application IDs, nonce SHA256 and the bound target. Its configured HTTPS root must occupy a different registrable domain from app hosts; caller return URLs are forbidden.

The console reuses local or SSO login and keeps a validated internal return destination. A verified human session submits the existing CSRF-protected launch POST. The API's parent validation does not refresh its TTL; existing foreground console authentication keeps its ordinary native behavior. It verifies immutable authentication method/authority epoch, current identity standing, membership/use permission, matching explicit user/group grants, exact active publication and the previously registered pending launch. Redis atomically consumes that pending transaction and creates a hash-only random 32-byte, 60-second launch code bound to the nonce hash, organization/application/exact hostname/user/parent and safe relative target. Wrong target/app, expired pending state or repeat issuance creates no fresh code. The returned redirect is built only from the current server-owned app hostname.

A normal **Open** click in My Applications creates one new unnamed tab and keeps the catalog open. Before navigating that tab to the validated server-owned start URL, the console records a two-minute, child-tab-only intent in its own origin's sessionStorage and severs the opener. The intent binds the signed-in user, organization, application, expected HTTPS app origin and root target. When that same tab returns from the proxy, the console validates and removes the intent before automatically submitting the existing CSRF-protected launch POST; redemption navigates that child only and must match the intended app origin. Neither a query flag nor a referrer creates launch intent. Untrusted external links, missing/expired intent or changed identity keep explicit confirmation instead of automatically issuing a session. Login, configured MFA, current grants, nonce/code single use and revocation remain authoritative.

Local one-click qualification must start from the configured HTTPS console origin. A Vite preview on a different origin can render the UI, but its tab-scoped intent is deliberately unavailable to the HTTPS console and cannot prove the automatic handoff. My sessions remains a separate secondary view with the current user's sessions across applications in the selected organization.

At the reserved redemption GET, the proxy sends the code, its host-only browser nonce and exact hostname to a dedicated direct-TLS AppProxy-authenticated API port. Current authority is checked again. Redis atomically validates the launch binding, consumes the code and creates a fresh independently hashed opaque app session. Nonce mismatch/replay creates no session cookie. A successful response sets the host-only Secure/HttpOnly/Lax app cookie, clears the pending cookie and returns 303 to the safe relative target, removing the code from the visible URL. Responses prohibit caching and referrer leakage. POSTs, upgrades and failed mutations are never replayed.

App Redis records contain hashed tokens and bounded indexes by organization/application/user/parent. The parent token needed for `GetNoTouch` is sealed with the existing master-key sealer, never stored as plaintext in app records or public metadata. Sessions retain the login snapshot's epoch and authentication method. Absolute lifetime cannot exceed the parent absolute deadline; accepted foreground requests alone may refresh app idle. Renewal, stream keepalive and passive/background traffic validate without touching app or parent idle. Every decision rechecks current publication, live identity, grants, durable parent revocation and conservative parent idle deadline. Four-second authority leases are further bounded by session/grant expiry.

Migration 171 introduces a monotonic per-user app authority epoch, a verified epoch on MFA challenges, and durable exact-parent logout hashes. Native local login captures the epoch from password verification. Transparent rehash and self-password change compare both the verified hash and epoch; password reset increments the epoch in the same transaction as the password/CLI sweep. MFA challenges bind that verified snapshot rather than acquiring a newer epoch during the second step. Fresh SSO login captures the current trusted identity snapshot. Epoch-less old parent records require a fresh login for app handoff. Native console compatibility is retained at initial epoch one; a later credential epoch change also denies those legacy parents. Native console authentication checks durable logout and the exact stamped epoch before refreshing idle. Self-password change returns its committed verified snapshot and replaces the current browser parent with that epoch and the original login method and original absolute login deadline. Other parents are denied. If the password commits but the replacement cannot be minted, the API reports `password_changed_login_required`; the UI offers a fresh login rather than claiming the password failed to change.

Logout commits a denial for the hash of its actual live server-side parent session before reporting success; cleanup in Redis is secondary. Missing cookies remain idempotent. An already recorded durable denial also permits an idempotent success during Redis failure. A presented cookie without live parent or durable denial returns a retryable failure: a lost Redis record could otherwise reappear after restoration. Redis/database resolution errors with a cookie cannot silently claim confirmed sign-out. Unknown tokens cannot create arbitrary durable rows. Tombstones retain the known parent absolute expiry and have no automatic cleanup in this slice. A Redis recovery or restored stale parent cannot undo a committed epoch or tombstone denial; database restore itself requires the later qualified operational procedure.

Own-session APIs return bounded public UUIDs and app/time metadata, never secrets. List/revoke operate only on the authenticated user's organization and session ownership. Current/other labels derive from trusted parent binding. UI handles scoped organization changes, stale requests, empty access, expiration and explicit retry; it does not invent active publication or successful termination.

Acceptance requires real local and configured-SSO handoffs, MFA snapshot/reset races, browser nonce/code replay and cookie isolation, safe returns/no open redirects, no admin bypass, unchanged parent TTL, foreground-only idle, own-session privacy/revocation, durable logout/reset during Redis failure/recovery, and stream authority deadlines. Native positive serving and full revocation/rollout qualification are completed with AA-6/AA-7. This file is a contract, not evidence that those checks have already passed.
