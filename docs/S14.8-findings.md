## ⛔ A1 — THE FAILOVER CONTROLLER COULD NEVER CLEAR A DEMOTION (permanent wedge) · FIXED

**Severity: high. It stops working exactly when the fleet is already degraded.**

`apps/api/internal/nodes/failover.go`

```go
var demoted []uuid.UUID          // nil
...
if len(configured) >= 2 {        // the ONLY assignment
    demoted = fc.Step(configured, freshness)
}
...
demotedChanged := !sameOrder(demoted, current.Demoted)
```

`org_hub_set.demoted` is **NOT NULL**. A nil slice reaches pgx as **SQL NULL**.

**THE FAILURE:** an org that has a demoted member and then drops below two configured hubs computes
`demoted = nil`, sees `demotedChanged = true` (nil ≠ `{member}`), writes NULL, and gets
`SQLSTATE 23502`. **The tick fails. And it fails again on every subsequent tick, forever** — the controller
is wedged until a human edits the row by hand.

> ## **THE HA FAILOVER CONTROLLER STOPS WORKING AT THE MOMENT IT IS MOST NEEDED,**
> ## **AND SAYS SO ONLY IN A LOG NOBODY IS TAILING.**

**HOW IT SURFACED:** 42 consecutive `failover_org_failed` lines in the CP log. I only looked because an
unrelated 500 sent me to `docker logs`. **Nothing else reports it** — the API is healthy, every screen
renders, the HA panel shows a hub set. A wedged controller is invisible from the product.

**FIX:** `demoted := []uuid.UUID{}`. One word.

**PROVEN ON THE WIRE, not asserted** — after the fix, monitored for 60s:

```
t+10s  failures60s=0  ticks60s=1  demoted={01900000-...-0000000f0003}
WEDGE CLEARED - controller ticking, zero failures
```

**AND `demoted` IS NOW DERIVED** — the controller demoted `ap-south` itself, for staleness.

## ⛔ A2 — A SPEC-DOCUMENTED INPUT RETURNS 500 · NOT FIXED, WORKED AROUND

**`POST /k8s/clusters/{id}/services` with `port_low` and no `port_high` returns `internal_error`.**

The spec says it is valid:

```yaml
port_high: { nullable: true, description: "High port; omit for a single port or all." }
```

The database forbids exactly that:

```sql
CHECK ((port_low IS NULL AND port_high IS NULL)
    OR (port_low IS NOT NULL AND port_high IS NOT NULL AND port_low <= port_high))
```

**Nothing validates between them**, so a documented input reaches Postgres and the user gets a 500 with
`"an unexpected error occurred"`. **Three-way disagreement: spec says yes, DB says no, handler says nothing.**

**I DID NOT FIX IT.** It is a mid-build fork (spec change vs constraint change vs handler validation) and the
protocol says those halt and surface. **I worked around it** by sending `port_low == port_high`, which
unblocked the exposure without hiding the defect. **Needs a disposition — see D6.**

**(b) MAY BE WHAT S10.3 MEANT.** The per-cluster DNS entry and the anti-collapse FQDN are not accidents — they
are the shape of a system expecting several clusters behind one site.

**⛔ I AM NOT RESOLVING THIS.** It is a data-model ruling whose wrong answer deletes paid-for design, and it
reaches past this screen. **Both options are on the table with their costs; the ruling is the founder's.**

**WHAT IS TRUE EITHER WAY:** today a second cluster on one site is **accepted by the API and cannot work**, and
nothing says so outside an agent log line. That is the defect, independent of which direction fixes it.

# PART F — D9, CHECKED BEFORE BUILDING

**Founder-ordered: confirm the inference is sound, not merely plausible, and say whether this stack can
demonstrate it.** Both answered. **The check changed the rule's wording and its confidence.**

## F1 — WHAT THE KIND ACTUALLY ASSERTS (read from the producer, not the enum name)

```go
// apps/node/internal/control/client.go:172
// K8sEndpointsUnavailable (S10.3 WF-K5) — this gateway fronts exposed Services but has NO successful
// endpoint view from the K8s API (unreachable / RBAC-denied / watch not synced), so no VIP can be
// DNAT-programmed (fail-closed).
```

**IT IS NOT "THE CLUSTER IS DOWN". IT IS "THIS GATEWAY HAS NO ENDPOINT VIEW", from three different causes.**
So my first framing — *"the cluster-reachability signal"* — was reading one fact as another, which is exactly
what `VERIFY-AGAINST-THE-SWITCH` is for.

**BUT THE RULE SURVIVES, BECAUSE THE HONEST PREDICATE IS REACHABILITY, NOT LIVENESS:**

| cause | cluster actually fine? | can a VIP be DNAT-programmed? | should a Service read `LIVE`? |
|---|---|---|---|
| cluster unreachable | no | **no** | **no** |
| RBAC denied | **yes** | **no** | **no** — it is not reachable through the tunnel |
| watch not synced | yes | **no** | **no** |

**In all three the Service is genuinely unreachable, so "not `LIVE`" is true in all three.** The rule is sound;
**the LABEL must say "not reachable", never "cluster down"**, or it asserts a cause it does not know.

## F2 — WHAT D9 DOES *NOT* COVER, AND ONE THING THE SCHEMA DOES NOT ENFORCE

**It does not close absence #2.** A single Service deleted **in Kubernetes** while the watch is healthy leaves
the kind FALSE and that Service still reading `LIVE`. **D9 covers #3, not #2.** My table implied it covered
both.

**AND `k8s_clusters` HAS NO UNIQUE ON `site_id`** — measured:

```
k8s_clusters_pkey             PRIMARY KEY (id)
k8s_clusters_org_id_name_key  UNIQUE (org_id, name)
k8s_clusters_org_id_vip_range_key UNIQUE (org_id, vip_range)
```

So **two clusters may share a site, hence a gateway.** The helm model is one gateway per cluster, in-cluster —
but the data model does not enforce it, so **the gateway→cluster mapping D9 relies on is an assumption, not an
invariant.** With two clusters on one site, one gateway's failed watch would mark both clusters' Services
unreachable. *Arguably still honest* (that gateway can program no VIP at all) but it is an inference worth
stating rather than discovering.

## F3 — ⛔ THIS STACK CANNOT DEMONSTRATE D9

My own survival test: `gw-local-1` reported **`site_link_down`**, not `k8s_endpoints_unavailable`. **No agent
here watches the k3s cluster** — in a real deployment the gateway pod runs in-cluster via helm with a
read-only `services + endpointslices` role; our node-agent is a compose container with no such role.

> ## **SO D9 WOULD SHIP AS A RENDERING RULE NOBODY CAN SEE WORK.**
> ## **THAT IS THE DORMANT-MACHINERY LAW WITH A HEALTH KIND ATTACHED.**

**⛔ AND D9 IS NOW DOWNSTREAM OF THE MODEL QUESTION (A3).** Its sentence — *"no Service on that cluster renders
plain LIVE"* — is **not derivable from served fields while N clusters may share a gateway**: one gateway's
failed watch would degrade Services on every cluster bound to that site, including ones it does not front.
**If A3(a) lands, D9 becomes sound BY CONSTRUCTION.** If it does not, D9 must weaken to *"a cluster whose site
has a gateway reporting no endpoint view"* — still better than plain `LIVE`, but a different claim.

**Three options, and this needs the ruling more than the rule does:**

**(a)** make the review environment produce the kind (run a gateway agent inside k3s with the helm role) —
real proof, most work.
**(b)** ship D9 with a **named substitute**: unit-test the rendering decision, record the wire proof as
DEFERRED with a trigger (the S10.3 box-walk, or first in-cluster gateway deployment).
**(c)** do not ship D9 until (a) exists.

**MY RECOMMENDATION: (b)**, which is the repo's own SUBSTITUTES ≠ SATISFIES convention — and the trigger is a
NAMED EVENT, not "later":

> ### **TRIGGER FOR D9's WIRE PROOF: the first in-cluster gateway agent watching this cluster** — S10.3's
> ### hostNetwork deploy (`helm install gw tunnex/tunnex-gateway`) with the read-only
> ### `services + endpointslices` role. Until that exists, `k8s_endpoints_unavailable` cannot fire here.

`make k3s-demo-verify` prints the limitation out loud so it cannot be forgotten the way a doc line can:

