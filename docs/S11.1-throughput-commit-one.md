# 1. THE PROMETHEUS PATH WAS INVESTIGATED FIRST, AS RULED. IT DOES NOT WORK.

**TWO INDEPENDENT REASONS, and the second is the decisive one.**

## 1.1 The metric does not exist

**The product exports exactly TWO Prometheus metrics.** Measured, not recalled — every `NewDesc` /
`MustNewConstMetric` in the tree:

```
internal/metrics/metrics.go:40   tunnex_scheduler_leader              1 if this replica holds leadership
internal/metrics/metrics.go:49   tunnex_gateway_policy_health{kind}   a gauge of COUNTS per health kind
```

That is the whole surface. (`tunnex_session` is a cookie name, not a metric.)

⚠ **THIS SAID "EXACTLY ONE" WHEN WRITTEN, AND IT WAS TRUE THEN.** `tunnex_scheduler_leader` landed after.
Corrected on re-measure — a paper that says "measured" ages into a claim that merely sounds measured, and
the *number* rotting while the *conclusion* held is the mild version of exactly that. Neither metric is a
per-link byte gauge, so the branch still closes here. **There are no per-link byte
gauges to query, so even the optimistic branch starts by adding the metric.**

## 1.2 ⛔ AND WE DO NOT OWN A METRICS STORE — this is the one that closes the branch

**EPIC 11 exposes `/metrics`. It does not run Prometheus.** There is no scraper and no time-series store
anywhere in `docker-compose.yml` or the deploy manifests. **`/metrics` is a surface for the OPERATOR'S
Prometheus to scrape** — an integration point, deliberately, so we carry no retention cost.

> ## **A SELF-HOSTED PRODUCT CANNOT READ FROM A DATABASE THE CUSTOMER MIGHT NOT HAVE.**

Querying Prometheus would mean **a configured datasource URL per deployment, credentials, a network path from
the control plane to the customer's monitoring stack, and a graceful answer for every operator who does not
run Prometheus at all** — which is most of them on day one. **The dashboard would show a chart or an error
depending on infrastructure we neither ship nor require.**

**RULED OUT. The remaining branch is a first-party table, and this document scopes it.**

# 2. THE HARD PART IS NOT STORAGE. IT IS RESET DETECTION.

```yaml
rx_bytes: "Raw gauge since the last handshake (display only, never summed as monotonic)."
```

**THE COUNTER RESETS ON EVERY HANDSHAKE**, which WireGuard performs roughly every two minutes on an active
link, and immediately on any interface restart. So a naive `value[t] - value[t-1]`:

- is **correct** while no handshake happened between samples
- goes **NEGATIVE** across a handshake
- **silently undercounts** if a reset lands mid-interval and the counter climbs back above its prior value

**A NEGATIVE DELTA IS THE EASY CASE — it is self-announcing.** The dangerous one is the reset that recovers:
sample 100, reset to 0, climb to 90 → a delta of −10 that a naive `max(0, …)` turns into **0 bytes for an
interval that actually carried 90.** *"Quiet"* and *"we lost the count"* draw identically.

## The rule this forces

> **A DELTA IS ONLY DEFINED WHEN THE SAMPLES SHARE A HANDSHAKE. ACROSS A HANDSHAKE BOUNDARY THE INTERVAL IS
> UNKNOWN, AND UNKNOWN IS ITS OWN VALUE.**

`node_peer_status` already carries `last_handshake_at`, so the boundary is **detectable, not inferred**: if
it changed between samples, the interval is `unknown`. **The chart must draw that as a GAP** — the exact
mechanism `Histogram`'s `gap` bin already uses, for the same reason.

**This is why the feature is not "add a table".** Get this wrong and the chart under-reports traffic during
exactly the busy periods that cause more handshakes.

# 3. DECIDE-ITEMS

**D1 — WHO SAMPLES?** The agent already reports on a ~30s cadence and the CP writes `node_peer_status`. **(a)**
The CP snapshots on every report — no agent change, sample rate = report rate, irregular. **(b)** The agent
sends deltas it computed itself — it can see resets it caused, but it is a protocol change and a
`ProtocolVersion` bump. **Recommend (a):** the reset boundary is visible in data the CP already stores.

**D2 — STORAGE SHAPE.** **(a)** A rollup table written by the existing reconciler (`site_link_samples`:
node, peer, bucket, rx, tx, complete). **(b)** Raw append + query-time aggregation — simpler writes, unbounded
growth. **Recommend (a):** EPIC 11 shipped leader election, so exactly one replica rolls up, and retention
becomes a delete rather than a compaction.

**D3 — RETENTION AND RESOLUTION.** The wireframe shows **7 days**. 5-minute buckets × 7 days × N links is
~2,000 rows per link per week. **Recommend: 5-minute buckets for 48h, hourly for 30 days.** A cost decision,
not a UI one — **founder's call.**

**D4 — AGGREGATION LEVEL.** The chart shows **org totals**; the data is **per hub member**. Summing across
members double-counts a byte that traversed two members. **Recommend: sum over LINKS, not members**, and say
so in the caption — otherwise the number is wrong in a way no reader can detect.

**D5 — EDITION.** Site-to-site is all-editions core (D11). **Recommend all editions**, consistent with the
S14.5 sweep. Flagged because a metrics feature is a plausible place to draw an enterprise line, and that
would be a **product** decision rather than a technical one.

# 4. WHAT THIS IS NOT

**NOT a general metrics platform.** One series, one purpose. **The moment it grows a second unrelated series
it should become an exporter and the operator's own Prometheus**, which is what `/metrics` already exists for.

**NOT a replacement for `/metrics`.** That stays the integration point for operators who do run monitoring.
This exists because **the product's own dashboard cannot depend on infrastructure the product does not
ship.**
