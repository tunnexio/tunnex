# S20.3a — Fenced Kubernetes connector handoff

Status: **LOCKED FOR P2 IMPLEMENTATION** on `k8-improvement`.

This story turns the S20.3 connector-pool foundation into a distributed,
restart-safe ownership handoff. The historical
`iotunnex/tunnex@codex/kubernetes-cluster-scope-ha` branch is implementation
evidence, not a merge base. Code is ported only where its contracts still fit
the current control plane, node agent, migrations, and leader-election owner.

## Measured starting point

- S20.3 provides pool configuration, membership epochs, deterministic
  three-tick promotion/five-tick failback decisions, dual-signal evidence, and
  fail-closed legacy/pool reads. It deliberately has no live promotion caller.
- Expand migrations `0081` through `0085` already preserve delivery envelopes,
  acknowledgement receipts, handoff operations, health history, Service UID
  observations, v2 capabilities, and handoff provenance. Current migration tip
  is `0116`; historical migrations are not replayed or rewritten.
- The current API already owns one PostgreSQL advisory-lock leader session for
  writing schedulers. P2 must reuse and re-confirm that exact session before
  every handoff write; a cached leadership boolean is not authority.
- Existing agents know neither an ownership envelope nor a serving lease. Their
  legacy desired-state and report paths must remain byte-compatible.

## Locked decisions

### D1 — Scope and compatibility port

P2 selectively ports the private mTLS delivery protocol, durable store,
handoff coordinator, health-history tick source, leader-gated scheduler, node
apply/read-back loop, and Service UID provenance needed for fencing. It does
not copy generated files from the historical repository; current sqlc and
OpenAPI generation remain authoritative.

P2 adds no public operator API or web UI. P3 owns customer-visible readiness,
attention, opt-in, edition, RBAC, and destructive/recovery copy.

### D2 — Exact capability negotiation; v1 never authorizes serving

Ownership delivery uses its dedicated mTLS-only agent routes. A node receives
an envelope only after advertising the exact supported ownership protocol
version on that request. Missing, older, newer, malformed, or cross-principal
capability fails closed.

Version 1 remains receipt-only for rolling compatibility and can never satisfy
prepare, withdraw, or serving readiness. A handoff requires version 2 applied
state attestation. Old agents continue their existing desired-state/report
behavior and never become accidental HA candidates.

### D3 — One immutable manifest identity per role

Every delivery binds organization, Site, cluster, pool, connector, operation,
role, promotion generation, monotonically increasing manifest revision, lease
epoch/expiry, exact owned routes, exact VIP map, and the live Kubernetes
Service UID provenance. The three roles are disjoint:

- `prepared_non_serving` has zero owned routes and no VIP map;
- `withdrawal` has zero owned routes and proves the prior lease is gone; and
- `serving` has the exact issued routes and VIP map.

The node applies, reads back, and durably records the exact result before it
acknowledges. A changed replay, stale revision/generation/epoch, expired lease,
partial apply, or mismatched read-back produces no acknowledgement.

### D4 — Break before make

Every promotion/failback executes this order:

1. issue candidate `prepared_non_serving` and receive fresh v2 applied ACK;
2. issue old-owner `withdrawal` and receive fresh v2 zero-ownership ACK, or
   wait until its control-plane-issued lease has expired;
3. compare-and-swap the pool active member and generation using the operation's
   expected generation and observed membership epoch;
4. issue the new-owner `serving` manifest under a strictly newer lease epoch;
5. receive fresh v2 serving ACK before recording the operation completed.

There is no path that serves the candidate before step 3, and no path that
changes database ownership before step 2. If the old owner is unreachable,
expiry is the only substitute for withdrawal; an agent timestamp is never
freshness evidence.

### D5 — Control-plane time and bounded leases

The control plane owns issue, receipt, and expiry time. Agent-observed time is
diagnostic only. Serving authority is bounded by the signed-in mTLS delivery
contract and expires locally even if the control plane disappears. A node must
withdraw ownership on expiry before accepting a successor lease.

Lease duration and scheduler cadence are bounded configuration with validated
safe defaults. A lease cannot be renewed across a changed generation,
membership epoch, manifest identity, or Service UID observation.

### D6 — Durable, idempotent, restart-safe operations

At most one non-terminal operation exists per pool. Its immutable artifacts,
digests, epochs, expected generation, decision transition, and receipt
provenance are stored before external delivery. Exact retries are idempotent
and retain their original control-plane receipt time. A restarted leader
reconstructs only from durable state; it never synthesizes an artifact or
restarts from an earlier phase.

Pre-CAS membership churn terminally aborts the operation. Post-CAS recovery
continues to converge the committed active owner to serving or truthful
attention; it never rolls ownership backward by inference.

### D7 — Leadership is a checked write prerequisite

The scheduler reuses the current advisory-lock elector. Each writing tick and
delivery issue verifies `pg_backend_pid()` and the exact advisory lock on the
same acquired connection. Losing or being unable to prove leadership stops new
writes. Every step remains replay-safe because leadership can change after any
committed transaction.

The scheduler is compiled and wired but defaults **OFF**. P3's explicit
organization opt-in and operator readiness gate must be present before a
customer can turn it on; edition unlock alone never activates it.

### D8 — Health history and selection truth

The scheduler persists consecutive evidence by candidate and membership epoch,
then feeds the S20.3 pure state model. Missing/old evidence resets the relevant
streak. Three healthy ticks may promote while the current owner is stale; five
healthy ticks may fail back to the preferred member. No eligible v2 candidate,
ambiguous evidence, or a non-terminal operation yields `needs_attention` and
no ownership move.

### D9 — Service identity is delete/recreate safe

The serving manifest includes only current exact-port Service children whose
cluster/namespace/opaque Kubernetes Service UID provenance is current. A
delete/recreate with the same presentation name is a new identity and cannot
inherit ownership. Missing, stale, cross-cluster, or unacknowledged UID
observation withdraws that Service from the issued manifest.

### D10 — Audit claims only committed transitions

Promotion/failback audit is written atomically with the active-member CAS and
names the system actor, cause, old/new connector, pool, decision transition,
generation, operation, and membership epoch. Prepare/delivery attempts are
operation provenance, not successful ownership claims. Failed or expired
operations remain inspectable without emitting a success audit.

### D11 — Expand, activate, and rollback

The forward path is: keep existing schema/data, deploy compatible API and node
code with scheduler disabled, observe v2 capability and UID provenance, then
allow the later P3 opt-in to activate eligible pools. There is no destructive
backfill and no new migration unless implementation proves an additive gap;
any accepted gap starts at `0117`.

Rollback is: disable scheduling, allow or command every issued lease to
withdraw/expire, then roll application code back while retaining the additive
ledger. Schema contraction and row deletion are explicitly outside this story.
An application rollback while a live serving lease exists is refused as an
operational procedure because old code cannot renew or safely revoke it.

### D12 — Proof and stop boundary

Required red/green proof covers exact capability negotiation, frame bounds,
cross-principal scope, replay, monotonic revisions and epochs, lease expiry,
apply/read-back persistence, prepare-before-withdraw, withdrawal-or-expiry
before CAS, CAS-before-serve, membership churn, leader-session verification,
leader loss/restart resume, Service UID recreation, and unchanged legacy
agent behavior. Both editions and the node's Linux ownership tests are gates.

P2 can be called **fenced handoff implemented** after local integration proof.
It cannot be called deployed HA until the box-walk proves primary loss, lease
expiry/withdrawal, promotion, traffic recovery, failback, and no simultaneous
VIP/route ownership on real Linux connectors. P3 UI and cluster-scope access
remain separate stories.

## Implementation slices

1. Pure manifest/envelope/lease contracts and current-schema query layer.
2. Private mTLS issue/poll/ACK store with exact v2 attestation.
3. Node apply/read-back, durable local state, expiry withdrawal, and run loop.
4. Durable coordinator, promotion CAS/audit, health-history resolver, and
   leader-session scheduler wiring default OFF.
5. Focused integration, mixed-version, restart, and Linux ownership proof;
   then formal multi-finder review before P3 begins.
