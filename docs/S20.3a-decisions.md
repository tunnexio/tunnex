# S20.3a — Fenced Kubernetes connector handoff

Status: **LOCKED FOR P2 IMPLEMENTATION** on `k8-improvement`.

This story turns the S20.3 connector-pool foundation into a distributed,
restart-safe ownership handoff. The historical
`iotunnex/tunnex@codex/kubernetes-cluster-scope-ha` branch is implementation
evidence, not a merge base. Code is ported only where its contracts still fit
the current control plane, node agent, migrations, and leader-election owner.

## Measured starting point

- S20.3 provides pool configuration, membership epochs, deterministic
  three-tick promotion/five-tick failback decisions, dual-signal evidence, and
  fail-closed legacy/pool reads. It deliberately has no live promotion caller.
- Expand migrations `0081` through `0085` already preserve delivery envelopes,
  acknowledgement receipts, handoff operations, health history, Service UID
  observations, v2 capabilities, and handoff provenance. Current migration tip
  is `0116`; historical migrations are not replayed or rewritten.
- The current API already owns one PostgreSQL advisory-lock leader session for
  writing schedulers. P2 must reuse and re-confirm that exact session before
  every handoff write; a cached leadership boolean is not authority.
- Existing agents know neither an ownership envelope nor a serving lease. Their
  legacy desired-state and report paths must remain byte-compatible.

## Locked decisions

### D1 — Scope and compatibility port

P2 selectively ports the private mTLS delivery protocol, durable store,
handoff coordinator, health-history tick source, leader-gated scheduler, node
apply/read-back loop, and Service UID provenance needed for fencing. It does
not copy generated files from the historical repository; current sqlc and
OpenAPI generation remain authoritative.

P2 adds no public operator API or web UI. P3 owns customer-visible readiness,
attention, opt-in, edition, RBAC, and destructive/recovery copy.

### D2 — Exact capability negotiation; only v3 authorizes handoff

Ownership delivery uses its dedicated mTLS-only agent routes. A node receives
an envelope only after advertising the exact supported ownership protocol
version on that request. Missing, older, newer, malformed, or cross-principal
capability fails closed.

Version 1 remains receipt-only. Historical version 2 can attest routes and a
VIP-map digest but does not carry or locally enforce lease expiry and does not
own the full serving domain; it therefore cannot satisfy prepare, withdraw, or
serving readiness. A handoff requires version 3. Old agents continue their
existing desired-state/report behavior and never become accidental HA
candidates.

### D3 — One immutable manifest identity per role

Every v3 delivery binds organization, Site, cluster, pool, connector, operation,
role, promotion generation, monotonically increasing manifest revision, lease
epoch/expiry, exact owned routes, WireGuard AllowedIPs, VIP/DNAT map, DNS
listener/zone/answers, and live Kubernetes Service UID provenance. The three
roles are disjoint:

- `prepared_non_serving` has zero owned routes and no VIP map;
- `withdrawal` has zero owned routes and proves the prior lease is gone; and
- `serving` has the exact issued routes and VIP map.

The node gates ordinary Kubernetes reconciliation through that same ownership
state, then applies, reads back, and durably records all four serving domains
before it acknowledges. A changed replay, stale revision/generation/epoch,
expired lease, partial apply, or mismatched read-back produces no
acknowledgement. Ordinary desired state cannot re-add a withdrawn domain.

### D4 — Break before make

Every promotion/failback executes this order:

1. issue candidate `prepared_non_serving` and receive fresh v3 applied ACK;
2. issue old-owner `withdrawal` and receive fresh v3 zero-ownership ACK, or
   wait until its control-plane-issued lease has expired;
3. compare-and-swap the pool active member and generation using the operation's
   expected generation and observed membership epoch; pool consumers fail
   closed behind the still-nonterminal operation;
4. issue the new-owner `serving` manifest under a strictly newer lease epoch;
5. receive fresh v3 full-domain serving ACK before recording the operation
   completed and exposing the new active owner to policy/topology/DNS.

There is no path that serves the candidate before step 3, and no path that
changes database ownership before step 2. If the old owner is unreachable,
expiry is the only substitute for withdrawal; an agent timestamp is never
freshness evidence.

### D5 — Control-plane time and bounded leases

The control plane owns issue, receipt, and expiry time. Agent-observed time is
diagnostic only. Version 3 carries the exact CP expiry in the authenticated
mTLS envelope and persists it locally. Serving authority expires and all four
domains withdraw even if the control plane disappears. Startup reconciles
expiry before polling; corrupt/missing state or backward wall-clock movement
withdraws immediately and never extends authority.

Lease duration and scheduler cadence are bounded configuration with validated
safe defaults. A lease cannot be renewed across a changed generation,
membership epoch, manifest identity, or Service UID observation.

### D6 — Durable, idempotent, restart-safe operations

At most one non-terminal operation exists per pool. Its immutable artifacts,
digests, epochs, expected generation, decision transition, and receipt
provenance are stored before external delivery. Exact retries are idempotent
and retain their original control-plane receipt time. A restarted leader
reconstructs only from durable state; it never synthesizes an artifact or
restarts from an earlier phase.

Pre-CAS membership churn terminally aborts the operation. Post-CAS recovery
does not blindly revert ownership: it converges the committed active owner to
serving or truthful attention while the nonterminal operation keeps every
ordinary consumer withdrawn.

### D7 — Leadership is a checked write prerequisite

The scheduler reuses the current advisory-lock elector. Each writing tick and
delivery issue verifies `pg_backend_pid()` and the exact advisory lock on the
same acquired connection. Losing or being unable to prove leadership stops new
writes. Every step remains replay-safe because leadership can change after any
committed transaction.

The scheduler is compiled and wired but defaults **OFF**. P3's explicit
organization opt-in and operator readiness gate must be present before a
customer can turn it on; edition unlock alone never activates it.

### D8 — Health history and selection truth

The scheduler persists consecutive evidence by candidate and membership epoch,
then feeds the S20.3 pure state model. Missing/old evidence resets the relevant
streak. Three healthy ticks may promote while the current owner is stale; five
healthy ticks may fail back to the preferred member. No eligible v3 candidate,
ambiguous evidence, or a non-terminal operation yields `needs_attention` and
no ownership move.

### D9 — Service identity is delete/recreate safe

The serving manifest includes only current exact-port Service children whose
cluster/namespace/opaque Kubernetes Service UID provenance is current. A
delete/recreate with the same presentation name is a new identity and cannot
inherit ownership. Missing, stale, cross-cluster, or unacknowledged UID
observation withdraws that Service from the issued manifest.

Migration `0119` replaces only the selected-connector trigger from `0084`: a
legacy cluster retains its exact connector rule; a pool-bound cluster accepts
only its exact active, eligible member under a positive generation. Standby,
former, revoked, cross-scope, invalid-key, and endpoint-less members are
refused. Historical migration `0084` remains immutable.

### D10 — Audit claims only committed transitions

Promotion/failback audit is written atomically with the active-member CAS and
names the system actor, cause, old/new connector, pool, decision transition,
generation, operation, and membership epoch. Prepare/delivery attempts are
operation provenance, not successful ownership claims. Failed or expired
operations remain inspectable without emitting a success audit.

### D11 — Expand, activate, and rollback

The forward path is: keep existing schema/data, deploy compatible API and node
code with scheduler disabled, observe v3 capability and UID provenance, then
allow the later P3 opt-in to activate eligible pools. There is no destructive
backfill and no new migration unless implementation proves an additive gap;
any accepted gap starts at `0119`.

Rollback is: disable scheduling, allow or command every issued lease to
withdraw/expire, then roll application code back while retaining the additive
ledger. Schema contraction and row deletion are explicitly outside this story.
An application rollback while a live serving lease exists is refused as an
operational procedure because old code cannot renew or safely revoke it.

If a later operator deliberately contracts migration `0120`, the preflight is
part of the operation, not an optional guard: prove that there are zero wire-v3
deliveries, non-null applied manifests, and wire-v3 capability rows before
running the down migration. The SQL migration repeats that check and refuses
otherwise. `golang-migrate` marks a refused down dirty before PostgreSQL runs
the transactional guard; after proving that no DDL committed, recovery is to
force the recorded version back to `118`, complete the application-owned v3
cleanup, re-run the zero-row preflight, and only then retry the contraction.
The retained PostgreSQL proof exercises the supported clean contraction path;
it does not present a deliberately dirty database as a successful rollback.

### D12 — Proof and stop boundary

Required red/green proof covers exact capability negotiation, frame bounds,
cross-principal scope, replay, monotonic revisions and epochs, lease expiry,
full-domain apply/read-back persistence, startup/disconnect/backward-clock
withdrawal, prepare-before-withdraw, withdrawal-or-proven-local-expiry before
CAS, nonterminal consumer withdrawal, CAS-before-serve, membership churn,
leader-session verification, leader loss/restart resume, Service UID
recreation, and unchanged legacy agent behavior. Both editions and the node's
Linux ownership tests are gates.

P2 can be called **fenced handoff implemented** after local integration proof.
It cannot be called deployed HA until the box-walk proves primary loss, lease
expiry/withdrawal, promotion, traffic recovery, failback, and no simultaneous
VIP/route ownership on real Linux connectors. P3 UI and cluster-scope access
remain separate stories.

## Implementation slices

1. Pure manifest/envelope/lease contracts and current-schema query layer.
2. Private mTLS issue/poll/ACK store with exact v3 full-domain attestation.
3. Node full-domain apply/read-back, durable local state, expiry withdrawal,
   ordinary-reconcile gate, and run loop.
4. Durable coordinator, promotion CAS/audit, health-history resolver, and
   leader-session scheduler wiring default OFF.
5. Focused integration, mixed-version, restart, and Linux ownership proof;
   then formal multi-finder review before P3 begins.

## Approved P0/P1 audit dispositions (2026-08-28)

The historical runtime audit found that its v2 node changed marker routes only,
carried no enforceable expiry, allowed a CP-only expiry fallback, and switched
ordinary consumers at the active-member CAS. The founder directed the team to
fix blocking issues and continue. The following dispositions are locked:

1. **Replace handoff eligibility with exact v3 capability.** v1/v2 remain
   compatible but cannot authorize HA.
2. **Lease the whole serving domain.** Routes, WireGuard AllowedIPs, VIP/DNAT,
   DNS listener/zone/answers, and ordinary Kubernetes reconcile share one
   authority and one full read-back ACK.
3. **Make expiry real on the node.** Persisted CP expiry, startup reconciliation,
   disconnect watchdog, and backward-clock/corrupt-state withdrawal are
   prerequisites to any expiry fallback.
4. **Gate consumers until serving confirmation.** For generation greater than
   one, a matching completed durable handoff is required; a CAS with a
   nonterminal operation compiles/delivers no Kubernetes ownership.
5. **Add migration 0119 for pool-aware UID authority.** Do not edit `0084`.
6. **Add a leader-owned bootstrap reconciler.** Scheduler eligibility requires
   fresh v3 capability, prepared standbys, and a verified current-owner serving
   lease; legacy desired-state success is never upgraded by inference.
7. **Preserve current S21/v9 policy and node contracts.** Historical files are
   adapted field-by-field, never used as wholesale replacements.
8. **Add migration 0120 for durable v3 payloads.** The existing `0081` ledger
   accepts only wire versions 1/2 and cannot preserve the full manifest or
   applied full-domain readback. `0120` expands those rows for exact v3 data;
   its down migration refuses while v3 provenance exists rather than deleting
   active lease history.
9. **Bind actionable dataplane coordinates in v3.** The approved P0 proof fix
   replaces the ambiguous flat WireGuard AllowedIPs set with entries keyed by
   the exact peer public key, and adds each Service's `service_cidr` and
   `dns_name`. The manifest identity, VIP-map digest, apply read-back, and ACK
   bind these values because they respectively control peer routing,
   ClusterIP/headless classification, and the authoritative DNS answer. A v3
   handoff with an unkeyed prefix, duplicated peer/prefix ownership, or a
   partial Service dataplane shape is invalid; v1/v2 compatibility is unchanged.
10. **Expand every provenance capability boundary in `0120`.** The fresh-plan
    child-scope table from `0085` is a separate handoff authority from the
    delivery capability table. Its constraint and member-evidence trigger must
    accept exact v3 with matching delivered/applied manifests while retaining
    exact v2 compatibility. Upgrading only the delivery table would create a
    code path that passes unit tests but can never persist a real v3 claim.
11. **Fence adopted generation-1 fields across withdrawal and restart.** Before
    a v3 activation, the node durably records the exact pool-scoped routes,
    peer-keyed AllowedIPs, VIP mappings, and DNS zones it adopts. The fence is
    independent of the active-lease checkpoint, accumulates later manifest
    revisions, and survives expiry, withdrawal, and restart. A zero lease
    suppresses those legacy base fields while preserving unrelated base state;
    only an explicit authoritative control-plane unfence for the exact
    org/site/cluster/pool scope may retire the tombstone. Field absence is not
    an unfence signal.
12. **Do not create parallel dataplane writers to satisfy v3.** The serialized
    coordinator applies the current owners in activation order DNS, DNAT,
    derived OpenVPN, routes, WireGuard and withdraws/compensates in reverse,
    ACKing only a complete actual readback. Main wiring stays disabled until
    the current owners expose actual readback and a single-writer handoff.
    Route/WireGuard, VIP/DNAT, DNS-VIP, and DNS-table/listener readback now use
    their existing owners and have been removed from the typed blocker set.
    OpenVPN applied-config/process proof (including the controlled-restart vs
    reload disposition) and the agent-main single-writer handoff remain typed
    blockers, not desired-state echoes.

## Approved P2 safety-review dispositions (2026-08-28)

The founder approved every recommended node and API review fix before P2 may
be activated. Default-OFF is retained until all are folded and re-reviewed:

1. Startup withdrawal works from durable pool-scoped ownership evidence before
   a fresh control-plane base arrives; missing/corrupt/expired state cannot
   leave stale kernel ownership serving.
2. Startup and lease installation recheck expiry and backward clock movement
   after full apply/readback, withdrawing before persistence or ACK if the
   deadline was crossed.
3. Compensation uses its own bounded recovery context and attempts every
   reverse-order stage while retaining joined errors for retry.
4. Fences classify the complete pool-owned Kubernetes domain. Changed or extra
   routes, peer prefixes, VIPs, DNS state, and later base revisions remain
   suppressed until an authoritative unfence.
5. Unfence is one prevalidated atomic base+fence transition bound to an exact
   base version/hash, and is refused while ownership is active.
6. DNS VIP ownership is independently enumerable after restart; unknown stale
   Tunnex-owned VIP/listener residue is swept.
7. nft DNAT readback verifies canonical live rule semantics; a retained digest
   comment on an altered rule is not evidence.
8. Route readback binds family, interface, protocol, metric, source hint, and
   destination rather than destination alone.
9. One serialized command lane owns base fetches, endpoint kicks,
   lease/watchdog events, every OS apply, and readback. Existing loops become
   producers, never parallel writers.
10. OpenVPN performs a controlled restart on exact config/CCD/material digest
    change and reports the digest loaded by the still-live process.
11. Service UID rows gain additive reporter/replay attribution. Legacy
    unattributed rows remain stored but ineligible; the selected owner freshly
    reports the UID while the store locks connector authority in the same
    transaction as replay/current updates.
12. Production activation requires the final same-transaction handoff
    provenance fence.
13. Fenced-base readiness is durable and keyed by exact pool and generation,
    rechecked on the leader session for each request.
14. The leader-bound runner loads the exact current phase's v3 attestation
    before each coordinator tick; wrong-role/generation/revision ACKs do not
    advance and restart resumes from durable phase state.
15. The production UID observation store and private mTLS route are wired in
    the server rather than terminating at an unwired 503 seam.
16. The node v3 poll/apply/readback/ACK consumer runs through the same
    serialized command lane. Activation remains impossible until that consumer
    and live-wire proof exist.

No disposition authorizes activation, deployment, push, PR, or merge. The
forward rollout remains expand -> compatible code default-OFF -> fresh v3
evidence -> P3 organization opt-in. Rollback remains disable -> withdraw or
expire every lease -> application rollback while retaining additive ledgers;
no destructive contraction is implicit.
