# Server Access recovery and rotation qualification

Updated 2026-10-05. This is local engineering qualification, not production recovery or a claim that a rotation UI exists. Community edition is included.

## Evidence and isolation

`tests/server-access-local/recovery-qualify.sh` copies **schema only** from the owned `aa0` fixture. It creates a fresh `sa_recovery_source_<random>` database, seeds entirely new synthetic admin/member memberships, explicit grant, gateway/server, CA, active session, encrypted recording, and logout tombstone, and generates a fresh synthetic master key. No existing users, secrets, keys, or row data are copied. Temporary session tokens use Redis **DB 3**, not the live fixture's DB 0, and are deleted individually after verification.

It makes a custom-format PostgreSQL backup of that synthetic source, verifies the keyed manifest/archive digest before creating a second `sa_recovery_dest_<random>` database, and restores only into that new database. An AES-256-GCM encrypted copy of the synthetic archive is retained with mode 0600. The master key is separate and is never printed or copied into the archive/manifest. The original `aa0` database is never restored or mutated by this runner. Fixture databases are retained for inspection; cleanup is a separate action.

Successful run: `sa_recovery_source_e25eb6296e51` → `sa_recovery_dest_e25eb6296e51`, schema **185, clean**. Synthetic seed, pre-restore verification, and restored-database verification passed; final verification took **5.15 seconds**, including the production recovery fence's five-second withdrawal wait.

Verified using production methods:

- Restored CA private material decrypts only with its original synthetic master. A wrong master and a manifest with substituted archive digest are refused.
- Restored memberships/role sets and durable logout tombstones match the synthetic source.
- Restored encrypted recording content replays with a current authorized parent. Old parents cannot replay after recovery; a newly authenticated parent at the advanced epoch can replay that same historical ciphertext.
- Mismatched CA private/public material is refused; replacing the correctly bound sealed CA and matching public key yields a different signer.
- Changing the pinned host fingerprint invalidates the old session authority binding.
- `Service.Boot` ends all restored pending/connecting/connected sessions with `control_plane_restarted`; sessions do not resume.
- The existing offline `RecoveryService.RecoverAuthority` advances user epochs and verifies its withdrawal barrier. A surviving Redis parent at the earlier epoch cannot obtain shell authority or replay access afterward. Roles remain unchanged.
- Recording DEKs can be rewrapped under another master without rewriting ciphertext. Wrong-master, wrong-organization/session, and modified-ciphertext access are refused by focused regression tests.

## Recovery order

1. Stop/fence every control-plane HTTP, private authority, proxy, and gateway-serving listener. Use the existing external restore marker and `backupctl` verification workflow; never restore over serving listeners.
2. Verify the separately custodied master key, manifest integrity, archive digest, matching schema/binary, and availability of external recording objects/configuration before replacing stores. PostgreSQL backups contain sealed values but are not automatically fully encrypted; encrypt the whole archive with a separate managed backup envelope.
3. Restore into an isolated validation target first. Verify tenant/role/log-out state and decryption. External filesystem/S3/GCS/Azure recording objects require separate coordinated backups at their original deterministic keys; a database dump alone cannot supply those objects.
4. Run the existing offline authority-recovery workflow, which advances all user epochs, and confirm its withdrawal wait before releasing the external barrier. Start Server Access afterward: its boot fence ends every restored active terminal. **Boot closure alone does not invalidate restored parent authority for new admissions; the epoch fence is required.**
5. Require fresh login/MFA and a new explicit terminal admission. Historical replay checks current role and parent authority independently. Inspect ordinary recovery/session audit evidence before reopening access.

## Rotation and compromise handling

- **SSH signer CA:** disable Server Access admission for the organization and terminate existing sessions; wait for independent lease closure. Prepare a new org-bound Ed25519 CA offline, keep the old private key out of exports/logs, and stage the new public trust/principal configuration on each host. Replace the sealed CA and matching public key atomically under the existing installation master. Re-run per-account host authentication checks before enabling admission. On compromise, remove old CA trust from hosts; mere CP rotation cannot revoke a still-valid SSH certificate trusted by an unchanged host. No first-class CA rotation endpoint/UI is implemented or claimed by this qualification.
- **Host key:** verify the new fingerprint independently, edit the registered pin, and run readiness again. Security-tuple edits invalidate old authority and clear readiness; do not silently accept a changed target key.
- **Storage credentials:** destination and credentials are snapshotted in each recording manifest. Changing current configuration affects new recordings. Keep historical credentials valid through retention, or provide an explicitly reviewed historical rewrap/migration path before revoking them. Revoking old credentials can make old replay/retention unavailable; cleanup preserves keys/configuration and retries rather than claiming deletion succeeded.
- **Installation master:** never replace/regenerate the key in place. It protects agent CA, SSH signer CA, MFA/SSO secrets, recording DEKs, storage credentials and parent bindings. The DEK rewrap test proves the cryptographic primitive only; a full installation-wide atomic migration, inventory and rollback tool remains required before operational master-key rotation. Back up master custody separately from encrypted archives and restrict both to different principals.

## Remaining acceptance boundaries

This qualifies synthetic PostgreSQL restore, production authority fences, CP signer/host binding checks and recording envelope rewrap. It does **not** qualify a restore of existing sensitive fixture/production data, a full installation master-key migration, external-object recovery, multi-CP HA recovery, or production RPO/RTO. Native host trust cutover and the complete Server Access envelope inventory are now independently qualified below; no integrated rotation UI is claimed. Those require dedicated scope and evidence. The initial full existing-fixture dump was rejected by automatic approval review because sensitive payload/destination authorization was insufficient; it did not execute, and this synthetic-only path was used instead.

## Additional local rotation gates completed

`recovery-native-rotation.sh` starts a **new** owned OpenSSH target on the existing private fixture network, with no host port. Synthetic Ed25519 CA/client private keys stay in the Go test process RAM; only old/new public CA trust is mounted into this target. Its own host key is generated inside the new target. Existing CP, gateway and target trust are untouched.

Final native run: target `sa-native-rotation-6f45716134b9`, **PASS in 0.76 seconds**. Old CA authentication initially succeeds with a real `fixture` UID-1000 PTY shell and 40×120 resize. Replacing host public trust rejects the old certificate **while its five-minute validity still remains**; the new CA succeeds with the same PTY/account/resize. Foreign CA, expired certificate, raw private-key authentication, and wrong pinned host are denied. Negative CA assertions require explicit SSH authentication denial; network EOF cannot count as successful revocation. OpenSSH `PerSourcePenalties` is disabled **only in this new negative-auth fixture** to avoid masking later assertions with a source penalty. The baseline target retains its configuration. This proves new-handshake trust removal; an already-authenticated shell still requires independent CP lease revocation/termination before operational CA cutover.

The extended synthetic backup/restore run uses `sa_recovery_source_2c1cd42ed3d1` → `sa_recovery_dest_2c1cd42ed3d1`, schema 185 clean. Recovery verification passed in **5.07 seconds**, then `TestRecoveryOwnedEnvelopeMigration` passed in **0.03 seconds**. It inventories and atomically rewraps **six actual restored Server Access envelopes**: the organization SSH CA, two session parent bindings, the recording DEK, current storage configuration, and snapshotted recording storage configuration. Every envelope preserves its plaintext binding, the signer public identity remains unchanged, historical replay succeeds, and the persisted terminal ciphertext SHA-256 stays unchanged. The previous master cannot open the rewritten envelopes.

This is an offline synthetic database migration qualification, not a shipping installation-wide migrator. The production master also protects MFA/SSO, agent CA and other product secrets outside this Server Access inventory. Operational replacement must inventory/migrate those domains atomically and preserve separate backup key custody; replacing the global master after only this partial-domain migration is unsafe. No global/master/API changes were made to the baseline installation. Synthetic test masters remain private ephemeral fixture files, and all test-owned Redis DB-3 parents are individually deleted.

The final replay also preserves the encrypted manifest's incomplete warning. No real cloud bucket or existing private recording was exported.

Download produces the currently captured authorized event set; an active recording is therefore a partial snapshot with status `capturing`. Disabled, failed and expired recordings reject download instead of producing an empty successful attachment. Archived metadata-only reads preserve the durable incomplete marker without fetching a remote manifest. Full replay/download also authenticates the encrypted manifest and archive digest before returning captured events.

New S3 archive manifests add a master-rotation inventory boundary: both archive configuration snapshots and externally stored encrypted manifest objects must be migrated. The manifest contains the wrapped DEK, so a complete operation must rewrite that binding, reencrypt the manifest under the replacement master, verify it through the archived replay path, and coordinate this with the database envelope cutover. Rewrapping database fields alone does not migrate archived replay and will correctly fail closed. The earlier six-envelope PostgreSQL recovery proof does not claim this new external-object migration or a shipping product-wide master migration tool.

## Self-contained encrypted S3 package and import

New archive completion also writes and verifies `recording-v2.tunnex-recording` under the deterministic organization/session S3 prefix before marking the archive available or releasing PostgreSQL payloads. Its `TUNNEX-RECORDING-V2` header identifies an installation-master-encrypted package, not plaintext replay JSON. The sealed payload includes the organization, original session and owner identities, wrapped per-recording DEK, encrypted events, count and ciphertext-chain digest, retention timestamp and incomplete marker. The dedicated package transport limit is 32 MiB; ordinary chunk limits remain 64 KiB, event count remains 4096, and cumulative encrypted session payload remains 16 MiB. Existing per-chunk/version-1 archives remain replayable and are not automatically converted into packages.

The actual Moto package test passed in 0.34 seconds using only synthetic source `sa_recovery_source_635e21016b60`. After downloading the complete package, it deleted its own original session and recording rows, fetched the same S3 package without database lookup, and imported identical output/resize/timing events. Import requires the current human parent, user epoch/email/password/logout state, current organization Replay permission and authenticated package owner or current SessionManage permission. A foreign tenant, a nonowner with a forged cached administrator role, and a logged-out parent were rejected. Import audits separate encrypted-package provenance and does not recreate a trusted session row or require an historical content grant.

Unit regressions additionally reject wrong installation master, corrupt/truncated or raw-chunk objects, missing/reordered events and digest mismatch, and prove package transport does not widen ordinary chunk limits. Private synthetic login/master/package artifacts are retained under `.runtime/package-import/` with mode 0600 for a separate API/UI proof; credentials and key material were not printed. Packages still require the originating installation master: this is encrypted portability within that custody boundary, not a claim of cross-installation migration.

The final UTF-8 browser fixture uses fresh source `sa_recovery_source_d04fd8afc66e` and private artifact prefix `.runtime/package-import/sa_recovery_source_d04fd8afc66e`. Actual S3 export/delete/import passed in 0.22 seconds.
