# S20.3 — Kubernetes connector-pool HA foundation

Status: **LOCKED FOR P1 IMPLEMENTATION** on `k8-improvement`.

This paper ports the smallest safe part of the historical
`iotunnex/tunnex@codex/kubernetes-cluster-scope-ha` work into the current
`tunnexio/tunnex` architecture. The historical branch is evidence and source
material, not a merge base: its single commit spans HA, agent fencing,
cluster-scope policy, UI previews, client/helper changes, conformance assets,
and CI changes. Those concerns do not become one story merely because they
shared an old commit.

## Measured current boundary

- Migrations `0079` through `0087` already exist on current `main`.
  `0079`, `0080`, `0081`, `0082`, `0083`, `0085`, `0086`, and `0087` are
  byte-identical to the historical branch. Current `0084` additionally installs
  the missing `set_updated_at` trigger.
- The generated database models expose connector-pool, handoff-operation,
  ownership-delivery, health-history, and cluster-scope rows, but current
  authored queries and runtime services do not operate those contracts.
- Current Kubernetes behavior is legacy single-connector ownership through
  `k8s_clusters.connector_node_id`. The S20 console truthfully calls connector
  selection configuration, not workload or data-plane readiness.
- Current migration numbering has advanced through `0116`. Existing migration
  numbers must not be replayed, renumbered, or copied over.

## Locked decisions

### D1 — Selective compatibility port, not cherry-pick

The historical commit is not cherry-picked. P1 reuses only contracts that are
still true in the current repository and adapts them at the current owners:
`apps/api/db/queries`, `apps/api/internal/k8s`, the Kubernetes topology read,
and the policy compiler. Generated outputs follow the current OpenAPI/sqlc
workflow; they are never copied from the historical branch.

### D2 — P1 is control-plane state, not a deployed HA claim

P1 contains:

1. the pure deterministic connector-pool state model;
2. fail-closed adaptation of current control-plane evidence;
3. transactionally configured pool membership;
4. membership-epoch guarded configuration; and
5. a legacy-compatible read/compiler boundary that resolves either the legacy
   connector or the exact pool active member, never both.

P1 does not schedule promotion, deliver ownership to an agent, move a VIP,
change WireGuard routes, or expose an operator control that says HA is active.
Those require P2 fencing.

### D3 — Existing single-connector clusters remain unchanged

A cluster with no `connector_pool_id` continues to resolve exactly through its
existing `connector_node_id`. Pool creation is a one-way, transactional bind:
the current legacy connector becomes preferred and active, is retained as a
member, and only then is the legacy column cleared. A row with both ownership
forms, neither usable form, a cross-org/site/cluster pool, or incomplete pool
state fails closed; it never guesses an owner or falls back across modes.

### D4 — Cluster-owned pool and stable service identity

One pool belongs to exactly one cluster in one organization and Site. A
connector cannot be a member of multiple cluster pools. P1 never changes active
ownership or generation after the legacy-to-pool bind. Cluster,
exposed-Service, FQDN, synthetic VIP, protocol, and port identities remain
unchanged.

### D5 — Deterministic health and hysteresis

Candidate order is admin priority descending, then connector UUID ascending.
A candidate must be active, non-revoked, same-org, same-Site, and have a valid
WireGuard public key and endpoint. Health requires two independent fresh
signals: control/policy acknowledgement and the current global Kubernetes
endpoint-view report. Missing, malformed, future, stale, or old-agent evidence
is unknown and fails closed.

Promotion requires three consecutive dual-signal healthy ticks while the
active connector is stale. Preferred failback requires five consecutive
healthy ticks. No eligible standby produces `needs_attention`; it does not
move ownership. The global endpoint view is not per-Service readiness and must
never be presented as such.

### D6 — Generation is not actionable before distributed fencing

P1 may read the initial positive generation as provenance, but it does not
change active ownership or generation. A formal review proved that making a
new `active_node_id` immediately authoritative to policy and topology readers
would let a disconnected old connector retain last-good state while the new
connector received ownership. P2 must therefore supply a versioned, expiring
ownership lease plus exact acknowledgement/withdrawal semantics before any
promotion mutation exists.

### D7 — No new database migration in P1

P1 uses the existing expand-only `0079`, `0082`, and `0083` contracts. If
implementation proves a real schema gap, work halts and surfaces a new
decide-item; any accepted additive migration starts at `0119`. Historical SQL
is never modified to make a new runtime assumption appear retroactive.

### D8 — Audit and actor truth

Pool configuration retains the caller's real human or system actor and cause.
Promotion/failback audit is deferred with the P2 handoff transaction; P1 writes
no ownership-transition success claim.

### D9 — No P1 edition or opt-in surface

P1 is internal compatibility and state machinery; it adds no customer-facing
endpoint or entitlement. P2/P3 must separately disposition availability,
organization opt-in defaulting OFF, RBAC, edition ordering, and UI. Unlocking
a capability may never turn enforcement on automatically.

### D10 — Proof and stop condition

P1 requires focused proof for deterministic ordering, three/five-tick windows,
dual-signal fail-closed health, cross-scope rejection, membership-epoch
conflict, transactional audit/rollback, legacy read preservation, invalid pool
withdrawal, and unchanged legacy Kubernetes compiler behavior. Both Go editions, generation
drift, node tests, helper tests, web gates, and builds remain story gates.

P1 stops before HTTP/UI, scheduler activation, agent delivery, client/helper
routing changes, cluster-scope policy, conformance packaging, deployment, or a
live failover claim. Repeated defects in the same state component halt the
port for a smaller state-model correction rather than another patch.

### D11 — Formal review dispositions

The P1 formal review findings were dispositioned in-session on 2026-08-28:

1. **Locked:** remove the unfenced live promotion mutation from P1; P2 owns it.
2. **Locked:** configuration mutations remain membership-epoch guarded, and P2
   must carry the observed epoch into every selection/handoff operation.
3. **Locked:** a pool active member is usable only while its exact node remains
   active, non-revoked, same-Site, valid-key, and endpoint-bearing. Policy,
   topology, and served-DNS projections fail closed from that same rule.
4. **Locked:** preserve `cause` for human and system configuration audits.
5. **Locked:** prove pool ineligibility at each consumer: policy authorization,
   node VIP/DNS programming, and served resolver delivery.
6. **Locked:** prove membership-epoch invalidation for priority, add, and remove
   mutations, including stale replay refusal.
7. **Locked:** preserve the released legacy setter's non-empty key/endpoint
   predicate; apply valid-key and trimmed-endpoint hardening only to new pool
   membership and pool ownership reads.

## Explicit deferrals

- **S20.3a / P2:** versioned per-pool/per-VIP manifest, non-serving standby
  preparation, persisted acknowledgement, lease/revision enforcement,
  withdrawal-or-expiry ordering, scheduler leadership, and primary-loss wire
  proof.
- **S20.3b / P3:** operator API/UI, bounded readiness/attention projections,
  RBAC and opt-in/edition disposition, exact destructive/recovery copy, and
  founder visual review.
- **Separate cluster-scope story:** approval-gated dynamic exact-port children,
  candidate discovery, compiler propagation, audit, and UI. Existing `0086`
  and `0087` storage does not authorize or expose that capability.

## Acceptance

P1 is complete only when the current repository can create/read/reconcile a
cluster-owned connector pool through its service boundary, reject stale
membership configuration, and compile legacy and valid pool-bound clusters
without widening access. It may be called an HA **foundation**, never deployed
Kubernetes HA, until P2 wire proof is committed.
