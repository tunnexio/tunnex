# AA-4 proxy authority contract

Status: AA-4 locally qualified on 2026-10-03; see [acceptance evidence](AA-4-development-evidence.md). This contract does not establish positive app-session authorization or evidence that drafts serve browser traffic. Dedicated authority ports and browser transport are qualified; AA-5/AA-6 supply positive session/publication authority. This contract follows [AA-0 authority](AA-0-authority-contract.md).

## Dedicated service identity

Use a distinct TLS-only App Access proxy credential family. It is not a browser session, CLI bearer, GitOps operator token or enrolled gateway certificate. Existing `machineauth` credentials hold the fixed privileged operator role, have a human owner and an organization scope; reusing them would grant unrelated authority and would not fit the installation-wide public proxy.

Proxy credentials are random secrets with a distinct prefix, stored by hash with active/revoked state and a monotonically increasing credential version. Authentication rereads current state on every internal request; errors, unknown tokens and revoked tokens all fail closed with the same generic response. Do not grant human management permissions or manufacture a human `UserID`. The dedicated internal verifier returns a purpose-scoped `AuthenticatedProxy` value and is the sole admission seam for these ports. Require real direct TLS on the dedicated internal listener, with TLS 1.3 minimum for the selected app transport; a forwarded-protocol header is not proof of TLS. Only service TLS requests enter it; browser cookies, CLI/operator authentication and gateway certificate principals confer no proxy authority.

Credential provisioning belongs to a later operator-local tool in AA-7. A secret is returned only through that explicit provisioning workflow. If a control-plane provisioning copy must be retained, seal it with the existing master-key `crypto.Sealer`/platform-secret pattern; normal authentication needs only the hash. No credential appears in tracked files, metadata responses, logs, browser storage or page content. Rotation/revocation changes the version and invalidates current leases within their qualified bound.

## Separate publication authority

Current applications have a database constraint requiring `state='draft'`, and current connector assignments have purpose `origin_check`. Neither a draft, hostname reservation, successful origin check nor a configured connector is publication authority.

Use a separate serving-publication record, initially empty, rather than treating latest draft configuration as active. Its eventual tuple contains organization, application, active revision/digest, exact hostname, assigned gateway, server-issued serving generation, purpose `browser_proxy`, publication state and authority version. Composite foreign keys bind the active revision to its organization/application/gateway/digest. The serving generation and purpose are distinct from AA-3 check assignments. AA-3 capability version 1 and its configured origin-check status do not establish browser capability or serving readiness; later publication requires explicit browser capability and exact serving-tuple connector/proxy acknowledgements. AA-6 owns the reviewed pending publication, exact acknowledgements, atomic active swap, disable and withdrawal behavior; AA-4 must not populate a synthetic active row or relax the draft constraint to obtain an allow.

Host claims remain reserved history/tombstones. Lookup accepts a single normalized exact ASCII authority, checks the operator app-domain boundary, and derives tenant/application/target from current database publication only. Reject ambiguous authorities, duplicates, IP literals, ports in host registrations, wildcard names, unregistered aliases and caller-supplied dial targets. Unknown hosts, unpublished drafts, missing publication and unavailable authority return generic denial without disclosing tenant or private topology.

## Internal authority ports

The following dedicated internal denial seams are implemented; positive authorization remains future AA-5/6 work:

- `LookupRoute(ctx, proxy, exactHost) (Route, error)`: returns a current published serving tuple and only the target configuration needed by the trusted proxy. Organization/app/gateway/target are database-derived. Until AA-6 establishes publication, all lookups deny generically.
- `AuthorizeRequest(ctx, proxy, routeBinding, opaqueAppSessionToken, requestMeta) (Decision, error)`: verifies exact active route/credential versions and derives user/parent identity from server-side app-session state. Metadata contains bounded method, safe relative navigation and same-origin evidence; it does not supply authoritative user, organization, origin or dial target. Until AA-5 app sessions and AA-6 publication exist, it denies.
- `RenewLease(ctx, proxy, streamID, routeBinding) (Decision, error)`: rereads current credential, publication, parent/app session, user/membership, explicit grants and assigned gateway authority. The server-issued stream identity binds all these facts. It never refreshes login/app idle and never grants a positive cache for a new request. Until the required authority exists, it denies.

- `ChannelAuthorize(ctx, proxy, routeBinding, actualVerifiedLeafSerial, entitled) (leaseUntil, error)`: the consumer must supply the actual verified gateway leaf serial, never CN/OU or an asserted tenant identity. Later authorization must resolve the current node/org and exact `browser_proxy` serving tuple, with lease expiry at most four seconds from decision start. Current AA-4 returns no lease and HTTP 403 for every call.

The direct authority listener is disabled by default; `TUNNEX_APP_PROXY_AUTHORITY_ADDR` explicitly enables it. It uses the server SAN `tunnex-app-authority` under the existing control-plane CA, TLS 1.3 minimum, 32 KiB request headers, 16 KiB request bodies and at most 256 accepted sockets. The unique `Authorization: AppProxy <tnxap_...>` scheme is admitted only by the dedicated verifier. The real TLS/isolated PostgreSQL HTTP qualification passed credential revocation, unavailable route 404, and request/renew/channel 403. These results do not establish positive sessions, leases, serving or operator provisioning.

A route response is configuration, not an allow decision. No response may advertise `access_allowed=true` based solely on route lookup or connector health. Internal ports are admitted only by the dedicated service verifier, outside human CRUD authentication, with no shared role that accidentally enables human management. Result/event metadata must be bounded and redacted.

## AA-5 session seam required by the ports

The existing parent `session.Store.Get` refreshes Redis idle TTL. Add a separate authoritative non-touching validation operation: one atomic Lua `GET` plus `PTTL` snapshot returns the immutable session record and observed remaining idle lifetime. Derive its conservative idle deadline from decision start plus the atomic remaining TTL, so response latency consumes validity rather than extending it. It does not expire, touch or delete keys. Missing records, non-expiring/expired TTL, absolute expiry and Redis errors deny. Existing console session key behavior remains compatible.

Dedicated app sessions use random opaque tokens stored by hash, indexed by organization/application/user/parent login. Absolute expiry is bounded by both app policy and parent absolute expiry. Only an accepted foreground browser request refreshes app idle, atomically on an existing nonrevoked record. Define foreground from the qualified proxy request flow, not a browser-controlled header claiming foreground activity; untrusted heartbeat/renewal traffic never touches idle. Stream renewals, background requests and passive keepalive validate without touching either parent or app idle.

Launch transactions store a hash of a 32-byte random, 60-second code, nonce hash, exact organization/app/host/user/parent login and normalized relative target. Redemption validates the dedicated proxy identity and bound browser nonce atomically before consuming and creating a session. A mismatch or replay creates no cookie. Reserved host-only secure cookies, code cleanup, unsafe-method origin checks and nonreplayed POST behavior follow AA-0; these are not relaxed by the machine port.

Reuse current same-org explicit user/group grant matching at one evaluation time, including active/nondeleted user, nonrevoked membership and current group membership. Factor reusable eligibility from the preview while keeping preview/publication denial honest. Current use permission, email verification and the existing local-password wall still apply; match the existing password wall's local-password availability semantics rather than inventing an SSO password. Check existing MFA enrollment policy using immutable parent `AuthMethod`; preserve the current SSO exemption and do not claim a factor was verified merely because SSO was used.

Every accepted request and renewal validates the live parent record. Parent logout therefore denies the next decision without requiring asynchronous fanout. Redis/database errors deny; a cached grant match or route does not replace authoritative state. Browser leases follow AA-0's maximum four seconds measured from decision start, renewal every two seconds and five-second closure target; their deadlines are additionally bounded by session and current matching-grant expiry.

The API seam review found no architecture blocker and confirmed these direct-TLS, conservative-deadline and foreground-classification requirements. This review is design evidence only.

## Required later proofs

Before acceptance, prove credential-type separation, TLS refusal, unknown/revoked/versioned credentials, exact host/no tenant oracle, empty-publication denial, distinct serving/check purposes, atomic parent no-touch validation with TTL unchanged, current grant eligibility and directory changes, session/nonce replay refusal, foreground-only app idle refresh, and cancellation within the qualified lease bound. AA-4 is not browser publication; AA-5/AA-6 supply the remaining authority and actual serving acceptance.

## AA-4 data slice evidence (in progress)

Migration 170 and SQLC/service ports are implemented locally. The serving-publication table is empty in the owned native runtime; no draft constraint was relaxed, no origin-check purpose was widened and no app sessions were added. The parent-owned native API build automatically applied additive migration 170 during integration; migration contents were then frozen. This is not publication or full AA-4 acceptance.

`GOFLAGS=-mod=readonly go test ./db ./internal/appaccess` passed. The owned child-database harness passed migration 169→170→169→170, credential hash-only storage, distinct-family/encoding refusal, current credential version and revoked-secret refusal, stale revocation, idempotent version/audit behavior and audit-failure rollback. Unknown, draft and pending-publication hosts were denied. Foreign organization/gateway and wrong digest publication tuples failed database constraints. Retained proxy authority history refused destructive down migration. AA-1/2/3 data regressions passed in the same harness.

Current concrete ports use `AuthenticatedProxy{CredentialID, CredentialVersion}` and a database-derived `RouteBinding{OrgID, AppID, GatewayID, Generation, Revision, AuthorityVersion, Digest, Hostname, Purpose}`. `LookupRoute` requires current proxy credentials, operator domain readiness, entitlement, organization opt-in, live organization/gateway certificate and exact active revision/hostname; production publication remains empty. `AuthorizeRequest` and `RenewLease` return denied decisions without lease timestamps. `ChannelAuthorize` returns no lease and a generic forbidden error. Later AA-5/6 must establish session/publication authority before these ports may allow.

The hash/version store is installation-wide service identity, explicitly documented in the query lint annotations. It has no tenant membership or operator role. Provisioning/revocation service methods have no human/agent HTTP endpoints and emit the named `app-proxy-provisioning` system audit actor. Repeated revocation of an already revoked credential returns its terminal version without another audit, regardless of the old expected version; a live credential still enforces the expected version.

### AA-5 lifecycle integration finding (read-only)

Parent validation alone does not yet establish logout/password-reset safety under Redis failure and recovery. Existing `http/auth_handlers.go` logout ignores `sessions.Delete` errors and reports success; `auth/service.go` password reset logs `DeleteAllForUser` errors and reports success. A retained parent record could become readable after Redis recovers. Before claiming successful logout/reset ends app sessions, qualify a narrow authoritative revocation hook or durable parent/user denial record, or explicitly surface and recover revocation failure. No lifecycle behavior has been changed by this review. Live user/membership eligibility remains independently necessary so directory revocation cannot depend on Redis cleanup.

### Proposed durable parent revocation boundary for AA-5/AA-7

Prefer a per-user monotonic database authority epoch to a wall-clock cutoff. Stamp the epoch captured by the successful login verification into newly minted parent records and copy it into app authority. Increment the epoch in the same database transaction as password reset and the CLI credential sweep. App handoff, requests and renewals compare the parent/app stamp with the current database epoch; Redis failure or a surviving/restored stale parent record cannot undo that committed revocation. Capture the stamp with verified authentication state, not by reading a newer epoch after verifying an older password. A login/reset race must either produce an old stamped parent that is refused or revalidate the verified state before minting.

Add a durable tombstone keyed by the hash of the exact parent login token for single-login logout. Commit that denial before reporting successful logout; Redis deletion and app-index cleanup then cannot be the sole revocation authority. Every app decision checks the tombstone independently of Redis presence. If the database cannot commit the denial, do not report authoritative success. Handling a Redis-outage logout must explicitly account for the HTTP authentication seam being unable to resolve a principal: a cookie being cleared is not proof that its server-side login was revoked. Unknown/caller-supplied tokens must not enable unbounded tombstone insertion; validate the available trusted parent binding or return a clear failure with a deliberate retry path.

Epoch comparison avoids clock-skew ambiguity. A timestamp-cutoff alternative would need a documented bound on clock skew and conservative comparison of parent creation time against a database-issued cutoff; silently trusting a future-skewed parent `CreatedAt` is unsafe. Legacy parent records lack the epoch stamp. Do not infer a current stamp from a still-live legacy Redis record after reset: require a qualified fresh native login or another authoritative migration proof before they can create app authority. This may preserve legacy console behavior while refusing ambiguous legacy app handoffs.

Do not prune logout tombstones before their parent can no longer be valid. Use the authoritative parent absolute expiry when known; if Redis is unavailable, a later shorter session configuration cannot establish the lifetime of a previously minted parent. Retain the tombstone conservatively until bounded cleanup is qualified. Recovery/restore qualification must ensure previously denied parent tokens cannot resume apps after stale Redis data is restored; an installation authority generation/epoch transition may be necessary for restore.

Required lifecycle proofs include password reset committing while Redis revocation fails, Redis outage then recovery, successful single-login logout with retained Redis data, login/reset races, epoch-less legacy records, cutoff/creation-clock boundaries if timestamps are used, unavailable database authority, and restore of stale parent records. In every accepted revocation case, new app requests and existing lease renewals remain denied after recovery. These are design requirements only; existing native auth/session code is unchanged during AA-4. The parent lane owns the later lifecycle integration.

The native MFA second-step is another epoch boundary. `mfa.CreateChallenge` currently receives only a user identifier; `VerifyChallenge` rereads the user before `http/mfa_handlers.go` mints the parent session. Future epoch integration must store the epoch from the verified password snapshot in the challenge at creation and compare it with current authority before minting. A pending password-authenticated MFA challenge cannot silently acquire a newer epoch after a password reset. Test reset/epoch change between password verification, challenge creation, TOTP verification and parent minting. A completed fresh SSO callback may use its current database identity snapshot because it supplies a new trusted IdP authentication; it must still validate current identity standing and preserve the SSO mint-time method.

### Independent AA-4 transport review (qualification in progress)

Source review confirmed matching route binding fields across data service, internal authority HTTP and proxy consumer: organization/application/gateway, revision/digest, serving generation, hostname, authority version and `browser_proxy` purpose. Browser and origin-check brokers remain separate. Origin forwarding resolves and validates every candidate before literal-IP dialing, uses registered origin TLS hostname/roots, preserves ordinary application credentials/cookies and strips reserved console/app authority.

Review found and relayed ordinary HTTP expiry needing immediate read/write deadlines (context cancellation alone does not unblock a slow downstream socket), fresh control-endpoint address resolution before origin dialing, and the missing `tnx_oidc_flow_http` console cookie alias. Subsequent source inspection confirmed those fixes were authored. It also found public/gateway TLS certificate reuse incompatible with the node's enrollment-CA trust and `tunnex-app-proxy` server name. The transport lane reports separate gateway-leaf configuration has been authored: gateway leaf signed by the enrollment CA with that SAN, separate from the operator's public app certificate. Source fixes and narrow transport test reports are not full real-pool acceptance; retained identity, actual outbound mTLS reconnect/rotation, authority denial and browser traffic qualification remain central gates.

Transparent password rehash is a separate compare-and-swap requirement. The current `auth.Service.Authenticate` verifies a user snapshot and later calls `SetUserPassword` unconditionally when the hash needs rehashing. A concurrent reset can commit a new password and authority epoch before that stale rehash writes the old password back. Future lifecycle integration must update the hash only when both the previously verified hash and its captured authority epoch still match. A failed comparison cannot overwrite reset credentials or mint authority from the stale verification. Qualify a password-verification/rehash/reset race against the actual database; an epoch check only at session minting does not repair the password overwrite. This remains an AA-5 requirement; no native authentication query changes are made during AA-4.
