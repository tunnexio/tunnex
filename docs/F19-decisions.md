# F19 — MCP harness enforcement consolidation

## Outcome

Any MCP-capable harness that uses Tunnex's managed local proxy receives the
same default-deny, endpoint-pinned, per-tool policy enforcement regardless of
whether the harness host is inside a Tunnex-routed network. The managed agent
restores its WireGuard runtime after reboot, retains Streamable HTTP MCP
sessions for discovery, and reports only usable inventories.

## Decisions

### D1 — Enforcement boundary: the explicit local proxy

The Tunnex-managed runtime exposes an explicit loopback Streamable HTTP MCP
proxy. It obtains policy from the control plane and evaluates each `tools/call`
before forwarding it. This is the enforcement point for OpenClaw, Claude Code,
DeepSeek-compatible clients, and any other MCP harness.

Direct connection to an upstream MCP endpoint is not protected. Product copy
must state this clearly and generated client configuration must point at the
local proxy, never the upstream endpoint.

### D2 — Harness neutrality: use MCP protocol, not vendor integration

Tunnex does not embed a provider SDK or hold model-provider credentials. The
product contract is standard Streamable HTTP on loopback plus an optional thin
stdio adapter where a harness requires stdio. This keeps policy independent of
Claude, OpenClaw, DeepSeek, OpenRouter, or a future harness.

### D3 — Control frames do not authorize tools

Only fixed MCP transport/control methods needed to establish or inspect a
session may pass without a tool rule: `initialize`, `notifications/initialized`,
`tools/list`, and `ping`. They cannot invoke tools. Every other unnamed MCP
method stays denied. Every `tools/call` remains default-deny and is matched to
the endpoint and tool policy.

### D4 — Session-aware inventory is authoritative

The inventory collector preserves a server-issued `Mcp-Session-Id` across
initialize, initialized notification, and discovery requests. A healthy
observation with failed tool discovery must not erase the previously observed
tool list; the runtime policy projection must fail closed until a fresh usable
inventory is reported.

### D5 — Runtime recovery is desired-state reconciliation

At service start, a previously applied runtime configuration is restored before
the next heartbeat. Operators must never install a manual IP route. Exact
policy-derived routes are generated by the control plane and are part of the
managed WireGuard configuration.

### D6 — Reusable MCP profiles assign to existing agent groups

An immutable MCP profile owns one canonical upstream endpoint and a policy
version derived from its observed inventory. An operator assigns a profile to
an existing agent group, producing independent per-agent runtime projections.
This is one-to-many configuration, not shared credentials: each managed agent
uses its own runtime credential and obtains its own policy projection.

An agent may have at most one active profile. Reassignment is an explicit
replacement that withdraws the old endpoint and policy before the next desired
revision is issued. The profile is valid only for the existing agent-template
edition gate; open builds continue to default-deny.

## Non-goals

- No interception or enforcement of a harness that bypasses the local proxy.
- No storage or management of model-provider API keys.
- No vendor-specific OAuth or plugin protocol beyond MCP and an optional stdio
  bridge.
