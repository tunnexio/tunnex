# S15.13 — Public installer edge TLS

## Goal

`curl -fsSL https://get.tunnex.io | sh` must produce a reachable single-host
deployment without asking a customer to add a second reverse proxy by hand.
The installer supports direct VMs, Cloudflare, and load balancers; none is a
special case in product configuration.

## Decisions

### D1 — Tunnex owns the single-host HTTP edge

`caddy` is part of the shipped Compose stack.  It is the only service exposing
the dashboard ports to the host and proxies internally to `nginx:8080`.
`nginx` remains the Tunnex application proxy and has no host port mapping.
The control channel (`8443/tcp`) and WireGuard (`51820/udp`) stay direct and
unchanged.  Its multi-architecture Caddy image is digest-pinned in Compose so
a mutable upstream tag cannot silently alter the public edge.

### D2 — Explicit provider-neutral TLS topology

The installer records `TUNNEX_TLS_MODE`:

- `direct` — the VM receives public HTTP/HTTPS.  With an HTTPS DNS hostname,
  Caddy obtains and renews the origin certificate.  This is the default for a
  direct public hostname and works with Cloudflare Full (strict).
- `terminated` — an external proxy or load balancer terminates TLS and sends
  HTTP to this VM.  Caddy deliberately serves internal HTTP only, preventing a
  redirect loop.  The public URL can still be HTTPS, so secure cookies remain
  enabled.
- `http` — direct, deliberately plaintext use for a public IP or an explicitly
  non-TLS test deployment.  It is supported but announced as not suitable for
  production credentials.

The installer asks for this only when it cannot derive the mode from the URL;
`TUNNEX_TLS_MODE` makes automation explicit.  It never attempts to infer an
AWS ALB, Cloudflare, DNS, or a customer reverse proxy from inside the VM.

### D3 — HTTPS needs a hostname when Tunnex terminates it

`direct` plus `https://<IP>` is refused before any files are written: public
certificate authorities cannot reliably issue the hostname certificate this
mode requires.  Use `http://<IP>` for a test, a DNS hostname for direct HTTPS,
or `TUNNEX_TLS_MODE=terminated` when an external TLS endpoint owns the
certificate.

### D4 — Cookie transport follows the configured public scheme

The installer writes `TUNNEX_COOKIE_SECURE=true` for an HTTPS public URL and
`false` for HTTP, and Compose passes it to the API.  This closes the former
state where a fresh HTTPS install used insecure session cookies by default.

### D5 — Observable network prerequisites

The installer prints and optionally opens host-firewall ports appropriate to
the selected topology.  It always calls out the independent cloud firewall or
load-balancer listener.  Direct HTTPS needs public `80/tcp` and `443/tcp` for
certificate issuance and traffic; terminated TLS needs the configured
load-balancer-to-origin listener instead.  No installer can create or alter a
customer's DNS, Cloudflare zone, AWS listener, or cloud security group.

### D6 — Customer installs select a release, not a CI SHA

With no override, both public installer entrypoints query GitHub's latest
published non-prerelease release and display/install its semantic tag (for
example, `v0.1.2`).  The SHA remains inside the signed release manifest and
digest verification path, never as the primary customer-facing version.  An
operator can still explicitly select a tag or a diagnostic `sha-*` build.

### D7 — Upgrades bridge pre-edge installations

The host updater detects a new edge-aware Compose file and writes only missing
edge variables from the existing `APP_BASE_URL`.  HTTPS hostnames default to
direct TLS, HTTP defaults to HTTP, and an HTTPS IP defaults to `terminated`
rather than incorrectly attempting public certificate issuance.  An explicit
operator mode is preserved.

## Non-goals

- Managed DNS, Cloudflare, or AWS load-balancer configuration.
- Issuing certificates for bare IP addresses.
- Changing the existing gateway mTLS or WireGuard ports.
- Kubernetes/Helm ingress; this story owns only the Docker quickstart.
