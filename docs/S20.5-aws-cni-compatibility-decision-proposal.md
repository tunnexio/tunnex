## C1 — closed, mechanism-based AWS adapter

Register the observed IPv4 nft-backed AWS SNAT mechanism in addition to the
existing IP-MASQ adapter. Preserve `New`'s legacy behavior; an explicit new
AWS-aware constructor accepts closed nft/iptables inspection runners and a
scoped authority guard. No cloud SDK, metadata-provider exception, environment
switch to skip health, or administrator-crafted chain is support evidence.

The only new owned rule is a return matching the **current canonical IPv4
tunnel CIDR as destination AND the exact WireGuard egress interface**, carrying
a distinct bounded Tunnex AWS ownership marker. It precedes AWS terminal SNAT;
foreign rules, their contents and relative order are preserved. No blanket
RFC1918/source exemption, CNI EXTERNALSNAT change, or new POSTROUTING bypass.

Use explicit nft-backed iptables readback to establish foreign compat-rule
semantics and nft handles for exact owned-rule mutation/readback. The runtime
image must actually provide the explicit selected tools. Never invoke an
auto-selecting iptables wrapper or round-trip `xt: null` foreign JSON through
nft. The observed KUBE-POSTROUTING conditional mark/masquerade path executes
before AWS SNAT: recognize its supported shape, do not assume every packet
is masqueraded, and prove fresh actual tunnel flows bypass unintended NAT.
An AWS return cannot undo an earlier NAT binding.

Missing tools, incompatible backend, unknown/ambiguous hook coverage, unknown
AWS chain topology, malformed ownership or unproved rule ordering block.
Only explicitly observed, registered mechanisms contribute required adapter
readiness: absent IP-MASQ must not make an otherwise supported AWS mechanism
fail, and arbitrary selection of one of multiple active mechanisms must not
hide another. No recognized active mechanism remains blocked. Unknown active
coverage is not relabelled not-applicable.

## C2 — journal authority, old epochs, and mixed versions

Introduce journal schema **3**, keeping schema 1/2 exact validation and cleanup
scope unchanged. Keep the existing IP-MASQ receipt and add a closed AWS receipt
only to new schema-3 epochs. No in-place migration of an active legacy epoch,
reset, reinitialization, or loss of baseline/ifindex/staging receipts. Preserve
v1 preparing refusal, v2 staged-link semantics, and restoring-before-cleanup.
New AWS authority starts only after a new epoch's receipt is durable.

Keep the old strict heartbeat JSON unchanged. Publish a separate bounded,
non-secret CNI-authority record correlated with exact node, manager Pod/boot,
heartbeat sequence, epoch and journal schema. Its closed scope is historical
IP-MASQ-only for legacy epochs or IP-MASQ+AWS for schema 3. It conveys no
credentials and cannot admit a Pod without the existing two advancing fresh
active heartbeat proofs and exact owner UID. A stale, mismatched, missing or
unknown record cannot grant new AWS write authority.

Use a separate manager-created, bounded node-local CNI operation lock to
serialize the manager's journal/cleanup transition with gateway CNI mutation.
The gateway holds that lock while validating current public authority and
performing its scoped operation; it has only a read-only state mount and never
writes the journal/authority. Manager kernel/state transitions hold the same
lock, with context-bounded acquisition. Do not reuse its process-lifetime
singleton lock. Revoke public authority before teardown can race new writes.

**Implementation refinement authorized by the user's instruction to finalize
the fix:** admission carries a closed scope and an absolute not-after, not
just an acquisition timeout. Runtime not-after is the matched heartbeat's
observation time plus its existing ten-second freshness window. Bound the
entire operation by the earliest of this not-after, the caller deadline, and
five seconds from operation start. Check cancellation before every mutation
and after final readback; a delayed inspection cannot commence another write
or publish Ready after expiry. Real subprocesses use the bounded context;
test runners that ignore cancellation must still hit explicit boundary checks.
Manager cleanup under its exclusive lock uses its durable journal scope and
the same five-second operation budget, not fabricated heartbeat authority.
This narrows C2; it does not fold the separate general startup timing proposal.

New gateway + new manager + legacy epoch may use only legacy authority; AWS
refuses until a clean new epoch. New gateway + old manager without the new
authority record refuses rather than silently assuming compatibility. An old
gateway remains an old reader and cannot become AWS-ready. An old manager
encountering schema 3 refuses without deleting or overwriting it; downgrade
across that boundary requires supported current-manager cleanup first. Do not
present such a deliberately incompatible downgrade as zero-touch rollback.

## C3 — ownership and lifecycle coverage

Baseline census on a new epoch observes both registered ownership namespaces
and rejects leftovers/ambiguous markers. Legacy journal cleanup continues to
scan and remove only its historical namespace. Schema-3 cleanup enumerates
only its exact two receipt namespaces, tolerates already-absent exact owned
artifacts, refuses malformed ownership, and preserves all foreign rules.
Gateway reconcile/withdrawal cannot exceed its currently validated scope.
Because nft JSON can hide compatibility comments, the new AWS-aware ownership
census also reads explicit nft-backed iptables output when the AWS chain exists.
Reserved AWS ownership text must correlate with an exact native owned rule;
opaque or malformed markers refuse before mutation. Cleanup does not require
the foreign runtime topology to remain operational. Legacy cleanup is unchanged.
Unknown API owner state retains the existing conservative enforcement policy;
it never proves last-owner absence or creates a new epoch.

No new gateway sysctl writer, host reboot rebootstrap, hidden rollout restart,
Secret/PVC repair, or credential rewrite is part of this correction.

## C5 — runtime admission before startup data-plane work

Locked correction under the user's direction to finalize the Kubernetes blocker,
after the first actual d2c9cba AWS install on 2026-09-05. This is a concrete C2
composition defect, not acceptance of the separate general startup-timing work.
The init check passed and the gateway enrolled, but every runtime restarted its
own required two-heartbeat proof history. Initial egress reconciliation observed
one fresh grant; immediate ownership startup withdrawal received the expected
"awaits two advancing exact-owner heartbeats" refusal, and main exited before
the periodic observer started. Repeated process starts therefore never earned
the runtime's second observation. Disk provisioning succeeded independently.

Runtime states are: identity available → waiting for current-process CNI
admission → ordinary startup reconciliation → steady-state reconciliation.
For Kubernetes only, retain the same runtime Store-backed guard and actively
sample it before the first egress/data-plane reconciliation. While it refuses,
keep process liveness available and readiness false. Wait outside the operation
lock, honor context cancellation, and release every successful admission probe
immediately; it is a synchronization point, not cached write authority. All
subsequent CNI operations still acquire and validate their own scoped, bounded
grant. A manager/boot/owner/epoch/scope change, stale observation or mismatched
receipt still resets/refuses admission exactly as C2 requires.

Keep a read-only sampler on that same guard alive with the process, rather than
performing only an initial two-observation wait. The normal desired-state HTTP
fetch can take up to sixty seconds, while observation history expires after ten;
without continued sampling, a successful slow fetch can recreate the first-proof
refusal at startup withdrawal. Sample at the existing two-second netprep cadence,
with no data-plane write or cached grant. The initial ready signal releases only
startup sequencing; later sampler success never directly sets gateway readiness.
Cancellation stops sampling, and the existing operation guard remains mandatory
even when the sampler has previously admitted this process.

Do not inherit init's proof count, shorten the two-observation requirement,
extend a grant's expiry, bypass withdrawal, hold the CNI lock while sleeping,
or turn arbitrary ownership-startup failures into success/retry. VM startup is
unchanged. Missing or incompatible runtime authority remains visibly blocked,
not Ready. This does not implement S20.5.2 failed-candidate rollout recovery or
S20.6 reboot rebootstrap; the failed walk still requires the supported lifecycle
operations and a new immutable candidate, never a remedial restart or live patch.

Required regression evidence: no data-plane startup before two advancing valid
runtime observations; repeated/same heartbeat, missing/stale/foreign authority
cannot pass; canceled waits exit promptly; probe locks are released before wait
and subsequent work; the same guard retains bounded observation history; later
operations still reject expired/changed grants; ordinary non-Kubernetes startup
is unaffected. Re-run node gates, independent review and fresh AWS enrollment.
