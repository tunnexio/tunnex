# S15.8 — Desktop posture visibility

Status: locked design (implementation follows)

## Problem

The desktop client reports posture and can receive a server verdict, but a
noncompliant warn-mode verdict is discarded. Require-mode blocks have a native
notification call, yet the client has no durable warning state and no reliable
in-window alert if macOS suppresses a native notification. An access-affecting
posture result must not be silent.

## Decisions

### D1 — Warn-mode noncompliance is a distinct client state (locked)

When the server returns `noncompliant` with `blocked=false`, the tunnel remains
up and the client enters `posture_warning`. It reports the warning once per
transition and clears it when the server next returns compliant.

### D2 — Block and warning are visible without OS notification permission (locked)

Both posture states are sent through the existing status channel and rendered
in the client window and tray. A native notification is best effort only; macOS
notification settings cannot suppress the in-app and tray evidence.

### D3 — Transitions are de-duplicated (locked)

Repeated 10-minute reports with the same verdict do not spam native
notifications. A warning promoted to a require-mode block produces the block
notification exactly once.
