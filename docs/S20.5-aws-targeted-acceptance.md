# S20.5 AWS repair — targeted acceptance

Status: **USER-DIRECTED ACCEPTANCE REVISION, 2026-09-06.**

The user directed us to reconcile the overbuilt walk, retain valid proof and
test broken/changed behavior instead of repeatedly restarting eleven legs.
This supersedes the exhaustive AWS walk requirement in the original box-walk
and AWS plan. It does not change product security contracts, authorize a merge,
or turn unrun cases into passes. Other stories' rules are unchanged.

## What was wrong with the old accounting

The eleven legs mixed environment setup, independent feature qualification,
regressions, and release gates. All-or-nothing leg counting hid real working
behavior inside incomplete composite legs. A new repository SHA was also
treated as invalidating unrelated component evidence. Reporting the latest
candidate as 0/11 conveyed less useful information than the actual evidence.

Some re-tests were necessary: changing AWS SNAT behavior required a new real
packet/client proof, and failing credential tests required a real repair.
That does not justify repeating installation, DNS setup or every CRD adoption
case after an unrelated API correction.

Measured example: `git diff dc70c9b 48f96b0 --name-only` changes only API
source/tests and evidence. `apps/node`, `apps/cli`, `apps/operator`, `apps/helper`,
`apps/web`, `apps/client`, `deploy`, and `Makefile` are byte-unchanged. The API
credential/health correction does not erase the existing node/Helm/retained-
identity evidence. Its health-report change does justify a small integration
smoke and the already-required HA regression, not a clean-cluster rebuild.

Historical evidence retains its original SHA, image digest, observations and
limitations. Reuse means relevant evidence remains valid; it does **not** mean
an old binary was built from a newer commit or an incomplete scenario passed.
The existing invalid B2-standby fault is still not reverse-crash proof.

## Shortest remaining engineering loop

1. Fix the observed same-content version/lease problem. Use a deterministic
   local regression for repeated wakeups with unchanged canonical base while
   a standby is absent. Check nearby safety behavior: real content/scope/
   generation changes still need exact ACKs, and unfence/restart/watch behavior
   remains correct. Do not replace this with a wider generic recovery project.
2. Publish/deploy only the changed components during iteration, with truthful
   source/digest provenance and compatibility checks. Do not rebuild/reinstall
   six images and four charts for each API-only edit. Produce the normal
   version-matched distributable once when needed for final packaging; do not
   weaken its signing, version or provenance contracts.
3. Run one bounded AWS sequence on the existing three-worker setup:
   - baseline: intended images, original identities, Ready, private IP and
     normal FQDN responses;
   - standby absent/restored: keep the healthy owner serving past the existing
     lease horizon, then verify returning identity/readiness and no recurrence
     of the observed startup mismatch/interruption;
   - active failure/restoration: condition the exact fault on fresh owner and
     readiness checks, observe automatic takeover and recovery, then restore
     the fixture and verify healthy traffic. Capture automatic failback if it
     happens; do not force a redundant second crash merely to match A/B names.
   Use normal product operations and the already-scoped scale fault, not host
   repairs. Deterministic wakeup cases belong in automated tests; if a particular
   event was not observed on AWS, do not fabricate that observation or wait
   unboundedly for it. Report measured outage; do not claim seamless failover
   or exhaustive bidirectional-crash certification.
4. Review the final changed behavior, then use required CI on the actual PR
   head. Open the draft PR after this targeted AWS proof, write the final PLAN
   pointer in the established order, and obtain fresh merge approval.

During iteration run the changed package and directly affected contract tests
(both editions for API changes). Run generation when generated inputs change.
Do not manually repeat the complete local matrix after every small patch or
docs commit. One final integrated verification plus required exact-head CI
remains; existing automated safety tests are not deleted or weakened.
