## 2.3 ⛔ THE AUTH LABEL MUST NOT INFER SSO FROM AN ORG-LEVEL FACT — the third state is REACHABLE

*"No local password ⇒ SSO"* reads a per-user absence through an org-level config. **Measured, and it is not a
corner case:**

```
users: 237 of 241 have password_hash IS NULL
demo org sso_configs: NO ROW — no provider configured at all
```

**A user with no password in an org with no provider is NEITHER.** The very first org a reviewer opens would
disprove the label.

**RULED: the label stops at the fact — `local password` / `no local password`, and nothing further.** The org's
provider is a fact about the ORG, not about how a person signs in. Same line already drawn for `AuthMethod`,
one step further out.

### ⛔ AND THE COLUMN DOES NOT SHIP — `password_hash` IS NOT PROJECTED. **D1b.**

**A CONSUMER WITH NO PRODUCER — the who-reads-this probe run backwards.** By the dormant-machinery law the
function came OUT rather than waiting for a story, and this ruling is where its reasoning now lives.

**D1b: the AUTH column needs ONE projected boolean.** Twin of D1's MFA column (three fields). **Both HELD** —

### THE SCREEN'S SHAPE, RULED

**An open-edition MEMBER sees:** email · name · role · status · joined · verified — **a coherent roster**, plus
**one panel-level line** stating that group and MFA detail are not available to them. **Not six blanked cells.**

- **The edition seam is a RENDER decision, never a style** (epic rule). A column hidden by `opacity` is still
  in the DOM, still announced, still reachable — *"gone only to a sighted mouse user."* **Gated columns are
  ABSENT from the column set, not dimmed.**
- **AND NOT THE S14.5 HALT IN REVERSE.** That halt was an upsell shown for a capability the API treated as
  core. **The inverse error is hiding something the open edition IS entitled to** — so only the group-derived
  content is edition-gated. Role, status, devices-for-admins and `email_verified` are **core and always render**.

### ⛔ THE DEVICES COLUMN HAS A FALSE-ZERO STATE — the Routed Ranges shape with a number

A **member** viewing the roster derives the group-by from a list containing **only their own devices**, so
**every other member renders `0 devices`.**

> ## **A FALSE ZERO IS WORSE THAN AN ABSENCE. It is a positive claim about another person's fleet, drawn**
> ## **from a response that was never about them.** ABSENCE OF PERMISSION IS NOT ABSENCE OF DATA — ruled on
> ## Routed Ranges; this is the same defect with a number instead of a cell.

**RULED: the column renders ONLY for `PermMemberManage` holders. For anyone else it is ABSENT from the column
set — never a count, never a dash, never a zero.** The reason goes on the panel, so a member is told the column
exists and is not theirs to see, rather than being shown wrong numbers or an unexplained gap.

# 4. FIXTURE — a PRECONDITION OF THE BUILD, NOT OF THE REVIEW

Two S14.10 reviews failed on states that were not reachable; **each cost a full cycle.** So before any code:

| state | why it must exist |
|---|---|
| a **deactivated** member | S2.6's distinct render is unobservable without one |
| an **unverified** member (`email_verified: false`) | §2.6's addition has no subject otherwise |
| **all three roles** (owner / admin / member) | `role` is the column the screen is named for |
| a **sole-owner org** | the last-owner 403 cannot be observed any other way |
| ⛔ a member with an **EMPTY NAME** | **added after it caught a live defect — see below** |

### ⛔ THE FIXTURE WAS LESS REPRESENTATIVE THAN A TEST DOUBLE, AND THAT HID A SHIPPED DEFECT

`users.name` is **`NOT NULL DEFAULT ''`** and `acceptInvitation`'s `name` is **OPTIONAL**. Measured:

```
users with name = '' or NULL : 144 of 241
demo-org members with a name : 5 of 5   ← every seeded member had one
```

The roster cell rendered `{m.name || m.email}` **and** `{m.email}` unconditionally, so a nameless member's row
read `nadia@… nadia@…`. **Nobody ever saw it**, because the fixture gave every member a name — while 144 real
users have none. It surfaced only because a test **mock omitted `name`**, and I first mistook the resulting
`Found multiple elements` for a test bug.

> ## **S14.10's TRAP WAS A DOUBLE MORE PERMISSIVE THAN THE SUBSTRATE. THIS IS THE SAME LESSON FROM THE OTHER**
> ## **SIDE: A FIXTURE LESS REPRESENTATIVE THAN THE DOUBLE. And only the fixture side is reviewable on a**
> ## **screen — the founder cannot see what the fixture never produces.**

Fixed (the email is the secondary line only when a name took the primary one) and `nadia-no-name@` seeded with
`DO UPDATE SET name = EXCLUDED.name`, so a re-seed is re-runnable **into** the empty-name state rather than
away from it.

### THE GROUP PANEL COUNTS GROUPS, NOT PER-MEMBER EDGES — a fan-out ruling

Per-member group membership needs `listGroups` **plus `listGroupMembers` PER GROUP**: an N+1, and at
pre-flight check 1's 10×/100× that is **51 requests for 50 groups.** The panel therefore renders group
**access + count from ONE request**, and the per-member `idp-sync` marker and `teamMap` edges stay **D2**.

**Rules, from S14.10:** seed the INPUTS a controller consumes, never a field it owns · any value relative to
`now()` is `ON CONFLICT … DO UPDATE`, never `DO NOTHING` · destructive writes are **org-scoped** · and the
census is read **from the API payload, never psql** (they disagreed in S14.10 and psql was wrong).
