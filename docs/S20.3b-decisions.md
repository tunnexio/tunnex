# S20.3b — Operator-controlled Kubernetes connector HA activation

Status: **LOCKED — FOUNDER APPROVED 2026-08-28** on `k8-improvement`.

Founder disposition: **D1–D12 LOCKED as recommended.** This paper changes no
product behavior by itself. Product implementation remains subject to the
repository's paper-first story sequence and the founder's separate no-commit,
no-push-until-preview instruction.

This story supplies the deliberately missing P3 boundary between S20.3a's
default-OFF fenced handoff machinery and an operator-visible HA capability. It
owns the explicit ownership-mode transition, the authoritative ordinary-base
classification/unfence transport, public HA configuration and status APIs,
and an organization opt-in that is OFF by default.

## Measured starting point

- S20.3a has an external `HandoffOwnershipModeTransition` seam. The P2
  bootstrap can prove one exact active member serving and every eligible
  standby `prepared_non_serving` through fresh v3 applied ACKs, but it cannot
  mint its own `fenced-base-ready` prerequisite.
- The P2 scheduler composition is default OFF and has a finite, non-sensitive
  operator-status projection. That projection is not a public route and does
  not itself start a leader campaign, scheduler, delivery, or handoff.
- A v3 node persists pool fences independently of lease state. An armed fence
  accumulates changed routes, WireGuard AllowedIPs, VIP/DNAT mappings, DNS
  zones/answers/listeners, and derived OpenVPN state across revisions,
  withdrawal, expiry, and restart.
- The node's `BaseAuthority` contract already requires scope-complete pool
  classifications. It releases a fence only for an explicit pool scope bound
  to the exact full-base version and SHA-256 hash, while no ownership is
  active. An empty authority object or missing field is not an unfence.
- A serving v3 manifest arms the current owner's fence today. A standby's
  `prepared_non_serving` manifest deliberately owns zero fields, so its ACK
  cannot prove a durable fence. P3 must close that gap with an explicit
  base-authority arm receipt; it must not reinterpret a prepared ACK as one.
- The current ordinary desired-state response carries no public ownership
  mode and no wired base-authority payload or receipt. Existing agents must
  continue decoding the old response and must never become HA candidates.
- Kubernetes cluster registration and Service exposure are currently core,
  all-edition capabilities. There is no approved commercial source that
  assigns connector HA to a paid tier, so P3 must not invent one.

## Decide-items and recommended dispositions

### D1 — Story boundary

**Recommendation: LOCK.** P3 implements only:

1. a durable organization HA opt-in and per-pool requested/actual ownership
   mode;
2. the leader-session-bound transition that returns P2's closed
   `fenced-base-ready` prerequisite;
3. a versioned private base-authority transport, node receipt, classification,
   and explicit unfence flow;
4. public read/mutate APIs for HA settings, pool transition, and truthful
   operator status; and
5. the minimum web call sites needed to make every public mutation reachable
   and to explain its effect.

Provider-first cluster enrollment, cloud inventory discovery, cluster-scope
access resources, multi-port expansion, and deployment/Helm changes are
separate stories. P3 does not rewrite P2 manifests, lease rules, scheduler
state machine, cluster registration, or Service exposure.

### D2 — Desired mode and actual mode are separate durable facts

**Recommendation: LOCK.** Add an organization setting with `enabled=false` by
default and an additive per-pool transition record. The record separates the
operator's request from achieved runtime truth:

- requested mode: `legacy` or `fenced_ha`;
- actual mode: `legacy`, `bootstrap_pending`, `fenced_ha`,
  `drain_pending`, or `blocked`;
- exact organization, Site, cluster, pool, active member, promotion
  generation, membership epoch, monotonic transition revision, and last
  committed reason code; and
- timestamps and actor/cause for the request, without raw delivery material.

Enabling the organization setting makes HA available; it does not silently
transition every pool. An explicit per-pool request is required. A setting or
pool row missing from an upgraded database means OFF/`legacy`, never ON.

The organization setting and pool request are configuration. Neither may be
reported as active HA until actual mode is `fenced_ha` and the existing P2
runtime status is non-blocked. `leader_idle` remains a control-plane role fact,
not a traffic, failover, or application-HA claim.

### D3 — The only legacy-to-HA transition

**Recommendation: LOCK.** A pool moves from `legacy` to `fenced_ha` only in
this order:

1. an authorized operator enables the organization setting and explicitly
   requests `fenced_ha` for one valid pool;
2. the transition row becomes `bootstrap_pending`; the failover scheduler
   remains ineligible;
3. the control plane sends every named member an exact base-authority
   `arm_fence` classification for its pool/generation and receives a durable
   exact authority receipt; this arms a standby tombstone without making the
   standby serve;
4. P2 issues the exact current-owner `serving` v3 envelope and exact
   `prepared_non_serving` envelopes to every currently eligible standby;
5. the current owner returns a fresh exact v3 serving ACK and every standby
   returns its exact zero-ownership prepared ACK;
6. on the same acquired advisory-lock connection, one transaction re-locks
   the organization setting, pool, membership, generation, active member,
   Service UID provenance, base-authority arm receipts, v3 deliveries/ACKs,
   and current transition revision;
7. that transaction records actual mode `fenced_ha`, its exact generation,
   membership epoch, and achieved base-authority revision, then returns the
   closed `fenced-base-ready` prerequisite; and
8. only then may the pool/generation enter the leader-bound scheduler source.

Any changed member, generation, active node, UID incarnation, expired ACK,
leader session, opt-in, or transition revision leaves the pool pending or
blocked. A process-local boolean, successful legacy desired-state fetch,
advertised capability header, v1/v2 receipt, prepared ACK without its matching
authority-arm receipt, or partial standby set cannot complete the transition.

Repeating the exact request or replaying the same transition revision is
idempotent. A competing different request receives a typed conflict; it never
silently replaces an in-flight transition.

An expired, unacknowledged base-authority delivery is also never extended,
rewritten, deleted, or superseded at the same transition revision. The
leader-held activation session re-locks the exact pool/member/generation
snapshot, advances to a new transition revision, and audits the exact old
revision, new revision, and `expired_unacknowledged_base_authority_delivery`
reason. Every member then receives authority under that new revision; prior
receipts cannot satisfy it, and P2 issuance remains closed until every new
exact receipt exists.

A previously acknowledged authority delivery whose durable receipt becomes
older than the locked freshness window is recovered by the same mechanism,
not by replaying or refreshing that receipt in place. The leader-held session
advances to another transition revision with the exact
`stale_base_authority_receipt` audit reason, preserves the old delivery and
receipt, and requires fresh exact receipts from every member before P2 can
resume. If stale receipts and expired unacknowledged deliveries coexist, the
single revision advance records
`expired_unacknowledged_and_stale_base_authority_receipts`.

### D4 — Versioned ordinary-base authority is part of the private mTLS contract

**Recommendation: LOCK.** Extend the full ordinary desired-state response with
an optional versioned `kubernetes_ownership_base_authority` object. It is
authenticated by the existing node mTLS principal and is additive for mixed
versions: old agents ignore it and remain legacy-only; P3 refuses them as HA
candidates.

For a new agent the object binds:

- wire version and a monotonically increasing per-node authority revision;
- exact node, organization, Site, full-base version, and canonical full-base
  SHA-256 hash;
- one scope-complete classification for every armed pool visible to the node,
  including the complete currently attributed pool-owned routes, peer-keyed
  AllowedIPs, VIP/DNAT mappings, DNS state, and derived OpenVPN inputs; and
- a separate explicit `unfenced_pools` list, when authorized.

Each classification carries one closed disposition: `arm_fence` for the
bootstrap generation or `maintain_fence` for a later ordinary-base revision.
`arm_fence` may create a durable non-serving standby tombstone from complete
control-plane attribution even when that standby's ordinary base currently
contains no pool fields. It cannot create a lease, overlay, or serving ACK.
Fence release is deliberately not another classification disposition; it uses
only the separate exact `unfenced_pools` assertion.

The node recomputes the base hash after strict decoding, rejects duplicate or
cross-scope classifications, and persists the accepted authority revision
before applying the projected base. A lower revision, changed replay, unknown
enum, missing classification for an armed pool, unclassifiable/ambiguous
field, or hash mismatch keeps the prior fence and produces no success receipt.

The authority object contains no credential or private key. It remains on the
private agent route and is not copied into a public operator response.

### D5 — Classification is complete attribution, not a best-effort filter

**Recommendation: LOCK.** The control plane classifies every ordinary-base
field owned by a fenced pool at the exact snapshot being sent. Classification
is by explicit organization/Site/cluster/pool provenance, never inferred from
CIDR overlap, naming, a selected connector, or equality with an old manifest.

An `arm_fence` classification first persists the complete pool tombstone and
returns its own exact receipt. An armed node fence then unions later
`maintain_fence` revisions into that durable tombstone. Therefore changed/extra
pool routes, AllowedIPs, VIPs, Service children, DNS state, and OpenVPN inputs
remain suppressed after withdrawal or restart. Unrelated ordinary state
continues to reconcile.

If the compiler cannot attribute the complete pool domain, it refuses that
base for the affected node and surfaces a finite `base_classification_invalid`
reason. It must not send an incomplete classification and hope the previous
fence catches the difference.

### D6 — Explicit unfence is a drain completion, never omission

**Recommendation: LOCK.** Disabling HA is an asynchronous safe transition:

1. the organization OFF switch immediately blocks new pool activations and
   new promotion/failback decisions;
2. every affected pool becomes `drain_pending` while its committed operation
   is allowed to reach a safe terminal point or is held for operator attention;
3. the active v3 lease is explicitly withdrawn and ACKed, or its CP-issued
   expiry is proven locally; every other pool member is also proven
   non-serving;
4. the ordinary compiler emits a new full base that restores single-connector
   legacy authority to the still-current active member and classifies the
   pool fields for every armed node;
5. a later exact base sends the pool in `unfenced_pools`, bound to that base
   version/hash and a newer authority revision; and
6. every affected new agent atomically persists the fence release and base,
   applies/read-backs it, and sends an exact base-authority receipt before the
   control plane records actual mode `legacy`.

Unfence is refused while any lease is active, any handoff is nonterminal, the
pool/member/generation changed, a node is missing its exact receipt, or the
base version/hash differs. Field absence, an empty authority object, agent
disconnect, pool deletion, organization opt-out, application rollback, or a
timeout never means unfence.

There is no public force-unfence endpoint in P3. A stuck drain remains visible
as `blocked`/`needs_attention`; destructive recovery requires a later paper and
separate authorization.

### D7 — Public API is OpenAPI-first and concurrency-safe

**Recommendation: LOCK.** The OpenAPI surface provides:

- read/update organization Kubernetes HA settings;
- list/get pool HA status; and
- set one pool's requested ownership mode.

Exact paths and generated operation names are chosen during the OpenAPI slice,
but the contracts are fixed here. Mutations carry an expected settings or pool
transition revision. A stale revision is refused; identical retries return the
same committed result. Enabling or disabling returns the requested state plus
the actual asynchronous state and never claims immediate completion.

Public responses expose stable enums, finite reason codes, generation,
membership-epoch-known plus its value, transition revision, and safe
timestamps. They omit DSNs, advisory-lock/backend PIDs, node certificate or
key material, delivery nonces, raw manifests, lease artifacts, raw dependency
errors, and internal SQL details.

The status service returns no partial-success list on a database/projection
failure. Unknown, missing, stale, or ambiguous evidence degrades or blocks;
zero is never fabricated as a successful count, epoch, revision, or readiness
fact.

### D8 — New named permissions; no invented commercial gate

**Recommendation: LOCK.** Add `k8s_ha:view` and `k8s_ha:manage`; do not reuse
`org:view`, `org:update`, or `k8s:manage` for this new capability.

- owner and admin receive both permissions;
- the fixed machine-operator role receives view only so automation can observe
  convergence but cannot silently activate or drain HA; and
- member and agent roles receive neither.

Every handler orders authentication, named permission, any future entitlement,
then object/state lookup so it leaks no cross-tenant or commercial oracle.

Kubernetes connectivity is currently core/all editions and no approved source
prices connector HA. P3 therefore adds no edition gate. If commercial policy
later assigns HA to a plan, that is a named follow-up decision with its own
entitlement census and downgrade behavior; it does not retroactively turn the
organization opt-in ON.

### D9 — Deployment readiness and organization opt-in are independent gates

**Recommendation: LOCK.** A deployment-level composition gate remains OFF by
default and validates schema, exact dependencies, timing, leader elector,
health source, P2 issuer/reader, provenance fence, bootstrap transition, and
base-authority receipt store. The organization setting cannot override a
missing or blocked deployment dependency.

Runtime eligibility is the conjunction of:

1. deployment composition ready;
2. organization opt-in enabled;
3. pool requested and actual mode `fenced_ha` for its current generation;
4. exact durable `fenced-base-ready` prerequisite on the current leader
   session; and
5. existing P2 health, provenance, and nonterminal-operation rules.

Edition/licence unlock, API availability, a rendered toggle, or a green status
poll never starts the scheduler by itself.

### D10 — Operator status and copy state consequences plainly

**Recommendation: LOCK.** The UI and API show configuration and runtime as
separate axes:

- organization: `disabled` or `enabled`;
- ownership transition: `legacy`, `bootstrap_pending`, `fenced_ha`,
  `drain_pending`, or `blocked`; and
- scheduler: `disabled`, `blocked`, `follower`, `leader_idle`,
  `leader_operating`, or `degraded`.

The UI must not label `leader_idle`, `fenced_ha`, or a healthy member count as
"highly available" without the live box-walk proof. It explains that enabling
can move private Service VIP, route, DNS, and OpenVPN ownership between
connectors; disabling stops automatic failover and safely drains back to one
connector, and can temporarily reduce availability while convergence occurs.

The disable confirmation states what survives: cluster registration, exposed
Services, VIP allocation, connector-pool membership, and audit history are not
deleted. It also states that a blocked drain leaves fences in place and may
keep affected Kubernetes traffic withdrawn until remediation. Cancel closes
the dialog; it performs no mutation.

Every mutating endpoint has one named web call site or is explicitly documented
as automation-only. The API mutation census and foreign-key actions are
reviewed so no destructive cascade or unreachable operation is hidden by the
wireframe.

### D11 — Audit distinguishes request, achieved transition, and failure

**Recommendation: LOCK.** Setting changes and pool mode requests are audited
atomically with their committed configuration transaction, naming the actor,
cause, scope, old/new requested state, and transition revision.

Achieved `fenced_ha` and achieved `legacy` are separate system-actor audits
written only with their exact state transition transaction. Bootstrap issues,
receipts, retries, blocked reasons, and drain attempts remain operational
provenance; they do not claim successful activation/deactivation. Raw secrets,
manifests, delivery nonces, and dependency error strings never enter audit.

### D12 — Expand, activate, roll back, and contract

**Recommendation: LOCK.** Forward rollout is:

1. add settings, transition, authority-revision, and exact receipt schema while
   every existing organization and pool remains OFF/`legacy`;
2. deploy mixed-version-compatible API and node code with deployment
   composition OFF;
3. observe v3 capability, UID provenance, complete base classification, and
   receipt readiness without activating a customer pool;
4. enable the deployment composition gate; and
5. let an authorized operator opt in an organization and explicitly request
   one pool at a time.

Application rollback is:

1. set the organization opt-in OFF and stop new scheduler decisions;
2. complete or disposition every nonterminal handoff;
3. withdraw/expire every v3 lease;
4. deliver and receive exact explicit unfence receipts for every armed member;
5. prove every pool actual mode is `legacy` and there are zero live v3 serving
   leases; and only then
6. roll application code back while retaining the additive ledger.

No down migration, row deletion, force-unfence, or implicit schema contraction
is part of rollback. A future contraction must preflight zero non-legacy pool
modes, zero live v3 leases, zero armed/unacknowledged authority transitions,
and organization opt-in OFF before separately authorized destructive SQL.

## Rejected alternatives retained for archaeology

- **Reject global-switch activation.** Enabling the organization setting does
  not transition every pool; each pool requires its own reviewed request.
- **Reject inferred readiness.** Capability headers, desired-state success,
  v1/v2 receipts, prepared ACKs without arm receipts, and process booleans are
  not `fenced-base-ready` authority.
- **Reject omission-as-unfence.** A missing field, missing authority object,
  disconnect, timeout, deletion, or application rollback cannot retire a
  durable fence.
- **Reject best-effort classification.** CIDR/name inference or a partial list
  cannot safely classify a pool-owned base domain.
- **Reject force activation/unfence.** P3 exposes no bypass around lease,
  receipt, generation, or exact base version/hash checks.
- **Reject permission and commercial inheritance.** HA does not ride on an
  existing permission or an unapproved edition assumption.
- **Reject status-by-narration.** Requested ON, `fenced_ha`, `leader_idle`, and
  healthy counts remain distinct facts and none alone claims live HA.

## Required acceptance proof

The implementation is not complete without all of the following evidence.

### Migration and compatibility

- Upgrading a pre-P3 database preserves every organization, pool, member,
  exposure, UID record, handoff ledger, and audit row; new settings read OFF and
  pools read `legacy`.
- Old API/new node, new API/old node, and rolling API replicas preserve legacy
  traffic. An old or v1/v2-only agent is visible as ineligible and receives no
  HA authority.
- Exact mutation retries are idempotent; stale/different revisions conflict;
  restart resumes the durable transition without inventing an ACK or mode.

### Ownership transition and authority

- The transition cannot return `fenced-base-ready` before the exact active
  serving ACK, every eligible standby prepared ACK, and every named member's
  exact durable base-authority arm receipt for the locked
  generation/membership epoch.
- Leader loss before commit writes no achieved mode; leader loss after commit
  is reconstructed from durable state on the new exact leader session.
- Changed/missing/extra classified routes, AllowedIPs, VIP/DNAT, DNS, and
  OpenVPN fields remain fenced across ordinary-base updates, withdrawal,
  restart, and manifest revision changes.
- Missing authority, omitted fields, changed replay, duplicate/cross-scope
  classification, ambiguous attribution, stale authority revision, and wrong
  base hash/version cannot unfence or produce a receipt.
- A prepared standby with no authority-arm receipt remains scheduler-ineligible;
  an arm receipt never makes that standby serve.
- Unfence is atomic and impossible with active ownership. Persistence failure,
  apply/readback mismatch, disconnect, or restart leaves the durable fence
  armed and actual mode non-legacy.

### API, authorization, and status truth

- OpenAPI generation produces Go/TS/RBAC/sqlc outputs with no drift.
- Sessionless requests are 401; callers without the new permission are 403
  before state/edition lookup; cross-org IDs disclose no object; owner/admin
  manage and machine-operator view behavior match the generated grant table.
- Settings OFF, deployment blocked, bootstrap pending, follower, leader idle,
  leader operating, degraded, drain pending, and blocked all render distinct
  API states with finite safe reason codes and correct false-zero handling.
- Every mutating endpoint has a tested call site, and destructive copy matches
  the handler response and foreign-key behavior.

### Runtime and live wire

- Both editions pass API tests/builds; node unit and Linux/race ownership tests
  pass; the complete repository gates pass.
- A committed box-walk enables one organization and one pool, kills the active
  connector, proves break-before-make and no simultaneous ownership, proves
  traffic/DNS/OpenVPN recovery and failback, then disables HA and proves exact
  drain, unfence receipts, and stable legacy traffic.
- The box-walk proves process restart and control-plane leader loss in both
  bootstrap and drain phases. Unit tests are substitutes for unavailable
  infrastructure, never satisfaction of the live-wire claims.

## Stop boundary

P3 may be called **operator-controlled connector HA implemented** only after
the migration, API, mixed-version, node authority, both-edition, Linux, UI call
site, review, and committed box-walk evidence are complete.

It is not provider-first cluster enrollment, cluster-scope access, multi-port
Service expansion, deployment rollout, or production activation. No commit,
push, PR, merge, deployment, organization opt-in, pool transition, or live
fleet mutation is authorized by this draft.
