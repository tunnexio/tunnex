# S16.1 — UI-managed upgrade box-walk

Status: SUBSTITUTE — local contracts and both edition gates prove the bounded
request, durable status, backup, and UI seams. A production-shaped host walk is
still required before public-beta readiness; it needs explicit deployment upgrade
authorization and is intentionally not performed from CI or this PR.

## Walk procedure

1. On a disposable Docker host, install with `curl -fsSL https://get.tunnex.io | sh`.
   Confirm `/usr/local/lib/tunnex/{upgrade.sh,upgrade-runner.sh}` is owned by
   root and the `tunnex-upgrade-runner.path` unit is enabled.
2. Sign in as a CP administrator. Confirm the dashboard shows only the current
   signed target and requires an explicit confirmation before requesting it.
3. Request the upgrade. Confirm the UI reconnects through the API restart and
   reaches `healthy` with retained dump and manifest filenames.
4. On the host, run `pg_restore --list` on the reported dump and
   `docker compose exec -T api backupctl verify --dump-sha256 < manifest`.
5. Stop after a forced preflight failure on a second disposable host. Confirm the
   UI reaches terminal `failed`, exposes no host output, and accepts a later
   request after the fault is repaired.
6. Confirm a non-CP-admin cannot read detailed status or request an upgrade, and
   a second request during an active run is rejected or converges on the same id.

## Evidence to commit during the walk

- Redacted systemd unit state and root ownership/modes.
- Signed release source/sequence, request id, and terminal UI state.
- Redacted backup verification output and the negative authorization/concurrency
  responses.
