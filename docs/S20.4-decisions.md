# S20.4 — Approval-gated Kubernetes cluster-scope access

Status: **LOCKED — FOUNDER APPROVED 2026-08-28**.

Founder disposition: **D1–D14 LOCKED as recommended.** Product implementation
remains subject to the repository's paper-first story sequence and the
founder's separate no-commit, no-push-until-preview instruction.

This story activates the dormant cluster-scope storage already present in the
current repository. It does not copy the historical branch wholesale. The
historical `iotunnex/tunnex@codex/kubernetes-cluster-scope-ha` implementation is
evidence for the exact-child and approval state model; current OpenAPI, RBAC,
edition/opt-in, policy, inventory, and UI ownership remain authoritative.

No deployment, push, PR, or merge is authorized by this paper.

## Measured current boundary

- Migration `0080` already split one logical exposed Kubernetes Service
  identity from its exact protocol/port child rows. Existing single-port rows
  retain their IDs, VIPs, DNS names, and static `k8s_service` grants.
- Migration `0084` and the current P2 worktree's `0117`, `0118`, plus
  attribution work provide the Service-UID and connector-ownership
  prerequisites. Cluster scope may consume only current, attributed,
  exact-cluster observations; a bare namespace/name match is not authority.
- Migrations `0086` and `0087` already add the dormant
  `k8s_cluster_scope` policy destination, scope grants, exact-child membership
  rows, immutable decision state, bounded fan-out, and membership origin. The
  current service, handlers, OpenAPI, RBAC, compiler, and released web app do
  not write or activate those rows.
- Current OpenAPI exposes registered clusters and manually exposed Services
  only. It has no agent-reported namespace/Service/port inventory, cluster
  scope, candidate, review-queue, or decision contract.
- Current policy creation accepts only static destinations. The compiler knows
  `k8s_service`, not `k8s_cluster_scope`; therefore dormant or malformed scope
  rows currently produce no entitlement.
- Current `k8s:manage` is core connectivity authority and the machine Operator
  holds both `k8s:manage` and `policy:manage`. Reusing either for approval would
  let an unattended principal approve access to a Service it exposed.
- The Kubernetes screen is connectivity-owned and broadly readable through
  `org:view`. Scope candidates, grantees, and decisions are governance data and
  have no safe call site there today.
- The provider-first enrollment UI is a presentation and installation
  dependency, not an authorization source. AWS/Azure/GCP/on-prem APIs are not
  connected for cloud-account discovery; live workload choices must come from
  the enrolled connector's authenticated Kubernetes observation channel.

No existing response field changes meaning. |
| Policy rules | Existing API accepts static destinations; old compiler ignores the dormant scope arm | OpenAPI-first cluster-scope request/response, dedicated service branch, and approved-child lowering | Organization opt-in defaults OFF. Do not enable until every API instance is scope-capable; rollback disables opt-in and proves zero output while retaining additive data. |

| Scope storage | `0086`/`0087` exist but have no runtime writer | Use them through authored queries and a transactional service; add only real gaps at the next free migration number | Never edit or renumber `0086`/`0087`. | Web | Kubernetes can register/expose/unexpose; Access owns grants | Kubernetes consumes provider/inventory exposure APIs; Access owns scope creation and review | Missing permission, edition, opt-in, or auxiliary data removes protected content from the DOM. |

The forward sequence is **expand schema → deploy dormant readers/writers →
verify both editions and zero output while OFF → enable one test organization →
wire proof → broader opt-in**. There is no implicit contraction. A rollback
first disables every organization, verifies scope-derived allows are absent,
and retains the additive rows for a later compatible binary. Rolling back to a
binary that can generically mutate scope policy rows while any scope is active
is forbidden.

## Recommended dispositions

### D1 — Cluster scope is approved exact-child expansion, never a wildcard

**Recommended: LOCK.** A scope names one registered cluster, but grants only
individual Tunnex-exposed exact-port children that are both explicitly approved
for that rule and still current under the same opaque Kubernetes Service UID.

Namespace is an identity/presentation field, never a selector. A scope grants
no Pod, Node, endpoint IP, ClusterIP, VPC/CIDR, Kubernetes API, namespace
wildcard, unexposed Service, or provider account capability. `any`, port ranges,
and inferred sibling ports are refused.

### D2 — One logical Service may have many exact children

**Recommended: LOCK.** Agent inventory returns each Service with a deterministic
ordered port list. Every selected `(protocol, port)` becomes its own
`k8s_services` child. Sibling children share the logical identity's VIP and
FQDN, but policy membership and approval remain child-specific.

The new multi-port exposure request is atomic: it re-reads one current
server-owned inventory identity, validates the complete selected port set, and
creates all children, exposure audits, and required pending memberships or
none. Duplicate ports, UDP/TCP substitution, stale UID, unknown port keys,
partial fan-out, and client-supplied VIP/FQDN/target-port values are refused.
The legacy single-child endpoint remains compatible.

### D3 — Inventory is connector-reported, bounded, and non-sensitive

**Recommended: LOCK.** The authenticated active connector reports current
namespace, Service name, opaque UID, and Service ports. The public API returns
a server-issued opaque inventory reference plus presentation fields and exact
port keys; it does not return the raw UID, Kubernetes credentials, ClusterIP,
Pod/endpoint IPs, node/VPC data, or cloud credentials.

Inventory is eligible only when its reporter is the current exact
org/Site/cluster owner, its sequence is replay-safe, and its observation is
fresh. Pool handoff may change the reporter without changing a Service UID.
Conflicting current UIDs, old generation, future timestamp, expired report, or
missing inventory fails closed with a typed unavailable/stale result. A failed
read is never represented as an empty cluster.

### D4 — Initial selection and later exposure have different meanings

**Recommended: LOCK.** At scope creation the server snapshots the current
eligible exact children. The administrator explicitly selects zero or more;
selected children become `approved` in the same transaction. No item is
selected by default.

Current unselected children have no active membership and are not called
rejected. An immutable initial-candidate evidence record retains their exact
child/UID tuple and selected boolean, because the existing
`initial_candidate_count` alone cannot prove which Services were offered.

An exact child exposed after scope creation creates one durable `pending`
membership per active scope in the same exposure transaction. It compiles to
nothing until approved. Failure or limit overflow aborts the entire exposure;
there is no exposed-but-unreviewed gap.

Explicitly adding an initially unselected current child is deferred to
**S20.4a explicit scope inclusion**. V1 never relabels such a child as a later
exposure; the operator may recreate the scope with a new explicit initial
selection.

### D5 — Decisions are one-way and human

**Recommended: LOCK.** Only `pending → approved` or `pending → rejected` is
valid. The server supplies actor and time. Same-decision retry returns the
stored result and emits no second audit; an opposing retry, reopen, or identity
change is a typed conflict.

Create, setting changes, scope enable/disable/delete, and decisions require a
verified non-machine human. The creator may later decide only if they still
hold the separate approval permission. Recent-auth/step-up and mandatory
four-eyes review are deferred because no repository-wide contract currently
exists for them.

### D6 — Named RBAC; connectivity and governance stay separate

**Recommended: LOCK.** Add:

- `k8s_scope:view` — read candidates, scopes, memberships, and the review queue;
- `k8s_scope:manage` — change the org opt-in and create/enable/disable/delete a
  scope; and
- `k8s_scope:approve` — approve or reject later memberships.

Owner and Admin receive all three by default. Member, Operator, and Agent
receive none. Scope creation also requires `policy:manage`; scope reads also
require `policy:view`. The named scope permission remains mandatory even where
today's role table makes the second check appear redundant. `k8s:manage`
continues to mean connectivity exposure only.

All server handlers authorize before edition, setting, scope, cluster,
inventory, count, or existence lookup. The generated web RBAC mirror is the
only client permission source; it is never hand-edited.

### D7 — Enterprise unlock, then organization opt-in

**Recommended: LOCK.** Cluster scope is Enterprise-only and adds an audited
organization setting `k8s_cluster_scopes_enabled`, default `false`. A licence
unlocks the capability but never enables it. Enabling does not create a scope
or approve a child.

Disabling immediately removes all scope-derived compiler output while
preserving scopes, memberships, and audit evidence. Re-enabling may restore
only still-live, still-approved exact children. Edition loss has the same
fail-closed enforcement result and preserves data for recovery. Scope creation,
scope enable, approve, and reject are refused while OFF. The setting update and
scope disable/delete remain available for safe withdrawal and cleanup; an
authorized Enterprise viewer may read preserved state with an explicit
disabled status.

### D8 — OpenAPI-first API ownership

**Recommended: LOCK.** Author the following concepts in
`openapi/openapi.yaml`, generate Go/TS/CLI types, then implement handlers:

1. provider-aware cluster enrollment metadata and a paged live Kubernetes
   inventory read;
2. atomic exact-port exposure from an opaque inventory Service/port selection;
3. paged cluster-scope candidates and scope/membership reads;
4. cluster-scope creation through the policy service with explicit initial
   child IDs;
5. an idempotent approve/reject command for one pending membership; and
6. audited organization setting plus scope enable/disable/delete operations.

Request bodies never accept UID, VIP, FQDN, actor, decision time, grantee
description, endpoint, or audit metadata. Cursor paging uses an opaque stable
server cursor; ordering and limits are deterministic. All organization,
cluster, rule, child, reporter, and source-subject relationships are rechecked
inside the write transaction.

### D9 — Compiler lowers to existing static-Service semantics

**Recommended: LOCK.** The snapshot builder reads only active, enabled,
approved memberships joined to the live exact child and current UID. Each is
lowered to the existing internal equivalent of the owning rule targeting that
one `k8s_service` child. The node wire format is unchanged only if this lowering
remains byte-equivalent to current Service allows and DNS-VIP allowances.

Pending, rejected, disabled, expired, opt-in-OFF, unlicensed, missing,
soft-deleted, recreated-UID, stale-inventory, invalid connector-owner, and
overflow states emit zero scope-derived allows. Approve, reject, disable,
delete, unexpose, deregister, opt-in change, and UID transition all invalidate
and republish through the existing policy propagation owner.

### D10 — Fixed fail-closed limits, no truncation

**Recommended: LOCK for v1.** Use server constants, not licence-derived or
organization-configurable values:

- inventory page size: maximum 100;
- eligible exact-child candidates considered for one scope: maximum 500;
- initially approved selections: maximum 100;
- memberships per scope: maximum 500;
- active scopes per cluster: maximum 20;
- exact ports in one atomic exposure request: maximum 32; and
- membership rows created by one exposure transaction: maximum 500.

The additive migration widens the dormant `initial_candidate_count <= 100`
check to the locked 500-candidate bound and adds the immutable initial
snapshot; it must not rewrite `0086`. Every limit has a typed refusal before
any partial rule, child, membership, audit, queue, or compiler output.
Pagination never changes the security bound or silently drops candidates.

### D11 — Audit is transactional and redacted

**Recommended: LOCK.** Register explicit actions for setting changed,
scope-created, initial-child-approved, later-child-pending, later-approved,
later-rejected, scope-enabled/disabled/deleted, and destructive cleanup.

Real transitions write exactly one same-transaction audit row. Actor/time live
in audit columns. Metadata is server-built and limited to IDs, bounded counts,
decision origin, and outcome; it excludes raw UID, Service/FQDN/namespace,
protocol/port, grantee, endpoint/IP, credentials, and caller text. An audit
write failure rolls back the mutation. The durable in-product pending queue is
the notification boundary; email, webhook, chat, and node-push notification
are not claimed.

### D12 — Destructive and recovery semantics are explicit

**Recommended: LOCK.** The API and UI distinguish:

- **Reject membership:** permanent for that membership; grants nothing; no
  reversal. Recovery is a new scope or the S20.4a explicit-inclusion flow.
- **Disable scope:** reversible; withdraws all derived allows; preserves every
  decision.
- **Delete scope:** irreversible for live scope/membership rows; records exact
  pending/approved/rejected counts before deletion; append-only audit remains.
- **Unexpose exact child:** soft-deletes the child, removes VIP/DNS/policy
  output, retains membership history as vanished, and frees the logical VIP
  only after the final sibling child is gone.
- **Deregister cluster:** refuses with typed `cluster_scope_cleanup_required`
  while any scope exists. The operator must explicitly delete scopes first;
  an old client can never silently cascade a newly introduced governance
  object.
- **Disable org setting:** reversible bulk withdrawal, not deletion.

Generic policy enable/delete handlers must recognize a cluster-scope rule and
require `k8s_scope:manage` plus the verified-human gate. They cannot provide a
machine-principal bypass around the dedicated scope API.

### D13 — Provider-first UI is truthful and code-native

**Recommended: LOCK.** The Kubernetes enrollment surface uses accessible
provider cards and recognizable code-native/vector brand marks for Amazon EKS,
Microsoft Azure AKS, Google GKE, and Self-managed Kubernetes. Provider choice
drives installation guidance and filtering only; it never implies cloud-account
discovery or changes scope identity.

The workflow is provider → enrolled/connected cluster → agent-reported
namespace → Service → exact port selection. Searchable dropdowns show loading,
stale, error, empty, and ready states distinctly. They never fabricate a
cluster, Service, port, readiness, or zero count. A manual advanced exposure
path remains available for compatibility, clearly separated from verified
inventory selection.

Scope creation and approvals live on Access, where policy governance already
belongs. Provider logo and cluster context may be reused as presentation, but
the broadly `org:view` Kubernetes page never receives grantee, scope, pending,
approval, or rejection data without the dedicated permission-gated response.

### D14 — Every mutation has a released call site

**Recommended: LOCK.** The absence-question inventory is part of acceptance:

| Mutation | Required released surface |
| --- | --- |
| Enable/disable organization setting | Access settings panel for `k8s_scope:manage` |
| Create scope with initial exact children | Access rule builder |
| Enable/disable/delete scope | Access scope detail/actions |
| Approve/reject pending child | Access pending-review queue/detail |
| Inventory-backed multi-port exposure | Kubernetes provider/cluster/Service flow |
| Unexpose child and deregister cluster | Kubernetes service/cluster actions with exact impact copy |

An API mutation with no named caller is held as unreleased, not counted as a
finished feature. All destructive dialogs state effect, recovery, audit truth,
and whether rollback exists.

## Required additive schema gaps

The implementation may add one migration at the next free number after the P2
chain for these measured gaps only:

1. default-OFF organization opt-in;
2. bounded, attributed namespace/Service/port inventory and opaque public
   inventory references;
3. immutable initial-candidate evidence; and
4. any check/index adjustment strictly required by the locked limits.

It must preserve all existing exposure, static-policy, UID, and dormant-scope
rows. Up/down/up PostgreSQL proof is required. The down path refuses while new
opt-in, inventory, snapshot, or scope data would be lost; normal rollback
leaves the additive schema in place.

## Acceptance and stop condition

Before this story may be called implemented:

- **Migration/sqlc:** up/down/up, legacy-row preservation, cross-org rejection,
  exact identity constraints, concurrent create/expose/decide/delete, and every
  limit prove all-or-nothing behavior.
- **RBAC/edition/opt-in:** permission-before-edition/lookup, Owner/Admin grants,
  Member/Operator/Agent absence, verified-human mutation, default OFF, edition
  loss, and disable/re-enable are proven in both editions.
- **Inventory/API:** reporter ownership, replay, freshness, UID replacement,
  multi-port atomicity, cursor stability, error-vs-empty, idempotent retry, and
  redaction are proven.
- **Compiler:** only live approved exact children emit the existing VIP,
  protocol, port, DNS, and placement shape; every fail-closed state emits zero;
  sibling ports and recreated UIDs never inherit approval.
- **Audit/destruction:** same-transaction audit, retry behavior, rollback on
  audit failure, generic-policy bypass prevention, vanished-child semantics,
  and cluster-deregister refusal are proven.
- **UI/DOM:** provider brand marks, keyboard/focus/selected states, cascading
  dropdowns, no fake cloud discovery, exact multi-port selection, initial
  approved/unselected absence, later pending, approved/rejected, read-only,
  empty/error/stale, edition, opt-in, and permission DOM absence are proven.
- **Visual gate:** run a production-shaped local preview and present desktop
  and narrow screenshots to the founder. Tests do not self-approve the design.
- **Wire gate:** after visual approval, prove one real enrolled cluster from
  report → exact-child exposure → initial approval → later pending → approval →
  traffic allowed → disable/unexpose withdrawal. EKS, AKS, GKE, and
  self-managed provider qualification remain named evidence legs; a unit test
  is a SUBSTITUTE, never a SATISFIED live leg.
- **Repository gates:** run the complete local gate list in `AGENTS.md`, both Go
  editions, and a feature-sized multi-finder review. Findings are held for
  disposition before folding.

The implementation stops for founder review at the local preview. It does not
commit, push, open a PR, deploy, merge, or enable an organization without a new
explicit instruction.
