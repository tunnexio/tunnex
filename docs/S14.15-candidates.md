# 1. THE INVITATION STORY — the read plus both mutations

## ⛔ THE SCOPE IS SMALLER THAN THE FINDING, AND ONE PREMISE OF MINE WAS WRONG

**`ListInvitations` ALREADY EXISTS** — `db/queries/invitations.sql:36`, `SELECT * FROM invitations WHERE
org_id = $1 ORDER BY created_at DESC`, org-scoped and ordered. It has **no HTTP consumer**. Identical shape to
`ListDomainClaims` at S14.13: *the query is written, the endpoint is not.*

**AND I WAS WRONG THAT resend/revoke SHOULD RE-KEY OFF AN ID.** The live schema carries

```
invitations_org_email_pending_idx  UNIQUE (org_id, email) WHERE accepted_at IS NULL AND revoked_at IS NULL
```

> ## **AT MOST ONE PENDING INVITATION CAN EXIST PER (ORG, EMAIL). SO EMAIL IS ALREADY AN UNAMBIGUOUS KEY**
> ## **FOR THE ONLY THING THESE VERBS CAN ACT ON, AND RE-KEYING WOULD BUY NOTHING.**

The gap was never the key. **It is purely that nobody can SEE the address to type.** That correction shrinks
the story from "one endpoint + two signature changes + a spec migration" to **one endpoint**.

## What the read returns — the table already holds all of it

`id · email · role · expires_at · accepted_at · revoked_at · invited_by_user_id · created_at`

Enough for the full surface with no schema change: pending vs accepted vs revoked vs **expired** (derived from
`expires_at`, not stored — the same derive-don't-store pattern as `sync_health`), who invited, and how long
ago. `invited_by_user_id` is `ON DELETE SET NULL`, so the inviter can be **gone** — the render needs a
null arm, which is exactly the `managed_by_machine` shape S14.11 registered.

## Who else consumes invitations

`invites.Create/Accept/Resend/Revoke` · `member_handlers.go` · `seeddata` · both generated clients. **The CLI
has the same blind spot** — it can create but not list. One endpoint fixes both surfaces.

⚠ **`SupersedePendingInvites`** silently revokes pending invites when a user joins another way (domain-capture
JIT). So the list must render `revoked_at` **with a cause**, or an operator will see an invitation they did
not revoke and have no explanation.

## Cost / unblocks

**Cost: SMALL-MEDIUM.** One spec path + handler + a `Pending invitations` panel on Users. No migration, no
query, no signature change. The fixture needs pending/accepted/revoked/expired rows.
**Unblocks:** closes 2 of the 3 remaining unreachable verbs; closes S14.11's registered broken workflow; makes
a mistyped invite revocable for the first time.

# 2. THE AUDIT-WRITE FIX — `UnmapGroup` + `SuspendDomainClaim`

## ⛔ CONFIRMED SMALL — BUT IT IS ONE CLASS IN **TWO CALL SHAPES**, NOT ONE LINE TWICE

The founder asked whether either verb lacks the context an audit row needs. **One does.**

**`UnmapGroup` — genuinely one line.** `humanAudit` takes its actor from `authctx.PrincipalFrom(ctx)`
(`idpsync/service.go:406`), so no new parameter is needed; the call drops straight into the existing
`withTx`. Sibling operations in the same file already audit this way.

**`SuspendDomainClaim` — NOT a human action, and that is the interesting half.** It fires from
`capturingOrgTx` **during someone else's signup**, so `PrincipalFrom(ctx)` is empty: there is no actor,
because no operator did this. Writing a human audit row would be **false**.

**The primitive already exists.** `db/queries/audit_logs.sql:13` inserts with **`actor_system`** and a
comment saying the metadata carries the CAUSE — built for exactly this. So the fix is
`actor_system = 'domain-capture'` plus a cause (`txt_record_missing`), not a missing capability.

⚠ **One real care point:** the suspend happens for the **capturing org**, while the transaction belongs to a
signup for a user joining that org. The audit row must be written against the **capturing org's** id, which
`capturingOrgTx` has in hand (`claim.OrgID`) — but it is the kind of cross-org write that has bitten this
repo before, so it wants a test that pins the org.

## Cost / unblocks

**Cost: SMALL.** Two call sites, one existing primitive each, two tests. No schema change.
**Unblocks:** removes the last two *destructive-and-silent* state changes on access-affecting surfaces.

# 3. THE HARNESS — **and the three-session diagnosis was WRONG**

## ⛔ ONE EXPERIMENT COLLAPSED IT. IT IS NOT A LEAK.

The standing theory was cross-test state pollution — "cumulative", narrowed across three sessions to
module-level state surviving unmount. **Two measurements just refuted it:**

1. **There is NO module-level mutable state** in `Settings.tsx` or `auth.tsx` (grep for `let`/`var`/mutable
   module consts: zero hits).
2. **Running ONE of the two tests with the other six filtered out still fails**, with a completely different
   error than the leak theory predicts:

```
× `sso_not_configured` DOES offer Configure …
  → Found multiple elements with the text: /status unknown/i
  Tests  1 failed | 6 skipped (7)
```

> ## **IT REPRODUCES IN COMPLETE ISOLATION. NOTHING ACCUMULATED — THE FAILURE IS INTRINSIC TO THE TEST, AND**
> ## **THE "CUMULATIVE" READING WAS AN ARTIFACT OF ONLY EVER RUNNING THE WHOLE FILE.**

And the error is a **query-specificity** failure, not a state failure: `Settings` renders the SSO panel **once
per provider**, so singular queries (`queryByText`) hit multiple matches. Three sessions of elimination were
searching for a leak that was never there.

**THIS IS THE SESSION'S SHARPEST PROCESS RESULT, and it belongs to the founder's own instruction:**
*register after the first refuted hypothesis, not the third.* The elimination table kept refining a theory
instead of re-running the cheapest discriminating test — **run the failing test alone** — which costs one
command and would have ended it in session one.

## Cost / unblocks — honestly

**Cost: SMALL, and no longer open-ended.** It reproduces in isolation with one command, so it is ordinary
debugging, not archaeology. **I will not promise a number** — the last three estimates were wrong because
they were estimating the wrong problem — but the candidate set is now *one failing assertion in one test*,
not *unknown state in an unknown module*.
**Unblocks:** the `DomainSection` DOM proof (owed since S14.13) and the two `it.fails` reds, which flip to
failures the moment it is fixed — the signal is already armed.

# RECOMMENDED ORDER — and where I disagree

**The founder's prior: invitation first (shipped access gap), audit riding along (same area, server work).**

## I AGREE ON #1 AND DISAGREE ON THE RIDE-ALONG.

**INVITATION FIRST — the argument is stronger than "it is an access gap".** It is the only write-only state
that is *itself* an access grant, its scope just shrank to one endpoint over an existing query, and it closes
two of the three remaining unreachable verbs. Nothing else here changes what an operator can DO.

⛔ **BUT THE AUDIT FIX SHOULD NOT RIDE ALONG, and the reason is measured, not stylistic.** "Same area, both
server work" is true of the *invitation* half and false of the audit half: `SuspendDomainClaim` is in
`enterprise/sso`, fires from a **signup** path, and needs the **system-actor** primitive with a cause and a
**cross-org write**. That is a different file, a different actor model, and the one care point in this whole
document. Riding it along means the review that should be asking *"is this org id right?"* is instead reading
an invitation panel.

**Order: 1) invitation · 2) harness · 3) audit fix.**

**Harness second, not last, and this is the change from my previous position.** It was deferred four times on
the belief that it was open-ended. **That belief is now refuted**, it is cheap, and it is the only item that
makes every *future* slice's DOM assertions real rather than provisional — including the invitation panel
built in step 1. Doing it second means step 1's panel is the first to get a proof instead of another owed row.

**If it does not collapse quickly, stop and accept provisional DOM assertions** — the founder's stated
preference, and now a decision with evidence behind it rather than a fifth default deferral.

# ⛔ CORRECTION — MY HARNESS FINDING WAS WRONG, AND IT WAS WRONG IN THE DIRECTION THAT CHANGED YOUR DECISION

The section above claims the three-session leak diagnosis was refuted, because the failing test **reproduced
in complete isolation**. **That measurement was contaminated by my own change, and the claim is withdrawn.**

**What actually happened.** I ran the isolation experiment against a tree that already contained S14.14's
directory-sync panel. That panel renders *"Directory-sync status unknown…"* **once per provider**, so
`queryByText(/status unknown/i)` found **two matches** and threw. A different failure, with a different
error, standing exactly where the original one used to be.

**Re-measured properly, by suppressing only the IdP panels:**

| tree | scope | result |
|---|---|---|
| IdP panels suppressed | **one test alone** | ✅ **PASSES** |
| IdP panels suppressed | **full file** | ❌ **FAILS with the ORIGINAL errors** — `Unable to find /status unknown/`, `Unable to find Configure` |

> ## **SO THE FAILURE IS CUMULATIVE AFTER ALL. THE THREE-SESSION DIAGNOSIS WAS RIGHT AND MY REFUTATION WAS AN**
> ## **ARTIFACT OF MY OWN NEW PANEL.**

**AND THE COST OF THE ERROR IS NOT THE WASTED MEASUREMENT — IT IS THAT I ARGUED YOU INTO AN ORDERING WITH IT.**
"Its open-endedness is now refuted, it is cheap, do it second" was reasoning built on a contaminated result.
**A wrong direction is worse than not having looked**, and this is that law with a decision attached.

**THE METHOD ERROR, NAMED:** I changed the subject and the instrument in the same step. The S14.13 reds were
written against a Settings page that had no IdP panel; measuring them on a page that has one is not
re-measuring the same thing. **When re-testing an old failure, pin the tree it was written against — or
suppress what has landed since.**

## Where the diagnosis actually stands

**One hypothesis tested and refuted this session:** missing auto-cleanup. There is no `setupFiles` and no
`globals: true` in `vitest.config`, so Testing Library's auto-cleanup never registers — the file's own comment
says so. **Adding an explicit `cleanup()` to `beforeEach` does NOT fix it.** Stopped there, per *register
after the first refuted hypothesis, not the third*.

**Honest cost, restated:** the candidate set is **narrow but not collapsed** — the failure needs ≥2 tests, is
not module-level mutable state (grepped: none), and is not auto-cleanup. **I will not estimate a session
count again**; the last two estimates were both wrong.

## REVISED RECOMMENDATION

**Do the AUDIT FIX next, not the harness.** It is two call sites with an existing primitive each, its one care
point is known (`SuspendDomainClaim`'s system actor and cross-org write), and it removes the last two
