# D1 — what "downgrade release" means for IdP directory sync

**Status: ✅ FOUNDER-RULED 2026-08-06 — OPTION (e). BUILT.**

> # ⭐ **A LICENCE MAY STOP GRANTING ACCESS. IT MUST NEVER STOP REMOVING IT.**

That one line is the durable part; everything below is the working that produced it. The finding it rests on
is filed separately in `docs/laws.md`, because it generalises past this feature.

⛔ **BOTH TENSIONS ARE ACCEPTED, NOT RESOLVED** — recorded as accepted in §5, so neither reads as an
oversight a later reader should tidy away.

---

# 1. THE DEFECT, MEASURED

A licence lapses → sync stops → **membership freezes at the last successful sync.** `group_members` rows with
`origin='idp_sync'` persist (`queries/idpsync.sql:59,67`); the compiler keeps compiling their grants; the
gateways keep enforcing them.

> ## ⛔ **A PERSON REMOVED FROM THE DIRECTORY KEEPS ACCESS INDEFINITELY, AND NOTHING SAYS SO.**

⚠ **This is the deprovision fail-open class S7.5.2's review already paid for once.** That review found a
cluster of fail-open paths on the error/edge branches the happy-path walk missed, and folded them closed
with reds — null `accountEnabled` becomes a hard error, a continuation-404 is not "group gone", a committed
removal always pushes. **Every one of those fixes is bypassed by the licence simply switching the
reconciler off.** The hole is not in the reconciler; it is in the gate that stops calling it.

There is no downgrade seam anywhere in `internal/enterprise/idpsync/` — I searched `reconciler.go` and
`service.go` for one and found nothing. This is not a weak release. It is **no release**.

---

# 2. ⛔ WHY THE POSTURE PRECEDENT CANNOT SIMPLY BE COPIED

The named precedent is `devices/health.go:260-294` — `ReleaseAllHealthBlocks`, which frees **every**
posture-blocked device on downgrade and audits it as `health_blocks_released_on_downgrade`. It is the right
model, and copying its *mechanism* here produces exactly the hole in §1.

The reason is a difference in what the enterprise feature *does*:

| | posture | IdP sync |
| --- | --- | --- |
| what the paid feature adds | a **restriction** — it blocks devices | a **revocation mechanism** — it removes access |
| release = stop doing it | devices unblock → **more permissive → safe** | removals stop → **more permissive → the hole** |

> ## ⛔ **A DOWNGRADE THAT RELEASES A RESTRICTION IS SAFE. A DOWNGRADE THAT RELEASES A REVOCATION MECHANISM
> ## IS A SECURITY HOLE.**
>
> **"Downgrade releases enforcement" is not a universal law — it is a law about restrictions.** Sync is the
> first gated capability that is not one, which is why this needs a ruling instead of a pattern.

⚠ **Stated plainly because the precedent is sitting right there and looks applicable.** Anyone implementing
"release on downgrade" here by analogy will implement the fail-open and believe they followed the
convention.

---

# 3. THE OPTIONS

## ⛔ (a) PERSIST — synced memberships stay, sync stops

**This is today's behaviour and the defect itself.** Listed only so it is on the record as rejected.
Leavers keep access; nothing surfaces it.

## ⛔ (b) MARK STALE — memberships persist, flagged as stale

The freshness clock already exists (S7.5.2's two-tier `ok → degraded → escalated`). This adds a terminal
state and a badge.

**Rejected: it labels the hole rather than closing it.** The grants still compile, the gateways still
enforce, the leaver still has access. **A warning that accompanies unchanged behaviour teaches the reader to
stop reading warnings** — the same argument that keeps `agentSummary`'s note absent when it is zero.

## ⛔ (c) HARD RELEASE — drop every `origin='idp_sync'` membership

The literal posture analogue. Safe against leavers, and **it violates a founder absolute**: every current
employee in a synced group loses access at the moment of lapse.

> ⛔ **"NO HUMAN IS EVER BLOCKED."** A licence lapse that disconnects the engineering team is the clearest
> possible violation of it. Rejected on that ground alone, before any argument about severity.

## ⚠ (d) CONVERT TO MANUAL — synced rows become operator-owned

Rewrite `origin='idp_sync'` → `origin='manual'`, drop the no-hand-edit 409, audit it, and tell the admin.

**Nobody loses access at the lapse, and the admin gains the ability to fix it.** But a leaver removed in the
directory still keeps access until a human acts — the hole is narrowed to "requires an admin to notice",
not closed. ⚠ **And it is not reversible in the obvious way**: on re-licence, converted rows are
indistinguishable from genuinely manual ones, so D1 disjointness (`refuse-unless-empty` 409) makes
re-binding the group awkward. That is a second decide-item hiding inside this option.

## ⭐ (e) RECOMMENDED — THE SUBTRACTIVE HALF KEEPS RUNNING. THE ADDITIVE HALF STOPS

> ## ⭐ **A LICENCE MAY STOP GRANTING ACCESS. IT MUST NEVER STOP REMOVING IT.**

After grace, the reconciler keeps running and applies **only removals and deprovisions**. Joiners are no
longer provisioned; movers no longer gain groups. **Leavers still lose access, exactly as they do today.**

**What the customer loses is real and is the thing they were paying for** — joiner-mover provisioning, the
"HR problem" half. What they keep is the half that is a security property rather than a convenience.

### It is a small change, because the reconciler is already built this way

`converge()` (`idpsync/reconciler.go:153-252`) is three sequential blocks with a clean seam between them:

| lines | block | under (e) |
| --- | --- | --- |
| `:186-203` | `// Adds (grant).` | **skipped** |
| `:205-236` | `// Removes + D3 delete-sweep (1(a)).` | **runs** |
| `:238-247` | `// Deprovision members listed as DISABLED` | **runs** |

The desired-set computation (`:154-172`) is shared and unchanged, so removals are still computed **from a
successfully-fetched member set** — the fail-static property S7.5.2 established is preserved exactly. **No
new failure mode is introduced; one block is not executed.**

### ⚠ The tension this creates, named rather than buried

**The degradation table says "after grace the gated capabilities stop." Under (e), IdP sync does not fully
stop.** That is a real inconsistency with the locked model and the founder should rule on it knowingly.

The reading that resolves it: **what is gated is the capability the customer bought — automatic
provisioning. The deprovision path is not a feature being sold; it is the product not leaking access.**
Under that reading (e) is consistent, but it is a reading, and it is the founder's to accept or reject.

⚠ **Second consequence:** the deployment keeps calling the customer's Entra tenant with their stored
credentials after they have stopped paying. Self-hosted, their infrastructure, their credentials — but it is
a fact worth stating out loud rather than discovering.

# 4. THE RULING

✅ **(e) — RULED AND BUILT.** (d) is recorded as the fallback that was not taken.

**What was built:** the Adds block is skipped when unlicensed (`idpsync/reconciler.go`), gated through an
injected predicate so no licence system is presupposed; `ProvisioningState` + the ruled operator copy
(`idpsync/health.go`); five reds and four mutations (§7).

## ⭐ THE ABSENCE OF `WithRemovalGate` IS THE DESIGN, NOT AN OMISSION

There is a `WithProvisioningGate`. **There is deliberately no `WithRemovalGate`, and that is the most
important line in this slice.**

> ## ⛔ **THE WAY TO BE CERTAIN A LICENCE CAN NEVER STOP A REVOCATION IS THAT THERE IS NOWHERE TO PUT THE
> ## CHECK.**

⭐ **CONSTRUCTION OVER DISCIPLINE.** A rule that says *"never gate the removal path"* is enforced by every
future engineer remembering it, and is broken the first time one does not. A codebase with no seam on that
path cannot be broken that way by accident — the change becomes an edit someone has to author deliberately,
in a diff a reviewer can see.

**And it is proven rather than asserted:** two of the four mutations plant exactly that check — one on the
Removes block, one on the Deprovision sweep — and **both are caught**. The property is not "we did not add
a gate there"; it is "adding one there fails the suite."

⚠ Recorded here because an omission and a decision look identical in a diff, and the next person to want a
symmetric API will read the missing setter as an oversight and complete it.

**Still owed by S12.1, not by this slice:** wiring the predicate to a real licence, the web panel, and an
audit event for the transition (mirroring `health_blocks_released_on_downgrade`).

⛔ **(a) and (b) must not be chosen.** Both leave a directory-removed person with working access, which is
the exact class this codebase has already paid to close once.

# 5. ⛔ THE TWO TENSIONS — ACCEPTED, NOT RESOLVED

Both were surfaced with the recommendation and both were accepted knowingly. **Recorded as accepted so that
neither reads as something a later reader discovered and should fix.**

## 5.1 It does not fully stop after grace, and the DEGRADATION TABLE is what bends

The locked model says *"after grace the gated capabilities stop."* Under (e), IdP sync does not fully stop.

⛔ **The table bends, not the ruling.** "Gated capabilities stop" was written about capabilities that
**GRANT**. A revocation mechanism is not a capability in that sense — it is the product not leaking access.
`docs/S12.1-licensing-decisions.md` §4 now says so explicitly, in the degradation section itself, **because
leaving the contradiction unstated is how a future reader "fixes" it in the wrong direction** — and the wrong
direction here is the fail-open.

## 5.2 It keeps calling the customer's IdP on a lapsed licence — ACCEPTED, AND MADE VISIBLE

The deployment keeps using the customer's stored Entra credentials after the licence lapses. Self-hosted,
their infrastructure, their credentials — accepted, **on the condition that it is visible rather than
silent.** The customer is entitled to know their deployment is still talking to their IdP.

⛔ **AND THE COPY MUST NOT READ AS A FAULT — which is a security requirement, not a style note.** The sync is
doing the correct thing; the state is *partially licensed*, not *broken*. An operator who reads "IdP sync:
error" does the obvious remedial thing — disconnects or re-enters the credential — **and the deprovision half
stops with it, reopening the exact fail-open this ruling closed.** Wording that reads as a fault CAUSES the
leak.

Implemented as `ProvisioningState` **alongside** `SyncTier`, never as a fourth tier value: `TierDegraded` and
`TierEscalated` mean *broken*, and a correctly-behaving deployment must not render red. The operator copy is
a constant (`ProvisioningPausedTitle` / `Body`) and is **mechanically pinned** — a test rejects fault
vocabulary (`error`, `failed`, `broken`, `unable`, …) and requires all three facts: the licence has lapsed,
new members are no longer being added, **removals are still being applied.**

### ⛔ THE WEB PANEL IS A NAMED ORDERING PRECONDITION, NOT A TODO

**The panel is not built, and it is not deferred either — it is ORDERED.** The paused state cannot occur
until a licence exists to lapse, so a panel built now would render a state no deployment can reach:
**dormant machinery, the defect this repo already reduced once by removal (S8.4 round-3 HALT, the resolver
release-rider).**

> **THE PANEL LANDS IN S12.1, IN THE SAME SLICE THAT MAKES LAPSE REACHABLE.** Not the slice after, and not
> a follow-up ticket — the same one, because the first moment the state can occur is the first moment it
> must be visible.

⚠ **And it is not starting from nothing.** The projection (`ProvisioningState`, `DescribeProvisioning`) and
the ruled copy are already built and mechanically pinned (§7). What is missing is only the wire: a licence
to read and a panel to render it. **The ordering precondition is "lapse must be reachable", and it is
checkable — not a date and not a memory.**

# 6. WHAT IS NOT DECIDED HERE

- Whether IdP sync should be gated **at all**. The founder locked the four gates and this paper works inside
  that. ⚠ Recorded only because it is the one option that dissolves the problem rather than managing it, and
  a future reader will ask why it is absent.

- The re-licence path in either option.

# 7. PROOF

**Five reds**, each naming what its failure would mean:

| red | asserts |
| --- | --- |
| `DirectoryRemovalStillStripsMembership` | ⛔ the security half — a lapse must not strand a leaver |
| `DisabledMemberIsStillSwept` | removal and sweep are separate blocks; proving one says nothing about the other |
| `DirectoryAdditionDoesNotProvision` | ⭐ **the ruling itself** — without it (e) is a refactor |
| `ValidLicence_StillProvisionsAndStillRemoves` | the negative half: "gate everything" passes the two above |
| `LapsedLicence_TransientFetchStillRemovesNobody` | fail-static re-proven **on the lapsed path**, not inherited |

**Four mutations, one at a time, all CAUGHT:** gate removed · gate inverted · **removes gated too** ·
**deprovision sweep gated**. The last two are the fail-open this ruling exists to prevent, planted
deliberately.

**Three more on the copy, all CAUGHT:** fault vocabulary introduced · the *"removals are still being
applied"* sentence dropped · the state check inverted.
