# 5. D3 — THE PEER COUNT IS A BACKEND CHANGE, NOT A UI ONE (founder-corrected)

**I proposed it as "one cheap query". It is a spec change with a codegen tail, and estimating it as UI work
was wrong.**

**WHAT IT ACTUALLY TOUCHES:** `openapi.yaml` (a new `Node` field) → `make generate` (Go server, Go CLI client,
TS types) → `make generate-check` drift guard → **both editions** build+test → the query-lint's `org_id`
scoping rule → a sqlc query.

## ⛔ THE QUERY SHAPE — AN AGGREGATE JOIN, BECAUSE A LIST ENDPOINT WITH A PER-ROW COUNT IS AN N+1 BY DEFAULT

```sql
SELECT n.*, COALESCE(p.peer_count, 0)::bigint AS peer_count
FROM nodes n
LEFT JOIN (
  SELECT node_id, count(*) AS peer_count
  FROM devices
  WHERE org_id = $1 AND deleted_at IS NULL AND status = 'active'
  GROUP BY node_id
) p ON p.node_id = n.id
WHERE n.org_id = $1
```

**`org_id` appears in BOTH halves.** The outer filter alone would leave the subquery org-wide — a count
computed across tenants and then joined down, which the query-lint exists to catch and which no test with one
org would ever notice.

## ⛔ THE STATUS SET, AND IT INHERITS AN EXISTING RULING

**S7.3: a pending device is EXCLUDED from what grants access and INCLUDED in what consumes resources.**

A pending device **holds a peer slot and a pool address**. So:

| status | counted? | why |
|---|---|---|
| active, approved | **yes** | obviously |
| **active, pending approval** | **YES** | it consumes a peer slot. S7.3's resource half |
| revoked | no | the slot and address were released by the full sweep |
| soft-deleted | no | same |

> **A `PEERS` COLUMN THAT SILENTLY DROPS PENDING DEVICES MISREPORTS THE EXACT NUMBER AN OPERATOR IS SCANNING
> FOR** — they are looking at capacity, and a pending device is consuming it.

**The column header therefore reads `PEERS`, and the panel note says *"includes devices awaiting
approval — they hold a peer slot"*.** The alternative — two numbers — is the density the epic's REDUCE rule
warns against.

## STILL A DECIDE-ITEM

**This is no longer a UI slice.** Either it rides S14.6 as a small API change with its full gate cost, or it
becomes a separate slice and the column ships in a later pass. **Founder's call — I am not making a spec
change inside a screen story without it being named as such.**

# 6. FOUNDER CORRECTIONS — D3 IS ITS OWN SLICE, AND THE COLUMN NAME WAS A CLAIM

## ⛔ `devices WHERE node_id = X` COUNTS **DEVICES**, NOT PEERS

**A gateway's WireGuard peers are not only devices.** A hub carries **SITE LINKS** as peers too — that is
what `node_peer_status` records. So the count I proposed **under-reports on exactly the gateway an operator
scrutinises hardest**, and it under-reports silently, because a number has no way to say which population it
came from.

> ## **A COLUMN NAME IS A CLAIM. THE RENDER FLOOR APPLIES TO LABELS, NOT ONLY TO PANELS.**

**Two honest options:** count **actual WireGuard peers** (devices + site links, which means reading
`node_peer_status` as well), or **label the column `DEVICES`** and count devices. **Not `PEERS` counting
devices.**

## ⛔ AND IT IS ITS OWN SLICE, NOT A RIDER

`openapi.yaml` → codegen ×3 → drift guard → both editions → query-lint → sqlc — **landing inside a PR whose
review attention is on layout.** Decision-first says a **wire-surface change gets its own commit-one**.

**S14.6 SHIPS AGAINST THE COLUMNS THAT EXIST TODAY.** The peer/device column is **absent, with its reason on
the panel grid**, and the count becomes the next slice with its own paper — including which population it
counts, which is now the interesting question rather than an afterthought.

The KEEP list says: **"THE COPY — carried VERBATIM. It states the product's laws in the interface."** The

### ⛔ PROPOSED DISPOSITION — one note per GROUP HEADER, not per row

**The notes are identical per health KIND, not per gateway.** Four `site link down` rows would carry four

`Needs attention (4) — no fresh handshake to hub. A down site bridge is never green.`

**That satisfies both rules at once:** the law stays visible in the interface (KEEP), and it renders once
rather than per row (SCALE). **When a group mixes kinds, the header carries the kinds present, and the row's
badge remains the per-row truth.**
