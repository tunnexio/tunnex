## R2 — why the query-lint guard never fired on `nodes.Revoke` (answered, read-only)

Neither hypothesis was right. `nodes` is **not** allowlisted, and the guard **does** inspect `:exec` queries — it
never looks at the return kind (`db/querylint_test.go:130-145`). Two separate reasons:

1. **`RevokeNode` passes legitimately.** Its statement contains `org_id` (`nodes.sql:96-99`), and the check is
   `strings.Contains(low, "org_id")` — string presence, nothing more. The SQL *is* scoped. The defect is one
   layer up in Go: `:exec` discards the row count, so a 0-row match returns `nil`. **A SQL lint cannot see that**,
   and no guard in the repo checks it.
2. **The two cascade sweeps are exempted by annotation** — `-- lint:cross-org` on `RevokeDevicesForNode` and
   `RevokeOVPNClientCertsForNode`; line 133-135 skips any query whose body contains that string.

**Sweep size, measured: 78 queries carry `lint:cross-org`, and 52 have no `org_id` anywhere in the statement** —
52 queries whose tenant safety rests on a prose assertion no guard verifies. Concentrated in `mfa.sql` (18),
`nodes.sql` (18), `sites.sql` (13), `devices.sql` (10). So: an **audit** of 52 annotations, not 52 fixes.

Checked and clean: zero non-exempted queries pass the guard on comment prose alone (possible — comments are
inside the matched body — but it does not happen today).

The correct pattern already exists in the same file: `SetHubPriority` (`service.go:1184-1198`) does an org-scoped
read plus an `:execrows` zero-row check.

## The seven roots

- ROOT 1 — D3 and D10 were designed against each other on the one column both are load-bearing on. The gone-gate reads cert_not_after; a successful-but-undelivered re-key is precisely what makes cert_not_after fresh. Four independent finders (binding, replay, regression, sql) hit this; it is the single highest-confidence defect in the pass and its guard test (rekey_integration_test.go:195-198) fabricates the state that makes it pass.
- ROOT 2 — attemptRekey decides its recovery inputs ONCE, before an infinite loop that never re-evaluates them and never exits on refusal. pendingWasOnDisk is sampled at entry (main.go:812), the identities slice is built at :837-849, HaveToken is never passed in at all, and the only loop exits are success and ctx-cancel. Three findings (join-token fallback unreachable, fingerprint identity never tried in-process, non-200 conflated with permanent refusal) are all instances of 'decided before the loop, never revisited'. The agent's half of the re-key protocol was never reviewed as a protocol.
- ROOT 3 — the device restore is authorized by state read BEFORE the identity commit and applied AFTER it, against a candidate set keyed only on (node_id, revoked_cause='cascade') with no memory of node status, prior device status, or transport. Four findings fall out of that one shape: the post-commit revoke race, pending-devices promoted to active, OpenVPN certs left on the CRL, and out-of-pool address reclaim. The schema recorded WHY a device was revoked (0059) but not WHAT it was, and the restore statement asserts terminal values for a heterogeneous set.
- ROOT 4 — node revoke authorizes on the caller's org but keys its cascades on node_id, and RevokeNode is :exec so the org mismatch is silent. One missing 'resolve the node inside the org' turns an ordinary API call into a cross-tenant destructive write whose record and effect land in different tenants. The two lint:cross-org annotations vouch for an upstream guarantee that does not exist, disarming the query-lint guard.
- ROOT 5 — uniform refusal is enforced in the handler but not at the edges that answer before it. ParseRekeyIdentifier validates identifier KINDS and the fingerprint's charset but never the cert_serial VALUE, so a schema-legal NUL reaches a Postgres text bind and escapes as 500; the OpenAPI validator's maxLength answers 400 where every other bad identifier answers 403. Both break the stated contract from outside the code that implements it.
- ROOT 6 — the throttle is keyed on the raw peer address, which in every shipped topology is the edge proxy, and it is registered above the access logger. One registration decision produces both a fleet-wide unauthenticated denial of the recovery path this epic exists to provide and the invisibility that makes it undiagnosable from the control plane.
- ROOT 7 — guards and comments that vouch for properties the code does not have. Five instances this pass: rekeyorder_test's 'every refused request costs the same' (source-order assertion only), rekeyquery_test's substring match (accepts an OR that re-keys every active node), TestLostResponseDoesNotBrickTheGateway's hand-applied UPDATE, migration 0061's 'a previous-version replica reads cert_serial' (no such version exists), and the WALL 6 comment at rekey.go:243-252 that the callee's own comment contradicts. This is the codebase's own census law failing on the story that was supposed to satisfy it — the check could not have failed.

```
WARN watch_failed_backing_off   remote error: tls: expired certificate
```

**Zero `agent_rekey_*` lines of any kind** — no attempt, no refusal, no throttle. The recovery path was never
entered.

## The cause

`attemptRekey` has **exactly one call site**: `apps/node/cmd/agent/main.go:77`, inside `main()`, reached from
`identity.Decide(certPEM, err, …)` evaluated against the credentials **loaded at boot**. No running loop
re-evaluates the verdict.

`renewLoop` (`main.go:525`) is the only thing that fires on a schedule, and it calls `client.Renew` — an **mTLS**
endpoint that requires the certificate that expired. Once expiry passes, every attempt fails at the TLS handshake
and retries on `renewRetryInterval`, forever. **There is no escalation from "renew keeps failing" to "attempt
recovery."**

## Why this is the case that matters

EPIC 13's headline claim is that a gateway recovers from certificate expiry **without operator action**. As
shipped, it recovers only if the process is **restarted first** — which is operator action, by an operator who
must first know to do it, on a box whose logs never mention re-key.

**This is the original incident.** `aws-gw-1`'s real-world expiry, the event that opened EPIC 13, happened to a
*running* agent. The epic was built to fix that, and the fix does not reach it.

The irony is recorded in the code: `main.go:57-62` explains that the old inline branch "looped forever on
`tls: expired certificate`". That comment describes, exactly, the behaviour still observed — one layer up.

**An earlier draft of this finding said pass 3 missed it. That was wrong** — I wrote it before reading
`docs/S13.1-review-pass3-partial.md`, which was on disk the whole time. Pass 3 raised it **twice**, precisely:

- **pass-3 #2 [CRITICAL]** — *"Expiry is decided ONCE at boot: the reconcile loop detects the expired cert at
  runtime, logs a now-false remedy, and never reaches attemptRekey."*
- **pass-3 #28 [HIGH]** — *"Re-key is boot-only: a certificate that expires while the agent is running is never
  recovered, and the agent tells the operator to do the destructive thing."*

Pass 3 also named the runtime consequences the walk later observed by hand: `/healthz` returning 200

**The fold half-landed.** `docs/S13.1-decisions.md:1265` closes all four claims with one row — *"the premise is

about a clock wrong at boot trapping a gateway **already inside** the loop. **Claim 2 is about never entering the

**The unfixed half was then written up as the reason the fix is safe** (`decisions.md:1275-1278`):

**THIRD INSTANCE OF WF-S13-3's CLASS.** A fold lands partially, and the missing half is documented as correct.

adjacency of subject matter.

**What follows for the batch protocol:** a fold row that closes N claims must show, per claim, the line that
closes it. A row reading *"claims 2/4/13/20 → the premise is re-read each pass"* is a summary, not a receipt, and

## Why §A did not catch it

**§A's staging created the only condition under which the code works.** Every Leg 1 run **stopped the agent**,
waited for expiry, then **started** it — a boot with an already-expired certificate, which is the one path
`attemptRekey` sits on. The expire-while-running case was never once exercised.

Three review passes were scoped to the re-key surface, the data path, and the agent loop. **Pass 3 covered the
agent loop and did not raise it** — plausibly because the loop it reviewed is the one that exists, and the
finding is about a loop that does not.

## MEASURED: 59 minutes stuck, 1.77 seconds to recover

Observed on aws-gw-2, 2026-07-31 (`walk-artifacts/S13.1/walk-record.md`):

| | |
|---|---|
| certificate expired | 14:41:45 |
| manual `docker restart` | 15:41:10 |
| `agent_rekeyed` — *"same node, same identity, new key"* | 15:41:11.774 |
| **stuck** | **59m 25s** |
| **recovery, once reachable** | **1.77s** |

**The recovery path is correct, instant, and unreachable.** `identified_by` shows `cert_serial` — identification
worked first try. Nothing was wrong with the credential material, the CP, the network, or the recovery code. The
gateway was recoverable for the entire hour; the only missing thing was a **second invocation of a decision the
agent already knows how to make.**

That is the argument for the ruling. A defect that made recovery *unreliable* would be a limitation. This one
makes a working feature **unreachable in its primary case**, and the fix on the wire takes under two seconds once
something calls it.

## THE COMPOSITION: two sound decisions make the stuck state PERMANENT

The boot-only call site alone would be survivable — something would eventually restart the process. **Nothing
will**, because of a second decision that is correct on its own terms.

`attemptRekey`'s loop has **only two exits: success and context cancel.** The agent **never exits** on refusal —
ruled deliberately, and rightly: a gateway that quits because the CP refused it is a gateway that stops carrying
traffic over a control-plane opinion.

Compose the two and **every automatic recovery mechanism is disarmed**:

| runtime | the mechanism | why it never fires |
|---|---|---|
| **Docker** (`--restart unless-stopped`, the observed B′ config, and what the UI's own install command emits) | restart on exit | the process **never exits** |
| **Kubernetes** (S10.3, the in-cluster gateway) | kubelet restarts an unhealthy pod | **there are NO PROBES.** `deploy/helm/tunnex-gateway/templates/deployment.yaml` declares neither `livenessProbe` nor `readinessProbe`, so kubelet has nothing to consult and the pod is **Ready unconditionally** |
| **systemd** (`Restart=on-failure`) | restart on non-zero exit | same as Docker: no exit, no failure code |

**CORRECTION (2026-07-31, from pass-3 claims #23/#26).** An earlier version of this table said kubelet "sees
liveness up." **That was wrong, and the truth is worse.** The chart ships **no probes at all** — verified by
reading `deployment.yaml`. The agent maintains an honest readiness signal (`/readyz` 503, and its own log says
*"Liveness stays up, readiness stays false"*), and **nothing in any shipped manifest consumes it.** The contract
that justifies never exiting has no consumer, which is claim #26 stated exactly.

The Docker case is confirmed by observation, not code: on aws-gw-1 the healthcheck is
`wget -qO- http://127.0.0.1:9091/healthz`, and `docker ps` printed **`Up About an hour (healthy)`**,
`FailingStreak: 0`, for a gateway whose node row was revoked and whose certificate had expired — while the agent
logged `agent_enroll_failed` and idled. **The healthcheck is wired to liveness on a container image whose own
agent distinguishes liveness from readiness.**

**No automatic mechanism can leave this state.** Not one of them is wrong; the trap is in the composition.
The exit condition that protects traffic is the one that removes the last path back.

That is also why remedy shape 2 is refused below: it proposes reversing the never-exits ruling, trading a
correct decision for a restart policy the control plane cannot observe.

## Candidate remedy shapes — NOT chosen, for disposition

1. **Re-evaluate on persistent auth failure.** Count consecutive `tls: expired certificate` failures and re-enter
   `identity.Decide` / `attemptRekey` in place.
2. **Exit and let the supervisor restart.** The observed container runs `--restart unless-stopped`; a process
   that exited after N consecutive expired-cert failures would recover for free at the next boot. Smallest
   change; relies on a restart policy the CP does not control.
3. **Anchor the renew timer so expiry cannot be reached** while running. Reduces the window; does not close it
   (a suspended VM, a clock jump, or a long outage still lands here).

## RULED 2026-07-31 (founder): MERGE-BLOCKING. Shape 1, corrected. Shape 2 REFUSED.

**Merge-blocking, not a registered limitation.** The feature is absent in its primary case — the motivating
incident, `aws-gw-1` expiring while running. A limitation describes a bounded edge; this is the centre.

**Shape 1, with a correction that matters.** "Re-evaluate on persistent auth failure" makes a **network signal**
the trigger, which would break `identity.Decide`'s structural guarantee — it takes **no network argument**, so a
transient outage can never reach a recovery verdict. Build instead:

> **Re-run `identity.Decide` ON A TIMER, against the same LOCAL inputs it reads at boot** — the stored
> certificate and the clock. Not escalation-from-failure: **the existing decision, invoked more than once.**

The distinction is the whole design. A timer over local inputs cannot be induced by anything on the network; a
failure-counter can. The no-network property survives, and the dormant edge closes.

**Shape 2 REFUSED** — it reverses the never-exits ruling and depends on a restart policy the CP cannot observe.

**Shape 3** is not a remedy: it narrows the window, and a suspended VM or a clock jump still lands inside it.

**Do NOT build during the walk.** Finish §B, then fold.

## The walk-design lesson

**A WALK THAT STAGES A PRECONDITION CAN STAGE AWAY THE DEFECT.** §A produced expiry by stopping the agent
because that was the fast way to get an expired certificate. The shortcut silently selected the working path.
Where a runsheet manufactures a state, it must say **how production reaches that state** and whether the
manufactured route differs — because here the difference *was* the bug.

# WF-S13-1 — SHARPENED TWICE (2026-08-01). The capability EXISTS; every client hides it.

Registered in §A as *"`active` is the wrong test"* and deferred on a risky-fix argument. **In one night it blocked
device creation outright and made §B unstageable.** Both facts are on the wire; the framing below is what changed.

## The placement rule, cited

| surface | how it picks a device's gateway |
|---|---|
| **API** | `devices/service.go:159` `Create` takes **`in.NodeID`** — an explicit input, validated by `GetOrgNode` (org-scoped, must be active, must have reported endpoint AND key) |
| **web** | `apps/web/src/lib/nodepick.ts:30` — `defaultDeviceNode(nodes) = selectableNodes(nodes)[0]`. First active **in list order**, sent as `node_id` (`Devices.tsx:109`) |
| **CLI** | `apps/cli/internal/cli/device.go:43-52` — iterate nodes, take the first `status == "active"`, `break`. **No flags on device create at all** |

**THE CAPABILITY IS NOT MISSING. IT IS HIDDEN, TWICE, INDEPENDENTLY.** The API has accepted a chosen gateway
since S5.1. Two clients each reimplemented the same silent pick and neither exposes it, so the org's
first-active-by-list-order node becomes a de facto singleton for device placement.

**Option 4 (make a node hub-primary) is REFUTED by this**: the rule is list order, not the hub set. Pinning
changes nothing about placement.

## Why `active` being the wrong test bites TWICE

1. **It selects a dead row.** `azure-gw` — active, no endpoint ever reported, six days stale — was first in list
   order, so every create attempt was routed to it and refused with `node_not_ready`, an error naming the
   OPERATOR'S agent configuration. **Device creation was impossible until a stale row was revoked by hand.**
2. **There is no override.** Even knowing which gateway you want, no shipped client will send it. §B's staging
   put all three devices on `k8s` and no product surface could place them on B′.

## What this does to the eventual slice

**Mark-don't-narrow would NOT have helped either instance.** Badging revoked or stale rows does not let an
operator CHOOSE, and choosing is what both failures needed. The slice is therefore:

- **a gateway picker on device create, in BOTH clients** (the CLI needs a `--gateway` flag; the web needs a
  select), defaulting to the current pick so nothing changes for the common case; and
- **a selectability test that is not `status='active'`** — the API already knows the right one
  (`endpoint != "" && wg_public_key != ""`, `service.go:72`), and the clients do not consult it.

**Smaller than the deferral assumed, and it prevents both observed failures.** Re-ranked accordingly: this is no
longer a latent modelling wart, it is a live blocker with two wire instances.

## Consequence for §B — recorded as SCAFFOLDING, per the CLI result

Because no client exposes `node_id`, staging the devices on B′ requires a **hand-crafted API call**. That is far
better than SQL — it runs the real create path, so validation, IP allocation, config issuance and audit all
happen exactly as in production — but **it is not a product action**, and it is recorded as
**WALK SCAFFOLDING VIA THE API**, with the same honesty as the `azure-gw` revoke.
