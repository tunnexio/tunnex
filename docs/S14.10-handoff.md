# 3. WHAT S14.10 ACTUALLY FOUND — the four that matter for S14.11

## 3.1 `ON CONFLICT … DO NOTHING` on a time-relative fixture (fixed, class registered)

`device_health` and `device_status` both had it. A fixture writing `now() - interval '3 minutes'` is three
minutes ago **once**, then ages forever, and every re-seed reported success. Posture drifted past
`HealthStaleTTL`, states served `unknown`, the sweep cleared `health_blocked` — **the device named
`blocked-device` was not blocked and `posture blocked` had never rendered on localhost.**

> **THE STANDING CHECK: any fixture value relative to `now()` is `DO UPDATE`, never `DO NOTHING`. The test is
> not "is it idempotent" but "is it re-runnable INTO the state it describes."**

`node_peer_status` had this fix three sections earlier with the reason written down. **A law written in one
block does not protect the block below it.**

## 3.2 Fixture writes a controller-owned field — 3 instances

`org_hub_set.demoted` · `devices.health_blocked` · **latent: `nodes.capabilities → ovpn_health`**, which
renders today only because no agent reports as `gw-eu-west`.

> **SEED THE INPUTS A CONTROLLER CONSUMES, NEVER THE FIELD IT OWNS.** The reconcile loop undoes the write and
> the row reads as applied. When the input is an HTTP request rather than a row (as `health_blocked` is),
> **register through the product** — the seeder now logs in and POSTs a real report.

## 3.3 The spec was a wrong source of truth — THIRD instance this stretch

After `listSiteSubnets` (a summary claiming `site:manage` where the handler authorizes `org:view`) and the
`policy_degraded_kind` edition paragraph, `health_state`'s description claimed `unknown` could mean *"the fact
was reported absent."* **It cannot.** `evaluated_state` is `NOT NULL` with `CHECK IN ('compliant','noncompliant')`
and the evaluator skips an absent fact (*"absence never blocks"*), so such a device evaluates **compliant**.

**I built a third UI label for it and FIVE reds passed against a state production cannot produce.** Caught only
by asserting on the rendered page (0 matches). **The spec-enum-vs-CHECK sweep would NOT have caught it** — see 4.2.

## 3.4 Two unscoped destructive writes, both mine

`UPDATE devices SET health_blocked = false` with no `WHERE org_id` touched 124 devices across every tenant.
**The blast radius was bounded by luck, not by the command.** Now a law: **any destructive write against a
shared database is org-scoped or it does not run** — `WHERE org_id`, including on the ones that look like cleanup.
