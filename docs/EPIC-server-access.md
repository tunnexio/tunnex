## Customer outcome and agreed scope

An administrator registers a private Linux server, selects a network-reachable enrolled Tunnex gateway, verifies the SSH host identity and tests the connection. Registration includes server name, private IP, SSH port and an explicit list of allowed **existing Linux accounts**. The administrator grants existing Tunnex users/groups access to selected accounts for bounded periods. A user signs into Tunnex, satisfies MFA, sees authorized Servers, chooses a permitted account and opens a browser terminal. No end-user VPN or local SSH client is required.

Linux accounts, groups, file permissions and sudo rights already exist and remain host-admin responsibilities. There is no automatic OS account creation in the POC. Several Tunnex identities may use one Linux account; every Tunnex session retains its own actor identity in Observer. A Linux username is not a substitute for the Tunnex actor or a promise of host-level attribution.

Proposed authentication uses short-lived OpenSSH user certificates and requires initial server-side CA trust setup. This is new work, not an existing Tunnex capability. Public user-CA trust on a server and verification of that server's host key are separate trust directions. Existing password/key access outside Tunnex is outside Tunnex's revocation boundary.

All servers emit ordinary access/audit events into the existing Observer surfaces. Only servers with recording enabled record terminal sessions. Recording policy is captured at session admission; toggle changes affect new sessions and never automatically delete old recordings. Replay is opened from the corresponding Observer session under a separate permission. Replay is a terminal transcript, not complete structured command or OS-process auditing. Closing SSH does not guarantee termination of background processes.

## Architecture and authority contract to freeze

Proposed path: Browser → TLS/WebSocket terminal broker → purpose-specific outbound authenticated gateway stream → SSH/PTY on the exact registered Linux server. CP owns identities, server revisions, grants, session authority and certificate issuance policy; selected gateway verifies the server host identity, holds the ephemeral session private key and executes the authorized SSH connection. A separate signer issues only public-key certificates after current authorization. This placement remains a SA-0 decision.

Bind every launch and stream to organization, actor, parent login, server, account, gateway identity, serving revision, grant decision and session ID. Browser input never supplies a dial target, username outside the effective allowlist or a reusable SSH credential. Use a single-use, short-lived launch transaction; check WebSocket Origin, cookie/CSRF boundaries, replay and concurrent redemption. Gateway enrollment credentials cannot mint SSH user certificates. Fail closed on unknown/revoked gateway identity and missing Server Access capability.

Allow one PTY shell per admitted session. Refuse SSH subsystem/file-transfer, arbitrary exec, agent/X11 forwarding, TCP/Unix forwarding and extra channels in the product protocol. Do not claim this confines a shell's OS privileges: a user can still run network/file tools allowed by the host. Apply bounded frame sizes, resize rates, queues and slow-consumer behavior; render terminal escapes using a qualified terminal library, not HTML injection. Disable terminal features that exfiltrate through browser integrations unless explicitly reviewed.

Certificate expiry limits future authentication; it does not terminate an authenticated shell. Broker and gateway independently enforce finite renewable authority and close SSH/PTY/stream on expiry or revoke. Recheck grant/user/group/account/resource changes, parent logout/MFA reset, gateway withdrawal, host revision and feature/entitlement changes. Push notifications are an optimization; lease expiry works with dropped messages and stalled renewals. Report requested versus confirmed termination and surviving OS-process limits truthfully.

Proposed stores: tenant-safe server registry/revisions and account allowlist; bounded user/group/account grants; readiness observations; session admission/lifecycle with parent and grant indexes; signer key references/issuance metadata; Observer events; recording manifest/chunk references and policy snapshot. Allocate migration numbers at implementation against current main. OpenAPI-first admin/list/grant/check/launch/session/replay contracts; gateway/signer APIs use distinct service authentication and never become public arbitrary-sign endpoints. State changes and audits require durable consistency/idempotency.

The latest recording lifecycle requires PostgreSQL-first capture for every new recording. A saved S3 connection supports manual export with automatic archival OFF; manual export retains PostgreSQL until expiry, which re-verifies the archive before releasing the source. Failed exports retain PostgreSQL and retry visibly. Without archival, expiry removes payload/key and retains audit metadata. Manual Download is an explicit authorized browser action, never automatic retention.

### Encrypted archive portability within the installation

New S3 archives include `recording-v2.tunnex-recording`, a verified self-contained encrypted package. Sessions → Import recording accepts this package and authorized Manual download JSON. Package upload requires explicit confirmation and current organization Replay permission plus original owner or SessionManage authority. It can replay after original session/recording deletion without restoring audit identity. The originating installation master remains necessary; no key is exported or plaintext silently substituted. Raw historical chunks/manifests remain server-replay formats and are not import files. Limits are 32 MiB per import package, 4096 events and 16 MiB captured encrypted payload; ordinary HTTP/chunk limits remain unchanged.
