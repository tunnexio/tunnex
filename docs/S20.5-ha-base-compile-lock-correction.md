# S20.5: HA ordinary-base compilation and transaction ownership

Status: decision-first correction in progress; not live acceptance.

C7 cleared DNAT printer refusal and achieved fenced HA at 00:55:14 UTC.
Later the CP stopped serving database-backed requests. Live PostgreSQL showed
one idle transaction after the accepted-classification query and three other
connections waiting on its transaction ID. Source inspection maps this to
ordinary-base maintenance: it owns pool/org/node locks, then invokes a base
compiler which acquires connections from the same four-connection pool.
Node liveness, Service UID observation and FQDN answer insertion consume the
remaining connections waiting for those locks. The callback cannot acquire
a connection to finish, and its transaction cannot release the locks.

The arm path has the same unsafe callback-inside-transaction shape. Drain
already calls the compiler outside its own transaction. The compiler is a
multi-query service path, including pool allocation and policy providers;
passing a transaction only to its first lookup would not solve the cycle.

Proposed bounded repair under essential-fix authorization: prepare ordinary
bases before opening the lock-owning transaction, then preserve all existing
leader, membership, topology, classification, generation and receipt checks
inside the transaction. Authority continues to bind the exact compiled base
version and content hash; changed bases cannot gain an ACK by assertion.
Revalidate plan/member scope under locks and refuse mismatches. Do not claim
the external multi-query compiler is an atomic database snapshot.

Reject raising connection limits, weakening locks or exact-hash verification,
forging receipts, killing sessions, and remedial restarts as fixes. A real
small-pool regression must demonstrate the lock/acquire cycle is absent in
both affected paths, with both editions tested and independent review before
deploying a new immutable candidate. C7 activation is historical evidence,
not sustained HA or end-to-end acceptance.
