Status: **paper before infrastructure correction; no product walk passed.**

## Observed failure

The new EKS control plane is ACTIVE and reachable with the separate task-only
kubeconfig. Its server reports `v1.35.6-eks-bca9cf6`. The node group has no
instances or registered Kubernetes nodes. Its managed Auto Scaling group logs
repeated `InvalidParameterCombination` failures: `t3.medium` is not eligible
for this account's Free Tier restriction. The first observed launch failure is
at `2026-09-05T10:13:59.766Z`; the same cause is present at 10:15, 10:17 and
10:21 UTC. This is not a vCPU quota failure or a Tunnex runtime failure.

The original preflight checked size, AMI, AZ offering and quota, but not account
instance eligibility. Add the explicit Free Tier eligibility check to this
walk's provisioning preflight; an offered instance type alone is insufficient.
Do not upgrade the account's billing plan as an implicit repair.

## Narrow correction under the user's AWS setup authorization

Use `c7i-flex.large`, retaining **2 vCPU, 4 GiB, x86_64**, the same selected
AL2023 release, one worker, encrypted 30 GiB gp3, IAM, VPC, subnet, access scope
and fixed min/desired/max=1. The AWS API reports this type FreeTierEligible=true
and offered in ap-south-1a. The existing protected demo CP already uses that
type; that fact does not authorize changing the demo.

Remove `CreditSpecification` rather than passing T3-only CPU credit settings
to a non-burstable type. No custom node bootstrap, image change, CNI edit,
worker-role broadening, account-plan change or quota bypass is proposed.
The same account-eligible type is the revised planning baseline for later
workers/CP, not permission to launch them before the capacity gate.
