# WHAT EXISTS TODAY — read before proposing, because it constrains every option

`apps/web/tailwind.config.js` carries the whole brand surface as **hardcoded hex under `theme.extend.colors`**:
`ink` 950-600 · `accent` 400-600 · semantic `ok`/`warn`/`danger`.

**There are ZERO CSS custom properties in the app.** Theme switching is currently impossible by construction —
Tailwind bakes hex into class output at build time.

## ⚠ AND THERE IS AN EXISTING SEMANTIC CONTRACT THAT MUST NOT BE LOST

The config documents a **deliberately NARROW reservation** (S4.4 decision f):

> `ok` = **LIVENESS ONLY** ("alive right now": online peer, healthy check). **NOT success feedback** — "sent /
> saved / role changed" use the accent, **so green keeps meaning "live"**.

**This is a shipped rule, not a styling preference.** A token migration that lets `ok` drift into a generic
"success" colour **regresses a documented decision** — and it would do so invisibly, because everything would
still look fine. **Any proposal here must carry it forward and, ideally, assert it.**

# D2 — HOW THEMES ARE EXPRESSED

## PROPOSED: **CSS custom properties as the source of truth, Tailwind reading them via `var()`. BOTH, and the reason is mechanical.**

**Neither alone works:**

- **Tailwind config alone** bakes hex at build time. Three themes would mean three builds, or `dark:`-style
  variant classes on every element — which is exactly the div-soup coupling this epic exists to remove.
- **CSS custom properties alone** loses Tailwind's utility ergonomics and every existing class in the app.

**The shape:**

```
packages/shared/tokens  ──emits──>  :root { --tnx-ink-900: …; }        (the values, per theme)
                         └────────>  tailwind preset { colors: { ink: { 900: "var(--tnx-ink-900)" } } }
```

Tailwind classes stay identical (`bg-ink-900`), so **no existing markup changes**. A theme swap is a
`data-theme` attribute on `<html>` that re-points the variables. **Runtime, no rebuild, one seam.**

## HOW THE EDITION-GATING SEAM SITS ALONGSIDE IT — they must NOT be the same seam

Item B decide-item 6 requires **all edition gating through ONE hook** so S12.1 rewrites the hook and nothing
else.

**PROPOSED: keep them strictly separate.** Theme answers *"what does this look like"*; edition answers *"does
this exist at all"*. **Edition must never be expressed as a theme** (e.g. hiding an enterprise control by
colouring it away) — that is a security-adjacent surface rendered invisible rather than absent, and the
component tier would still find it by role. **One hook for edition, one attribute for theme, no interaction.**

# D3 — THE ACCESSIBILITY FLOOR, AND A CHECK THAT **FAILS** RATHER THAN WARNS

## The floor: **WCAG 2.1 AA**

- text contrast **≥ 4.5:1**; large text and UI/graphical boundaries **≥ 3:1**
- every interactive element reachable and operable by keyboard, with a **visible focus indicator**
- `prefers-reduced-motion` honoured by the motion tokens

## The gate — TWO layers, and the first is mechanical

**1. A CONTRAST TEST OVER THE TOKEN SET.** Contrast is **computable from the token values**, so this is a unit
test, not a review: for every (foreground, background) pair the system permits, assert the ratio meets its
floor. **It fails the build; it does not warn.** Proven the way this repo requires — darken a token until the
pair drops below 4.5:1 and show the test go red.

**This is the layer that answers "a check that fails rather than warns."** A linter that emits warnings is a
convention; a failing test is a mechanism.

**2. `design:accessibility-review` as DEFINITION OF DONE** for anything with rendered output — from S14.2
onward, since S14.1 has no screens. **A screen that cannot be tested by role is not done** (registration
consequence 1).

**AND THE SEMANTIC RESERVATION GETS A TEST TOO** — `ok` is liveness-only. Proposed as an assertion over the
token metadata so the rule is enforced by a mechanism rather than by whoever remembers S4.4.

# D4 — WHAT "DONE" MEANS FOR A TOKEN SLICE WITH NO SCREENS ON IT

**The honest problem: tokens nobody consumes prove nothing.** A slice that adds files and asserts they exist is
the render-floor failure one layer down — and this epic has already ruled that dormant machinery cannot be
proven.

## PROPOSED DEFINITION OF DONE — the epic's own method, applied to its first slice

> **The EXISTING app renders identically through the NEW tokens.**

Concretely:

1. **`packages/shared` exports the token set**, including the semantic reservation as data.
2. **`apps/web/tailwind.config.js` contains NO hardcoded hex** — it consumes the shared preset. *(This is the
   verifiable half: a grep-able absence, gated.)*
3. **The CSS custom properties are emitted** and a `data-theme` swap re-points them.
4. **The contrast gate passes and is PROVEN TO FAIL** on a deliberately darkened token.
5. **`make web-gate` (typecheck + vitest + build — NOT Playwright; e2e runs in CI only) is GREEN** — typecheck, test, build. **And the component tier's 227 tests still pass
   unchanged**, which is the point: **a token migration that changes no behaviour must not change a single
   test.** If one needs rewriting, the migration changed a decision.
6. **CI green at a named sha**, per `GATE-REPORT-NEEDS-SHA`.

**Item 5 IS the slice's real proof.** It makes S14.1 a **refactor under a green suite** — the epic's method,
demonstrated on the smallest possible change before it is trusted on 17 screens.

# ⚠ FINDING — `generate-check` DOES NOT DETECT A HAND-EDIT. It protects the SOURCE↔ARTIFACT RELATIONSHIP.

**Found while proving the guard rejects, and it is REPO-WIDE — not an S14.1 defect.**

`make generate-check` depends on `make generate`. So a hand-edit of an emitted artifact is **REGENERATED BEFORE
THE DIFF RUNS** — the edit is silently overwritten, the tree comes back clean, and the check reports **green**.

```
hand-edit tokens.css  →  generate-check  →  generate overwrites it  →  git diff clean  →  GREEN
```

**WHAT IT ACTUALLY CATCHES: a STALE COMMIT.** Change `src/tokens.ts` without regenerating and the guard prints
the before/after lines and fails — proven by changing `ok` from `#2ecc8f` to `#22c55e`.

**THIS APPLIES TO EVERY GENERATED ARTIFACT IN THE REPO** — `api.d.ts`, `rbac-policy.json`, the sqlc output, the
RBAC mirror. All have the same shape.

**A HAND-EDIT IS SELF-HEALING, NOT DETECTED.** That is arguably fine — the edit cannot survive the next
`make generate`, and CI runs `generate-check` on every PR, so it never reaches `main`. **But it is not what
"the guard rejects tampering" would mean**, and anyone reasoning about the drift guard should know which
property it has.

**NOT FIXED — registered.** It is a repo-wide property, not an S14.1 defect, and changing it (diff BEFORE
regenerating, then regenerate) is a change to every generator's gate. **TRIGGER: the next change to
`make generate-check`, or a finding that depends on artifact tampering being detected.**

# ⚠ DEFECT — THIS PAPER CLAIMED COVERAGE THE ARTIFACT DID NOT HAVE (found 2026-08-01, corrected in S14.3 slice 0)

**Founder-ruled: a DEFECT, not a gap.**

The coverage table in **D1** lists five groups — colour · **typography** · **spacing** · **radius / border /
elevation** · **motion**. The emitted artifact carried **thirteen variables and every one was a colour.** Font
*families* shipped (into the palette JSON); a size scale, a spacing scale, radius, elevation and motion did
not.

**A PAPER VOUCHING FOR A PROPERTY THE ARTIFACT LACKS IS THE SAME CLASS AS A COMMENT VOUCHING FOR ABSENT
CODE** — and this repo paid for that class once already, in S14.2's mutation 1, where a comment explained why
an assertion was rigorous and the assertion was checking something else.

## WHY THIS SLICE'S OWN GATES MISSED IT — the part worth fixing

`tokens.test.ts` asserted **theme completeness** (every theme supplies every name in `TOKEN_NAMES`),
**contrast** (colours against colours), and **the `ok` reservation** (source against a rule). All three passed.
**All three were aimed at the names that existed. NOTHING COMPARED THE CLAIM TO THE ARTIFACT.**

**The failure is not that a gate was weak. It is that the promise had no gate at all** — and a promise with no
gate reads exactly like a promise that is kept, because everything it is measured against agrees with it.

## THE CORRECTION, in S14.3 slice 0

1. **The scales are emitted** — `--tnx-text-*` · `--tnx-space-*` · `--tnx-radius-*` · `--tnx-elevation-*` ·
   `--tnx-duration-*` · `--tnx-ease-*`. **13 → 44 variables**, plus a `@media (prefers-reduced-motion: reduce)`
   block that re-points every duration to `0ms` **unconditionally**, so a component that forgets to check the
   preference still animates for zero milliseconds.
2. **`CLAIMED_COVERAGE` is the claim, as data** — hand-authored to mirror this paper, **deliberately NOT
   derived from the scales.** A derived list would compare the token set to itself and pass by construction:
   the fixture-restates-production shape, which is how the original claim survived unchallenged.
3. **The census compares claim to artifact**, reading the generated CSS **from disk**. **Proven to reject
   twice:** a category claimed with nothing emitted goes red, and a scale renamed in the emitter while the
   claim keeps its old name goes red.

**A `?raw` import of the CSS returns an EMPTY STRING under vitest** (CSS processing is off by default and the
raw query is swallowed with it). It failed loudly here only because the assertions are lower bounds; had any
been an "and nothing unexpected" check, **an empty artifact would have satisfied it vacuously.** Hence the
read-from-disk, and hence the guard that asserts the artifact is non-trivial.
