# S20.5 Windows enrollment gate fix

Status: authorized test-fixture repair; production durability behavior is unchanged.

## Observed failure

GitHub Actions CI run `33589539118`, Windows client job `100120535604`,
failed five adjacent explicit-abandon tests in
`apps/client/test/enrollmentrecovery.test.ts`. Each failed while seeding its
initial durable anchor, before reaching the intended unlink ambiguity, with
`EnrollmentAnchorStoreCorruptError`.

The fixtures declared `platform: "darwin"` but delegated their ordinary
directory synchronization to the runner's real filesystem. On a Windows
runner, directory `fsync` returns the narrowly expected unsupported
`EPERM`/`EINVAL` class. The production durable-file primitive accepts that
class only when the runtime is truthfully `win32`; the false Darwin declaration
therefore converted normal fixture setup into a corrupt-store refusal.

## Repair decision

Only the five generic explicit-abandon fixture runtimes will change. Their
platform classification will come from `process.platform`, matching the real
filesystem calls that their custom `syncDirectory` callbacks perform.

This preserves the proof boundary:

- production `durablefile.ts` remains byte-unchanged;
- no test is skipped or weakened;
- Windows still accepts only the production-classified directory-`fsync`
  `EPERM`/`EINVAL` fallback;
- injected `EIO`, missing-parent `ENOENT`, restored-anchor, and foreign-map
  conditions still occur only after the real unlink boundary selected by each
  test;
- POSIX runners still require successful real directory synchronization; and
- S20.5.1 automatic Windows terminal-uninstall recovery remains deferred and
  untouched. These tests cover current S20.5 managed-enrollment abandonment,
  not that terminal-recovery authority.
