# 3. ⛔ SEED THE UNCOMFORTABLE CASE — second immediate payment

The fixture row for *inviter deleted* (`invited_by_user_id` is `ON DELETE SET NULL`) **crashed the endpoint on
its first run**: `u.email::text` types the column non-nullable, the LEFT JOIN yields NULL, and the scan 500'd
the **whole list**. Without that row it would have shipped and broken the first time an inviter was deleted —
**the one moment the list matters most.**

**Second time a deliberately-awkward seed row has paid immediately** (S14.11's empty-name member was the
first, and it exposed a shipped render defect the same way). **Keep seeding the uncomfortable case:** the
empty name, the deleted parent, the 77-character address, the group with no members. A fixture that only
contains healthy rows tests the happy path twice.

# 4. WHAT WAS MEASURED AND CHANGED THE SCOPE

- **`ListInvitations` already existed** in sqlc with no HTTP consumer — the `ListDomainClaims` shape again.
- **Email was already an unambiguous key.** `UNIQUE (org_id, email) WHERE accepted_at IS NULL AND revoked_at
  IS NULL` permits at most one pending invite per pair, so re-keying off an id would have bought nothing.
  **My own premise, refuted before it cost anything.**
- **Four states, three stored.** `expired` is derived from the clock; a status column would be correct at
  write time and wrong a day later.
- **Controls only where the server acts.** Revoke matches `accepted_at IS NULL AND revoked_at IS NULL`, so on
  a terminal row it changes nothing and reports success. Resend IS offered on expired — it mints a new token
  and is the only recovery path.
