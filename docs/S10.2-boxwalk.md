## What this walk must prove (the teeth — ARTIFACT-WORKS, not ARTIFACT-EXISTS)

The proof is NOT "`kubectl apply` and the CR goes Ready." A CR going Ready proves the operator reconciled,
NOT that GitOps GOVERNS. The teeth (from `docs/S10.2-decisions.md` Slice 5):

1. **A declared `TunnexGrant` ADMITS a real flow that was DENIED before it** — the exact WF-K6 shape
   (deny → allow with drop/accept COUNTER evidence), driven from **YAML, not the dashboard**.
2. **The inverse:** `kubectl delete` the grant → **the flow DIES** (revocation on the wire, drop counter),
   and the delete is **audited with the CR as the cause**.
3. **Delete-cascade audit:** `kubectl delete tunnexcluster` cascades away services + grants with a forensic
   row naming the **cascade counts + the CR as cause** (the S10.3 H2 lesson).
4. **The ownership surface:** the dashboard shows the managed objects badged and **warns** on a manual edit
   (withholds the control), never silently reverts.
5. **Honest status + drift on the wire:** a rejected CR goes `Ready=False` naming the CP code; a CP object
   deleted out-of-band is recreated with `Drift=True` surfaced in `kubectl get`.

Anything short of a flow that flips **deny→allow→deny under `kubectl apply`/`delete`** does not discharge
this walk.

## Before you start — two bars that decide pass vs finding

- **ZERO-TOUCH BAR.** `kubectl apply` / `kubectl delete` are the walk's SUBJECT. The ONLY commands you may
  hand-run are DIAGNOSTIC — reading nft counters and audit rows to OBSERVE an effect. Anything else you must
  hand-run on the gateway or cluster to make a leg's flow work (a manual route, a hand-written nft/DNAT rule,
  a manual DNS entry) is a **FINDING** — number it and HOLD it. Zero-touch was the S8.2c / WF-K5 bar; it holds
  for GitOps too (declaring state in git can't require a side-channel to take effect).
- **LEG 3→4→6 IS DECISIVE (WF-K6 standard).** It must be the SAME flow (one client, one Service FQDN), a
  FRESH connection at each transition (let curl exit between attempts — a reused keep-alive would mask the
  policy change), and COUNTER evidence at BOTH ends: the drop counter moving at Legs 3 and 6, the accept
  counter moving at Leg 4. **A CR going Ready proves the operator RECONCILED; only the drop→accept→drop
  counter deltas prove it GOVERNS.** No counter movement shown = the leg is INCONCLUSIVE, never passed.

## Leg 0 — mint · install · deploy · verify-reconciling (complete, copy-paste)

Run from a clean checkout of the branch. Shell vars used below: `CP` (control-plane URL), `ORG` (org uuid),
`OWNER_TOKEN` (the OWNER's `tnx_` CLI bearer — from `tunnex login`, NOT a machine token). No machine-credential
UI exists yet (D3 scoped the principal CP-side; the mint endpoint IS the one-time-secret ceremony — see the
registered UI follow-up in docs/S10.2-decisions.md).

### 0.1 — Build the operator image AT THE BRANCH SHA (provenance)
```bash
git checkout story/S10.2-operator && git rev-parse --short HEAD   # note this sha — it is the census value
SHA=$(git rev-parse --short HEAD)
docker build --build-arg VERSION=$SHA -t tunnex-operator:$SHA apps/operator
docker save tunnex-operator:$SHA | sudo k3s ctr images import -   # import into k3s (S10.3 WF-K5 pattern)
sudo k3s ctr images ls | grep "tunnex-operator:$SHA"             # VERIFY present in the cluster store
```
- **PASS:** the image tag equals the branch sha AND is in the k3s image store (avoids the S10.3 ErrImageNeverPull trap).

### 0.2 — Mint the machine credential (the real one-time-secret ceremony)
```bash
curl -sS -X POST "$CP/api/v1/organizations/$ORG/machine-credentials" \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"gitops","role":"operator"}'
# → 201 {"id":"..","name":"gitops","fingerprint":"..","token":"tnxm_..."}   ← token shown ONCE
```
- **PASS:** 201 with a `tnxm_` token + a fingerprint. Commit the **fingerprint** as evidence; the **token** goes
  ONLY into the Secret in 0.4 — gitignore any scratch file you paste it into (it is a live credential).
- **NEGATIVE CHECK (one-time-secret):** `curl -sS "$CP/api/v1/organizations/$ORG/machine-credentials" -H "Authorization: Bearer $OWNER_TOKEN"`
  returns the credential with a fingerprint and **NO token field** — the secret is never re-served.

### 0.3 — Install the CRDs
```bash
kubectl apply -f apps/operator/config/crd/
kubectl get crd | grep tunnex.io   # tunnexclusters / tunnexexposedservices / tunnexgrants — Established
```

### 0.4 — Deploy the operator (RBAC + Secret + Deployment)
```bash
kubectl apply -f apps/operator/config/rbac/role.yaml    # the tunnex-operator ClusterRole
kubectl apply -f apps/operator/config/deploy.yaml       # Namespace/SA/ClusterRoleBinding/Deployment (placeholders)
# the machine token as a Secret — NEVER committed:
kubectl -n tunnex-system create secret generic tunnex-operator-credential --from-literal=token='tnxm_...'
# fill the non-secret config + the provenance-tagged image:
kubectl -n tunnex-system set env  deploy/tunnex-operator TUNNEX_CP_URL="$CP" TUNNEX_ORG_ID="$ORG"
kubectl -n tunnex-system set image deploy/tunnex-operator operator="tunnex-operator:$SHA"
```

### 0.5 — Verify it is RECONCILING (and is the right build) BEFORE any CR
```bash
kubectl -n tunnex-system rollout status deploy/tunnex-operator             # Available
kubectl -n tunnex-system logs deploy/tunnex-operator | grep -m1 version    # → "tunnex-operator starting" version=<SHA>
kubectl get tunnexclusters -A                                              # empty, no errors
```
- **PASS:** Deployment Available; the startup log's `version` **equals `$SHA`**; no CRs yet; no auth errors in the log.
- **EVIDENCE:** the mint response (fingerprint only), `k3s ctr images ls` line, the startup log (version + connected).

### BUILD-PROVENANCE CENSUS (mandatory — the founder's condition)
The running operator MUST report `version=$SHA` (the `45860e0`-or-later branch build). **A stale image (a
pre-fold build) reproduces the EXACT C1 symptom:** every CR you apply in Leg 1 goes `Ready=False`
`email_not_verified`. So **if Leg 1 shows `email_not_verified`, run `kubectl -n tunnex-system logs
deploy/tunnex-operator | grep version` FIRST** — a mismatched sha is a PROVENANCE failure (redeploy the
correct image, 0.1 + 0.4), NOT an unfixed C1. Never conclude the fold regressed until the version matches.

## The CR manifests (pre-filled for the azure-gw / k3s rig)

Values from the S10.3 WF-K5 rig: k3s on `azure-gw`, the `hello` Service in `default`, cluster `prod`, zone
`k8s.local`, VIP range `100.64.0.0/16`, k3s Service CIDR `10.43.0.0/16`. **Fill the two `REPLACE_*`:**
`REPLACE_SITE` (the site you bound azure-gw to — not recorded here) and `REPLACE_EMAIL` (your login, the grant
subject). **The FQDN each manifest produces is shown as a comment — read it before you apply; a mismatch shows
up now, not at Leg 3.**

**Split into TWO directories on purpose:** `walk/` (cluster + service, applied at Legs 1–2) and `walk-leg4/`
(the grant, applied at Leg 4 ONLY). This is structural — `kubectl apply -f walk/` at Legs 1–2 CANNOT pick up
the grant, so the DENY half (Leg 3, grant absent) can't be skipped by an accidental `apply -f .`.

```bash
mkdir -p walk walk-leg4

cat > walk/cluster.yaml <<'YAML'
apiVersion: tunnex.io/v1alpha1
kind: TunnexCluster
metadata: { name: prod-cluster, namespace: default }
spec:
  site: REPLACE_SITE            # the site fronting azure-gw (D1: one gateway = one site)
  name: prod                    # cluster-zone becomes  prod.k8s.local
  vipRange: 100.64.0.0/16       # synthetic VIPs; disjoint from pool/sites/other clusters
  serviceCIDR: 10.43.0.0/16     # k3s default Service CIDR (NOT 10.96/12 — that's kubeadm)
  dnsZone: k8s.local
# → status.clusterId set, status.dnsVip ~ 100.64.0.2 ; every Service FQDN ends in .svc.prod.k8s.local
YAML

cat > walk/service.yaml <<'YAML'
apiVersion: tunnex.io/v1alpha1
kind: TunnexExposedService
metadata: { name: hello, namespace: default }
spec:
  cluster: prod-cluster         # the TunnexCluster RESOURCE name (same namespace)
  namespace: hello              # <-- the K8s namespace the hello Service lives in; change to "default" if that's where it is
  service: hello
  protocol: tcp
  port: 80
# → RESOLVABLE FQDN:  hello.hello.svc.prod.k8s.local   (or hello.default.svc.prod.k8s.local if namespace=default)
#   status.vip ~ 100.64.0.3  — THIS is the name you curl in Legs 3/4/6
YAML

cat > walk-leg4/eng-to-hello.yaml <<'YAML'
# ⚠ APPLIED AT LEG 4, NOT NOW. The deny half (Leg 3) must be proven with this grant ABSENT.
apiVersion: tunnex.io/v1alpha1
kind: TunnexGrant
metadata: { name: eng-to-hello, namespace: default }
spec:
  subjectKind: user
  subject: REPLACE_EMAIL        # your login — resolves via /members to your device(s)
  service: hello                # the TunnexExposedService RESOURCE name
# → status.ruleId set; the flow to hello.<ns>.svc.prod.k8s.local flips DENY→ALLOW
YAML
```

**Confirm the FQDN before applying anything:** the Service you will curl is
`hello.<namespace>.svc.prod.k8s.local`. Set `service.yaml`'s `spec.namespace` to wherever the `hello` Service
actually runs (`kubectl get svc -A | grep hello`) — that value IS the `<namespace>` in the FQDN.
