## 2.1 One census result worth stating, because it could have gone the other way

**Link health is available in the OPEN edition.** `Node.policy_degraded_kind`'s schema description says
*"Zero Trust (enterprise, S7.4b)"*, which reads as enterprise-only — but the computation has explicit
open-edition branches:

```go
// internal/nodes/service.go:1966
case !enterprise && siteHubDown:
    kind = KindSiteHubDown // edition-independent (routing/peers are core, D11)
case !enterprise && siteLinkDown:
    kind = KindSiteLinkDown
```

and `ListNodes` sets the field unconditionally (`internal/http/node_handlers.go:62`). **So the mesh's
linked/degraded/down legend is real in both editions**, and no part of this screen needs an edition gate.

**⛔ FOUNDER-RULED: THIS IS A DEFECT IN ITS OWN RIGHT, AND IT IS REGISTERED AGAINST THE SPEC — NOT AS A NOTE
IN THIS PAPER.**

My first draft filed it here and argued that correcting it "regenerates four targets, so it is a finding,
not a drive-by fix". **That is backwards.** The artifact that is wrong IS the description; a note about a
misleading description, filed somewhere the reader of the description will never look, leaves the misleading
text shipping and adds a second place to be out of date.

> **A DESCRIPTION THAT CONTRADICTS THE CODE IS NOT DOCUMENTATION DEBT. ON AN OPENAPI-FIRST CODEBASE THE SPEC
> IS THE SOURCE OF TRUTH, SO A WRONG DESCRIPTION IS A WRONG SOURCE OF TRUTH.**

It is load-bearing in a specific, checkable way: **a future reader gates a UI on `edition === "enterprise"`
because the schema told them to**, and the open edition silently loses a health signal it is entitled to.
That is the edition-vs-failure class this epic has already had to sweep twice.

**DISPOSITION: corrected in `openapi/openapi.yaml` as a slice of S14.5**, with `make generate` +
`make generate-check` + both-edition build/test, because the field is the one this screen reads. **Comment-
only; zero behaviour change.** The correction cites `internal/nodes/service.go:1966` so the next reader can
verify rather than trust.

**This is the standing "who-reads-this" probe firing on a DESCRIPTION rather than a field** — the producer
and the consumer disagreed, and only one of them was load-bearing.

## 2.1b ⛔ HALT-AND-SURFACE — THE OPEN EDITION IS SHOWN AN **UPSELL** FOR A CAPABILITY IT ALREADY OWNS

**Found while opening `Sites.tsx` to start building. It contradicts §3 of this very paper, which I wrote
from `ENTERPRISE_PATHS` without opening the page.**

```ts
// apps/web/src/pages/Sites.tsx:89
if ((mRes.data as Meta).edition !== "enterprise") return;   // never loads sites, nodes, subnets, hub set

// apps/web/src/lib/sitesview.ts:38,55
canView: isEnterprise,
if (!i.isEnterprise) return "upsell";
```

**AND THE API DISAGREES, EXPLICITLY AND IN WRITING:**

```go
// apps/api/internal/http/site_handlers.go:19
// (all editions, D11); Zero-Trust governance of the resulting site traffic is enterprise (Slice 3).
// :95   site:manage (all-editions core, D11)
// :280  All-editions core like the rest of the site model (authorize FIRST, no edition gate)
```

`ListSites` authorizes on `org:view` and nothing else. **`/sites` is not in `ENTERPRISE_PATHS`. No site
endpoint returns `403 edition_required`.**

**So the open edition can create sites, bind gateways, advertise and approve subnets, and run site-to-site
transit — through the CLI and the API — while the dashboard tells it to buy enterprise.**

### Why this is a decide-item and not a fix I take

**It is not "a screen is missing".** It is the product **soliciting payment for a capability it already
ships**, which is a claim about what is sold, and that is the founder's call, not a build detail.

It is also the **third instance of the edition-vs-failure class this epic**, and the first in this direction:

| instance | shape |
|---|---|
| Pending approvals (S14.4) | a successful refusal rendered as **failure** |
| Access Rules (S14.4) | the same defect, still live one card over |
| **Sites (here)** | **a capability rendered as ABSENT AND FOR SALE** |

**The first two made the product look broken. This one makes it look smaller than it is** — and unlike a red
error card, nothing about an upsell looks like a bug, so it can sit indefinitely.

### The two readings, and what each costs

**(a) The gate is the bug** — the site model is core by D11, the API says so three times, the CLI honours it.
**Remove the gate; the open edition gets the screen it already has the endpoints for.** Cost: the redesigned
screen must have a coherent open-edition rendering, which is work S14.5 would then own.

**(b) The gate is the intent** — site-to-site is meant to be enterprise, and the API is what is wrong.
Cost: **this is a much bigger change than a UI gate** — it means adding `edition_required` to ~10 endpoints,
adding them to `ENTERPRISE_PATHS`, and it **breaks open-edition users who already use them**. It also
contradicts `D11` and the comment at `site_handlers.go:19` that separates the core site model from the
enterprise Zero-Trust governance *of* site traffic.

**RECOMMENDATION: (a).** The written intent is unambiguous and appears in three places on the server. **But
the upsell copy is a commercial statement, so it does not get removed on my reading of a code comment.**

**HELD. Building the redesign in the meantime** — every other part of this screen is edition-independent, so
the gate decision changes *who sees it*, not *what is built*.

# 3. THE CUTS, UNDER THE FOUR-WAY TEST

## ✅ BUILD AS DRAWN

## 🔁 BUILD IN A DIFFERENT FORM — subject supported, wireframe's RENDERING unsupported

### 3.1 The mesh is per-REGION in the wireframe. Ours is per-SITE. **(four-way test, case 2 — SECOND INSTANCE)**

**Founder-recorded as the four-way test working.** The first instance was Site-Link Throughput on Overview
(the subject exists, no time-series endpoint renders it as drawn). This is the second: **the subject is
supported and the wireframe's RENDERING is not**, so it is built in a different form rather than cut or
faked.

**The pattern both instances share: the missing thing is a DIMENSION the drawing assumed, not a capability.**
Site-Link Throughput assumed time; this assumes geography. Neither is a feature gap — both are the design
having a field we do not serve.


The wireframe's five peers are **cloud regions** carrying `count` sites each. **We have no region field on
`Node` or `Site`** — the Gateways table's `cloud · region` sub-line is wireframe copy, not a served field.

**Form:** one node per **site**, hub at centre from `is_site_hub`. **No count glyph** (a site is one thing,
not forty), **uniform radius** (nothing to scale by), edge tone from `policy_degraded_kind`.

**This is the honest version of the same picture.** Inventing a region grouping to match the drawing would
mean deriving it client-side from gateway names, which is a guess wearing a diagram's authority.

### 3.2 Node radius ∝ site count, edge width ∝ count → CUT, uniform instead

Both encode a `count` we do not have (3.1). A radius that varies by nothing but looks like it varies by
something is worse than a uniform one.

### 3.3 Selected-node readout `{{ selIp }}` → the site's approved CIDRs

**There is no IP on `Site` and none on `Node`.** The nearest true fact is the site's approved subnets, which
is what an operator wants from that line anyway. Rendered as `kind · CIDR(s) · status`.

### 3.4 Cross-site DNS forwarding, org-wide → **DECIDE-ITEM D1**, see §5

The wireframe lists zones org-wide with a `via <site>` column. **Our endpoint is per-site**
(`/sites/{siteId}/dns-forwards`), so an org-wide list is **N requests, one per site**.

### 3.5 "Per-link byte counters" footnote → keep the counters, move them

`rx_bytes` / `tx_bytes` exist **only on `HubMemberMetrics`** — per hub-set member, not per site link. So the
counters render in the **HA Hub Set** panel where they are true, and **the mesh does not claim them**. The
footnote's warning (*cumulative since handshake, never dressed up as rates*) moves with them; the spec says
the same thing in its own words: *"Raw gauge since the last handshake (display only, never summed as
monotonic)."*

## ❌ ABSENT — no endpoint

### 3.6 `● WIRE-TRUTH TOPOLOGY` chip

**It is a claim, and claims need a source.** The mesh's edges are handshake-derived and therefore genuinely
wire-truth; but the chip as drawn asserts it for the whole screen, including the DNS list and the subnet
queue, which are control-plane rows. **Rendered scoped to the map, or not at all** — see **D2**.

### 3.7 "Reject" on a pending subnet

There is no reject operation. The nearest is `removeSiteSubnet` (**un-advertise**, line 2336). **The control
ships, labelled `Un-advertise`, not `Reject`** — a button that says Reject and performs a delete is a lie
about what the server did.

## 🚫 ABSENT — the spec forbids

Nothing on this screen. **Sites is not in `ENTERPRISE_PATHS`** (`apps/web/src/lib/edition.ts`), so the whole
screen is open-edition, and §2.1 confirms the health signal is too.

**Recorded as a finding, not a deferral.** `NodeLink` was built in S14.3 (`components/viz.tsx:300`) with
**Sites named as its consumer**, and shipping this screen without wiring it would make it the third
producer-without-consumer of the epic.

**It is wired here.** What it needs, measured against its current signature
(`nodes: Node[]`, `links: Link[]`, `failed`, `source`, `empty`):

- **hover and selection** — it is a static SVG today; the wireframe's *"hover to trace a link · click a node

Both are changes to a **shared primitive**, which is where all three of this epic's real visual defects came
from. **They re-earn a gallery combination** (a mesh with one of each link tone, selected) rather than being
covered only on the Sites screen.

# 5. DECIDE-ITEMS — held for the founder

**D1 — cross-site DNS forwarding: org-wide or per-site?**
Org-wide matches the drawing and is what an operator wants (one zone maps to one resolver ORG-WIDE, so a
per-site view cannot show the conflict the rule is about). Cost: **N+1 requests**, one per site, on a screen
that already loads sites, nodes, pending subnets and the hub set.
**Options:** (a) org-wide, fan out, load-once per visit · (b) per-site, as today, and the org-wide rule
stays copy rather than a view · (c) org-wide, and register an aggregate endpoint as a follow-up.

**⛔ RULED: (a). N+1 ACCEPTED.** *"The one-zone-one-resolver-org-wide rule is a real invariant and unreadable
per-site."*

**Build note the ruling implies:** the fan-out is bounded by site count and issued **once per visit**, not
per render — a `useEffect`-per-site would re-fire on every state change the mesh's selection causes. One
load, one merged list, `failed` surfaced per site so a single site's failure does not blank the org view or
silently shorten it. **A shortened list is the worse failure here: this view exists to show a conflict, and
a conflict you cannot see because one fetch failed reads as no conflict.**

**D2 — the `WIRE-TRUTH TOPOLOGY` chip.**
(a) scoped to the map panel, where it is true · (b) dropped · (c) page-level as drawn.
**Recommendation: (a).** Page-level would assert wire-truth over the subnet queue, which is a control-plane
table, and that is the reassuring-label failure mode this epic keeps catching.

**D3 — does the mesh replace `SiteCardView`, or sit above it?**
The wireframe shows only the mesh; our shipped screen shows a card per site with everything inline.
**Recommendation: mesh above, cards below**, cards driven by the selection. Replacing the cards outright
would delete working management surface to match a drawing that never had to manage anything.

**D4 — 21 em-dashes in `Sites.tsx` rendered copy** must be cleared as part of this section's done
(`docs/EPIC-14-ui-redesign.md:331`). Confirming that is in scope for S14.5 and not deferred.
