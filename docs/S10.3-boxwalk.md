# EPIC 10 — Kubernetes in-cluster gateway — box-walk runsheet

The walk that proves the product: **install the chart, expose a Service, reach it by name from a laptop that
was already connected — zero-touch.** WF numbers are assigned as findings land.

Grounded in `deploy/helm/tunnex-gateway/`, `apps/api/internal/k8s/service.go`,
`apps/api/internal/sites/routedranges.go`, `apps/web/src/pages/{Kubernetes,Access}.tsx`,
`apps/node/internal/egress/dnat_linux.go`, `apps/node/internal/dnsforward/dnsforward.go`,
`apps/node/internal/reconcile/reconcile.go`, `docs/S10.3-decisions.md`.

## THE ZERO-TOUCH BAR (every leg)

Sanctioned terminal commands: the `helm install`/`upgrade` itself, and **read-only diagnostics**
(`kubectl get/logs/describe`, `nft list`, `dig`/`nslookup`, `ip addr`). Everything else — connectivity,
exposing Services, grants — happens through the **Tunnex UI/API**, and the gateway **self-provisions**. If a
step needs a hand-placed secret, a manual route, a resolver edit, or any workaround to make a feature work:
**the walk STOPS and it is a finding.** A leg that only passes with a manual prop is INCONCLUSIVE, never a pass.

## Prerequisites (Pawan)

- **A conforming cluster** — EKS / GKE **Standard** / AKS / k3s. NOT GKE Autopilot (Fork-2: Autopilot blocks
  the privileged/hostNetwork pod — accepted-unsupported). The node needs `/dev/net/tun` (tun module) + CoreDNS.
- **`kubectl` + `helm`** context set to that cluster.
- **The control plane reachable from in-cluster** — api:8080 + agent-mTLS:8443 (a `tunnex-cp` release, or a
  reachable external CP). Cross-namespace addressing: `<svc>.<ns>.svc.cluster.local`.
- **ENTERPRISE CP for the ZTNA legs.** Connectivity (register cluster, expose Service, reach-by-name) works on
  the OPEN CP. The GRANT that reaches a Service (`dst_kind=k8s_service`) is enterprise-gated — the open CP
  returns `edition_required`. **Recommendation: run the WHOLE walk on an enterprise-tagged CP**
  (`TUNNEX_BUILD_TAGS=enterprise`, the S9.1-boxwalk mechanics) — it is a superset, so both connectivity and
  ZTNA legs run in one walk. If only an open CP is available, the ZTNA legs (WF-K6/K7) defer to a second walk.
- **A client device already connected** — a Tunnex desktop/WireGuard device (the decisive leg's laptop) and,
  for the OVPN parity leg, an OpenVPN client with an exported profile.
- **An org where you can** mint a join token, register a **site** first (a cluster is fronted by one site's
  gateway, D1), and expose Services.

Commit evidence DURING the session under `walk-artifacts/`; gitignore scratch WG/join credentials at creation
(private keys).

## WF-K1 — PREFLIGHT PASS (`helm install --wait` on a conforming cluster)

**Goal.** The pre-install hook Job (F7) runs, asserts `/dev/net/tun` + cluster DNS *by answer content*, passes,
and the gateway Deployment comes up — from one `helm install --wait`.

1. Mint a join token (Nodes → join token). Prefer a Secret (F5, keeps it out of Helm history):
   `kubectl -n <ns> create secret generic tunnex-gw-join --from-literal=TUNNEX_JOIN_TOKEN=<token>`
2. Reserve/know the public WG endpoint (F6): static LB IP or NodePort address, `host:port`.
3. `helm install tunnex-gw deploy/helm/tunnex-gateway -n <ns> --wait --timeout 5m \`
   `  --set acknowledgePrivileged=true \`
   `  --set controlPlane.apiURL=http://<cp-api>.<cpns>.svc.cluster.local:8080 \`
   `  --set controlPlane.agentURL=https://<cp-agent>.<cpns>.svc.cluster.local:8443 \`
   `  --set endpoint=<PUBLIC_HOST:51820> \`
   `  --set service.type=LoadBalancer --set service.loadBalancerIP=<reserved-ip> \`
   `  --set existingJoinTokenSecret=tunnex-gw-join`

**Expected.** `helm install` returns success. `kubectl -n <ns> logs job/tunnex-gw-tunnex-gateway-preflight` →
`preflight: OK — privileged context admitted, /dev/net/tun present, cluster DNS answers.` (hook is
`hook-succeeded`-delete, may already be gone; install success is primary). Gateway pod Running.
**FAILURE.** Timeout; Job `Error`; gateway CrashLoopBackOff; FATAL on tun/DNS. A pass requiring
`preflight.enabled=false` is a finding.

## WF-K2 — PREFLIGHT REFUSAL (PSS-restricted — proves M4 + guard-before-exec)

**Goal.** Into a PodSecurity-restricted namespace, `helm install --wait` fails **at the hook** with the
friendly context, NOT a 5-min timeout or crash-loop.

1. `kubectl create ns gw-restricted && kubectl label ns gw-restricted pod-security.kubernetes.io/enforce=restricted`
2. Re-run WF-K1 with `-n gw-restricted`.

**Expected.** Install fails fast; preflight pod admission-REJECTED (hostNetwork+NET_ADMIN+hostPort+hostPath all
forbidden); real Deployment never starts. `kubectl -n gw-restricted get events | grep -i 'forbidden\|PodSecurity'`.
**FAILURE.** Hangs to timeout; OR gateway Deployment crash-loops; OR the pod is *admitted* (PSA not enforcing —
record as SUBSTITUTE, trigger "enforced-restricted cluster available"). A tun-less variant must log the loud
FATAL, never a `FailedMount` hang (the M4 regression this leg guards).

## WF-K3 — ZERO-TOUCH SELF-PROVISION (join token → CSR → mTLS → serving)

**Goal.** The gateway enrolls with no manual step; identity persists across a pod restart.

1. `kubectl -n <ns> logs -l app.kubernetes.io/component=gateway` → `agent_enrolling` → `agent_enrolled`
   (`node_id`). No `agent_not_enrolled`.
2. Sites page → the bound site: the gateway node appears enrolled, green liveness.
3. `kubectl -n <ns> delete pod -l app.kubernetes.io/component=gateway` → new pod logs
   `agent_reusing_stored_identity` (re-attached the SAME cert off the state PVC, no re-enroll, no fresh token).

**FAILURE.** `agent_enroll_failed`/`agent_csr_failed`; node never appears; OR restart logs `agent_enrolling`
(PVC didn't hold the cert → re-enroll needs a manual token = zero-touch bar broken).

## WF-K4 — REGISTER CLUSTER + EXPOSE SERVICE (via the UI)

**Goal.** Through the dashboard: register the cluster (disjoint VIP range validated), expose a Service; UI
shows the server-computed FQDN; the node's `nft` shows the VIP→ClusterIP DNAT.

1. Kubernetes page → **Register cluster**: fronting site, cluster name (DNS label, e.g. `prod`), synthetic VIP
   range (disjoint, e.g. `100.64.0.0/16`), Service CIDR (default `10.96.0.0/12`), DNS zone (e.g. `k8s.acme.com`).
2. Cluster card → **Expose Service**: name (`api`), namespace (`default`), protocol.
3. Row shows the **FQDN read from server** (`<service>.<namespace>.svc.<cluster>.<zone>`) — copy, don't construct.

**Expected (wire truth).** On the node, `sudo nft list table ip tunnex` shows a `prerouting` chain (priority
**-101**) with `ip daddr <SERVICE_VIP> dnat to <REAL_CLUSTERIP>`; `<REAL_CLUSTERIP>` equals
`kubectl -n <namespace> get svc <name> -o jsonpath='{.spec.clusterIP}'` (resolved via CoreDNS, no K8s API).
`ip addr show dev wg0` shows the reserved DNS VIP (`.2`) assigned as a `/32` (fork-1 `ReconcileDNSVIPs`).
**FAILURE.** Register rejected on a disjoint range / accepted on an overlapping one; blank/constructed FQDN; no
`prerouting` chain or a DNAT to a stale/wrong ClusterIP; a headless Service (`clusterIP: None`) silently mapped
instead of refused.

## WF-K5 — ★ THE DECISIVE LEG: client reaches the Service BY NAME (zero-touch), records the resolution path

**Goal — the epic's most important proof.** From a laptop **already connected** (no reconfig), reach the
exposed Service **by its FQDN** through its VIP. And **record HOW the name resolved.**

**Pre-state (must be zero-touch, fork-1):** the connected device received the cluster's VIP range in its
WireGuard AllowedIPs AND the cluster-zone → DNS-VIP resolver — both over the routed-ranges poll, no hand-edit.
Verify BEFORE touching the Service:
- `wg show` (or the client's route table) shows `100.64.0.0/16` in AllowedIPs — the VIP range the CP now
  returns from `ListRoutedRanges` (fork-1), applied by the client `RoutedRangesMonitor → setAllowedIPs`.
- the client's resolver config has `prod.k8s.acme.com → 100.64.0.2` (the routed-forwards half →
  `setResolvers`). **If either needed a manual edit, the walk STOPS — finding.**

**The leg:** from the laptop, `dig api.default.svc.prod.k8s.acme.com` (or `curl` the Service).
- Expected: resolves to the Service's **VIP** (e.g. `100.64.0.5`), and the connection reaches the real pod
  (VIP → DNAT → ClusterIP → kube-proxy → pod).

**★ RECORD THE RESOLUTION PATH (the walk-manifest condition):** capture WHERE the name resolved.
- **Local direct-answer** (the query went to the cluster gateway's DNS VIP, answered by the agent's H1
  forwarder) → the local answer suffices; **(C) cross-site forwarding is NOT needed** — note it, trigger stays
  unfired.
- **Required forwarding** (the laptop's DNS reached the Service name only via a cross-site hop) → **(C)'s
  trigger has fired WITH evidence** — record the trace; (C) synthetic-resolver kind gets its commit-one.
  Capture `dig +trace` / the resolver the laptop actually queried.

**FAILURE.** The name doesn't resolve; resolves to the ClusterIP (DNAT bypassed / wrong); the VIP range or
resolver required a manual edit (zero-touch broken); or the connection reaches nothing (DNAT/kube-proxy
ordering wrong).

## WF-K6 — ZTNA ENFORCING (enterprise CP): grant reaches Service · no grant → denied

**Goal.** With the org **enforcing**, a `dst_kind=k8s_service` grant is the difference between reach and deny.

1. Access page → new rule → destination kind **"Kubernetes Service (in-cluster)"** → pick the exposed Service
   → source = the laptop's group/user. Save.
2. From the laptop, reach the Service by name (WF-K5) → **flows** (grant present, both-enforce: device gateway
   + cluster gateway authorize; `compiler.go` k8s_service case).
3. Delete the grant (or test a device with none) → reach again → **denied** (default-deny; the flow is dropped).
4. Toggle enforcing off/on and confirm the transition matches the policy-health surface.

**FAILURE.** Reachable with no grant (default-deny broken); denied WITH a grant (both-enforce placement wrong);
enforcing state not honored.

## WF-K7 — OVPN PARITY (WF-OVPN-11 twin): an OpenVPN client reaches the Service too

**Goal.** An OpenVPN client of the same org, connecting to the gateway, reaches the exposed Service — OVPN did
not inherit the gap when WireGuard's was fixed (fork-1).

1. From the OVPN client (exported profile), connect. `ip route` shows a pushed route to each exposed Service
   VIP `/32` + the DNS VIP `/32` (`OVPNPushRoutes` fork-1); the DNS VIP is a pushed resolver.
2. `dig`/`curl` the Service FQDN → resolves to the VIP, reaches the pod.
3. **OVPN-DNS fallback check** (walk-watch): confirm the OVPN client's NON-cluster DNS still works with the
   DNS VIP in its resolver list — a non-cluster query to the DNS VIP is answered `REFUSED` (not NXDOMAIN), so
   the client falls back to its other resolvers. Verify a `dig google.com` still resolves.

**FAILURE.** The Service is unreachable from OVPN (the WF-OVPN-11 asymmetry recreated); OR non-cluster DNS
breaks because the DNS VIP wrongly claims authority (NXDOMAIN instead of REFUSED for out-of-zone).

## WF-K8 — UNEXPOSE / DEREGISTER SWEEP (observed LIVE)

**Goal.** Removal is a full sweep on the wire and in the audit log.

**A. Unexpose one Service** (Kubernetes page → row → Unexpose; soft-delete + `pushOrg` <5s):
- `nft list table ip tunnex` → that VIP's DNAT line GONE (atomic free-sweep).
- `dig <that FQDN> @<cluster-dns-vip>` → **NXDOMAIN** (unexposed → not in map → authoritative NXDOMAIN).
- Access page: a rule reaching it shows the amber **vanished badge** (compiles to nothing, not a silent no-op).
- Audit: `k8s.service_unexposed` row (H2).
- Client side: the Service VIP `/32` remains routable (the whole VIP range stays in AllowedIPs) but resolves
  to nothing — honest, not a stale mapping.

**B. Deregister the cluster** (cluster card → Deregister → type the name; FK-cascade):
- ALL its DNAT rules gone; every FQDN under the zone → NXDOMAIN; the DNS VIP unassigned from wg0.
- VIP range (incl. DNS VIP) + DNS zone freed — a new register can reuse the range; the client's routed set
  drops the VIP range on the next poll.
- Audit `k8s.cluster_deregistered` with `services_deleted` + `grants_deleted` counts (H2) — verify they match;
  proves a governance cascade (hard-deletes enterprise grants) is traceable.

**FAILURE.** A DNAT survives an unexpose; name still resolves; dependent grant silently still matches (no
badge); VIP range still-in-use after deregister; OR `k8s.cluster_deregistered` missing/zeroed counts.

## WF-K9 — NET_RAW CHECK (datapath under `drop:[ALL] + add:[NET_ADMIN]`)

**Goal.** Confirm WG handshake + DNAT + DNS all work under the M7 posture (no NET_RAW). If anything on the live
path needs a raw socket it fails here.

1. `kubectl -n <ns> get pod -l app.kubernetes.io/component=gateway -o yaml | grep -A8 securityContext` →
   `drop:[ALL], add:[NET_ADMIN]`, `allowPrivilegeEscalation:false`, `seccompProfile:RuntimeDefault`,
   `runAsNonRoot:false`. NO `NET_RAW`, NOT `privileged:true`.
2. **The datapath legs passing IS the NET_RAW proof** — WF-K4 (handshake + DNAT), WF-K5 (the `:53` DNS answer),
   all green under this cap set = nothing needed a raw socket.
3. `kubectl -n <ns> logs -l app.kubernetes.io/component=gateway | grep -i 'permission\|EPERM\|not permitted'`.

**FAILURE.** A raw-socket op fails EPERM; WG/DNAT silently non-functional; OR someone added
`NET_RAW`/`privileged:true` to make it work (that IS the finding). **Named coupling:** `runAsNonRoot:false` is
load-bearing for the `:53` DNS bind (no CAP_NET_BIND_SERVICE in the set) — do not flip it (see decisions paper).

## Walk-manifest OBSERVATIONS (not legs)

- **L1 — multi-gateway cluster-DNS reachability (untested, inherited class).** The cluster-zone resolver is
  pushed org-wide, but only the gateway FRONTING the cluster answers it. A single-gateway walk (k3s: the client
  homes to the one gateway that fronts the cluster) does NOT exercise the case where a device is homed to a
  DIFFERENT gateway with no site-link transit to the cluster — that device SERVFAILs cluster names (scoped;
  non-cluster DNS intact). Note it as inherited reachability class (same as site-subnet/DNS-forward reach),
  UNTESTED here — do not claim the multi-gateway case passed.

## WALK FINDING — WF-K-CHART-1 (walk-blocking, FIXED mid-walk)

**Preflight PASSED, install deployed, but the gateway pod could not ENROLL:**
`agent_enroll_failed (400): node_name_mismatch — this token is pinned to a different node name`.

**Cause:** the CP pins each join token to a NODE NAME (the enroll dialog set `k8s`). The gateway pod runs
`hostNetwork`, so the agent's `hostname()` is the k3s NODE hostname (`azure-gw`) — which differs from the
token's pinned name → the CP refuses. The `tunnex-gateway` chart had **no way to set the enroll node name**;
the docker-run cloud-gateway flow bakes `TUNNEX_NODE_NAME`, the chart forgot to. So the standard pinned-token
enroll fails on the chart path — a real gap, walk-blocking.

**Fix (folded):** added a `nodeName` value → `TUNNEX_NODE_NAME` env (deployment.yaml + values.yaml), documented
that it must match the token's pinned name. `--set nodeName=<pinned name>` on install. (A hostNetwork pod's
hostname can't be overridden via `spec.hostname`, so an explicit env is the only lever — the fix is correct,
not a workaround.)
