# S20.5 — Customer-grade Kubernetes zero-touch installation and lifecycle

Status: **LOCKED — FOUNDER DIRECTED 2026-08-30**.

Founder direction: build the Kubernetes installation and lifecycle as one
provider-neutral product path, use parallel implementation lanes, keep the work
on the current branch, and do not publish it yet. The next live walk must not
need a walk-time source patch, Secret/PVC edit, host sysctl command, CNI edit,
or rollout workaround.

This paper is commit-one in the story sense: decisions precede product edits.
It authorizes the local implementation and its tests. It does not authorize a
commit, push, deployment, cloud mutation, PR, merge, or release.

## Measured starting boundary

- S20.3b explicitly leaves deployment and Helm changes to a later story.
- The `tunnex-gateway` chart deploys one in-cluster connector, but the web UI
  emits `joinToken.secretRef`, a value shape the chart does not accept. Helm
  coerces that map into a literal string instead of refusing it, so the emitted
  command cannot enroll a gateway.
- The UI also names a `tunnex/operator` Helm chart that does not exist.
- The chart has no values schema, Kubernetes probes, exact-node host bootstrap,
  state-retention contract, existing-claim reuse, digest input, or gateway
  render gate. Its preflight checks only `/dev/net/tun` and DNS and may run on a
  different node from the gateway.
- The node already serves `/healthz` and `/readyz`, but Kubernetes does not use
  them. A pod can therefore be `Ready` while enrollment or the data plane is
  not ready.
- The AKS HA walk required manual host `rp_filter`, CNI masquerade, Secret/PVC,
  and rollout changes. Dirty branch work makes those datapath repairs possible,
  but the CNI mechanism is embedded in the generic egress manager, called AKS
  specific, and treats every chain-read error as not applicable.
- Provider/platform on a registered cluster is presentation and guidance only.
  It is not evidence of the actual CNI, CSI, endpoint controller, or node
  posture and must never select a privileged mutation.

## Locked outcomes

### D1 — One common lifecycle, capability adapters at the edge

**LOCKED.** AKS, EKS, GKE Standard, and self-managed Kubernetes use one CLI
lifecycle, one gateway chart, one operator chart, one node agent, and one
state/health model.

Common lifecycle is:

`discover → plan/digest → approve → apply → verify → ready`, with an explicit
rollback path. Provider/CNI/CSI/endpoint adapters may return typed facts and
narrow actions, but provider names never branch the datapath. Detection uses
the Kubernetes or host mechanism actually present. `unknown`, `ambiguous`,
`blocked`, and `not_applicable` remain distinct results.

The first live-qualified adapter is the nft `IP-MASQ-AGENT` mechanism observed
on the AKS walk. Its name and match are mechanism based, so the same adapter may
apply wherever that exact chain exists. EKS/GKE/self-managed fixtures prove the
common contract now; support is not claimed live until each provider leg runs.

### D2 — The customer entry point is `tunnex k8s`, not a secret-bearing Helm command

**LOCKED; supersedes EPIC-10 D2's raw-token Helm transport.** A Helm value and
the rendered Secret are retained in Helm release history. A one-time secret is
still a secret before it is consumed, so a customer-grade flow cannot put it
there.

`tunnex k8s install` uses the caller's existing CLI login to:

1. resolve one explicitly selected organization (or the sole organization);
2. read the control-plane public/gateway endpoints from server metadata;
3. discover and print a redacted Kubernetes plan plus stable SHA-256 digest;
4. persist the opaque claim/request/generation in an owned token-blind
   Kubernetes lifecycle anchor before any credential is minted;
5. mint or idempotently redeliver one claim-bound, node-name-bound,
   single-use gateway token;
6. stream a create-only Kubernetes Secret manifest to `kubectl create -f -`
   without putting the
   token in argv, a values file, logs, or Helm history;
7. re-read the release/Secret/anchor/PVC fingerprint, acknowledge the exact
   persisted generation, then run create-only
   `helm install --atomic --wait` with non-secret values;
8. verify the real Deployment readiness, connected endpoint, and exact
   control-plane claim consumption; and
9. CAS-delete the consumed bootstrap Secret and lifecycle anchor only after
   success. A failed install retains the minimum typed recovery state for a
   bounded retry and names objects, never the token value.

The command may prompt for plan approval; `--yes` is the deliberate non-
interactive form. It refuses a multi-organization guess, an unlogged-in caller,
an unverified/unauthorized token mint, an ambiguous default StorageClass, an
unsupported Service mode, or missing `kubectl`/Helm context before mutation.

Raw `joinToken` remains a backwards-compatible chart escape hatch but is
labelled insecure and is not emitted by the product or used by the walk.

### D3 — Host posture is common and exact-node

**LOCKED; lifecycle ownership refined by D10/D10a.** `/dev/net/tun`, IPv4
forwarding, WireGuard reverse-path filtering, nftables, and UDP port
availability are Linux gateway requirements, not Azure requirements.

The final design does not let a release-scoped gateway init container mutate
broad host state. The separate cluster-singleton `tunnex-host-posture` release
from D10/D10a runs one privileged manager on each eligible node, journals the
pre-Tunnex baseline before mutation, owns restoration, and is the sole writer
for broad host sysctls plus the exact journal-owned `wg0` reverse-path filter
from D10c. The gateway keeps its narrow `NET_ADMIN`/`NET_BIND_SERVICE`
capability set and no host `/proc/sys` mount. Its credentialless,
non-privileged init container only waits for two advancing manager heartbeats
which contain that exact Pod UID. It receives no service-account token, join
token, state PVC, network credential, or arbitrary command input.

The manager validates the complete fixed gateway Pod authority contract rather
than trusting the owner label alone. A malformed label-selected Pod is ignored
with bounded change-only diagnostics and cannot become an owner; ambiguous API
readback or conflicting Pod UID identity blocks mutation. The manager and real
gateway probes are authoritative because they observe the actual selected
node. Restricted admission fails before false readiness with the missing
posture named; there is no privileged gateway sidecar.

### D4 — CNI compatibility is reconciled by observed mechanism

**LOCKED; writer split refined by D10c.** Extract a small Linux `k8snetprep`
reconciler from the generic egress manager. It performs read-only common-host
verification and owns mutation only for registered CNI adapters. A host
posture mismatch blocks readiness while the shared manager heals it; the
gateway never writes a host sysctl.

For the nft ip-masq adapter:

- exact chain-not-found is `not_applicable` only with no active tunnel; an
  active tunnel with no registered mechanism is `blocked` with
  `no_registered_adapter`; tool/permission/parse failures are likewise
  `blocked`, never silently absent;
- only a Tunnex-commented return rule scoped to the current tunnel CIDR and
  WireGuard egress is owned;
- insert is idempotent and read back;
- controller deletion heals on the next reconcile;
- CIDR/interface change replaces the old owned rule; withdrawal removes every
  obsolete owned rule; and
- unrelated foreign rules are never flushed, reordered, or rewritten.

Adapter state is logged in a finite, redacted form. Provider metadata remains
guidance only.

### D5 — Endpoint discovery uses Kubernetes Service truth

**LOCKED.** For a `LoadBalancer` gateway Service, an empty explicit endpoint
means the agent discovers `status.loadBalancer.ingress[].ip|hostname` from its
own named Service through the existing read-only Kubernetes credential. The
Service port supplies the WireGuard port. It waits without claiming readiness,
publishes the endpoint only after a valid read, and re-reads so controller
changes converge.

An explicitly configured endpoint wins. `NodePort` requires an explicit
reachable node address in v1; the product does not guess public node identity.
The lifecycle never reserves a cloud IP, adds provider annotations, or calls a
cloud API. Operator-supplied `service.loadBalancerIP`, repeatable Service
annotations, and existing image-pull Secret names remain provider-neutral
Kubernetes inputs: the CLI validates them, includes them in the redacted plan
and approval digest, passes them unchanged to the chart, and verifies their
non-secret Service/Deployment readback. It never generates a provider
annotation, creates a registry credential, or reads a pull Secret body.

### D6 — Identity storage is retained by default and never silently reset

**LOCKED.** A gateway PVC contains the node certificate, WireGuard key, HA
fences, leases, and authority evidence. Helm uninstall therefore retains it by
default. The chart supports an explicit existing claim for reinstall/recovery.

Lifecycle modes are:

- `enroll`: empty/new state plus a one-time token;
- `reuse`: an existing retained claim and no token; and
- `rotate`: **not automated in this story**. It refuses with guidance until the
  old node is safely detached/revoked and a separate new claim is named.

There is no automatic PVC delete or fence removal. `tunnex k8s purge-state`
requires the release to be absent, the exact claim name, and a typed
confirmation. The command states that recovery is impossible after deletion.

### D7 — Kubernetes probes, immutable rollout inputs, and lifecycle verbs are real

**LOCKED.** The gateway Deployment consumes the existing agent health server:

- startup/liveness: `/healthz`;
- readiness: `/readyz`; and
- named `health` container port `9091`.

The chart accepts an image digest as the preferred immutable input and a tag as
the compatibility fallback. External configuration changes use a non-secret
rollout revision; changing or deleting a consumed join Secret is not required
for ordinary restart/upgrade.

CLI lifecycle verbs are `plan`, `install`, `status`, `upgrade`, `rollback`,
`diagnostics`, `uninstall`, and guarded `purge-state`. Upgrade and rollback are
Helm-revision based, atomic, wait for real readiness, and preserve the claim.
Diagnostics exclude Secret bodies, Helm values that may contain legacy raw
tokens, private keys, certificate bodies, and service-account tokens.

One invocation manages one connector identity/release. HA A and B are two
independent releases with distinct names, endpoints, Services, and PVCs; this
prevents the shared-Secret/shared-PVC surgery seen in the walk. Pool creation,
HA enablement, promotion, and safe drain remain owned by S20.3b and its UI/API,
not inferred by Helm.

#### D7a — The Leg 9 sustained-failure action is the scale subresource

**LOCKED (founder-approved 2026-08-31).** For the HA wire proof only, the
supported sustained-failure injection is a write to the exact gateway
Deployment's Kubernetes `scale` subresource: replicas `1 → 0` to remove that
one connector, then `0 → 1` to restore it. This is consistent with D7 because A
and B are independent one-replica releases, preserves the release, Service,
PVC, claim, and immutable Pod template, and lets the ordinary control-plane
health and S20.3b ownership scheduler observe a sustained member absence.

This narrow evidence action is not a lifecycle remedy, customer management
surface, manual promotion, safe-drain substitute, Helm values change, or new HA
behavior. It is allowed only in Leg 9 after both releases are ready and the pool
is already `fenced_ha`; it must use the scale subresource rather than editing or
patching the Deployment template. Restoring replicas does not declare recovery:
the walk waits for the exact identity to become ready and for automatic
ownership/failback evidence. Any manual pool promotion, fence change, Pod spec
edit, rollout restart, or scaling performed to repair an install remains
disqualifying.

### D8 — Package the existing GitOps operator truthfully

**LOCKED.** Package the existing operator as `tunnex-operator` and its three
cluster-singleton CRDs as a separate, retained `tunnex-operator-crds` lifecycle
chart. The operator uses an externally created one-time machine Secret,
least-privilege RBAC, no data-plane privilege, and the existing API-only
reconcile/finalizer/status behavior. Packaging adds no GitOps feature.
Its readiness probe authenticates against the configured control-plane org, so
bad URL/org/token inputs cannot make `helm --wait` report a false success.

The CRD chart upgrades monotonically before the rollbackable operator chart.
It contains no workloads or credentials, validates the exact previous Helm
owner before the narrowly scoped adoption of legacy install-only CRDs, and
keeps CRDs on uninstall. `--take-ownership` is not a general force switch: an
ownerless same-name CRD is adoptable only when its complete spec, after removing
only Kubernetes' exact `conversion: {strategy: None}` API default, matches a
source-controlled fingerprint of a Tunnex raw-manifest schema. Unknown,
manually changed, or newer unannotated schemas fail closed before Helm applies
anything. The current CRD release and the known legacy `tunnex-operator` Helm
release remain valid owners. Operators must not run `helm rollback` on the CRD
release; ordinary operator rollback cannot touch CRD schemas.
Both operator charts require Kubernetes 1.29 or newer, where the CRD's CEL
admission semantics are stable; the gateway lifecycle keeps its separate floor.

The lifecycle CLI may install it through a separate explicit verb. The web UI
must never show the operator command until that real chart contract exists, and
must use exact supported value names thereafter. Operator registration and
later reconciliation carry provider/platform presentation only when the CR
explicitly supplies a valid pair; omission leaves the control-plane value
unchanged and never infers or resets it.

### D9 — Distribution is part of the feature

**LOCKED.** CI lints and semantically renders all four charts
(`tunnex-host-posture`, `tunnex-gateway`, `tunnex-operator-crds`, and
`tunnex-operator`) on every relevant change. A version tag packages the charts
with the exact app version, publishes them as OCI artifacts, attaches checksums
to the release, and publishes the operator image alongside the existing node
image. The CLI defaults to the version matching its own release and allows an
explicit local chart path for development.

A local chart that only works from a source checkout is not called customer-
grade or released.

Private pre-release qualification is a separate, non-shipping provenance
surface. `deploy/k8s-walk-candidate-package.sh` accepts only a clean committed
`HEAD` plus explicit digest references for every release image and writes one
local bundle. Its single bounded candidate scalar is stamped into the CLI and
the version/appVersion of all four deterministic chart packages; the manifest
binds that version, full source SHA, toolchain inputs, chart and CLI checksums,
and the six digest-only image references. The script accepts no credential and
performs no registry, Kubernetes, cloud, or control-plane mutation.

After an independently authorized private-registry publication preserves those
exact chart bytes and image digests, that bundle may establish the box-walk's
pre-release provenance. It is never called released, never changes the public
support claim, and never substitutes for the stable version-tag workflow before
customer release. A dirty checkout, mutable image tag, mismatched chart bytes,
or manually restamped artifact is refused rather than qualified.

#### D9a — Private candidate runtime version is bounded, not authoritative

**LOCKED (walk-blocker disposition 2026-08-31).** The enrollment and re-key API
contract caps `agent_version` at 50 characters. A private candidate therefore
defines `0.0.0-walk.sha<first-32-lowercase-hex-of-source-sha>` as its runtime,
CLI, Helm version, and appVersion scalar: 46 characters for every supported Git
object format. The 128-bit abbreviation is sufficient to distinguish bounded
private walk candidates, but it is never a provenance root and no consumer may
reconstruct or accept a full source identity from it.

The package script stamps the CLI and charts but accepts an already-built node
image digest; it cannot inspect or restamp that image. The separate node-image
build **MUST** pass the exact bounded candidate scalar through the Dockerfile's
`VERSION` input. Qualification **MUST** record that build input and, after
enrollment with no `TUNNEX_AGENT_VERSION` override, prove the control plane's
exact `agent_version` readback equals the manifest candidate version. The
bundle alone does not prove the embedded node version, and missing or
mismatched evidence leaves the candidate unqualified.

The manifest's complete `source.sha`, artifact checksums, and digest-only image
references remain the immutable provenance authority. Qualification and
publication **MUST** compare that full identity and **MUST** refuse the same
bounded candidate version paired with a different full source SHA as a
collision. This is an acceptance condition, not collision detection performed
by the local packager. Truncating the full manifest identity, weakening image
digest pins, or raising the API limit merely for a private packaging convention
is rejected.

### D10 — Ownership and restoration of broad host sysctls (HELD-1 resolved)

**LOCKED (founder-approved 2026-08-30).** A chart-owned privileged posture
manager runs once per eligible node as a DaemonSet. Before the first Tunnex
gateway owner mutates host posture, it atomically journals the exact original
values in a versioned hostPath record under Tunnex ownership. Its owner set is
made from live gateway Pod UIDs scheduled to that exact node, not an in-Pod
counter. While at least one owner exists it continuously reconciles
`ip_forward=1` plus `conf/all` and `conf/default` `rp_filter=0` while a gateway
is active. On last-owner removal it restores each journalled value only when the
live value still equals the Tunnex-owned desired value; an external change is
never overwritten. The journal update and owner-set update are crash-safe and
bounded, and the manager refuses mutation when it cannot prove its state.

Rejected alternatives remain: an operator-owned prerequisite would not be
zero-touch; deliberately leaving values changed for node lifetime violates
reversible lifecycle; guessed restoration and single-Pod reference counts are
not ownership proof.

### D11 — Crash cleanup for host-network data-plane artifacts (HELD-2 resolved)

**LOCKED (founder-approved 2026-08-30).** The same D10 per-node posture manager
is the crash authority for host-network data-plane artifacts. It reconciles an
authoritative live gateway Pod-UID owner set, prunes dead owners after API
readback, and on last-owner removal cleans only exact Tunnex-owned WireGuard,
nftables, route, and CNI artifacts recorded in the host journal. Cleanup is
bounded, idempotent, and fails closed on ambiguous ownership. The ordinary
gateway process still performs fast SIGTERM teardown, but its `defer` is an
optimization rather than the lifecycle authority.

The chart runs the connector in the
node network namespace. Normal SIGTERM can execute the process teardown, but
SIGKILL, container-runtime failure, and forced Pod deletion cannot. Therefore a
dead or rescheduled Pod can leave its WireGuard interface plus Tunnex-owned nft
and CNI rules on the old node; container-netns destruction is not a cleanup
authority for this deployment.

A Helm hook or process `defer` alone remains rejected because both are
bypassable.

#### D11a — Journalled staged-link ownership transaction

**LOCKED (founder-approved 2026-08-31, revised direction A; supersedes the
2026-08-30 alias-on-create mechanism).** The AKS wire run disproved the premise
that an `IFLA_IFALIAS` supplied with a WireGuard `RTM_NEWLINK` create is applied
atomically: the create succeeded but live readback returned an alias-empty
`wg0`. Tunnex therefore does not rely on alias-on-create on any Kubernetes or
cloud provider. The provider-neutral contract consumes only the Linux
rtnetlink API and the existing host journal.

The journal schema advances to v2 and makes creation a monotonic staged-link
transaction:

1. before link mutation, persist one bounded collision-resistant opaque
   Linux-safe staging identity/name, the fixed final name `wg0`, expected kind
   `wireguard`, expected ownership alias, node/epoch, and phase `planned`; the
   same baseline must have proved both names absent;
2. create only the uniquely named staging link, read back its exact name, kind,
   and positive ifindex, and persist that receipt as phase `created` before
   proceeding;
3. set the ownership alias on that existing staging link, read back the same
   name/kind/ifindex plus the exact alias, and persist phase `marked`;
4. only while final `wg0` is still absent, atomically rename the marked staging
   link to `wg0`; read back the same kind, alias, and ifindex under the final
   name and persist phase `committed`; and
5. only a committed receipt may unlock nftables, routes, CNI, sysctl ownership,
   or an active admission heartbeat. The staging link must then be absent.

The crash authority is the conjunction of the durable transaction record and
exact kernel readback; a staging name, alias, or ifindex alone is never
authority. Restart resumes only the next monotonic phase for that exact
transaction. An absent expected link may be recreated only from `planned`; an
unexpected final link, wrong kind/alias/ifindex, simultaneous staging and final
links, phase regression, malformed transaction identity, or any unjournalled
candidate blocks without marking, renaming, configuring, or deleting it. Last-
owner cleanup applies the same conjunction and removes only the exact staged or
committed link proved by that journal. The unmarked crash window is confined to
the opaque staging name: an alias-empty final `wg0` is never a normal
intermediate and is never adopted.

V1 compatibility is explicit and fail-closed. A v1 `preparing` journal never
executes link creation or marking. A v1 `active` journal may continue only
after read-only validation of its exact recorded final name, WireGuard kind,
ownership alias, and positive ifindex; it is not translated in place. Exact
last-owner cleanup remains bounded by that same recorded identity. A restored,
artifact-free v1 epoch may start a fresh v2 transaction only after the complete
D10/D11 baseline is clean. The observed failed-create shape — v1 `preparing`,
no recorded ifindex, and an alias-empty final `wg0` — remains ambiguous and is
never automatically marked, renamed, deleted, or migrated.

For this disposable pre-release qualification only, that ambiguous v1 node is
reset through a provider-managed full-node reimage or replacement after the
failed atomic Helm install has converged to absence. The provider operation
must remove the node-local journal and kernel state together, and the walk
restarts from a freshly proved Leg 0 baseline. Manually setting the alias,
deleting `wg0`, deleting the hostPath journal, editing a chart object, or
changing the PVC remains disqualifying and is not a customer recovery claim.

**DEFERRED TO S20.6 — host-reboot rebootstrap.** A normal node reboot can
preserve the hostPath journal while removing kernel-only WireGuard and nftables
state. S20.5 fails closed on that shape rather than silently resetting a
committed receipt or restoring stale sysctl originals. S20.6 must define a new
journalled rebootstrap epoch, recapture the post-boot baseline, and wire-prove
access recovery before Tunnex claims ordinary node-reboot self-heal. Trigger:
before any customer-facing claim that Kubernetes host posture survives an
ordinary node reboot. Manager/container process crashes and the explicitly
recorded disposable full-node fixture reset remain in S20.5 scope.

The rejected two-command fixed-name create/mark sequence remains rejected: a
crash leaves an ambiguous final `wg0`. A temporary/random name or ifindex
without the durable phased journal likewise remains rejected.

#### D11b — nft structural-handle readback

**LOCKED (founder-approved 2026-08-31, direction A).** `nft -a list chain`
annotates both the chain declaration and executable rules with handles. The
ownership validator accepts only the complete anchored readback shape: the
exact `ip` or `ip6` Tunnex table wrapper, one declaration of
`chain tunnex_posture_owner { # handle <positive-decimal>`, the sole exact
Tunnex counter marker rule with decimal packet/byte counters and one positive
handle, and the two structural closing braces. A missing or second wrapper or
declaration, extra brace, second or foreign rule, duplicate marker, extra
prefix or suffix, or malformed handled line fails closed before mutation.

This is a provider-neutral Linux nftables readback contract. It adds no cloud
SDK, provider label, CNI assumption, or provider-specific recovery branch.

#### D10a — Shared manager release ownership

**LOCKED (founder-approved 2026-08-30, direction A).** D7 requires gateway A and B to
remain independent Helm releases, while every object in the current gateway
chart is release-scoped. A DaemonSet inside each release creates multiple
privileged managers on one node; a shared fixed-name object cannot be safely
owned or removed by either independent release. `keep`, live `lookup`, and a
host lock merely orphan ownership and cannot prove the last cluster owner.

Ship a separate cluster-singleton
`tunnex-host-posture` chart/release which the CLI installs and upgrades once per
cluster under the fixed release `tunnex-host-posture` in namespace
`tunnex-system`. The chart refuses any other release identity; the CLI discovers
that identity cluster-wide and gateway releases in any namespace register live
Pod UIDs and assert its contract/readiness. Redesigning one gateway release to own multiple identities
remains rejected as a D7 rewrite. A per-release DaemonSet plus lock or orphaned
`keep` object remains rejected as unsafe lifecycle ownership.

#### D10b — Shared-manager eligibility and gateway placement

**LOCKED (founder-approved 2026-08-30, direction A).** The normal zero-touch
manager release is eligible on every Linux node and tolerates every taint. Its
privileged presence does not authorize mutation: the exact-node live gateway
Pod-UID owner proof from D3/D10 remains the only trigger for host posture or
artifact ownership. This avoids a circular install on dedicated or tainted
gateway pools and lets independent A/B releases select different pools without
rewriting shared-manager eligibility.

The CLI exposes separate, provider-neutral gateway node-selector and toleration
inputs. It validates and canonicalizes them, binds them into the redacted plan
and approval digest, passes them only to the gateway chart, and verifies the
exact live Deployment placement before claiming success. No cloud/provider
label is inferred. Applying one gateway's selector to the shared DaemonSet is
rejected because a later B selector could evict the manager from A's node; a
manual manager preinstall as the normal customer path is likewise rejected
because it breaks the one-command clean-cluster contract.

#### D10c — One writer for the manager-owned WireGuard reverse-path filter

**LOCKED (founder-approved 2026-08-31, direction A).** The live AKS walk proved
that setting `conf/default/rp_filter=0` after creating the staged WireGuard link
does not change the value already inherited by that interface. It also proved
that `hostNetwork` plus `NET_ADMIN` does not make the gateway container's
`/proc/sys` writable. These are provider-neutral Linux/Kubernetes facts, not an
Azure repair branch.

The cluster-singleton host-posture manager is the sole writer. After it proves
the exact journal-owned WireGuard alias and positive ifindex and publishes the
same link as `wg0`, preparation must set and read back
`net/ipv4/conf/wg0/rp_filter=0` before an active heartbeat. Every later manager
reconcile must verify and heal that exact value. The per-interface value is not
added to the broad baseline receipts: `wg0` did not exist before Tunnex, its
original value is therefore undefined, and exact last-owner cleanup deletes
the owned interface. A foreign, alias-empty, wrong-kind, wrong-name, or
wrong-ifindex link blocks before this sysctl mutation.

Gateway `k8snetprep` reads and verifies the per-interface value but never
writes it. It remains the owner of only the exact registered CNI marker rules.
Mounting writable host `/proc/sys` into each gateway, allowing both manager and
gateway to race as sysctl writers, or treating a strict readback as ready are
rejected.

Leg 5 may inject one bounded provider-neutral drift only after the exact
journal-owned `wg0` identity and active manager heartbeat are captured: a
short-lived privileged Kubernetes test Pod on that same disposable node writes
only `net/ipv4/conf/wg0/rp_filter=1`, then exits. The walk must observe manager
self-heal back to `0` without another mutation and delete the completed fixture
Pod. This is failure injection, not a remedy or customer install step; any
other sysctl, chart object, CNI, route, nftables, or WireGuard mutation remains
disqualifying.

**LOCKED (founder-approved 2026-09-01, existing direction A; live fixture
clarification).** The test Pod uses `hostNetwork: true` so the bind-mounted
`/proc/sys/net` resolves in the host network namespace that owns `wg0`; a
hostPath mount alone does not change the Pod's network namespace. It still
automounts no service-account token, mounts only host `/proc/sys`, and receives
no Secret, PVC, identity state, or gateway credential. A terminal setup attempt
whose log proves the target path was absent before the write and whose live
host readback stayed `0` performed no drift injection: record and delete that
exact failed fixture before one corrected replacement. Only one successful
`0 -> 1` injection is permitted.

### D12 — Upgrade and rollback provenance (HELD-3 resolved)

**LOCKED (founder-approved 2026-08-30).** Every lifecycle-created Helm revision
is stamped with exact contract `tunnex-zero-touch/v1` in both the Helm history
description and a fixed live Deployment annotation. Upgrade requires the
currently deployed revision description and live annotation to match before
any reuse of values. Rollback requires the target history description to match
before mutation and verifies the live annotation plus normal readiness after
mutation. A missing, malformed, or conflicting marker refuses; neither path
reads Secret bodies or legacy Helm values. A legacy release needs a separate
explicit token-blind migration and is not silently adopted by this story.

Helm can roll a release back to any
positive revision. A revision created before this lifecycle contract may lack
Kubernetes mode, host preparation, real probes, immutable inputs, and external
one-time-Secret transport. Upgrade currently uses
`--reset-then-reuse-values`; on a legacy release that can carry a raw
`joinToken` into the new Secret manifest and Helm history again. Deployment
rollout plus Service ingress is therefore not enough evidence that either an
upgrade source or rollback target is customer-grade and token-blind.

Version-only age gates remain rejected because chart age is weaker than exact
lifecycle provenance. Silently upgrading from or rolling back to an unproven
revision remains forbidden.

#### D12a — Provenance of a rollback-created revision

**LOCKED (founder-approved 2026-08-30, direction A).** Helm `install` and `upgrade`
accept `--description`; `helm rollback` does not and writes its own
`Rollback to N` history description. Rewriting Helm storage would require
decoding a release body which can contain legacy values and Secret manifests,
violating D12's token-blind boundary.

The CLI accepts Helm's native `Rollback to N` only when a bounded, cycle-safe

#### D13a — Crash-consistent remint protocol

**LOCKED (founder-approved 2026-08-30, direction A).** The current token request and

#### D13i — Retained-state reuse-versus-purge fencing

**LOCKED (founder-approved 2026-08-30, direction A).** Reuse install and
`purge-state` share a provider-neutral Kubernetes Lease that serializes every
mutation of one retained PVC. The Lease is bound to the exact namespace,
release, claim name, and live PVC UID; its holder is an opaque operation UUID.
It is advisory only for this narrow retained-state boundary and does not replace
the D13h control-plane install epoch, abort ordering, or hard install deadline.

The Lease has a bounded lifetime and is renewed while Helm is running. A live
foreign holder refuses without mutation and is never deleted. A crashed holder
may be replaced only after expiry and a fresh exact reproof of the PVC binding
and operation preconditions; malformed, foreign, or differently bound Lease
objects refuse even when expired. Every create, renewal, takeover, and release
uses live UID/resourceVersion readback so stale holders cannot overwrite or
remove a successor's lock.

Reuse acquires the fence before its last retained-state read and before Helm.
It releases only after the exact claim is mounted by the ready release and the
post-install readback succeeds, or after a failure is freshly proven safe with
the release absent, the same PVC UID still present, and no live pod mounting
the claim. Ambiguous failures retain the fence until its bounded expiry.
`purge-state` acquires only after typed confirmation, then repeats release
absence, mount absence, exact PVC/provenance, and terminal control-plane claim
proofs under the fence before deleting the PVC by UID/resourceVersion. It
releases its own fence after a proved non-mutating failure or successful exact
deletion, and never removes a foreign live holder.

A point-in-time final check, delete preconditions on the PVC alone, or retrying
the check/delete sequence remains rejected: an existing-claim Helm install does
not mutate the PVC object, so UID/resourceVersion preconditions cannot detect a

### D14d — Tunnel ownership is a three-state machine, not boolean patches

| State | Proven fact | Allowed `Disconnect` behavior |
|---|---|---|
| `inactive` / helper `down` | no Tunnex tunnel or cleanup obligation remains | idempotent zero-wire success |
| `up` / helper `up` | the helper confirmed the tunnel and owner channel | send `tunnel_down`; only its success reaches `inactive` |
| `cleanup-required` / helper `failed` | partial/ambiguous bring-up, owner loss, or failed cleanup may have left kernel state or a kill-switch | always reconnect/send `tunnel_down`; stay failed and retryable until success |

The client enters provisional `cleanup-required` before sending `tunnel_up`.

successful response moves to `up`. Both `up` and `cleanup-required` send a real
down request. A down error never reconstructs an Up lifecycle or reinstalls
resolver state because platform teardown may already have removed the device
and routes before kill-switch cleanup failed. It remains cleanup-required;
successful helper cleanup alone clears cached address/routes/resolvers and
reaches inactive.

Helper `Supervisor.Down` mirrors that rule. Backend cleanup failure preserves
`StateFailed`, owner/retry eligibility, and the dead-man cleanup obligation;
the ordinary request path and dead-man path reach `StateDown` only after backend
cleanup succeeds. Startup `CleanStale` failure is the same obligation but keeps
its cleanup kind: later Disconnect/dead-man retries `CleanStale`, not a fresh
backend instance's potentially inert `Down`. No new Up is accepted from
`StateFailed`; cleanup must prove Down first. Loss of an inactive status/posture
socket remains a read failure, never a fabricated tunnel failure.

This reduction replaces resolver-rollback, active-generation, and zero-wire
special cases as independent authorities. The single ownership state decides
whether cleanup is owed; generation still rejects stale callbacks but cannot
erase that obligation.

### D14f — macOS host-network takeover is a journaled transaction

**LOCKED (2026-09-01, repeated-cleanup review reduction).** Full-tunnel PF and
DNS changes are not best-effort UI configuration; they are host networking
state that must survive helper failure. PF arming requires a successful
`pfctl -E`, a parseable exact enable-reference token, and durable atomic token
journaling. Failure to enable, identify, or persist that reference cannot
report the kill-switch armed; rollback flushes the anchor and releases the
exact in-memory token, and an incomplete rollback remains cleanup-required.
A split-tunnel Up first proves any stale full-tunnel PF/DNS state removed; a
cleanup refusal occurs before it creates a device or changes a route.

The PF journal is versioned and records the enable attempt's PID plus the exact
token when known. Cleanup reconciles it against `pfctl -s References`: an absent
token is already released; a present token is released exactly once and absence
is re-read before journal removal. If `pfctl -E` succeeds but its token output is
unparseable, the helper may use the captured child PID plus the pre-enable
reference snapshot **only inside that immediate `armPF` transaction**, before
the short-lived child identity can be recycled. Once that transaction returns,
PID-only state is never cleanup authority, even in the same long-lived helper:
the `pfctl` process has exited and the OS may reuse its PID for another enabler.
Deferred or restarted cleanup therefore reconciles only a durable exact token;
a PID-only record refuses Up/Down as explicit operator repair rather than
risking another process's reference. If kernel enable, exact token recovery, and
durable intent persistence all fail together, no userspace retry can truthfully
reconstruct that lost kernel identity.

Before the first `networksetup` mutation, the helper must read every target
service conclusively and atomically persist an exact DNS recovery journal. A
failed read or journal write is a pre-mutation refusal. A failed first or later
DNS mutation triggers restoration from that journal. If restoration is
incomplete, the journal is retained and the tunnel bring-up returns failure so
the Supervisor remains `cleanup-required`; a later Down or startup cleanup
retries the same journal. Only complete restoration removes it.

The backend never reports Up after an unproved PF enable or partial DNS apply,
never interprets a DNS read error as “automatic,” and never deletes the only
recovery evidence before the corresponding kernel/service state is restored.
Pinned WireGuard/control-plane host routes use their own phased durable
ownership journal. A pre-existing exact host route is borrowed without mutation
only when it already matches the required next hop; a conflicting route is a
pre-mutation refusal and is never deleted or replaced. A new route records
durable `intent` before `route add` and durable `owned` only after the add
succeeds. Restart cleanup deletes only an exact matching `owned` route. An
`intent` record is ambiguous after restart and remains operator-repair state;
same-process compensation may delete only the exact route it just proved it
added. Endpoint and control-plane roles may share one borrowed or owned route,
and dropping one role never removes or re-pins the other's route. Down and
startup cleanup delete every exact owned route idempotently and retain the
journal on any failure; route cleanup, DNS restoration, and PF release must all
succeed before Down is reported. Before PF, device, or route
mutation, full-tunnel Up also reads the exact endpoint, control-plane, and
per-family physical-default route facts. A successful route query with no
`gateway:` field is the only proof of an on-link destination; a command/read
failure is not collapsed into on-link. A typed no-route result is tolerated only
for a family unused by the current endpoints and is retained as unavailable, so
a later cross-family re-home refuses before its peer UAPI rather than skipping a
required pin. Deterministic tests cover PF enable/token/journal failures,
incomplete PF rollback and process-restart exact-token reconciliation, immediate
PID recovery plus deferred/restart PID-only refusal with no foreign release,
route-query failure versus proved on-link, foreign matching/conflicting routes,
intent/owned crash boundaries, same-host and shared-role route preservation,
DNS journal-write refusal, first- and
mid-apply failure, failed DNS rollback followed by successful retry, and the
ordinary success/Down path.

**Rejected alternative:** keep ignoring PF/DNS journal or mutation errors and
rely on `CleanStale`. `CleanStale` cannot release an unidentified PF reference

Down while leaving host networking state behind.

The control-plane rollout consumes that bundle only. It requires the operator

The mutating sequence reuses the host-upgrade safety order: verify the installed
Compose baseline, create and validate a PostgreSQL backup plus its existing

all six digest references and four exact chart archives, transactionally install
the bundle-owned Compose and digest pins, and run Compose with `--pull never`.
The rollout never performs a bare `compose pull`; postgres and redis retain

supported. If compensation itself cannot be proved, the refusal prints the

### D14l — Helper lifecycle is one fenced state machine

**LOCKED (2026-09-01, repeated-helper-fold tripwire; recommended A).** The
helper stops accumulating local concurrency exceptions. One app-lifetime model
owns Supervisor state, Server ownership, live backend mutation, and watchdog
self-uninstall:

| Axis | Values | Authority |
|---|---|---|
| terminal fence | `open` / irreversible `uninstalling` | Supervisor app lifetime |
| tunnel truth | `down` / `up` / `failed` | Supervisor after backend proof |
| cleanup kind | `none` / `live-or-partial backend` / `prior-process stale` | the transition that created the obligation |
| session identity | monotonic generation plus exact config identity | accepted Up/teardown transition |
| live mutation lease | read lease bound to one generation | AllowedIPs/gateway-peer update |

`Up` and `BeginUninstall` take the write side of one session barrier. A live
AllowedIPs, gateway-peer, or resolver-install update takes the read side **before**
reading state and holds it through its host mutation and session bookkeeping. An
exclusive live-mutation mutex inside that read lease serializes those update verbs,
so the later verb snapshots the state published by the earlier one. Down takes the
write side first and then the cleanup-attempt mutex; therefore it cannot begin backend
or resolver cleanup until every accepted live mutation has drained, and no old mutation
can land after Down publishes. Owner loss may still start promptly while an update is
resolving or applying, but every platform backend serializes FailClosed/update mutation
internally; most importantly, a replacement Up cannot enter the backend until every
lease from the prior session has drained. Thus an old delayed update either linearizes
before teardown or is refused before host mutation; it can never mutate a new device.
The existing Server lifecycle critical section still makes
Supervisor Up/Down and owner-pointer publication one ordered operation, and an
old owner close cannot detach a replacement.

A gateway-peer swap has one additional truth boundary: its WireGuard UAPI may
have changed the peer before a later PF or host-route step refuses, and even an
IpcSet error is not proof that the multi-line update applied nothing. Resolver,
key-validation, unsupported-mode, and already-down refusals occur before that
boundary and leave the session Up. Any apply/PF/route failure at or after the
boundary advances generation, clears the live config, and publishes retryable
`failed` / backend-cleanup-required. A proven live **split-tunnel** session then
fails static: its adapter and exact protected-prefix routes remain installed so
protected traffic cannot fall through the physical default, while all further
live mutation is refused until explicit or dead-man Down performs cleanup. A
full-tunnel session may close its adapter because the already-armed PF/WFP fence
still blocks physical egress. Mid-Up failures without a published live adapter
retain the ordinary cleanup/fail-closed path. It never leaves ordinary Up with
Supervisor naming the removed peer, and never calls closing an unfenced split
adapter fail-closed. A later Down owns the exact host-state cleanup; no
AllowedIPs update can run against the ambiguous peer in between.

`BeginUninstall` is an irreversible app-lifetime transition. It acquires the
write barrier, sets `uninstalling` and advances generation **before** cleanup,
then invokes the exact recorded cleanup kind. Every resolver request preserves an
explicit `install` versus `empty-cleanup` intent from the IPC envelope into the
Supervisor. A non-empty install requires exact `up` state and the current generation
under the session read barrier plus exclusive live-mutation mutex; `down` returns
`not_up`, `failed` returns `cleanup_required`, and `uninstalling` returns
`helper_uninstalling` before any filesystem/NRPT call. An empty cleanup remains
idempotently permitted in `up`, `failed`, or `down`, but it never substitutes for or
silently clears the Supervisor's terminal cleanup proof. The terminal uninstall path
continues to own its internal cleanup and refuses external host mutation. Thus two
authenticated full-sweep reconciles cannot overlap, and a request queued behind Down
or dead-man cleanup cannot recreate resolver state after tunnel absence was proved.
An empty-cleanup callback failure is itself partial host-cleanup truth: before returning
the exact error, the Supervisor advances generation, clears live config, records resolver
cleanup owed, sets immediate retry, and publishes `failed` even if it entered from clean
`down`. A replacement Up is then `cleanup_required`; the next Down or dead-man tick runs
the registered full-sweep cleanup and only proved success can republish `down`. A
successful empty cleanup while already Down remains an idempotent Down.
Owned-resolver cleanup is a first-class
retryable lifecycle obligation, not a fire-and-forget callback: startup installs
it before stale cleanup, and dead-man release, Down, startup SelfHeal, and
BeginUninstall publish `down` only after both backend and resolver absence are
proved. Filesystem/NRPT work runs outside the Supervisor mutex but inside the
session write barrier. A refusal retains `failed` plus the owed resolver cleanup,
and the next Down/BeginUninstall/dead-man tick retries immediately without a
fresh heartbeat window or admitting replacement Up.
From that instant every Up and live host mutation is refused with a typed static `helper_uninstalling` response;
Down/BeginUninstall remain retryable cleanup verbs. Backend cleanup failure
keeps `failed`, the terminal fence, recovery journal, service, and helper binary.
Only proved `down` permits the watchdog to remove PF configuration, WFP/service
registration, runtime recovery files, or the executable. If later service/file
removal fails, the watchdog enters terminal-removal mode and retries every tick
independent of app-presence debounce. An app/update reappearing cannot reverse
the Supervisor fence or suppress completion. The living terminal helper never
accepts a new tunnel. macOS and Windows use this identical Supervisor fence;
only their post-cleanup removal mechanics differ.

Every accepted Up, teardown start, owner loss, and terminal transition advances
generation. Blocking status reads and post-call bookkeeping recheck the exact
generation/config before publishing effects. A clean pre-arm refusal is also a
proof obligation, not merely an error code: no kernel enable reference, anchor
rule, interface/route/DNS mutation, **or recovery journal** may remain. In
particular, an atomic journal rename followed by directory-sync failure is
ambiguous publication; compensation must reconcile the file that actually
exists. `pf_arm_failed` is returned only after both host state and journal
absence are proved. Any residue or unprovable removal is `failed` /
cleanup-required. A captured `pfctl` PID is recovery evidence only inside the
immediate `armPF` transaction. After that transaction, including a delayed retry
in the same process, a PID-only journal remains operator-repair state because
the OS may already have reused the PID.

Dead-man backend release and its owned-resolver sweep are one write-side session
transaction. The Supervisor may drop its internal mutex around filesystem work,
but retains the session write barrier until the old resolver sweep completes;
replacement Up and resolver reconciliation cannot publish new host state that
the old sweep can then delete.

Full-tunnel host-route bookkeeping distinguishes exact endpoint and
control-plane roles from route ownership. Same-host/key failover preserves the
existing proved route byte-for-byte, failback to a control-plane-shared host
removes only the abandoned endpoint role, and an on-link/borrowed route is never
silently replaced with a stored default gateway. Durable route `intent` is not
ownership authority: only exact `owned` state permits later deletion.

A successful gateway lookup with no concrete next hop proves only that the
**current initial endpoint** is on-link; that endpoint-specific proof is not a
transferable physical default. A full-tunnel re-home to a different endpoint is
therefore refused with typed `endpoint_unresolved` whenever the captured
physical default for that address family has no concrete next hop. The refusal
precedes peer UAPI, PF reload, and route mutation, leaving the exact current Up
session intact. A same-host key or port change may keep using the current
endpoint-specific on-link proof and remains allowed.

Windows endpoint pins follow the same ownership law as Darwin. A foreign exact
route is never deleted/replaced, a matching route may be borrowed but is never
removed by Tunnex, and a new pin is durably journaled `intent` before a no-delete
AddRoute then promoted to exact `owned` state. CleanStale and Down delete only an
exact matching owned destination/LUID/next-hop, retain flags and journal on any
refusal, and never use ambiguous intent as deletion authority. The `%ProgramData%`
journal directory and file do not rely on inherited ACLs: before any read/write,
and again after atomic replacement, the helper verifies owner SYSTEM plus a
protected DACL granting full control only to SYSTEM and Builtin Administrators.
The journal directory is created atomically with that descriptor, and the temp
file is created inside that already-protected directory, proved non-reparse and
protected before its first write, then re-proved after the write-through replace.
A pre-existing directory or file whose owner/DACL was loose is never repaired
then trusted: it is repair-required with zero content read or route mutation.
Any reparse point, other ACE, untrusted owner, missing protection, or ACL
read/apply refusal blocks pin/cleanup; Users and Authenticated Users never
receive journal access.

An absent Windows endpoint journal and absent Tunnex journal directory are a proved
clean read and MUST NOT create `%ProgramData%\Tunnex` as a side effect. Terminal
uninstall removes only that exact directory after proving it is non-reparse,
SYSTEM-owned, protected with the exact SYSTEM/Administrators-only DACL, and empty.
Removal is non-recursive: a foreign entry, ownership/ACL mismatch, reparse point, or
remove refusal is surfaced and retains the terminal retry obligation. Ordinary
cleanup may remove the exact owned journal file but cannot broadly remove a directory.

Uninstall configuration edits have the same durability boundary as runtime
journals. If macOS atomically renames a `pf.conf` without the Tunnex anchor but
directory sync fails, a retry that observes the line already absent must still
sync `/etc` before deleting backup/service recovery evidence. Observing content
alone is not proof that the prior rename survived a crash.

The transition order is fixed:

| Request/event | Required order | Result |
|---|---|---|
| Up | write barrier → reject terminal/non-down → validate → advance generation → backend Up → publish config/state | `up`, clean typed refusal, or `failed` |
| live update | read barrier → capture exact up generation/config → exclusive mutation → backend mutation → exact-current bookkeeping; on a possibly-partial peer swap publish `failed`, preserving a live split adapter/routes or relying on the existing full-tunnel PF/WFP fence | old or current session only; never replacement; partial peer truth is retryable cleanup-required `failed` without split fall-through |
| Down | write barrier → cleanup-attempt mutex → mark teardown/generation → backend cleanup → owed resolver cleanup → publish only proved result | waits for accepted live mutations; `down` only when both surfaces are clean; otherwise retryable `failed` |
| owner loss | exact Server owner detach → generation advance → backend FailClosed | `failed`; no replacement owner affected |
| dead-man release | write barrier → exact backend cleanup → owed resolver cleanup → publish `down` → return exact joined cleanup result → release barrier | no replacement tunnel/resolver mutation can race the old sweep; refusal remains `failed`, retries immediately, and is logged rather than silently reduced to a boolean |
| startup SelfHeal | register resolver cleanup → write barrier → stale backend cleanup → resolver cleanup → serve only after proved `down` | stale resolver failure is fail-closed/retryable, never log-and-serve |
| self-uninstall | write barrier → terminal fence/generation → backend + resolver cleanup → terminal-removal retry loop | no removal or future Up before proved `down`; app reappearance cannot cancel retries |

Deterministic barriers cover delayed AllowedIPs and gateway-peer updates across
Down→Up, dead-man sweep versus replacement Up/resolver reconciliation, two
concurrent resolver desired sets, non-empty resolver install refusal after Down
and dead-man cleanup, idempotent empty cleanup while Down, resolver cleanup
failure/retry through
dead-man/Down/startup/uninstall, same-host control-plane/gateway route ownership
during re-home, foreign route refusal and intent/owned crash boundaries,
Up-versus-BeginUninstall in both orders, apply/PF/route failure after a gateway
swap with split fail-static and full-tunnel fence preservation,
terminal-removal failure followed by app reappearance, cleanup-refusal retry,
dead-man backend/resolver refusal diagnostic propagation followed by successful
retry, absent-journal read without directory creation, verified-empty terminal
directory removal and foreign/non-empty refusal, and journal
rename-success/directory-sync-failure. Darwin additionally proves that a
gatewayless initial endpoint cannot authorize a different failover endpoint:
the different-host attempt refuses before UAPI/PF/route effects while a
same-host peer change remains admissible.
Race tests cover all transitions; Darwin and Windows cross-compiles are
mandatory. The fold stops unless all of these invariants hold: no backend
mutation from generation A after backend Up for B, no ordinary Up after an
ambiguous/partial peer swap, no Up after the terminal fence, no service/runtime
deletion before cleanup proof, no stale owner or Stats effect on a replacement,
no clean refusal with a durable recovery artifact, and no platform
implementation that bypasses the common barrier. Windows terminal success also
requires proof that the exact owned journal directory is absent; it never performs
recursive or foreign cleanup.

**Rejected alternative:** add post-call generation checks, watchdog-local
booleans, or another Server-only mutex. A post-call check is too late to undo a
mutation of the replacement backend, a watchdog boolean cannot fence already
accepted IPC work, and independent locks recreate the owner/lifecycle split
that D14j already rejected.

### D14m — Terminal uninstall is durable across helper restart

**LOCKED (2026-09-01, restart-boundary P1; recommended A).** Terminal intent is
one common helper lifecycle law, not a process-local watchdog flag. Before
publishing `uninstalling` in memory or touching backend/resolver state, the
helper atomically publishes a versioned, secret-free terminal-intent marker and
proves both its contents and published namespace durable (file plus directory
sync on Darwin; flushed file plus `MOVEFILE_WRITE_THROUGH` on Windows). Windows stores the marker
as a separate exact non-reparse, SYSTEM-owned, protected
SYSTEM/Administrators-only `%ProgramData%\Tunnex-uninstall.intent` file, so the
existing `%ProgramData%\Tunnex` journal directory can be removed while terminal
intent remains restart-visible. Darwin uses an exact root-owned, non-symlink,
mode-restricted durable authority outside `/var/run`. A pre-existing loose,
foreign, malformed, or unverifiable authority is never repaired then trusted.
Failure before publication has zero terminal or host effect and is a visible
refusal; once publication becomes visible, neither platform returns from `Arm`
until directory durability is proved, so no Up-capable process can continue
beside inconclusive terminal evidence.

Startup checks that authority **before opening a listener or serving any IPC**.
A valid marker reconstructs the irreversible Supervisor fence, selects
prior-process stale cleanup, resumes backend/resolver and platform removal, and
never accepts Up. An invalid/unreadable marker fails closed without serving. The
marker remains through every cleanup, process crash, service-manager restart,
and removal retry; a restarted helper therefore converges toward removal rather
than reopening. It is removed only after the relevant restart authority is
proved absent. The trusted installed helper's offline finalizer then revalidates
the marker/path ownership, ACL or mode, non-reparse/non-symlink identity, and
exact service-manager absence; removes only exact allowlisted platform residue
and the now-verified-empty Windows journal directory while the marker remains;
then removes the marker durably as the terminal-state commit. It never removes a
broad parent such as `%ProgramData%` or `/Library/Application Support`, and no
recursive deletion is permitted.

Windows Add/Remove Programs and the bare-box script share one packaged path:
live installed `tunnex-helper.exe --uninstall-cleanup` sends additive typed
`begin_uninstall` over the existing caller-authenticated named pipe; the service
durably arms terminal intent, proves host cleanup, returns `down`, and answers a
second exact `down` status readback. Packaging then stops/deletes the SCM service
and confirms it absent. Only after that confirmation may the same trusted
installed binary run its offline finalizer; only finalizer success lets NSIS
delete helper/application files. Service absent plus a valid marker resumes at
the finalizer; service and marker both absent are idempotently clean only when
the exact authority directory is absent. Residue without a valid marker is
repair-required. Any refusal or inconclusive readback stops before the next
authority-destroying step and never claims uninstall success.

`begin_uninstall` has one stricter authorization rule than ordinary desktop
verbs. Path membership alone is insufficient because every authenticated user
can execute the installed helper binary from its trusted Program Files path and
thereby turn that binary into a terminal-uninstall confused deputy. The peer
must therefore be the exact installed helper executable **and** its process
token must be LocalSystem or an elevated member of Builtin Administrators. A
non-admin or unelevated installed-helper process is refused before durable
intent, Supervisor state, host cleanup, or SCM authority changes.

Darwin drag-to-Trash self-uninstall follows the same marker-first law. It arms
durable intent before Supervisor cleanup, retains the marker while removing the
PF anchor and the Up-capable helper's launchd restart authority, and hands off to
an exact root-owned copied finalizer under a separate launchd job that has no IPC
listener or tunnel verb. That repair-only job is installed and proved before the
Up-capable job is removed, retries until original launchd absence is exact, then
removes exact runtime/install residue and the marker. Only after terminal state
is absent does it remove its own plist and binary; if it crashes during that
last residue-only phase, its still-loaded KeepAlive job or its on-disk plist
resumes cleanup without ever reopening the helper. App reappearance cannot
cancel a marked terminal transition. Crash injection after marker rename,
directory sync, in-memory fence, host cleanup, response, finalizer handoff,
service stop/delete or launchd bootout, and before/after finalization must always
resume terminally and must never expose an Up-capable listener.

The finalizer must not create a last-instruction crash gap by deleting both its
plist and executable before arranging launchd removal. Before either finalizer
artifact is removed, it starts and proves an exact detached unload waiter whose
already-loaded image waits for both paths to become absent and then boots out
the repair-only label. A crash before the artifacts disappear leaves KeepAlive
or the plist able to restart cleanup; a crash after they disappear leaves the
proved waiter able to unload the in-memory job. No state crosses a point with
neither restart nor unload authority.

Every Darwin launchd-absence proof is exact, including the original helper and
the residue-only finalizer. `launchctl print system/<label>` proves absence only
when it returns the platform's service-not-found status 113 **and** its output
names that exact label as missing from the system domain. Exit 64, a different
nonzero status, empty/mismatched output, or any execution error is ambiguous and
therefore refuses or retries; it can never authorize marker, runtime, install,
plist, binary, or in-memory job removal.

The command carries no token, secret, alternate socket, arbitrary path, or
unauthenticated maintenance surface. Static packaging contracts prove the
shared script is staged, terminal proof precedes SCM mutation, offline
finalization follows confirmed SCM absence, every failure retains the last
remaining repair authority, and scripts perform no ProgramData deletion.
Cross-platform helper tests prove durable-before-memory ordering, clean
publication refusal, startup terminal reconstruction, cleanup/removal retry,
authenticated IPC allowlisting, exact response plus second readback, idempotent
absent state, post-fence and post-restart Up refusal, and secure exact finalizer
removal. Race tests and Darwin/Windows cross-compiles remain mandatory.

**Rejected alternatives:** retain a process-local fence, remove the marker when
host cleanup first reaches `down`, call ordinary `tunnel_down` or `--wfp-clean`,
stop/delete before durable intent, let scripts delete ProgramData, or let NSIS,
the bare script, and Darwin maintain independent state machines. Every one
admits either a restart-open window or deletion of the only repair authority.

### D14n — Desktop control-plane waits and identities fail closed

**LOCKED (founder-approved 2026-09-01; final managed-desktop review fold).** A
control-plane request may run while it owns the one managed-lifecycle FIFO turn.

15-second `AbortController` deadline. Expiry returns only the static

### D14o — Managed desktop enrollment has a durable local identity before create

**LOCKED (founder-approved 2026-09-01; recommended recovery package).** A
managed desktop never asks the control plane to generate the WireGuard private
key. MAIN generates one X25519/WireGuard keypair locally, proves that its raw
32-byte private value derives the advertised raw 32-byte public value, and
durably stores a versioned pre-create anchor before the first device POST. The
anchor is separate from the final tunnel-config store, origin-keyed, protected
by Electron `safeStorage`, mode `0600`, and atomically published from a
same-directory temporary file only after file and namespace durability plus an
exact decrypted readback. The existing explicit insecure-storage opt-out is the
only permitted plaintext exception. If anchor persistence or proof is
inconclusive, no POST occurs.

**Portable durability amendment (founder-approved 2026-09-01).** Publication
uses the same ordered proof on every client platform: sync the completed
same-directory temporary file, atomically rename it, reopen and sync the final
file, then perform the exact decrypted readback before any POST or anchor clear.
POSIX additionally requires the parent-directory sync after both rename and
unlink. Node/libuv may report Windows directory `fsync` itself as unsupported;
only the explicitly classified win32 `fsync` `EPERM`/`EINVAL` result is a
permitted bounded fallback after the final-file sync. The same error on POSIX,
an open failure, an unclassified error, a final-file sync failure, or a readback
failure is an inconclusive publication and refuses. Error surfaces remain
static and never include a path, ciphertext, private key, or serialized anchor.

**Recovery-read and explicit-abandon amendment (founder-approved 2026-09-01).**
A visible final pathname is not itself durability proof. Every read that may
return an enrollment anchor or final managed tunnel record first reopens and
syncs that exact published file, applies the same platform namespace rule above,
then reads the synchronized encrypted bytes and completes the store's exact
decrypt/shape/key-derivation proof. This read-side reproof is also the recovery
path for a prior rename that became visible before file or directory sync
returned. Until it succeeds, a visible anchor cannot authorize a roster read,
POST, mode call, or helper action, and a visible final record cannot authorize
anchor clear or helper use. A persistent reproof refusal is surfaced only as the
existing static corrupt-store error; paths, ciphertext, private keys, anchors,
and underlying filesystem diagnostics remain private. True absence and the
split/full mode state machine otherwise retain their existing semantics.

An unresolved anchor also has one explicit customer-owned terminal transition:
**Abandon enrollment and re-enroll**. The existing managed lifecycle FIFO first
captures one fixed credential lease and proves the exact normalized origin,
authenticated user, live organization membership, and credential fingerprint
against the durably re-read anchor. The UI supplies an explicit confirmation but
receives only the boolean recovery state; no anchor, public/private key, token,
fingerprint, node, or device identifier crosses preload. MAIN obtains a fresh,
complete current-user-visible roster for the anchored public key before
quiescing, then proves the privileged helper exactly `down` and advances the
lease before any destructive step. It rechecks the same durable anchor and lease
and obtains a second fresh current-user-visible roster proof.

If that proof contains one sole same-owner live or pending row, MAIN revokes that
exact row and requires a further fresh current-user-visible roster read to prove
it terminal or absent before clearing. Zero visible matches, or visible foreign,
multiple, or terminal matches, may clear only on that fresh bounded proof plus
the explicit user confirmation; they never authorize revocation of a guessed
row. This read does not claim access to soft-deleted or otherwise hidden server
history. That hidden history remains protected by the server's organization-
locked same-public-key replay guard, while the post-clear Connect generates a
fresh key that cannot revive or collide with a retired or foreign old key. A
different origin, user, organization, or fingerprint; lost membership;
malformed or unavailable roster; helper state other than exact `down`;
lease/anchor drift; or clear-durability refusal performs zero clear and mints no
replacement key. Only after durable anchor absence may a later Connect generate
a fresh keypair.

While such an anchor belongs to the exact signed-in user, organization selection
projects its organization as the enrollment lock even when no final tunnel
record exists, and selection mutation is refused. A foreign-user anchor is never
projected as that user's enrollment or preference. This makes response-loss and
conflict recovery visible without exposing recovery material and prevents a
different organization choice from turning the next Connect into an opaque
local conflict.

The desktop process itself is a required outer enrollment lock. MAIN acquires
Electron's cross-process single-instance lock before `whenReady`, store
construction, IPC registration, helper access, API construction, or window
creation. A losing process exits with zero storage, control-plane, helper, IPC,
or window effects. The primary handles `second-instance` only by restoring and
focusing its existing client window; the notification carries no credential,
anchor, key, organization, or device fact. This prevents two desktop processes
from publishing different locally generated keys through independent atomic
renames and POSTing two otherwise valid enrollments that the server's same-key
replay guard cannot converge.

The anchor binds the normalized control-plane origin, selected organization,
authenticated human owner, credential fingerprint, selected gateway, stable
device name/platform, original create mode, and local public/private keypair.
The bearer itself is never stored in it. Every in-process operation still uses
the exact D14c/D14n lifecycle lease. A replacement credential cannot resume the
anchor blindly: after restart it may be rebound only after the new fixed lease
proves the same origin, exact user, and live membership in the anchored
organization. A different user, organization, or origin is a static refusal.
No anchor or private-key field crosses preload, renderer, logs, errors, argv, or
the control-plane request.

Creation sends the existing `CreateDeviceRequest.public_key` with explicit
managed provisioning. A client-key response must contain only public device
facts; a returned `private_key` or `config` is invalid. The final mutable facts
come from the existing mode endpoint, whose same-value request is an idempotent
read-through: it returns current address, dial peer/endpoint, routes, DNS, MTU,
keepalive, status, and public identity without another update, audit, or push.
The client combines those facts with its locally held private key, validates the
complete helper-facing config, atomically publishes the final tunnel record
while the anchor still exists, and only then clears the anchor. A pending device
is published with `pending=true` before the ordinary stable approval gate; it
never arms the helper early.

Client-only list-then-retry is insufficient. The current database index is
partial to `status = 'active'` and scoped to one node, so two pending creates can
reuse one public key, while a response-loss retry can race the first commit or a
subsequent revoke/removal. No new endpoint, request field, response field, or
database migration is needed to close that window. Ordinary managed-human
client-key creates already take the organization advisory lock. Under that same
lock, before cap or address allocation, the service reads the complete
organization history for the submitted non-empty public key, including pending,
revoked, and soft-deleted rows:

- zero rows continues the ordinary create;
- exactly one non-deleted `active` or `pending` WireGuard-human row owned by the
  requested user is the idempotent replay of that identity: return its exact
  UUID/allocation and current status with no cap spend, address allocation,
  create audit, or gateway push;
- a foreign owner, non-human/non-WireGuard row, revoked/deleted history, or more
  than one match is a typed `device_key_recovery_conflict` refusal with no
  mutation.

The organization lock serializes two different-owner or different-node creates
that carry the same public key. Full history makes a revoked credential
one-way: an explicit re-enrollment generates a new key rather than silently
reviving one an administrator retired. Browser/server-generated, static export,
OpenVPN, and agent-bootstrap paths remain byte-for-byte on their existing
semantics. A live recovered device may have been legitimately re-homed after
the original request; the client accepts that only when the organization roster
contains one exact public-key row with the anchored owner, then obtains the
current node/dial facts from the mode response. Multiple or foreign matches are
never guessed away.

The durable states and their sole authorities are:

| State | Durable facts | Permitted next action |
|---|---|---|
| absent | no final record, no anchor | resolve org/node, generate key, publish anchor |
| anchored | exact local identity and create intent, no bound UUID | full-roster public-key recovery; idempotent same-key POST only on zero matches |
| bound | anchor plus exact server device UUID | repeat exact identity proof and idempotent mode read-through |
| published | final encrypted tunnel record; anchor may still exist | exact local/private-key-derived comparison, then anchor clear |
| pending | published final record with `pending=true` | approval monitor only; no helper Up |
| conflict | anchor plus foreign/ambiguous/retired proof | no automatic POST, clear, key change, or helper mutation; explicit re-enrollment owns a new key |
| corrupt | anchor or final store cannot be strictly read | no network or overwrite; retain every recoverable byte for explicit repair |

Crash recovery is deterministic at every boundary:

| Crash/fault boundary | Recovery rule |
|---|---|
| before anchor durability | no server effect; a later attempt starts fresh |
| anchor temp write, sync, rename, namespace sync, encryption, or readback | no POST unless the exact anchor is proved durable |
| after anchor, before/during POST, lost/malformed `201`, or response timeout | retain the same key; list every row, then recover or use the server's idempotent replay guard |
| after response/list match, before UUID bind | repeat the public-key scan and bind the same sole row |
| after UUID bind, during mode update, or after a lost mode response | repeat the same-value mode request; no duplicate audit/push |
| final temp write/rename/sync ambiguity | anchor remains; exact final readback decides absent versus byte-valid published state |
| final publish before anchor clear, or clear durability failure | derive the public key from the final private key, compare origin/org/owner/device UUID, then retry only the anchor clear |
| final-store corruption or final/anchor mismatch | zero API/helper action and zero overwrite; never treat corruption as absence |
| device cap, unavailable gateway, or transient control-plane refusal | retain the anchor and retry the same identity after the condition clears |
| pending approval, rejection, revocation, foreign owner, or duplicate history | pending follows the approval state machine; every terminal/ambiguous case blocks automatic re-enrollment |

The raw-key choice is measured rather than assumed: Node's X25519 PKCS8/SPKI
wrappers preserve WireGuard's standard-base64 32-byte private/public values, an
independent Go `crypto/ecdh` derivation matches generated Node pairs, and the
RFC 7748 private vector `77076d...2c2a` derives public
`8520f0...4e6a`. Tests preserve that golden vector plus crash injection at every
storage/request boundary, active and pending response-loss replay, concurrent
same-key creates, foreign/multiple/retired history, cap-before-replay ordering,
gateway/mode drift, credential replacement, pending approval, corrupt final
storage, and the renderer/log secret boundary.

**Rejected alternatives:** keep the server-generated one-time private key and
attempt to re-fetch it; store a private key or encrypted response server-side;
silently mint a new key after a timeout; trust list absence without a locked
same-key replay guard; depend on the active-only index; add a permanent
idempotency table/API token; choose the first matching row; clear a corrupt
store; or let a new login, organization selection, or gateway choice overwrite
an unresolved identity.

### D14p — Private candidate target and fresh-store cutover are one proved transaction

**LOCKED (founder-approved 2026-09-01; final live-rollout safety fold).** A
private candidate may touch Azure only after the operator supplies three
independent, non-secret expectations: the canonical tenant UUID, canonical
subscription UUID, and complete canonical ACR resource ID. The ACR ID must bind
that subscription and the registry name supplied separately. Immediately after
managed-identity login, before an image build, push, registry login, backup,
store preparation, installed-file write, or restart, the publisher and rollout
read back the active account tenant/subscription and the ACR's complete resource
ID plus login server. Every byte must equal the expectation. The publication
record binds all three Azure identities, and rollout requires the operator to
repeat them rather than treating the bundle as authorization. A wrong tenant,
subscription, resource ID, or registry refuses with zero registry, store,
deployment, or runtime mutation.

The ordinary existing-store upgrade remains the default when no fresh-store
arguments are present. The disposable S20.5 walk adds one explicit paired mode:
a safe PostgreSQL database name plus a canonical Redis logical-database selector.
One without the other refuses. Names are bounded lowercase PostgreSQL identifiers;
selectors are bounded by the configured Redis logical-database range; both must
differ from the current stores. No URL, password, token, or other credential is
accepted in argv. Fresh mode is deliberately limited to the bundled Compose
PostgreSQL and Redis authorities so the script can prove which stores it owns.

| State | Authority | Permitted transition and proof |
|---|---|---|
| `target_unverified` | operator inputs plus installed environment | parse only non-secret store identities; prove current API identity matches the bundled database and Redis selector |
| `boundary_verified` | managed-identity account and ACR readback | exact tenant, subscription, ACR resource ID, and login server match before any external or store mutation |
| `baseline_backed_up` | current database plus current API | dump the exact named current database; bind its digest and schema to the current control-plane key; run preflight against that same live store |
| `fresh_store_prepared` | bundled PostgreSQL/Redis | target database is absent and created once, or exists with zero user relations; target Redis DB has zero keys; old database OID/schema and Redis key count are recorded and never flushed, dropped, restored, or migrated |
| `installed_pair_backed_up` | exact installed `.env` and Compose bytes | retain byte-identical recovery copies before either installed-file move |
| `mutation_started` | one rollout process | install both files, restart with `--pull never`, and let the candidate migrate only the fresh target in fresh mode |
| `healthy` | runtime and store readback | exact candidate images, API/public health, exact API store identity, expected clean schema on the selected target, and unchanged old-store identity all pass |
| `baseline_restored` | one automatic compensation seam | after any post-restart failure, restore both baseline files, restart the exact baseline images/stores with `--pull never`, and prove baseline health plus store identity before returning the original failure |

Fresh preparation is retry-safe: an absent database may be created, an already
empty database may be reused, and any non-empty database or Redis DB refuses.
The failed fresh database/Redis selector is retained as evidence; rollback never
drops, flushes, rewrites, or restores it. Old stores remain the rollback
authority. The dump command, backup manifest, preflight, API identity proof, and
schema readback must all name the same current or selected database; a bundled
PostgreSQL dump may never stand in for an unrelated `DATABASE_URL`.

| Failure boundary | Mandatory result |
|---|---|
| before fresh preparation | no store or runtime mutation; private authentication state is removed |
| after database creation but before installed files | old runtime/stores remain active; retain the empty fresh target and verified recovery evidence |
| either installed-file move | restore and byte-verify both baseline files before any restart |
| `compose up`, dependency, health, image, API-store, or schema readback | automatically restore both files, restart exact baseline images against exact old stores, and prove internal/public health plus old-store identity |
| automatic compensation cannot be proved | return failure, name only the bounded non-secret recovery paths/hashes and failed state, and never claim the walk eligible; no hidden manual repair earns leg credit |

Temporary Azure/registry credentials retain D14k's isolated-store and cleanup
rules. Tests name explicit Tunnex and wrong-Bolster fixtures, prove each identity
mismatch occurs before any build/push/backup/fresh-store/installed-file/runtime
command, cover absent and empty targets, refuse non-empty targets, prove fresh
migration and automatic baseline recovery, and scan every output/artifact for
secret sentinels.

**Rejected alternatives:** rely on ACR's globally unique login server; trust the
bundle's Azure target without a separately repeated rollout expectation; switch
`DATABASE_URL` manually; reuse Redis DB 0 and flush it; dump whichever bundled
database happens to be named while the API uses another; delete a failed fresh
target; print recovery credentials; or report a backup path and leave a failed
candidate running for an operator to repair.

#### D14p review folds — exact store, ownership, crash, and input authority

**LOCKED (2026-09-01, founder standing approval; independent-review folds).**
The private rollout's safety boundary is reduced to four additional invariants.

1. **The running API, dump, preflight, schema readback, and rollback must name the
   same stores in both modes.** Before backup, ordinary/default mode now applies
   the same effective-store proof as fresh mode: `POSTGRES_DB`, `DATABASE_URL`,
   the running API's effective database, `REDIS_URL`, and the running API's
   effective Redis selector must all identify the bundled authorities. An
   external URL, a `TUNNEX_DATABASE_URL`/`TUNNEX_REDIS_URL` override, or any
   mismatch is unsupported by this private walk helper and refuses before dump,
   pull, fresh preparation, installed-file mutation, or restart. The dump names
   the proved current database explicitly, its manifest schema must equal that
   database's schema, and default-mode schema readback names that same database.
   This refusal is narrower than product support for customer-managed stores: it
   records that this bounded helper has no credential-safe external-store backup
   authority and may never substitute its bundled dump for one.

2. **The deployment lock has kernel ownership, not pathname ownership.** One
   persistent regular lock file in the deployment directory is opened and held
   with an exclusive non-blocking `flock` for the whole apply transaction. The
   inode is never removed by cleanup; closing the owning descriptor releases the
   lock automatically on normal exit, signal, or process death. A contender
   that did not acquire the lock cannot release or unlink the owner's lock.

3. **Installed-pair mutation has durable intent and restart recovery.** After the
   exact database/manifest/environment/Compose recovery artifacts and baseline
   runtime/store identity are durably written, but before the first installed
   file rename, one atomically replaced and directory-synced transaction journal
   records only bounded non-secret recovery coordinates, hashes, node
   enablement, baseline image identities, and store selectors. `mutation_started`
   and in-memory cleanup ownership advance before that first rename. `INT`/`TERM`
   use the same compensation seam immediately; `SIGKILL`, host restart, or a
   second-file/restart crash leaves the journal. The next authenticated apply,
   while holding the deployment lock, must restore and byte-prove the exact
   environment/Compose pair, restart with `--pull never`, prove baseline images,
   health, and effective old-store selection (plus unchanged old-store identity
   in fresh mode), then durably remove the journal before beginning a new
   transaction. A malformed journal, missing/inexact recovery artifact, failed
   restore, or ambiguous journal removal refuses and remains retryable; success
   never clears intent before all candidate readbacks pass.

4. **The consumed bundle is one private snapshot.** The supplied directory is
   copied into the rollout's mode-restricted work directory before qualification.
   Exact tree-kind, file/directory set, checksum-ledger, document, helper-byte,
   and cross-binding validation runs against that snapshot, and every later
   Compose copy, registry coordinate, chart comparison, image pin, and runtime
   readback uses only the snapshot. Changes to the caller-owned source directory
   after snapshot creation therefore cannot alter the qualified transaction.

Required regressions hold one rollout lock while a contender refuses without
releasing it; kill the process after the first installed-file rename and after
candidate restart, then prove next-run baseline recovery; refuse a default API
whose effective database differs from the bundled dump authority before backup;
and mutate the caller bundle after snapshot qualification while proving the
installed and read-back bytes remain those of the private snapshot.
