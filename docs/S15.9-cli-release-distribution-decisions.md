# S15.9 — CLI release distribution decisions

## Scope

Publish the existing Linux Tunnex CLI as a verifiable release artifact and make
the public download page expose only artifacts that are actually present on the
same immutable tagged release. This story also carries the approved desktop
download-page layout already previewed locally.

## Evidence at entry

- `apps/cli/cmd/tunnex/main.go` implements login (including device-code login),
  device creation, and `wg-quick` up/down.
- Tagged releases currently attach macOS and Windows desktop installers, but do
  not build or attach a Linux CLI binary.
- The public website's `dl.tunnex.io/latest/tnx-linux-amd64` link is not backed
  by the tagged-release provenance contract and must not be presented as a
  verified download path.

## Decisions

### D1 — Delivery channel: locked

The CLI ships as two tag-bound, `CGO_ENABLED=0` Linux binaries:

- `tnx-linux-amd64`
- `tnx-linux-arm64`

The release job computes and attaches `Tunnex-CLI-SHA256SUMS` from those exact
bytes. The page obtains the URLs and checksum link from the existing release
metadata endpoint; it never constructs a `latest` URL or guesses an asset
name. The existing desktop checksum asset remains unchanged.

### D2 — Release provenance: locked

The CLI build runs on every PR as a compilation proof and uploads its artifact
on tags. Release attachment waits for the verified build artifact from the same
workflow run. A tag is the immutable source of truth for version, asset URL,
and checksum; a mutable bucket alias is rejected.

### D3 — Website availability: locked

The desktop page keeps the approved Tunnex card layout. It adds a Linux CLI
setup panel for advanced/headless use, but enables its architecture download
controls only when both Linux assets and the CLI checksum asset are present on
the selected tagged release. Missing/incomplete metadata is an honest
unavailable state, not a broken external link.

### D4 — CLI semantics: locked

The page documents the existing CLI only: login, browserless device-code login,
device creation, and `tunnex up/down`. It does not claim Homebrew, a desktop
replacement, silent update, or an approval-policy bypass. The server remains
the authority for credential validity, device approval, limits, and revocation.

### D5 — Package-manager distribution: deferred

Homebrew is deferred until a signed/notarized macOS package and a first-party
cask release process exist. This story must not create an unsigned cask or
advertise an unimplemented install path.

## Acceptance checks

1. Both Linux CLI architectures compile on the CI Ubuntu runner.
2. A tagged release attaches both binaries and their checksum file, derived in
   the same workflow from the downloaded artifacts.
3. The website consumes only complete tag-bound CLI metadata and exposes no
   `latest` download URL.
4. Existing macOS and Windows release assets and their checksum contract stay
   intact.
