## Registered by the gateway-revoke fix (2026-08-07) — NOT resolved

⛔ **1. A REAL DELETE FOR A GATEWAY IS ITS OWN STORY.** There is no `DELETE FROM nodes` anywhere — no API
operation, no CLI verb, no service method. Revoke is the only retirement and the row is permanent.

⚠ **And the FK picture says why a delete endpoint cannot be written casually.** Measured live:

| table | ON DELETE |
|---|---|
| `devices` | **CASCADE** |
| `node_peer_status` | CASCADE |
| `ovpn_server_certs` | CASCADE |
| `node_join_tokens` | **NO ACTION** |

⛔ So a delete written without ruling the cascade first is **a data-loss verb wearing a tidy-up name**: it
silently destroys every device homed on that gateway, rows and pool addresses together. And a leftover
join token blocks the delete outright, so the naive version fails on exactly the gateways that were
enrolled most recently.

⛔ **2. WHAT A REVOKED GATEWAY STILL HOLDS — the retention picture, unmeasured.** Peer slot, pool address,
cert serial, site links. The FK picture above is not the same question: FKs say what a DELETE would
cascade, retention says what a REVOKE leaves behind and for how long.

⚠ **Registered rather than guessed.** Whether a revoked gateway keeps consuming an address-pool slot
changes what "revoke to free a slot" actually frees, and that answer belongs in a measurement, not in a
sentence written to make this note complete.
