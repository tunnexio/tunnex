This walk proves that a clean cluster can install, operate, upgrade, recover,
and run two independent HA gateways without a walk-time product patch or
manual infrastructure repair. Unit and render tests are substitutes only; they
do not satisfy this wire proof.

This S20.5 walk does not claim ordinary node-reboot self-heal when a committed
hostPath journal survives but kernel-only state disappears; that lifecycle is
named and deferred to S20.6. Manager/container restarts, Pod rescheduling, and
the recorded pre-walk disposable provider reset remain in scope.

Create `walk-artifacts/S20.5/` at the start of the live session. Store redacted
command output and screenshots there as each leg runs. Never save a join token,
machine token, private key, certificate body, kubeconfig, or service-account
token.

## Disqualifying actions

Any of the following makes the affected leg **INCONCLUSIVE**:

- `kubectl edit` or an ad-hoc patch of a Secret, PVC, Deployment, CNI object,
  `ip-masq-agent`, or chart-owned object;
- a manual host `sysctl`, nftables, route, WireGuard, or `/dev/net/tun` repair
  (Leg 5's exact one-shot D10c `wg0` drift fixture is failure injection, never
  a repair);
- a rollout restart used as a remedy rather than the lifecycle operation under
  test;
- copying a raw token into Helm values, argv, a values file, a log, or an
  evidence artifact; or
- SCP/source hot-patching a running control plane, node, CLI, or chart.

Read-only `kubectl get/describe/logs`, nft listing/counters, and API reads are
allowed as evidence.

One narrow Deployment mutation is allowed: Leg 9 may use the Kubernetes
`scale` subresource on the exact A or B gateway Deployment to inject a sustained
failure (`1 → 0`) and restore that same connector (`0 → 1`). It is never allowed
as an install, readiness, or recovery remedy; no Deployment template, Helm
value, pool role, fence, or promotion may be edited with it.

One narrow host fault injection is allowed by D10c in Leg 5. After recording
the exact manager-owned `wg0` alias/ifindex and active heartbeat, create one
short-lived privileged Pod on that same disposable node. Its only host mount is
`/proc/sys`, its only mutation is writing `1` to
`/host/proc/sys/net/ipv4/conf/wg0/rp_filter`, and it exits immediately. Record
that injected readback, then prove the existing manager returns it to `0`
without another mutation. Delete only the completed fixture Pod afterward. It
must use the candidate's digest-pinned node image and receive no Kubernetes
credential, identity state, network credential, or gateway Secret.
The fixture sets `hostNetwork: true` solely so `/proc/sys/net` resolves in the
host network namespace that owns `wg0`; it automounts no service-account token.
A failed setup Pod may be replaced only when its log proves the target path was
absent before any write and a live host readback proves the value remained `0`.

## Leg 0 — provenance and clean baseline

If an earlier candidate left the exact D11a v1 failed-create shape — a durable
`preparing` journal with no ifindex plus an alias-empty final `wg0` — first
capture that redacted refusal, wait for the failed atomic Helm install to leave
no release/workload, and perform a provider-managed full-node reimage or
replacement. Record the exact provider operation and instance identity; for a
replacement also record the old and new Kubernetes node UIDs or provider IDs.
Prove the reset node has neither the node-local journal, final `wg0`, nor a
staged Tunnex link. This is pre-walk fixture reset, not a passed
product-recovery leg. Do not set an alias, delete a link or journal, edit a PVC,
or repair the old node in place.

Record:

```bash
git rev-parse HEAD
tunnex version
helm version --short
kubectl version --client
kubectl config current-context
kubectl -n tunnex get secret,pvc,deploy,svc 2>&1 || true
```

For a private pre-release qualification, also verify the local candidate bundle
before its separately authorized private-registry publication:

```bash
(cd "$CANDIDATE_DIR" && sha256sum -c SHA256SUMS)
jq '{candidate_version,source,cli,charts,images}' \
  "$CANDIDATE_DIR/candidate-manifest.json"
```

Record the separate node-image build's exact `VERSION` input and prove it equals
the manifest candidate version. The packager accepts an already-built digest
and does not inspect its embedded version, so this build record is required
evidence rather than a property inferred from the manifest.

Pass only when either the public release or the private qualification manifest
binds the committed source SHA, CLI, all four charts, and every runtime image to
one version; the private candidate scalar is no longer than the 50-character
`agent_version` API limit and its 32-hex source abbreviation matches the full
manifest `source.sha`; every selected runtime image is digest-pinned; a private
OCI pull reproduces the recorded chart checksum; and no old A/B gateway state
is present. The full manifest source SHA, never the abbreviated version, is the
provenance authority. The private path is walk evidence, not a customer release
or support claim. A retained claim intended for the later reuse leg must be
absent now.

## Leg 1 — redacted plan, no mutation

Run `tunnex k8s plan` for gateway A. Capture the plan and SHA-256 digest. Verify
that it contains no token and that no Kubernetes object was created.

## Leg 2 — one-command gateway A enrollment

Run `tunnex k8s install ... --yes` once. Capture the CLI result, Deployment,
pod/init status, Service status, PVC identity, agent connection, `/readyz`, and
absence of the consumed bootstrap Secret. Prove the Deployment has no
`TUNNEX_AGENT_VERSION` override and the control plane's exact `agent_version`
readback equals the manifest candidate version; a 400 enrollment refusal or
different readback fails the candidate rather than authorizing an API-limit or
runtime override workaround. Capture redacted host-posture journal/log readback
proving that the candidate journal's `planned` phase (schema 3 for the AWS
continuation, preserving v2 staged-link semantics) was durable before link creation, the uniquely named
staging link was created and marked, the same positive ifindex was atomically
renamed to final `wg0`, and phase `committed` preceded the active heartbeat.
Final kernel readback must show name `wg0`, kind `wireguard`, the exact Tunnex
alias and recorded ifindex, with no transaction's staging link remaining.

Pass only if host posture and every observed registered masquerade mechanism
(IP-MASQ-AGENT and/or AWS SNAT) were reconciled without another mutation command.
For the AWS continuation, prove the durable AWS receipt and the exact correlated
manager authority before gateway CNI mutation; absent IP-MASQ alone is not a
failure when the observed AWS mechanism is ready. An alias-empty final `wg0`, simultaneous
staging/final links, a phase skip/regression, identity mismatch, or readiness
before `committed` fails the leg.

## Leg 4 — cluster, pool, HA, and private Service

In the dashboard, register the cluster, select both connectors, create the
pool, enable HA, expose one private Service, and grant the test user. From the
desktop client, record the Service FQDN/VIP and repeated successful responses.

## Leg 5 — persistence and controller self-heal

Delete/reschedule each gateway pod sequentially. Prove node ID, certificate,
WireGuard public key, claim and client access are preserved. Set the test node
to strict `rp_filter` only through D10c's exact one-shot fixture and prove the
singleton manager self-heals the exact owned `wg0` value. Let the CNI
controller rewrite its managed masquerade chain through the environment's
normal controller path; prove the product converges both without a repair
command. If no normal controller rewrite occurs during this disposable walk,
that CNI sub-proof remains deferred rather than authorizing a patch or manual
nft mutation.

## Leg 6 — immutable upgrade and Helm rollback

Upgrade A through `tunnex k8s upgrade` to a digest-pinned image from the same
verified private candidate (pre-release qualification) or public release, then
rollback to the named Helm revision. Capture release history, image digest,
identity before/after, readiness, and uninterrupted private-Service access.

## Leg 7 — retained uninstall and reuse

Uninstall B. Prove its Deployment and Service are gone but its claim remains.
Reinstall with `--mode reuse --existing-claim ...`; prove no join token was
minted and the same identity and access return.

## Leg 7a — interrupted bootstrap, expiry recovery, and typed abort

Use a disposable third release and only lifecycle inputs to create a controlled
pre-enrollment failure: select a syntactically valid gateway node label that no
node has and use a short Helm timeout. Prove the atomic install leaves no Helm
release or Deployment, retains only the exact token-blind lifecycle anchor,
immutable bootstrap Secret metadata, and any Tunnex-owned PVC, and prints no
token.

For one claim, run `tunnex k8s abort-install` with the exact release, claim UUID,
and typed confirmation. Prove the control-plane claim is aborted, an exact
partial identity is revoked if present, the owned Secret and anchor disappear,
and the PVC is retained for the separate `purge-state` decision. No `kubectl
delete` is allowed.

For a fresh disposable claim, repeat the controlled failure and let the normal
token TTL elapse without editing any object or database row. Retry through
`tunnex k8s install` with valid gateway placement. Prove the existing anchor
drives one CAS remint/redelivery generation, the old immutable Secret identity
cannot be reused, exactly one node identity enrolls, readiness succeeds, and
the consumed Secret plus anchor are removed. Capture only claim, request,
generation, UID/resourceVersion, state, and audit fingerprint metadata; never
the raw token or sealed response.

## Leg 8 — GitOps chart and real reconciliation

Install the exact `tunnex-operator-crds` OCI chart from the same verified
private candidate (pre-release qualification) or public release first and wait
for all three CRDs to be Established, then install the version-matched
`tunnex-operator` from an external machine credential Secret with its manifest
image digest. Apply one `TunnexCluster` CR with an explicit valid
provider/platform pair. Prove Ready=True, derived control-plane ID, dashboard
GitOps ownership, operator health/readiness probes, and no data-plane or
cluster-admin RBAC.

In disposable clusters, exercise every live `lookup` branch below. Recreate the
disposable cluster (or restore its clean snapshot) before each refusal case so
one branch cannot lend ownership annotations to another. Record the CRD UID,
resourceVersion, annotations, normalized spec hash, Helm output, and Helm
release state before and after each command.

| Existing CRD fixture | Expected live result |
|---|---|
| No CRD | Fresh install succeeds and all three CRDs become Established |
| Owner is the same `tunnex-operator-crds` release | A repeat upgrade succeeds |
| Owner is the legacy `tunnex-operator` release in `tunnex-system` | `--take-ownership` succeeds |
| No Helm owner; all three specs are exact raw Tunnex legacy manifests | `--take-ownership` succeeds and records the new owner |
| No Helm owner; one same-name spec has any added, removed, or changed field | Refused as `not an approved Tunnex legacy schema`; UID/resourceVersion/spec and Helm state stay unchanged |
| Any other Helm release owner, or a Helm owner from another namespace | Refused as an ownership takeover; UID/resourceVersion/spec and Helm state stay unchanged |
| Schema-generation annotation is newer than the chart | Refused as a downgrade; UID/resourceVersion/spec and Helm state stay unchanged |

For the ownerless success fixture, apply the exact historical raw manifests at
their recorded content tips (`025368ab` for all three initial CRDs, or
`1160009` for the connector-aware `TunnexCluster`) and first prove both Helm
owner annotations are absent. For the unknown-ownerless refusal fixture, change
one copied schema field before applying it; do not patch a real customer CRD.
The legacy-owner and unexpected-owner annotations are test-fixture setup only,
never an installation remedy. Run the documented version-matched OCI command
with `--take-ownership` unchanged in every adoption case, then compare the
captured before/after evidence. Static render/helper tests are a **SUBSTITUTE**,
not this cluster-backed proof. Never use `helm rollback` on the CRD release.

## Leg 9 — HA A→B and B→A

First prove both exact one-replica gateway Deployments are Ready, the pool is
`fenced_ha`, A is the observed owner, B is standby, and fresh desktop-client
private-Service requests succeed continuously. Record the starting scale
subresources, connector identities, promotion generation and client timestamps.

Use only the exact A Deployment's scale subresource to set replicas `1 → 0`.
Do not delete a Pod separately or mutate Helm, the Service, PVC, pool, fence, or
role. Keep fresh client requests running until the control plane automatically
records B ownership and successful responses recover; capture the outage and
recovery timestamps, transition evidence, request results, and both gateway
log streams. Restore A through the same scale subresource (`0 → 1`) and wait for
the same A identity and readiness to return without treating scale-up as proof
of ownership.

After the control plane has automatically reached the required ready state for
the reverse direction, inject the sustained B failure with only B's scale
subresource (`1 → 0`) and prove automatic A ownership plus client recovery.
Finally restore B to one replica and prove both original connector identities
are Ready, the pool remains `fenced_ha`, and fresh requests succeed. No manual
promotion is allowed. Failover SLA is recorded separately; automatic A→B and
B→A correctness is mandatory for this leg. A scale write used to repair any
other leg is disqualifying.
