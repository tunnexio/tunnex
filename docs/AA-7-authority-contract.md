# AA-7 withdrawal, restore and event authority contract

Status: implementing with isolated database/Redis and source tests; functional integration acceptance pending. AA-6 qualification is still in progress. This document does not authorize migration173, restore, restart, credential rotation, or release. None of the proposed AA-7 behavior is claimed implemented or qualified.

## Existing boundary and remaining gap

AA-5 checks the current user `app_auth_epoch`, retained hashed parent-logout tombstones, current parent Redis TTL, membership, grants, feature entitlement, and exact serving binding on app decisions. AA-6 adds staged publication and durable disabled-pointer confirmation after a post-commit monotonic five-second wait. App-session revocation currently deletes Redis state. Pending launch consumption, one-use code redemption, app-session removal, and stream removal also use Redis atomics.

Restoring an older Redis snapshot can restore a revoked app session or a consumed launch/code while its parent, grants and publication remain current. User epochs and parent tombstones do not cover that independent app-session revocation. Restoring an older PostgreSQL backup can additionally undo parent tombstones, user epochs, proxy revocations, and publication withdrawals. A generation stored only in that same backup cannot detect rollback of its own source. These are distinct gaps; Redis deletion alone is not a durable revocation claim.

## Durable records proposed for migration173

Use one installation-wide authority record with a fresh random UUID, monotonic database version, changed-at timestamp, and named system/human audit attribution. Do not derive the UUID from wall time. Read the current UUID from PostgreSQL for each authority decision; no local-cache TTL may extend the four-second serving lease. Infrastructure failure denies new admission and renewal.

Stamp this UUID into pending launch records, launch codes, app sessions, and stream records. Pending/code/session/stream records without a stamp are refused. Register, launch, redeem, request and renewal compare the captured UUID to the current authority UUID; a handoff whose UUID changes before consume/mint is refused. Atomic Redis admission must compare the exact expected stamped record, not replace its stamp with the current UUID. Generation changes never turn stale records into valid records. Record lifetimes remain bounded by the native parent absolute expiry and their existing tighter limits.

Add durable app-session revoke tombstones keyed by installation UUID, organization, application, user, and server-issued session UUID. Store actor attribution, revoked-at, original absolute-expiry snapshot and a bounded reason enum. The UUID is not the browser credential; never store plaintext cookies, native parent tokens, sealed parent material, or token hashes in event metadata. Exact tuple lookup prevents foreign-session discovery. Tombstone existence denies even if its stored expiry has passed; no automatic tombstone GC is included until restore-safe cleanup is separately qualified. Index `(org_id,app_id,user_id,session_id)` for authority lookup and `(org_id,app_id,revoked_at,id)` for operational history. Keep history when a user or directory subject is physically removed, using retained identity snapshots and nullable same-org live references where appropriate.

Both self-revoke and administrator revoke must commit the scoped tombstone plus transactional audit before Redis cleanup. Cleanup failure leaves durable denial; return requested/confirmed semantics honestly and do not undo the committed tombstone. An administrator requires the existing named session-management permission and supplies the exact org/app/user/session tuple. No token-only, installation-wide, or arbitrary-user delete port is exposed. A missing/foreign session must not disclose existence; idempotence uses the exact retained tombstone tuple. Listing remains bounded and tenant scoped; administrative filtering does not grant app-use permission.

## Restore barrier and invalidation procedure

The mandatory restore procedure stops every control-plane instance, private app-authority listener, public app-proxy listener and background readiness worker before restoring state. In HA topology, all participants must be fenced; local single-process success is not HA proof. Database/key manifest verification remains required before writes. Restoring Redis without PostgreSQL still requires this barrier, because a consumed record may be replayed.

After the restored database has the required schema, an offline operator-local recovery command executes one audited transaction:

1. Generate a fresh installation UUID and advance its database version.
2. Revoke and version-bump every dedicated AppProxy credential. Do not reuse privileged machine-operator credentials or print retained secrets.
3. Cancel all live publication/readiness operations, invalidate their instance claims, and withdraw active/pending serving pointers with advancing authority versions and cleared withdrawal confirmations. Preserve immutable revisions, operation history and permanent hostname ownership.
4. Advance every restored user's `app_auth_epoch` to invalidate restored native parents and pending password-verified MFA challenges. Old parent records must not acquire the new epoch. Fresh verified login is required. The legacy epoch-zero console compatibility path must remain denied after the advance.
5. Insert a named recovery audit recording the new generation/version and bounded counts, never credential material.

Only after a confirmed commit does the recovery process wait a full monotonic five seconds. If the command crashes, restart repeats the full wait; old wall-clock timestamps are not confirmation. Persist exact generation/version-bound recovery completion after the wait. Any error keeps all listeners stopped. New proxy credentials must be provisioned through the dedicated local workflow, current gateways must report fresh capability, and each app must pass fresh origin/public readiness before republishing. No automatic replay of retained published rows occurs.

A restored database may contain an older recovery completion row. Therefore the external restore barrier must require a new operator recovery invocation for every restore; reading a stored completion flag alone cannot authorize reopening. Integrate this requirement into the supported runner/runbook with an external restore-in-progress marker that is created before state replacement and removed only after the new recovery transaction, wait, and readback. Its identity must not come from the restored DB/Redis snapshot. This protects the documented managed restore path; bypassing it with raw database restore cannot be described as automatically detected. Do not rotate master keys or gateway CA keys as part of this procedure.

## Events, privacy and retention

Configuration, grant, session revocation and recovery changes use the existing transactional `audit_log` producer. Browser admission/denial, app-session lifecycle and stream termination need a separate typed app producer; a VPN flow event is not a browser decision. Existing `access_events` assumes packet addresses, node-flow counters and VPN retention accounting, so do not invent packet fields merely to fit its schema.

Propose a tenant-scoped app event table with server UUID, CP-received time, event kind, bounded outcome/reason enums, app/revision/serving-generation/installation-generation, optional server-issued session/stream/correlation UUIDs, user/gateway/proxy identity snapshots and nullable same-org live references. Unknown-host or unauthenticated generic denial has no tenant authority and must not be assigned a guessed org. Record safe aggregate counters instead. Never persist host-independent raw URLs, query strings, request/response bodies, Authorization/Cookie headers, PEM material, parent/session tokens, nonce/code values, private keys, raw connector errors or client-supplied arbitrary text.

Use keyset pagination `(org_id,created_at,id)`, plus bounded app/user/session filters and indexes. Retention has an explicit per-org row/age cap, bounded batch pruning and health/drop counters. Authority must not rely on event delivery. Transactional mutation audits fail the transaction if unavailable; decision telemetry uses bounded buffering with truthful dropped-event accounting rather than unbounded growth or blocking every request indefinitely. Define which lifecycle events are transactionally durable versus best-effort before claiming completeness. Deleting telemetry cannot remove durable revoke tombstones.

The required independent app-event permission is already named `app_access:event_view` (`PermAppAccessEventView`) in current RBAC; the epic shorthand `app_event:view` must not create a second accidental permission. Use the existing exact name unless central contract explicitly renames it with generated mirror compatibility. Event reads must work when VPN Zero Trust is off and when the App Access feature is disabled or entitlement is lost, under this independent permission. Existing Audit Log/Access Events navigation may expose app filters, but separate producers and permissions remain explicit.

## Narrow source plan and gates

Data lane: migration173 installation authority, revoke tombstones, typed app-event schema/indices and SQLC scoped queries. Schema173 is forward-only: its down migration refuses while the installation singleton exists, even with no event/tombstone rows, because Redis authority minted under initial UUID1 is invisible to SQL. Binary rollback requires a forward-compatible binary and offline fresh-generation recovery; unsupported schema downgrade must not discard the authority stamp. API authority lane: stamp/compare all ephemeral records, current DB UUID check on every serving decision, scoped durable self/admin revoke, typed event producer and read service. Root lifecycle lane: offline recovery command and backup-runner barrier, durable account epoch advance, RBAC/UI/operations and packaging integration. Transport lane: existing independent lease expiry watchdog remains authoritative; generation/revoke tests use genuine channels and stop long HTTP/SSE/WebSocket/upload/download within the qualified bound. No notification or cleanup success substitutes for current authority.

Actual child PostgreSQL/Redis tests must restore previously captured stale records after self/admin revoke, code redemption and recovery; old records must remain denied. Cover exact foreign org/app/user/session refusal, audit failure rollback, Redis cleanup outage, absent UUID, DB authority outage, concurrent mint/recovery, restored parent/MFA records, old recovery-marker replay and restart before completion. Every withdrawal trigger requires new-request plus already-open stream proof even when notifications are dropped. A recovery that partially fails must never reopen listeners. Verify event privacy, independent permissions, disabled-feature reads, bounded retention/drop behavior and durable-tombstone preservation.

Existing integration points are [backup-restore.md](backup-restore.md), `apps/api/cmd/backupctl/main.go`, `apps/api/internal/backup/manifest.go`, `deploy/upgrade.sh`, [access-event-operations.md](access-event-operations.md), and [upgrade-release-signing-checklist.md](upgrade-release-signing-checklist.md). The current backup runbook verifies the master key then invokes raw `pg_restore`; its reconnect/last-known tunnel discussion does not qualify browser authority after restore. Add the stopped-listener recovery barrier explicitly while preserving existing gateway trust and VPN behavior. Upgrade runners must never treat a backup restore as an ordinary restart.

Signed artifacts, Compose/Helm/installer listener defaults, certificate renewal and rollback compatibility need their existing release contracts extended for app-proxy/configuration and schema173. Unsupported downgrade must refuse retained authority history rather than drop it. Tie local evidence to source and built artifact digests. AA-7/AA-8 acceptance is not release, remote deployment, or approval to modify a live fleet.

## Tradeoffs requiring central review

Installation-wide restore invalidation deliberately forces fresh user login, proxy reprovisioning and app republish. This is broader than individual session revoke, but avoids silently resurrecting credential/publication state from database backup. The offline barrier must be operationally enforced; a DB-only UUID cannot detect unauthorized rollback. Tombstones retained without GC grow over time; initial bounds constrain session issuance, while safe cleanup remains separately qualified. Decision-event loss policy must be honest and distinct from transactional mutation audit durability. HA fencing and restore sequencing need separate proof before an HA recovery claim.
