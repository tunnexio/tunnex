# S20.5 CRD review fixes

Status: locked implementation boundary for review findings 9 and 32; findings
8, 11, and 22 remain held as described below.

## Findings 9 and 32 — execute the real preflight

The CRD chart contract must execute `templates/00-preflight.yaml`, including
its real three-name loop, cluster-scoped `lookup` calls, release namespace, and
chart generation. Named-helper fixtures remain useful fingerprint unit tests,
but they are not evidence for that wiring.

The offline substitute uses Helm 3 server dry-run against a local, read-only
Kubernetes API fixture. The fixture serves discovery plus exact CRD `GET`
responses and refuses every non-GET request. Contract cases exercise:

- all three current-owner generation-1 CRDs, proving the loop and repeat path;
- a foreign Helm release owner;
- the current release owner from another namespace; and
- a sane newer generation (`2`), not the malformed-generation parser case.

The request log must show the three exact cluster-scoped CRD lookup paths on
the success case and the expected first lookup on each fail-fast refusal. The
success/newer pair pins the preflight generation at 1 without a source grep.
These tests are still an offline substitute. The full live lookup/adoption
matrix in the box-walk remains mandatory and is not marked complete by them.

## Findings 11 and 22 — no silent fingerprint policy expansion

D8 explicitly requires a complete normalized-schema fingerprint for an
ownerless same-name CRD, while separately declaring the current CRD release
and the known legacy `tunnex-operator` release valid owners. The live matrix
also requires repeat upgrade by the same release and adoption from the legacy
release. It does not explicitly say whether a valid generation marker is
trusted provenance after manual schema drift, or whether same-release and
generation-marked legacy objects must also match a historical fingerprint.

Requiring those additional fingerprints would therefore be a new policy
choice, not a mechanical review fold. Findings 11 and 22 remain held pending a
product decision between:

1. generation-marker authority for valid current/legacy owners; or
2. fingerprinting every adoption/re-install state, including the maintenance
   contract for every prior generated schema and Kubernetes normalization.

This slice does not change either branch.

The exact locked D8 distinctions are: ownerless same-name adoption requires a
complete normalized-schema fingerprint; unknown, manually changed, or newer
unannotated schemas fail closed; and the current CRD release plus the known
legacy release remain valid owners. The current helper implements these
branches:

| Existing state | Current branch |
|---|---|
| No Helm owner | Require an approved legacy fingerprint |
| Legacy owner, no generation marker | Require an approved legacy fingerprint |
| Current owner, no generation marker | Trust owner; do not fingerprint |
| Current owner, valid generation marker | Trust generation; do not fingerprint |
| Legacy owner, valid generation marker | Trust generation; do not fingerprint |
| Other owner or other owner namespace | Refuse |
| Generation newer than the chart | Refuse |

Server-dry-run fixtures record both generation-marked fingerprint bypasses as
descriptive current behavior. They are evidence for disposition, not a support
claim or a decision that the behavior is correct.

## Finding 8 and other non-goals

Helm rollback of the CRD release remains explicitly unsupported. This slice
does not add a hook, admission controller, rollback engine, or any claim that
the limitation is technically enforced. It also does not change CRD schemas,
ownership rules, generation values, chart packaging commands, or customer/live
cluster resources.

The integration history rewrote the connector-aware historical content tip
from the unavailable story-local `3ccbaf71` to reachable commit `1160009`.
Rendering that manifest through the existing fingerprint guard produces the
already-approved fingerprint, so the test and provenance comment use the
reachable equivalent without changing an approved hash or schema.
