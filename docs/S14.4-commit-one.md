## ⚠ THE MEASUREMENT THAT SHAPES THE WHOLE SLICE: **THE OVERVIEW ENDPOINT SUPPLIES FOUR OF THE SIX STAT CARDS**

`OrgOverview` returns **members, devices, nodes, online**. The ruling keeps **six** cards. **Sites** and
**Pending approvals** are **not in that response** — they need `GET /sites` and `GET /devices/pending`.

**So the six cards are six cards from THREE endpoints, and the honest consequence is that they RESOLVE
INDEPENDENTLY.** Four appear together; two appear when their own fetch lands. **A card that has not loaded
renders as loading; a card whose fetch FAILED renders as unavailable. Neither renders `0`.**

**PROPOSED, and it is the alternative worth naming: do NOT add an aggregate field to `/overview`.** That would
be an API change to serve a layout, it would make one slow query gate the whole page, and **a single failure
would blank six cards instead of two.**

# D2 — THE LIVE NAV COUNTS: A **SHELL-LEVEL** DATA DEPENDENCY

The nav renders `Gateways 3/7`, `Sites 1 DOWN`, `Devices 3`, `Access ENFORCING`. **The shell is rendered on
every screen, so this makes AppShell — which owns no data today — acquire a data dependency no screen owns.**

## ⛔ THE RULE, RESTATED BECAUSE THIS IS THE MOST-SEEN SURFACE IN THE PRODUCT

> **ABSENT UNTIL LOADED. ABSENT ON FAILURE. NEVER `0`. NEVER A REMEMBERED NUMBER.**

**A nav badge reading `0 DOWN` because a fetch failed is the reassuring-empty defect in the one place every
user looks**, on every screen, all day. **It is strictly worse than the same defect on a page**, because the
user never navigated to it and has no reason to suspect it.

**PROPOSED SHAPE:** one `useNavCounts()` hook at the shell, `Loaded<T>` per source, and **the count renders
only in the `ok` state**. The label is always present — **the DESTINATION never depends on the count loading**,
which is S14.2's nav rule still binding.

**PROPOSED, and it needs a ruling: the counts poll.** `HealthStatus` already polls `/healthz`. If the counts
are static-on-mount they go stale the moment anything changes, and a stale count is a **remembered number**
wearing a live badge. **Proposal: refresh on route change, plus a slow interval — not a fast poll**, since four
extra requests on a timer for decoration is a cost the user pays for a number they glance at.

# THE THREE OPEN QUESTIONS — RULED

## 1. **"PEERS ONLINE" — THE HONEST LABEL STAYS.** *(founder-ruled)*

`online` is derived from **last-handshake recency** (S3.6), not a live session. **`Seen in last 3 min` is what
the data supports; `Online Peers` claims a liveness it does not carry.**

> ### **A RENDER-FLOOR VIOLATION IN A WORD IS STILL A RENDER-FLOOR VIOLATION.**

**And this project has already ruled it, three times, in three places:** S3.6 shipped *"Seen in last N min"*
**deliberately** · S4.3 inherited it as the honesty position · S6.3's **"never green while dead"** is the same
rule on the client.

### ⚠ FOURTH RENDER-FLOOR FINDING AGAINST THE WIREFRAME — AND IT IS A **NOUN**, NOT A CHART

**THE WIREFRAME CONTRADICTS ITSELF.** Its own caption reads:

> *"Status derived from WireGuard handshake liveness — never green-while-dead"*

…directly beneath a label reading **"Online Peers."** **The caption states the honest rule and the label breaks
it.**

**THE CLASS IS NEW, and that is why it is filed separately:** the first three violations (*fleet risk*,
*site-link throughput*, the *area chart*) were **CHARTS**. This one is a **LABEL**.

> ## **A LABEL IS A CLAIM WITH NO CHART TO INSPECT — WHICH MAKES IT THE EASIEST KIND TO SHIP.**

A chart invites the question *"where does this data come from?"* — it has axes, a shape, a visible scale, and
someone eventually asks. **A noun invites nothing.** It costs one word, survives every review, and asserts a
property of the system as confidently as any graph. **Audit the words in the redesign the way the charts were
audited.**

## 2. **NO AGGREGATE FIELD ON `/overview`** *(founder-ruled — recorded as a RULE, not a preference)*

> ## **AN API CHANGE DRIVEN BY A LAYOUT CONVERTS INDEPENDENT FAILURES INTO ONE BLAST RADIUS.**

Three endpoints failing independently degrade **two cards**. One aggregated endpoint failing blanks **six**.

> ### **SCREENS COMPOSE ENDPOINTS. ENDPOINTS DO NOT COMPOSE THEMSELVES FOR SCREENS.**

The pull is real and it always sounds like efficiency — *"one request instead of three."* **What it actually
buys is a shared fate**: the slowest query gates the fastest, and the least reliable one decides what the whole
page shows. **A layout is the wrong reason to couple data sources**, and layouts change more often than
endpoints do.

## 3. **NAV COUNTS — the emphasis stands, and the reason is recorded verbatim so it survives**

> ## **A WRONG COUNT ON A PAGE THE USER *OPENED* IS A BUG THEY MIGHT NOTICE.**
> ## **A WRONG COUNT IN *PERMANENT CHROME* IS FURNITURE.**

**That is why absent-never-zero is STRICTER here than anywhere else in the app.** The user did not navigate to
the nav, did not ask it a question, and has no moment of expectation against which to check its answer. **It is
simply always there, and always believed.**

**PLUS the ruled behaviour:** counts refresh on **route change** and on a **slow interval** — not a fast poll.
A static count is a remembered number wearing a live badge; a fast poll is four requests on a timer for
decoration.

## 4. **GATEWAY HEALTH LIST — ALL gateways, unhealthy first** *(my recommendation, ruled by silence, built)*

*"Nothing is wrong"* and *"we have no gateways"* must not render identically.

## ⛔ FOUR MUTATIONS, AND **THREE OF THEM PASSED FIRST**

**This is the slice's real result. The mutations did not confirm the guards — they found three that did not
exist.**

| # | mutation | first run | after |
|---|---|---|---|
| **D1** | `badgeText` renders `"0"` for unknown | **3 failed** ✅ | — |
| **D2** | a failed fetch degrades to `length 0` | **PASSED** ❌ | **1 failed** ✅ |
| **D3** | `isFreshOrg` drops the *known*-empty requirement | **WILL NOT COMPILE** | — |
| **D4** | healthy gateways sort **first** | **PASSED** ❌ | **1 failed** ✅ |

### D2 — THE DECISION WAS LIVING IN A `useEffect`

`sites.ok ? ok(len) : FAILED` rewritten as `ok(sites.ok ? len : 0)` — **the classic route to a false count** —
went **green**. Every assertion was on the pure `badgeText` layer; **nothing looked at the mapping that
produces its input.**

**Fixed by EXTRACTING `countFrom` and testing it.** This project's own three-layer shape says the decision must
be pure and unit-tested and the component must only render it. **The mapping WAS the decision, and it was
inside a hook.**

### D4 — INDIRECT COVERAGE IS COVERAGE OF THE PATH, NOT OF THE DECISION

Reversing the sort so **healthy gateways come first** went green: the screen test asserted the badge *appeared*,
never *where*. **A broken gateway sorted below three healthy ones is a broken gateway below the fold** —
present, and not seen.

### D3 — THE MUTATION IS NOT EXPRESSIBLE, WHICH IS STRONGER THAN A PASSING TEST

Weakening `isFreshOrg` to accept a failed count **does not compile**:

```
TS2339: Property 'value' does not exist on type '{ state: "failed" } | { state: "ok"; value: number }'
```

**The tagged union makes the weakening unwritable.** `.value` exists only on the `ok` branch, so a guard that
stops requiring `ok` loses access to the number it needs. **A guard enforced by types beats one enforced by
discipline — and this one cannot be removed by accident at all.**

**Recorded honestly: on the screen today the PRIMARY protection is that a failed `/overview` leaves `data`
null**, so the block never renders. `isFreshOrg` is belt-and-braces. **It is gated directly anyway**, so the
guard survives a refactor of how the screen handles a null `data`.

## A TEST ASSERTION THAT WAS WRONG IN AN INSTRUCTIVE WAY

`expect(screen.queryByText("0")).toBeNull()` — *"no card shows 0"* — **failed, correctly.**
`/devices/pending` returned `[]` and the card rendered a **true zero**. We DID learn there are none.

> **THE RULE IS NOT "NEVER SHOW 0". IT IS "NEVER SHOW 0 FOR SOMETHING WE DID NOT LEARN."**

**A page-wide text query cannot tell those apart, because on screen they are the same character.** The
assertion is now scoped to the failed card — the only place the distinction lives.

## ONE HARNESS FINDING

The get-started panel links to `/devices`, so rendering `Dashboard` without a `MemoryRouter` throws
*"Cannot destructure property 'basename'"* — **surfaced as an UNHANDLED ERROR, not a clean failure**, so the
visible symptom (*"could not find Get started"*) pointed away from the cause.
