# Where the human review step goes — `trials.status`, or somewhere else

**Status: ⛔ PAPER. HELD FOR THE FOUNDER. Nothing built, no schema touched.**

Manual issuance (S12.4 §1) needs a place for "a human has not signed this yet". The destination repo
(`tunnex-web`) already has a shipped trial lifecycle with a daily cron walking it. **This paper reads that
machine first and then proposes**, because a new state in a state machine a scheduled job already walks is
where this gets expensive quietly.

---

# 1. ⛔ WHAT READING THE CRON CHANGED — THERE ARE **TWO** MINT PATHS, NOT ONE

My earlier report named `src/pages/api/trial/verify.ts` as the place a real signer would be swapped in.
**That was incomplete.** `onTrialApproved` — the function that calls `Issuer.issue()` — has **two** callers:

| caller | when | who is present |
| --- | --- | --- |
| `src/pages/api/trial/verify.ts` | a person clicks the email verification link | the requester |
| `src/lib/lifecycle.ts` — the promote leg | ⛔ **the daily cron, 03:17 UTC, in beta mode** | **nobody** |

The cron's beta-launch pass loops `pendingLaunchTrials()` and calls `onTrialApproved` for each one.

> ## ⛔ **SWAPPING A REAL SIGNER INTO THE `Issuer` SEAM MAKES A SCHEDULED JOB MINT UNREVOCABLE KEYS IN A
> ## LOOP, UNATTENDED, AT 03:17 IN THE MORNING.**

That is strictly worse than the verify path, where at least a human triggered something. **Fixing the
`verify.ts` comment alone would have left the more dangerous caller untouched** — and it is the caller
nobody would think to look at, because the comment that invites the swap is not in that file.

⚠ **The fix therefore has to be at the seam, not at a call site.** Any solution below must hold for both
callers by construction, not by remembering there are two.

---

# 2. WHAT THE MACHINE LOOKS LIKE TODAY

`trials.status IN ('pending_launch', 'active', 'expired')`, one row per domain (`domain TEXT UNIQUE`).

| status | meaning | who moves it |
| --- | --- | --- |
| `pending_launch` | verified, approved, **no key yet, clock NOT started** | cron promote leg (beta only) |
| `active` | key issued, clock running | `activateTrial()` from `onTrialApproved` |
| `expired` | clock ran out | cron expiry leg |

**The clock starts at ISSUANCE, and that is a public promise** — `trial-issuance.ts` says so explicitly:
*"The public promise: the trial clock starts at KEY ISSUANCE."* `pending_launch` exists precisely to hold a
trial whose key has not been minted yet **without burning its 14 days.**

⭐ **That is the same shape the review queue needs.** A trial awaiting a human is a trial that has been
approved and has no key and must not be losing days.

Every cron send is gated by `claimEmailEvent` (`UNIQUE(trial_id, kind)`) — at-most-once by construction.

# 3. THE SHAPES

## Shape A — add `pending_approval` to `trials.status`

A fourth state; the cron's selects are status-scoped so they ignore it.

⛔ **Costs, and the first is structural rather than fiddly:**

- **SQLite cannot alter a CHECK constraint.** The migration is a table rebuild — create, copy, drop,
  rename — on the table that holds every live trial, with a UNIQUE constraint and two other tables
  referencing its semantics. On D1, in a migration applied automatically by `deploy.yml` on push to main.
- **Every status-scoped query becomes a question.** There are six in `lifecycle.ts` alone. Each is currently
  correct by exhaustion over three states; a fourth makes "is this query complete" a fresh judgement at
  every site, including sites written later by someone who does not know the state was added.
- ⚠ **And it does not fix §1.** The seam still mints when called; the new state only records that a human
  looked. Both callers still reach `issue()`.

## Shape B — a separate queue table; `trials` untouched

`licence_approvals` alongside, holding what is awaiting a signature.

**Cheap and zero-risk to the shipped machine.** ⛔ **And it creates two sources of truth about whether a
domain is getting a key** — `trials.status` and the queue can disagree, and the one-truth violation's
subject would be licence issuance. **Rejected on that ground.**

## ⭐ Shape C — RECOMMENDED: THE ISSUER **IS** THE QUEUE. NO CHANGE TO `trials` AT ALL

**Reading the cron produced this one, and it is the shape the destination repo already built for.**

`IssuanceResult` is already a union:

```ts
type IssuanceResult = { issued: true; licenseKey: string } | { issued: false; reason: 'pending_launch' };
```

⭐ **"Not issued" is already a first-class outcome, and BOTH callers already handle it correctly** — verify
sends the approval email and parks the trial; the cron logs and moves on. The seam was built to defer.

So the real signer is **never** wired to either caller. What is wired is a `reviewQueueIssuer`:

1. it records the claims into a queue for a human,
2. it returns `{ issued: false, reason: 'pending_review' }`,
3. the trial stays `pending_launch` — **which already means exactly "approved, no key, clock not started"**,
4. a human signs from the admin view, which mints and calls the existing `activateTrial()` path.

⛔ **AND IT FIXES §1 AT THE SEAM RATHER THAN AT TWO CALL SITES.** Neither caller can mint, because the
issuer they hold does not mint — **including the 03:17 cron, by construction rather than by anyone
remembering it exists.**

**Costs, stated honestly:**

- one new `reason` value in the union — a type change, and every `switch` over it is compiler-checked
- **`pending_launch` becomes slightly overloaded**: "waiting for beta" and "waiting for a human" are both
  parked-without-a-clock, which is what the state models, but the *name* now says less than it means.

  > ~~⚠ Worth renaming, and a rename is cheap in a way a CHECK-constraint change is not~~
  >
  > ⛔ **STRUCK 2026-08-06 — THIS WAS WRONG, AND IT WAS RULED ON BEFORE IT WAS TESTED.** Left visible
  > rather than edited away: **the record that the claim was checked is worth more than a clean line.**
  >
  > **`pending_launch` names TWO different things** — a `trials.status` value inside a CHECK constraint,
  > and an `IssuanceResult.reason` TypeScript literal. The sentence is true of the **reason** and false of
  > the **status**: renaming a CHECK'd value on SQLite is a create-copy-drop-rename of the table holding
  > every live trial, **applied automatically by `deploy.yml` on push to main.** That is the exact cost
  > Shape A was rejected for — and taking it for tidiness would be worse than taking it for a feature.
  >
  > ⭐ **AND THE COLLISION IS THE BETTER DIAGNOSIS THAN THE RENAME.** Most of the confusion is that one
  > string names two things. Separating the **reason** (adding `'pending_review'`) removes it at zero cost
  > and is compiler-checked, while `trials.status = 'pending_launch'` keeps meaning exactly what it always
  > meant: **parked — approved, no key, clock not started.**
  >
  > ✅ **RULED: the free half only. No table rebuild.**
- ⚠ **One behaviour to confirm:** in beta the cron promotes each `pending_launch` trial once, burning its
  `trial-key-delivery` claim. Under Shape C the promote attempt defers to the queue and the claim is spent,
  so the cron will not retry — the trial waits for the human, which is correct, but it means **the queue is
  the only path forward and a trial cannot be re-promoted by the cron.** That must be deliberate.

---

# 4. RECOMMENDATION

**Shape C.** It needs **no change to `trials`**, no table rebuild, no fourth state, and it closes the
two-caller problem at the seam. It also uses the deferral mechanism the destination repo already shipped and
tested rather than adding a parallel one beside it.

**What still needs schema, and only this:** `issued_keys` (what was minted, and under which `kid`) and
whatever the queue rows live in. **Neither touches `trials`.**

⛔ **Held. Nothing built until this is ruled.**
