# S10.3a — Private Kubernetes service handoff

## Locked outcome

An enrolled Tunnex client may reach an exposed Kubernetes Service through its
existing site edge gateway even when the cluster and its node agent have no
public endpoint or load balancer.  The application remains a Kubernetes
`ClusterIP`; neither a public Ingress nor a public LoadBalancer is created.

## Observed defect

S10.3 groups a cluster's synthetic VIP mappings by `site_id`.  With an EKS
connector and an existing edge gateway bound to the same site, both gateways
receive the map.  Only the in-cluster connector has the read-only
EndpointSlice watcher, so the edge correctly fails closed as
`endpoints_unavailable` instead of forwarding the VIP to that connector.

## Decisions

1. **A cluster is fronted by one named connector node, not every node in its
   site.**  The connector alone receives the Kubernetes DNS/VIP mapping and
   can DNAT a synthetic VIP to a ready pod.
2. **Existing site edge gateways enforce user policy.**  A matching device
   flow is allowed at its ingress edge only for the granted pre-DNAT VIP and
   port; it never receives broad VPC access.
3. **The control plane compiles an explicit private service handoff peer and
   a /32 VIP route from edge to connector.**  This is a Tunnex-managed
   WireGuard peer, including the return route to the device pool.  Same-site
   exclusion in ordinary site routing does not suppress this distinct service
   link.
4. **The connector accepts only the managed encrypted handoff, then performs
   the existing ready-endpoint DNAT.**  It does not trust a cloud route or a
   manually created NAT rule as proof of authorization.
5. **No manual `wg set`, iptables, public NodePort, public worker address or
   public application listener is an implementation option.**  Reconcile owns
   the resulting data plane.
6. **The connector owns a high-priority destination rule for the device-pool
   return path.**  A host-network connector can share its namespace with a CNI
   that installs source-based rules for pod IPs (observed on EKS VPC CNI).  The
   backend reply is still sourced from the pod IP when routing runs, so that CNI
   rule can select a pod ENI before conntrack restores the synthetic VIP source.
   The node agent therefore reconciles `to <device-pool> lookup main` ahead of
   provider rules, but only when that pool is an explicit desired tunnel route.
   It reserves priority 100, prunes departed Tunnex-shaped rules, and leaves
   unrelated rules untouched.  This is provider-neutral; nft policy remains the
   authorization boundary and no non-pool destination is broadened.

## Acceptance

- An edge gateway has no Kubernetes watcher and no VIP DNAT rule for the
  cluster.
- It receives a single-valued route for each authorized synthetic service VIP
  to the cluster connector.
- The connector receives the VIP mapping, resolves a ready pod endpoint, and
  returns device-pool traffic through the same edge peer.
- Revoking the service grant removes the edge permission and flushes existing
  flow state; a connector/watch fault remains fail-closed.
- Existing cross-site routes and ordinary same-site HA gateway behaviour are
  byte-identical.
- A pod reply whose source matches a provider CNI policy rule still returns to
  the client pool through `wg0`; removing the pool route removes the companion
  priority rule.

## Non-goals

- Automatic cloud route failover, public endpoint provisioning, generic
  relays, and multi-connector load balancing are not part of this story.
