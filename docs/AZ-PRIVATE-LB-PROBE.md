# Bounded owned private load balancer HTTP probe

Design only; do not execute until the lead verifies gateway readiness and authorizes this owned target's setup. Keep the existing application probe unchanged. The distinct target is private frontend `10.231.1.10:8080`, reached by runtime DNS name `lbapp.azure-s2s.test`. The lead must inventory the owned internal load balancer, frontend, backend pool, TCP rule and health probe before mutation. Never create a public frontend. The DNS record points to the private frontend; clients must resolve its name normally, without hosts entries or curl `--resolve`.

Run a separate bounded HTTP/1.1 server on a distinct backend port (for example 18080, after checking it is unused). The load balancer TCP rule maps frontend 8080 to that backend port. Respond to `/azure-lb-probe/<nonce>` only, with a short per-run nonsecret marker and the observed remote source address; return 404 elsewhere. Use explicit Content-Length, flush each response, and support keep-alive so one established TCP session can be tested across policy changes. Bound each socket timeout, request count and total lifetime; retain exact server PID, owned rule identifiers and log path. The health probe uses a separate fixed health path whose response carries no application proof. Do not replace the existing TCP8080/UDP8081 server.

From owned client namespace `azure-s2s-client`, source `10.233.10.2`, resolve `lbapp.azure-s2s.test` through the existing office conditional forwarder. Verify DNS returns the inventoried private frontend, then connect using that freshly resolved result and HTTP Host `lbapp.azure-s2s.test`. Record the actual DNS response/CNAME chain and timestamp. For source preservation, correlate backend socket remote address `10.233.10.2` with both gateway and backend packet capture; an echoed arbitrary header is not proof. Inspect Azure LB floating-IP/SNAT and NSG settings if the source differs; do not claim preservation from successful HTTP alone.

Qualification sequence:

1. With both VPN paths verified and no application grant, DNS may succeed under its separate DNS grant, but fresh HTTP to the LB must time out/refuse without a marker. No static route or broad subnet permission substitutes for policy.
2. Grant only source `10.233.10.2`, destination private frontend `/32`, TCP8080 with bounded expiry through the normal control-plane path. Confirm actual applied revision before testing. Perform at least eight fresh HTTP connections and eight requests on one persistent HTTP/1.1 connection; every success must carry the current marker and captured source.
3. Identify the selected VPN slot from actual forwarding state/captures. Fault only that owned slot using the established exact ownership-attested mechanism. Repeat fresh and persistent requests, record actual recovery delay, inspect selected alternate slot and backend source. Persistent survival is an observation, not a promised guarantee.
4. Revoke the grant normally while retaining the established socket. Require both fresh and existing traffic to stop returning application markers within the enforcement bound. Repeat with normal expiry as a distinct run; a newly connected socket does not certify existing-flow expiry.
5. With both VPN slots faulted, test the name again and HTTP; prove protected DNS has no public/cross-profile fallback and application packets do not escape WAN. Restore only owned faults, obtain current healthy reports, and retest under a current bounded grant if authorized.

Cleanup removes only this probe's owned grant, HTTP process, LB rule/health probe/backend association and DNS record, after capturing their identities and confirming ownership. Do not delete the LB's shared frontend/backend VM, private resolver, zone, existing app probe or unrelated resource. Evidence should distinguish LB forwarding, DNS, policy enforcement, source preservation and selected-path behavior. No result is implied by this design or the earlier direct-VM application proof.
