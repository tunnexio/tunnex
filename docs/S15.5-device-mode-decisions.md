# S15.5 — Stable device identity across split/full mode changes

Status: locked design (API slice; client/UI implementation follows)

## Problem

The managed desktop client keys its cached profile by server origin. A split/full
toggle currently revokes that profile's device and calls `POST /devices`, which
creates a second device row. A mode toggle changes baked routes, but it must not
change the device principal shown to the operator.

## Decisions

### D1 — Device UUID is stable across mode changes (locked)

An authenticated mode mutation targets an existing device UUID. It preserves the
owner, name, platform, gateway, assigned IPv4/IPv6 allocation, audit identity,
and device cap accounting. It updates only the desired `full_tunnel` mode and
returns the new route/config facts.

### D2 — Never deduplicate by hostname or display name (locked)

`name` is a display label and is not a machine identity. Two machines can share a
hostname. Durable recovery after local keychain loss requires a separately
persisted installation identifier and an explicit conflict/recovery flow; it is
not part of this API slice.

### D3 — Preserve the existing WireGuard credential (locked)

The API deliberately does not store private keys, and the desktop client has no
key-generation seam. Mode mutation therefore keeps the existing public/private
key pair and returns only mutable configuration facts (allowed IPs, DNS,
addresses, endpoint and gateway public key). A future key rotation is a separate
credential-rotation story with one-time secret delivery.

### D4 — Server-side authorization and serialization (locked)

Only the owning user or an authorized member manager may mutate a device in the
organization. The service locks the device row, accepts only active/pending
devices, preserves allocation/cap state, updates the mode atomically, audits the
old/new mode, and pushes the affected gateway after commit. Revoked/deleted
devices are rejected and never resurrected.

### D5 — “Current mode” means desired issued mode (locked)

The Devices API/UI reports the persisted `full_tunnel` mode. Live transport mode
requires a future client health/status field; it is not inferred from a stale
handshake.

## Required follow-up slices

1. OpenAPI route/schema, generated Go/TypeScript clients, and API service/query.
2. Client mode toggle: stop tunnel, call the mode endpoint with stored device ID,
   merge returned facts while retaining the private key, persist atomically, and
   reconnect. No revoke/create call.
3. Devices UI mode column and regression fixtures.

## Safety tests

- split→full and full→split retain the same UUID, IPs, key, cap count, and row;
- owner/org/status authorization and revoked/deleted rejection;
- concurrent mode changes serialize and audit each committed transition;
- gateway push occurs only after commit;
- returned facts never contain a private key;
- local reconnect with unchanged mode remains get-or-create and does not mint.
