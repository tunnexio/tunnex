# S12.5 — the org question. Commit-one, decisions only.

⛔ **A CUSTOMER CAN PAY FOR SOMETHING THEY CANNOT USE.** `multi_org` became a paid Enterprise capability in
S12.1. The pricing page sells it, the licence unlocks it, the API serves it — **and the web UI throws away
every organization but the first.**

This is not a gap discovered by inspection. It is a **contradiction the licensing work created**: before
S12.1 the second org was unreachable *and unsellable*, which was consistent. Selling it made the
discarding a defect.

---

> ⭐ **THE STORY THIS PAPER OPENS WAS NAMED IN A CODE COMMENT BEFORE IT WAS NAMED BY ANYONE.**

### 1b. ⛔ THE THREE SURFACES GIVE THREE DIFFERENT ANSWERS — measured, not assumed

| Surface | What it does with a user's N organizations |
|---|---|
| **API** | Serves **all of them**. `GET /api/v1/organizations` returns every membership; `authctx.Principal.Roles` is `map[uuid.UUID]string` — orgID → role. **The server has been multi-org the whole time.** |
| **Electron client** | Uses **all of them**. `httpdeviceapi.ts:126 orgIds()` returns `orgs.map(o => o.id)` and the caller iterates. ⭐ **The desktop app is already correct** — it was never the client that discarded. |
| **Web UI** | Uses **the first**, fourteen times over. |

⚠ **This corrects the framing this story was handed.** It is not "the client discards what it was handed" —
**one of two clients** discards. Electron and the API agree; the web app is the sole dissenter, and any
design that adds a server concept of "current org" would have to break Electron to do it.

### 1c. ⚠ THE LOGIN PAGE'S `Organization` FIELD DOES NOT SELECT A TENANT — CONFIRMED, STILL TRUE

`pages/Login.tsx:301`. Its value flows to exactly one place:

```ts
api.GET("/api/v1/auth/sso/{provider}/start", { params: { path: { provider }, query: { org } } })
```

**Nowhere else.** It is a required query parameter of the SSO start endpoint — the IdP cannot be chosen
without knowing the tenant — and it is **not read on the password path at all**. A user who types an org
slug and signs in with a password is not sent to that org.

⛔ **AND THAT IS A SEPARATE DEFECT, NOT A DETAIL OF THIS ONE:** the field is visible to every visitor,
labelled `Organization`, with placeholder `acme`. It looks exactly like tenant selection. **A user in two
orgs will type the one they want and land in the other**, and nothing will tell them why.

## 2. THE THREE SHAPES — with costs. ⛔ HELD. None is ruled.

### A — Pick-on-login
A chooser after authentication when N > 1; the selection is stored and used for the session.

**Cost:** every entry into the app costs a decision, including the ~100% of users with one org — unless
gated on `N > 1`, which makes the flow conditional and the tests two-pathed. ⚠ **And it answers the wrong
question**: an admin comparing two tenants must sign out to switch.

### B — A switcher in the shell ⭐ RECOMMENDED, AND THE REASON IS THAT NOTHING SERVER-SIDE CHANGES

One `useCurrentOrg` context at the shell, defaulting to the first org, persisted; a switcher in the header
when `N > 1`; **the fourteen call sites read the context instead of index zero.**

**Cost:** fourteen call sites edited, and each one's loading/error path re-verified — they currently
*fetch* the list, so they lose a fetch as well as gaining a source. Every page must handle the org changing
underneath it (refetch on switch, not on mount alone).

⭐ **Why it is the recommendation:** the API is already multi-org, Electron is already multi-org, and
`RequireOrg` is already org-agnostic. **B is the only shape where the fix is entirely inside the surface
that is wrong.** A and C both add a concept the server does not have, and both would require Electron —
which is correct today — to be changed to stay correct.

⚠ **It also discharges a deferred item by name**: the `useCurrentOrg` hook, deferred since S4 and cited in
`App.tsx`'s own comment.

### C — Server-side "current organization"
A session-scoped current org, set by an endpoint, honoured by unscoped routes.

**Cost:** the highest, and it buys a property nobody asked for. Every `{orgId}` route already takes the org
explicitly — that is the RBAC boundary. ⛔ **Introducing an implicit session org creates a second way to
address a tenant, and two addressing modes is how a request ends up authorized against one org and executed
against another.** Also breaks Electron, which passes org IDs explicitly and correctly.

## 3. ⛔ WHATEVER THE SHAPE — the three surfaces must be made to agree

The measurement's real finding is not `orgs[0]`. It is that **API, login page and web UI answer the same
question three ways**, and no test anywhere asserts they agree.

**In scope regardless of which shape is ruled:**

1. The login `Organization` field is **labelled as tenant selection and is not**. Either it selects the
   tenant on every path, or it is labelled for what it is (SSO tenant hint) and hidden on the password path.
2. **A guard that fails when a new call site reads index zero.** Fourteen sites drifted to the same defect
   independently because nothing named it. ⚠ Subject must be **the capability** — "which org does this page
   act on" — not the string `[0]` (`docs/laws.md`).

## 4. ⚠ WHAT THIS STORY DOES NOT DO

**No user counting, no seat gates** (founder standing rule). A switcher shows organizations the user is
already a member of; it grants nothing and counts nobody.

**No change to the org ceiling.** Creating orgs stays licence-gated at creation (S12.1 §3). This story is
about reaching orgs that already exist.

---

# ⛔ RULED (founder): SHAPE B — AN ORG SWITCHER

**The reason, recorded AS the reason:** the server is already multi-org. `Roles map[orgID]role`, and
`GET /organizations` already returns every membership. **Only the client discards what it was handed.**

> ## ⛔ **A AND C BOTH CHANGE THE CONTRACT TO MATCH A CLIENT LIMITATION. B FIXES THE CLIENT.**

⭐ **And B is the only shape that serves the case that is broken TODAY:** a user **invited into a second
org** — which happens in **Community**, with no licence involved and no ceiling touched, because being
invited is not creating — **cannot reach that org by any means at all.** They are a member. The API will
serve it. The UI will never show it to them.

⚠ **A would not have helped them either**, unless they knew to type an org slug they may never have seen.

## ⭐ A's ARGUMENT, CONSIDERED AND REJECTED — with its reason, because it is a good one

`PLAN.md:12` states the tenancy model: **"Tenant routing: Single domain (`app.tunnex.io`), org resolved from
membership after login."** A pick-on-login screen looks like the literal reading of that sentence.

**REJECTED, and the reason is that B is that sentence IMPLEMENTED, not contradicted.** B resolves from
membership too — it simply **stops resolving to index zero**. The sentence constrains *where the org comes
from* (membership, not a subdomain, not a URL) and says nothing about *when the user is asked*. A adds an
interrogation the sentence never required, and charges it to the ~100% of users with one org.

# The three remaining decide-items, answered by measurement

## 1. ⛔ THE `useOrg()` SEAM DOES NOT EXIST. It is the thing to be BUILT, not the thing to confirm.

**Measured:** `grep -rn "useOrg\|useCurrentOrg\|OrgContext\|OrgProvider" apps/web/src` returns **exactly one
line, and it is a comment** — `App.tsx:235`, naming the hook as deferred.

There is **no hook, no context, and no provider.** Nothing reads through a seam, because there is no seam.
**Fourteen files each fetch `GET /organizations` themselves and each take `[0]`.**

> ⭐ **SO THE FINDING IS INVERTED, AND IT MATTERS FOR THE ESTIMATE.** "33 files read the hook and none of
> them change" would make B nearly free. The truth is that **fourteen files change**, because the hook they
> would read does not exist yet. B is still the right shape — the work is still confined to the surface
> that is wrong — but it is a fourteen-file edit, not a one-file one.

⚠ **Nothing "reaches around" the hook. Every single site reaches around it, because there is nothing to
reach around.** `App.tsx`/`RequireOrg` is the sole exception and needs no change: it asks *whether*, never
*which*.

## 2. The login `Organization` field — ⛔ RELABEL. It is not left alone.

It stays SSO-only, as ruled. But it currently sits above the password form labelled `Organization` with
placeholder `acme`, and **a user in two orgs will read it as tenant selection, type the org they want, sign
in with a password, and land in the other one** — because the value reaches exactly one call, the `?org=`
query on `/auth/sso/{provider}/start`, and is never read on the password path.

⛔ **A control that looks like it steers and does not is worse than no control**, and once a switcher exists
the harm is no longer hypothetical: the user now has a *correct* place to switch, and this field competes
with it.

**Ruled into the build: label it for what it does, and show it only where it does it.**

## 3. ⭐ SERVER-SIDE MEMBERSHIP ENFORCEMENT — **ALREADY COMPLETE. MEASURED. NO WORK NEEDED.**

The concern is exactly right in principle — *a switcher that only changes client state is a
client-invented boundary* — and the measurement says the server already refuses to accept one:

```go
// http/session.go:36 — rebuilt from the DATABASE on EVERY request, keyed on the session's user
memberships, err := q.ListMembershipsByUser(r.Context(), sess.UserID)
roles := make(map[uuid.UUID]string, len(memberships))

// http/handlers.go:64 — every org-scoped route
role, member := p.RoleIn(orgID)
if !member { return apierr.NotFound("org_not_found", "organization not found") }
```

⛔ **The client cannot influence `Roles`.** It is not carried in the token, not sent by the browser, and not
cached across requests — it is a query against `memberships` for the authenticated user, per request.
`bearer.go:61` does the same for token auth. An org ID the caller is not a member of is refused **before
any handler runs**.

⚠ **And the refusal is a 404, not a 403** — the no-oracle convention: a switcher that somehow requested a
foreign org would learn nothing about whether it exists.

> ⭐ **SO THE SWITCHER IS PURELY A VIEW CONCERN, PROVABLY. It selects among orgs the server will already
> authorize; it cannot select one the server would not.** That is what makes B safe as well as cheap.

⚠ **In scope anyway: a test that asserts this**, because the property is currently true by construction and
nothing names it. If a future change caches `Roles` at login, the switcher silently becomes the boundary.

# The build's own record

## ⭐ THE SERVER-SIDE FINDING, MEASURED — write it down so the next person does not re-do it

> ## ⭐ **A SWITCHER NEEDS NO NEW AUTHORIZATION WORK. THAT IS WHY B IS CHEAP, AND IT IS MEASURED, NOT ASSUMED.**

**The client never names the organization it is allowed to act on.** Three independent layers, each checked:

| Layer | Measured |
|---|---|
| **1. The principal** | `Roles map[orgID]role` is rebuilt from `ListMembershipsByUser` on **every request** — `http/session.go:36` (cookie) and `http/bearer.go:61` (bearer). Never sent by the client, never in a token, never cached across requests. |
| **2. The path org** | `authorize(ctx, orgID, perm)` → `p.RoleIn(orgID)`; a non-member gets **404 `org_not_found`** before any handler runs (`http/handlers.go:64`). ⚠ There is **no function named `orgFromPath`** — the check is real, the identifier is not; it lives inside `authorize`. |
| **3. The queries** | Org scoping is in the SQL itself: **203 `org_id` references across 17 query files** (`org_id = $1` ×74, `$2` ×20, and so on). ⚠ Not 20 — that understates it by an order of magnitude. |

⛔ **So the switcher changes which `orgId` the pages SEND, and nothing else.** Sending a foreign one produces a
404 from layer 2 and would produce no rows from layer 3 even if it did not. **The client is not one of the
three layers**, which is precisely why it cannot invent a boundary.

⚠ **Asserted, not left to construction** — `apps/api/internal/http/org_membership_boundary_test.go`. The
property is true today by accident of design; caching `Roles` at login is an obvious-looking optimisation
that would silently promote the switcher into the boundary, and no other test would notice.

## ⛔ THE LOGIN FIELD — RULED (b): KEEP IT, LABEL IT

### (a) — hide it on the password path — CONSIDERED AND **REJECTED**

⛔ **It would remove the ONLY working SSO entry point for a customer whose IdP is configured.**
`/auth/sso/{provider}/start` **requires** `?org=`; with no field there is no way to supply it, and SSO sign-in
stops working entirely.

> ## ⛔ **A REAL REGRESSION TRADED FOR A COSMETIC ONE.**

⚠ **RECORDED SO NOBODY LATER "TIDIES UP" BY DELETING IT.** The field looks decorative on the password path
and is load-bearing for SSO. Anyone removing it should have to argue past this paragraph.

## ⛔ ONE ORGANIZATION → THE SWITCHER IS **ABSENT**. A decision, not a side effect.

`OrgSwitcher` returns `null` when `orgs.length < 2`. **Absent, not present-and-inert.**

⭐ **A control with one option teaches nothing and clutters every screen**, and a disabled dropdown invites
the reader to wonder what is wrong with their account. Almost every user has exactly one organization, so
present-and-inert would be the *common* case and the useful case would be the exception.

> ⭐ **AND ITS ABSENCE BECOMES INFORMATION: seeing the switcher means you belong to more than one tenant.**
> That is worth knowing before you delete something.

⚠ **Written down because it would otherwise read as a side effect of the list having one entry** — and the
next person, finding a control that sometimes is not there, would have no way to tell the difference.

## ⚠ ONE MEASUREMENT HELD AGAINST THE BRIEF: THE SEAM'S 33 CONSUMERS DID NOT EXIST

The build was directed on the basis that `useOrg()` was an existing seam with 33 consumers that would not
change. **`grep -rn "useOrg\|useCurrentOrg\|OrgContext\|OrgProvider" apps/web/src` returned exactly one
line, and it was a comment** — `App.tsx`, naming the hook as deferred.

**Fourteen files changed**, because the seam they would have read did not exist. ⭐ **B remained the right

rewire, and the estimate that made it look nearly free was of a seam that had never been built.
