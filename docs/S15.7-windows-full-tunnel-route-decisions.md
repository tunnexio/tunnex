# S15.7 — Windows full-tunnel endpoint route selection

Status: locked design (implementation follows)

## Problem

Windows full tunnel installs split-default routes on the Wintun adapter and
must pin the WireGuard endpoint to the real physical default route. The current
selection compares only the route metric. Windows routing priority is the sum of
the route metric and the interface metric, so a multi-adapter machine can pin
the endpoint through the wrong physical interface and lose egress once the
full-tunnel kill switch is armed.

## Decisions

### D1 — Select the effective physical default route (locked)

The helper selects an operational, non-tunnel default route by the Windows
effective metric: `route metric + interface metric`. It preserves the selected
route's LUID and next hop when creating the endpoint host route.

### D2 — Never use a down interface as an endpoint escape route (locked)

Candidate routes on interfaces that are not operationally up are excluded. If
there is no physical default route, retain the existing no-op behavior rather
than inventing a gateway.

### D3 — Local proof is a substitute, not a Windows wire proof (locked)

The selection logic gets regression coverage and Windows cross-compilation in
this slice. A real Windows full-tunnel run remains required before declaring
the observed outage fixed: it must show a handshake, a pinned endpoint route,
working direct-IP egress, and DNS resolution.
