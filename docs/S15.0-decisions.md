# 1. SCOPE, FIXED BY MEASUREMENT — argued here so it is not re-derived later

The registration paper's cost model was refuted by its own measurement pass. The scope below is what survived,
with citations, and it is the reason this is a commit-one about a **principal** and not about a destination.

## 1.1 The destination half is ALREADY SHIPPED

`resources` carries `cidr` + `protocol ∈ {any,tcp,udp}` + `port_low`/`port_high` under live CHECKs
(`resources_check`, `resources_port_low_check`, `resources_port_high_check`). **An MCP server at
`10.1.2.3:8080/tcp` is expressible today, with zero schema change**, as a `resource` with
`protocol=tcp, port_low=port_high=8080` referenced by the existing `dst_kind='resource'`.

⛔ **AND A NEW `dst_kind` WOULD BE INVISIBLE TO ENFORCEMENT BY CONSTRUCTION.** `hashAllow`
(`apps/api/internal/policyspec/hash.go:15-21`) is exactly five fields — `{SrcIP, DstCIDR, Protocol, PortLow,
PortHigh}`. **`dst_kind` never reaches the compiled artifact.** By the time enforcement sees a destination it
is resolved addresses and ports; a `resource` and a hypothetical `mcp_server` are indistinguishable to it.

**The `k8s_service` precedent claim is struck.** `policy_rules` uses a **discriminator column per kind** under
an exclusive-arm CHECK (`policy_rules_check`), so a new kind costs a new column + two constraint rewrites +
compiler resolution + goldens — **to add something enforcement cannot see.**

**No version bump, structurally.** `RequiredVersion` (`apps/api/internal/policyspec/policyspec.go:128-149`)
triggers only on `VIPMappings`/`K8sDNSZones`→7, `PoolCIDR`→6, `Routes` or a CIDR `SrcIP`→5, else 4. A
CP-resolved destination emits an `AllowEntry` **byte-identical in shape** to a resource's — nothing for an old
agent to fail to understand, therefore nothing to refuse.

## 1.2 The audit half is INHERITED — conditionally, and the condition binds

`src_device_id` is **agent-stamped from the compiled artifact's `/32`→device map**; the CP performs one FK
join to `src_user_id` (`apps/api/internal/accesslog/ingest.go:40-75`). Explicitly **not** an `src_ip` lookup.

⛔ **THE CONDITION: attribution works IFF the principal is a `/32` the artifact maps to a device.** A
principal shape that is not address-bearing goes dark on attribution **silently — the flow log will not
complain.** That is a constraint on the principal design (**D15**), not a property of the audit layer.

## 1.3 The principal IS the epic

`devices.user_id` carries **three loads at once**: the per-user device cap
(`apps/api/db/queries/devices.sql:98-104`), the posture cut's *"which human account launched it"*, and any
future delegation link. **One column, three questions.**

`machine_credentials` has **no `user_id` column** — live schema: `id · org_id · name · role · token_hash ·
fingerprint · created_at · last_used_at · revoked_at`.

> ## **THE DESTINATION HALF IS SHIPPED. THE AUDIT HALF IS INHERITED. THE PRINCIPAL IS THE EPIC.**

Previously carried as *unverified — unlocated, not absent.* ⚠ **The first search was aimed at a package that
does not exist (`internal/authn`); it lives in `authctx`.** *An absence found by one encoding is not an
absence* — this one was found by the second.

| question | answer |

| **values** | `AuthLocalPassword` · `AuthSSO` · `AuthBearer` · `AuthMachine` · `""` (legacy) |

# 2. WHAT THE SELF-HOSTED INDUSTRY ACTUALLY DOES

Written against sources rather than memory, because this is the section that stops us re-inventing.

## 2.1 Teleport — `rfd/0209-mcp-access.md`, implemented in 18.1

MCP servers are registered as **apps** under the existing Application Service — deliberately reusing HTTP/TCP
app machinery rather than building a new service. The connection handler parses the stream into JSON-RPC
messages and tracks type by message id.

**The enforcement shape, and it is the part to copy:**

- on `tools/call` — check the access-checker; **if denied, synthesise an error result and return it to the
  client without forwarding upstream**
- on the response to `tools/list` — filter out tools the identity may not call
- ⛔ **THEY DO BOTH, AND THEY SAY WHY: filtering the list is not enforcement, because nothing prevents a
  malicious client from calling a tool that was never listed.**

**Audit:** `mcp.session.start`/`.end`, `mcp.session.request`, `mcp.session.notification`; a denied
`tools/call` carries the error. **`tools/list` and `resources/list` are deliberately NOT recorded — too
frequent.** ⚠ Note for us: that is a real tension with a flow-log product, and it is a considered choice
rather than an oversight.

⛔ **AND A DEFAULT FLIPPED BETWEEN PAPER AND PRODUCT, IN THE DIRECTION WE SHOULD COPY.** RFD 0209 specifies
that if `mcp.tools` is unspecified, **all tools are allowed**. The shipped documentation says **no tools are
allowed if unspecified**. They moved from fail-open to fail-closed between design and ship. **Take the shipped
default.**

## 2.2 Octelium — the transferable method

**No bespoke MCP engine.** MCP is treated as JSON-RPC over HTTP and generic L7 body policy is applied — a CEL
expression over the parsed body (`bodyMap.method == "tools/call"`, `params.name in [...]`, argument-level
predicates), gated on request buffering with a max size. Argument-level policy falls out for free.

⚠ **AND THE GAP IS INSTRUCTIVE: no `tools/list` RESPONSE filtering was found in their MCP guide.** So a client
sees tools it cannot call and discovers the boundary by hitting a refusal. **Enforcement is the request half;
catalog filtering is the UX half. Shipping only the second would be the defect; shipping only the first is
defensible and must be SAID.**

## 2.3 agentgateway — Linux Foundation / Agentic AI Foundation

Rust data plane, Cedar policy, **tool federation** — one endpoint fronting many MCP servers with a per-client
virtual catalog. Their founding argument was that MCP's **statefulness** defeats ordinary gateways: long-lived
sessions, server-initiated messages, `tools/list` fan-out needing per-session response adjustment.

⛔ **`2026-07-28` substantially undercut that argument** — stateless core, `Mcp-Session-Id` retired. Their
federation value stands; the "you need a new kind of proxy" claim does not, to the same degree.

## 2.4 What NONE of them has — and the honest bound on our claim

**Cross-organisation delegation.** agentgateway says so in its own framing: it is governance **for your trust
domain**, and the cross-org trust layer (DIDs, verifiable credentials, delegation chains surviving an org
boundary) is still missing across the field.

> **Intra-org agent identity is PARITY, not catch-up. The paper must not imply the cross-org half.**

# 3. DECIDE-ITEMS — FIVE RULED, ONE HELD

## ⭐ D14 — the ruling everything else waits on

**`machine_credentials` has no `user_id`. Every machine principal shipped today is ALREADY OWNERLESS.**

> ## **THE QUESTION IS NOT "PERMIT OWNERLESS AGENTS". IT IS "KEEP THE OWNERLESS PRINCIPAL WE ALREADY HAVE."**

**The mechanical argument, which replaces the philosophical one:**

> **An ownerless agent is outside the cap query (`user_id`-keyed), outside any delegation link, and STILL
> INSIDE THE POOL. It costs the scarce thing and escapes both accountable ones.**

⚠ **AND DELEGATION EXISTS IN NEITHER LAYER.** `audit_logs` carries `actor_user_id` and `actor_system` as
**parallel columns, not a chain** — an event is attributed to a human OR a subsystem, never *"this system
acting for that human"*. `X-Tunnex-Cause` (S10.2) supplies **which CR triggered this**: provenance of the
TRIGGER. Delegation is provenance of the AUTHORITY. **The operator has the first and not the second.**

## ⛔ **RULED (2026-08-04): AGENTS ARE OWNED. OWNERLESS PRINCIPALS ARE NOT KEPT.**

**The mechanical argument above IS the reason for the ruling** — not a supporting note to it.

### ⛔ THIS IS A CHANGE TO SHIPPED BEHAVIOUR, NOT A GREENFIELD CHOICE

`machine_credentials` has **no `user_id` today**, so **every existing machine principal is ownerless and must
migrate.** The ruling is therefore not "new principals get an owner" — it is "the ones already running stop
being exempt".

### THE MIGRATION SHAPE — papered now, so it does not arrive during a slice

**The question the migration turns on: what happens to a credential that has no owner to assign?**

There is no `created_by` on `machine_credentials` (live schema: `id · org_id · name · role · token_hash ·
fingerprint · created_at · last_used_at · revoked_at`), so **for an existing credential the minting user is
not recoverable from the row.** That forecloses the cheapest option before it is proposed.

The three shapes, with what each costs:

| shape | what it does | cost / objection |
|---|---|---|
| **back-fill from audit** | recover the minter from `audit_logs.actor_user_id` on the mint action | ⚠ **depends on retention** — a credential older than the audit window has no answer, and a partial back-fill is the worst outcome: some owned, some not, with nothing marking which |
| **require re-mint** | existing credentials are revoked; operators mint fresh, owned ones | honest and complete. **Breaks running GitOps operators at the moment of upgrade** — this is the real cost and it must be scheduled, not discovered |
| **grandfather as a named exception** | existing rows keep `user_id NULL` under an explicit flag | ⛔ **REJECTED BY THE RULING'S OWN LOGIC — it leaves the ownerless principal alive under a different name**, which is the outcome the ruling closes |

⛔ **AND THE NULL COLUMN IS ITSELF A DECISION.** If `user_id` is added nullable to permit migration, the
nullable state IS the grandfather clause whether or not it is called one — and *absence must be the closed
state* applies: a NULL owner must be **refused at use**, not merely un-set at rest. **If it is nullable, name
the enforcement point that refuses it.**

**→ RESOLVED BY D19 (below).**

## ⛔ D19 — THE MIGRATION SHAPE. **RULED (2026-08-04): ASSIGN-EXPLICITLY.**

**An admin names an owner for each existing machine credential.** A fourth shape, and it is the one that
guesses nothing and breaks nothing.

**Why not the three costed above:**

- **not derived from `audit_logs`** — no retention dependency, and **no partial back-fill**, which this paper
  already identifies as the worst outcome: some owned, some not, and **nothing marking which**
- **the credential SURVIVES**, so a running GitOps operator does not break at upgrade
- **grandfather stays rejected** by D14's own logic

> ## ⚠ **AND THE RE-MINT OBJECTION MATTERS MORE THAN IT LOOKS. Breaking a live operator at the moment of
> ## upgrade is the S13.1 CLASS — a gateway that stops working during an ordinary maintenance action — and
> ## S13.1 cost an entire epic.**

| # | step | note |

# 7. D14/D19 — THE TWO OWED QUESTIONS, CLOSED

Both were owed *before* a slice, precisely so they could not arrive during one.

## 7.1 ⛔ WHERE A NULL OWNER IS REFUSED

**The problem restated:** step 1 ships `user_id` **nullable**, and *a nullable `user_id` IS the grandfather
clause whether or not it is called one.* **Until the refusal point is named, step 1 ships the thing D14 ruled
against.**

### MEASURED — the use path funnels through exactly ONE function

A machine credential is **used** via the resolver at `apps/api/internal/http/machine_bearer.go:25-51`. It is
**the only place a `*authctx.Principal` carrying a `MachineID` is constructed.** Every handler downstream
receives an already-built principal; none of them re-reads the credential.

**And that seam already fails closed FOUR times, all by the same `return nil, nil`:** unknown token (`:32`),
DB error (`:35`), **revoked** (`:39`), and the no-oracle rule that makes all three indistinguishable.

> ## **SO THE REFUSAL IS ONE LINE AT ONE SEAM, BESIDE FOUR REFUSALS THAT ALREADY LIVE THERE.**
> ## A credential with no owner is refused exactly where a revoked one is.

⛔ **AND IT MUST NOT BE RESTATED PER HANDLER.** *A guard made the caller's responsibility is inherited by every
new caller* — that law cost this repo **seven call sites, four of them wrong, and a fourth instance of the
same fix**. The machine path is the one place in the product where that mistake is currently impossible to
make, because there is only one constructor. **Keep it that way.**

### ⭐ THE TYPE CAN MAKE IT IMPOSSIBLE, AND THIS IS THE CHEAPEST MOMENT IN THE EPIC TO GET THAT

`authctx.Principal` is built here as a **struct literal** — every field optional by construction, which is
exactly how `policyHealthBadge` came to be *structurally forbidden from forming the verdict it was named for.*

**The owner field does not exist yet.** So the choice is available now and will not be again:

| shape | what a forgetful caller gets |
|---|---|
| add `OwnerID` as another optional field | compiles. **Discipline.** The `policyHealthBadge` shape, reproduced deliberately |
| ⭐ **a constructor — `authctx.NewMachinePrincipal(ownerID, cred, …)` — that cannot be called without an owner** | **does not compile.** Construction |

> ## **A GUARD ENFORCED BY TYPES BEATS ONE ENFORCED BY DISCIPLINE, AND THE TYPE DOES NOT EXIST YET.**
> ## Adding the field first and the guard second is choosing the weaker one on purpose.

⚠ **The type cannot cover the DB read** — `cred.UserID` arrives nullable from Postgres during steps 1–3 and
something must still refuse `NULL` at the seam. **Types make the PRINCIPAL impossible to build wrong; the
seam check makes the ROW impossible to use.** Both, and the seam check retires at step 4 when the column
contracts to `NOT NULL`.

### THE RED, NAMED

**A machine credential with a NULL owner, USED, must be refused** — same 401 shape as a revoked one, no
oracle.

**The mutation that proves it:** remove the NULL-owner check from the seam and the red must fail. ⚠ **And a
second red for the direction that is easy to miss: an owned credential must still be ACCEPTED** — a guard that
refuses everything passes the first red and is not a guard. *A count used as a guard must count what it guards
against.*

## 7.2 THE ASSIGNMENT SURFACE — what an admin sees in step 2

**Real work, not a footnote.** *A capability with no caller is one nobody can reach* — the verb census
measured that class at **eleven** in this product.

### What must be on screen, minimum

| field | why it is needed to CHOOSE |
|---|---|
| `name` | the only human-meaningful handle |
| `fingerprint` | disambiguates two credentials with the same name — **the duplicate-name case this repo has now hit three times** |
| `created_at` | age is the strongest available proxy for provenance when provenance is absent |
| `last_used_at` | separates a live operator from an abandoned credential |
| **currently in use** | ⛔ **assigning an owner to a credential mid-flight is a different act from assigning one to a dormant row**, and the admin must know which they are doing |

### ⛔ THE SCREEN MUST NOT IMPLY THE SYSTEM KNOWS THE ANSWER

**`created_by` does not exist** (live schema: `id · org_id · name · role · token_hash · fingerprint ·
created_at · last_used_at · revoked_at`). **The admin is CHOOSING, not CONFIRMING.**

⛔ **No pre-selected owner, no "suggested" owner, no most-likely-minter.** A pre-filled field is *a
client-invented value sitting where a server fact belongs* — this repo has filed **both directions** of that
error. The copy must say the system does not know, because it does not.

### PERMISSION

**Owner-only, matching `machine:manage`** — the verb that mints these credentials. ⚠ **Reasoned, not
inherited:** assigning an owner decides *whose* cap the credential spends and *whose* name appears in the
delegation link, so it is at least as consequential as minting. A narrower gate would be a hole; a wider one
would let a non-owner assign accountability to someone else.

### ⚠ THE EMPTY STATE, AND IT MUST BE EARNED

**Zero unassigned credentials reads as "all owned."** On a **migration** screen that is precisely the
reassurance that must be earned rather than defaulted to — *the more a view exists to surface a problem, the
more dangerous its empty state.*

**Two states, two sentences, never one:**

- **"No machine credentials exist"** — nothing to assign
- **"All machine credentials have an owner"** — the migration is complete

⛔ **And a third that must be distinguishable from both: the list failed to load.** An unreachable query
rendering as an empty list is *"migration complete"* written by an error path.

# 10. D21 — IS AN UNVERIFIED ACCOUNT ELIGIBLE TO OWN A MACHINE CREDENTIAL?

**Status: OPEN — surfaced at the S15.1 founder review, first pass. Not decided.**

The picker lists every member of the org, `unverified-admin@demo.tunnex.local` included. The founder
asked whether it should, and explicitly said to surface rather than resolve it.

**The facts, so the ruling has something to stand on:**

- An unverified account **cannot perform org mutations** — the surrounding Settings controls are gated
  `canEdit={emailVerified}`. On capability grounds it is already a second-class principal.
- **But ownership here is accountability, not capability.** The owner does not act; the machine acts
  *for* them. Excluding unverified accounts means a credential cannot be assigned to the person who is
  genuinely responsible for it until they click a link in an email — and D14's whole argument is that
  an *unowned* credential is the bad state.
- **And the inverse is real.** An unverified address may not reach a person at all. An audit trail that
  names an address nobody has proven they control is weaker than it looks, and this field exists to be
  leaned on precisely when something has gone wrong.

⚠ **THE TWO ARGUMENTS DO NOT MEET IN THE MIDDLE.** One says an owner must be reachable; the other says an
owner must be assignable *now*, because the alternative is NULL and NULL is refused at use. A middle
option exists and is not free: allow the assignment, mark the row as owned-by-an-unverified-account, and
carry that on the audit record — more surface, and it invents a third ownership state that the schema does
not have.

⛔ **D19 RULED assign-explicitly AND DID NOT RULE ON ELIGIBILITY.** That is the gap; it is not a
re-litigation of D19.

**Not blocking S15.1.** The picker's current behaviour (all members eligible) ships unchanged, and this
records that it shipped as an *unruled default* rather than as a decision — so a later ruling is a change
of mind about a known open question, not the discovery of an accident.

# 14. D23 — **A FAIL-OPEN THAT UNDERCUTS D14.** HELD FOR RULING; NOT BUILT.

**Found while answering D21's edge. Surfaced before S15.1 closes, deliberately not folded into it.**

## The defect

`MachineAuth` (`machine_bearer.go`) checks **`cred.RevokedAt`** and **`cred.UserID.Valid`**, and nothing
else. So a credential whose owner is **deactivated**, has **lost email verification**, or has been
**removed from the org** keeps authenticating — indefinitely.

> ## **THAT IS THE D14 RULING WITH ITS POINT REMOVED.** Credentials were bound to owners *so that
> ## accountability exists*. The moment the owner stops being accountable, nothing stops the credential.

⚠ **D21 makes it sharper, not softer.** As of this story we **refuse to assign** an unverified owner —
and we **accept one indefinitely at use**. The gate is at the door and the room has a window. The
inconsistency is new, and it is ours.

| the owner… | today |
| --- | --- |
| **deleted** | cannot happen — FK `ON DELETE RESTRICT` |
| **deactivated** | **credential keeps working** |
| **loses email verification** | **credential keeps working** |
| **removed from the org** | **credential keeps working** |

## The two dispositions

### 1 — CHECK THE OWNER'S STANDING AT USE *(recommended)*

**In the same seam that already refuses NULL**, beside the two arms that are there — `RevokedAt`,
`UserID.Valid`, and now the owner's standing. ⛔ **One place, not restated per handler.** Every handler
re-implementing an auth predicate is the class this repo has paid for before: a guard made the caller's
responsibility is inherited by every new caller, and the census is never run again.

Mechanically it is one extra condition on the credential lookup — the row already joins nothing, and
`GetMachineCredentialByHash` can carry the owner's `status`/`deleted_at`/`email_verified_at` the same way
`ListMachineCredentialsForOrg` now carries `owner_email`.

⛔ **AND THE COST IS AN OUTAGE WITH A HUMAN CAUSE, STATED PLAINLY:** the moment an offboarded employee is
deactivated, **every GitOps operator they owned stops authenticating.** Pipelines fail. Reconciles stop.
Nothing warns anybody first, and the failure surfaces in CI logs belonging to a team that did not perform
the deactivation.

> ## **THAT IS CORRECT BEHAVIOUR AND IT IS STILL AN OUTAGE.** Both halves are true and the second does not
> ## excuse the first. This is exactly the class D19 refused to solve with a re-mint: the recovery path
> ## cannot be "mint a new credential in a hurry", because that is the path that produces unowned
> ## credentials, which is what D14 exists to end.

**So it needs an operational answer, not just a check** — and that answer is the actual decide-item:

- **reassignment before deactivation**: the offboarding flow lists what the leaver owns and refuses, or
  warns, until each is reassigned. Turns a surprise outage into a checklist item.
- **a grace window**: the credential keeps working for N days after deactivation while the screen shows it
  as orphaned. ⚠ Softer, and it reintroduces exactly the window D14 closed — an unaccountable credential
  that still works. Recorded as an option, not a recommendation.
- **surface first, enforce later**: ship the *orphaned-owner* state on this screen with no enforcement,
  measure how many real credentials are in it, then enforce. ⛔ **This is the unlock-then-opt-in convention
  applied to a security check**, and it is the honest order given nobody knows the blast radius yet.

### 2 — EXPLICITLY OUT OF SCOPE, WITH THE REASON WRITTEN DOWN

Defensible only if the reason is that **the fix is not machine-credential-shaped.** Whether a principal's
loss of standing propagates to credentials that name it spans **devices, sessions, OpenVPN certs and
machine credentials** alike — and S7.5.2 already produced a deprovision fail-open cluster in precisely this
shape. Fixing one of N here would imply the other N were considered.

⚠ **But "out of scope" must not be recorded as "not a defect".** It is a fail-open, it is live, and it is
now *inconsistent with a ruling made in the same story*.

## Recommendation

**Disposition 1, sequenced as surface-first**: ship the orphaned-owner state on the credentials screen
(no enforcement), measure, then enforce at the seam with a reassignment path in the offboarding flow.
That gets the honest signal onto the screen immediately without turning a deactivation into an unannounced
outage, and it keeps the enforcement in **one** place when it lands.

⛔ **HELD. Not built, not started.** The founder rules it.

## 15.1 ⭐ THE FIXTURE COULD NOT HAVE FAKED THIS, AND THAT IS WHY THE SUBSTITUTE IS HONEST

The seeded credentials carry `sha256('fixture-<name>')` as their `token_hash` — **a digest belonging to no
issued token.** They render on the screen and they **cannot authenticate, by construction**, because no
string hashes to them.

⛔ **SO THE WIRE PROOF COULD NOT HAVE BEEN FAKED WITH THE FIXTURES EVEN BY ACCIDENT.** A fixture that
authenticated would have been a seeded backdoor; the same property that makes it safe makes it useless for
this proof, and it forced the honest answer — *there is nothing live to demonstrate against* — instead of a
green that meant nothing.

> ## **A FIXTURE BEING HONEST IN THE DIRECTION NOBODY CHECKS.** Fixtures are normally audited for being too
> ## NARROW — the `owner_email` field this very story found missing. This one is audited for being too
> ## CAPABLE, and it was already right: `-- ⚠ token_hash is random and belongs to no issued token: these are
> ## DISPLAY fixtures. They can never authenticate, which is correct — a seeded credential that worked would
> ## be a seeded backdoor.`

⚠ **That is the difference between a SUBSTITUTE and an UNTESTED CLAIM.** The substitute names what could not
run and why it could not run. Had the fixtures been able to authenticate, the proof would have "passed"
against a credential no operator will ever hold.
