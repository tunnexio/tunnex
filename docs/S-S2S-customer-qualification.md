## MTU, MSS, PMTUD and large-packet matrix

AWS Site-to-Site VPN has a maximum MTU1446 and IPv4 MSS1406, with smaller safe values depending on negotiated ESP algorithm and NAT traversal. Jumbo packets are not supported; AWS VPN does **not** support Path MTU Discovery. These limits apply to VGW/TGW and routing mode does not remove them. [AWS VPN quotas](https://docs.aws.amazon.com/vpn/latest/s2svpn/vpn-limits.html).

For the current fixed AES-CBC/SHA2-256 profile, AWS documents MTU1438/MSS1398 without NAT-T and MTU1422/MSS1382 with NAT-T. Do not promise1446 or derive payload from an assumed cipher. Capture actual IKE/CHILD transform, integrity, UDP encapsulation, outside IP family, physical underlay MTU, XFRM MTU and actual TCP options in each direction. Lower underlay PMTU may require a smaller qualified value. [AWS customer gateway sizing](https://docs.aws.amazon.com/vpn/latest/s2svpn/cgw-best-practice.html).

Current source `kernel_apply.go` defines `AWSIPv4TunnelMTU=1422`, lowers owned oversized/legacy XFRM links and preserves smaller operator-qualified values; it is a profile ceiling, not measured PMTU. This code is shared with BGP although its comment names static. The current cycle9 v8 worker source installs lease/interface/grant-bound TCP MSS clamps using the actual owned tunnel MTU, including TCP under ANY grants while leaving UDP unchanged. Native component readback and packet tests passed. Freshly verified physical/route MTU can lower owned tunnel MTUs conservatively before renewed authority; unseen downstream bottlenecks are not discovered. Readback of1422 MTU alone does not establish successful large transfers. Live qualification remains separately bound to the serving binary.
