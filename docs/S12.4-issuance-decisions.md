# 1. ⭐ WHY ISSUANCE IS MANUAL — AND THE REASON IS NOT "WE ARE SMALL"

**FOUNDER-RULED: keys are signed and issued by a human, deliberately.**

The reason is structural and it will still be true at a hundred customers:

> ## ⛔ **OFFLINE VERIFICATION MEANS THERE IS NO REVOCATION. A KEY THAT LEAVES HERE IS ALIVE UNTIL ITS
> ## EXPIRY, AND NOTHING WE DO AFTERWARDS CAN REACH IT.**

That is not a gap — it is the product's central promise. `architecture-licensing.md` §5 already recorded the
trade: *"You trade instant revocation for sovereignty."* The customer's deployment never calls home, which
is the reason a sovereignty buyer picks Tunnex, and it is exactly why a mis-issued key cannot be recalled.

**Combine that with automated minting and you get a system in which a mistake cannot be taken back.** A
malformed band, a wrong expiry, a trial granted to an abusive requester, a bug in the form handler — each
becomes a permanent grant. There is no "oops, revoke it" and there never will be.

> ## ⭐ **A HUMAN IN THE LOOP IS A DESIGN PROPERTY OF AN UNREVOCABLE SYSTEM, NOT A SHORTCUT WE OUTGROW.**

⚠ **The thing that would change this ruling is REVOCABILITY, not VOLUME.** If keys ever become short-lived
enough that a mistake expires before it matters — the reissue model in §5 of the architecture doc — the
argument weakens. Volume alone never weakens it: a hundred automated mistakes are worse than ten manual
ones, not better.

# 2. WHAT GETS BUILT

Four pieces, all on Cloudflare, all outside the product repo's runtime path.

| piece | what it does |
| --- | --- |
| **Worker — request form** | company · contact · band · term · use case. Public, unauthenticated, rate-limited |
| **D1 — store** | `requests` · `issued_keys` · **`domain → trial_issued_at`** so one company cannot take repeated trials |
| **Ed25519 signing** | WebCrypto inside the Worker. Private key as an encrypted Worker secret |
| **Admin view** | pending requests, and ONE action: sign and email |

**The admin action is deliberately one button and not a form.** Everything that determines what the key
says — band, term, domain — is captured at request time and reviewed; the signing step approves or it does
not. A signing screen with editable fields is a second place for a typo to become an unrevocable grant.

# 3. ⛔ THE PRIVATE KEY IS THE WHOLE COMMERCIAL MODEL

**Stated here, in the paper, rather than in a comment above the signing function.**

> ## ⛔ **IF THE SIGNING KEY LEAKS, ANYONE CAN MINT A VALID LICENCE, FOR ANY BAND, WITH ANY EXPIRY,
> ## FOREVER — AND YOU WILL NOT KNOW.**

Three properties, and it is their combination that matters:

1. **Unlimited.** The key authorises minting, not one licence. A leak is not a lost sale; it is the end of
   the commercial model as a mechanism.
2. **Unrevocable.** §1. Every key minted with the stolen secret is alive until its own expiry, and the
   attacker chooses the expiry.
3. ⛔ **UNDETECTABLE.** Deployments never call home. **There is no telemetry that could show a key we did
   not issue being used, because that telemetry is precisely what the product promises not to have.**

## 3.1 Rotation, and what it costs

The public key is **baked into the binary at build time** (`architecture-licensing.md` §3). So rotating the
signing key means:

**a new binary → every customer upgrades → every live key re-issued.** Customers who do not upgrade keep
verifying against the compromised public key, which the attacker can still mint for. **Rotation is not an
operation we can perform; it is a migration the entire installed base must perform with us.**

## 3.2 ⛔ THE RECOVERY PLAN — AND THE HONEST ANSWER IS THAT IT CANNOT BE TRIGGERED

The founder asked for the recovery plan or a statement that there isn't one. **There is a plan, and it has
a defect that no amount of planning fixes:**

| step | status |
| --- | --- |
| Detect the compromise | ⛔ **IMPOSSIBLE BY CONSTRUCTION.** No deployment reports anything |
| Rotate to a new signing key | possible |
| Ship a binary trusting the new key | possible |
| Get every customer to upgrade | possible, slow, and not in our control |
| Invalidate keys already minted by the attacker | ⛔ **IMPOSSIBLE.** Only expiry ends a key |

> ## ⛔ **THE PLAN EXISTS AND CAN NEVER BE TRIGGERED BY EVIDENCE — ONLY BY SUSPICION.** There is no event
> ## that will tell us to run it.

⚠ **That inverts where the effort belongs.** For a normal secret, you invest in detection and response. Here
detection is structurally unavailable, so **essentially all of the value is in PREVENTION**, and the
response plan is a thing we would execute on a rumour.

**What prevention means concretely, and it is the whole mitigation:**

- ⚠ **CORRECTED DURING THE BUILD.** This paper first said the private key is *"generated inside the Worker
  and never exists in plaintext anywhere else."* **That is not achievable and the implementation proved
  it:** to place a key into a Worker secret you must first hold it as text. **The key exists in plaintext
  exactly once, on whatever machine generates it.**

  > ⛔ **THAT MOMENT IS THE ONLY TIME THE COMMERCIAL MODEL IS COPYABLE — AND IT IS A HUMAN PROCEDURE, NOT
  > A CODE PROPERTY.** It cannot be tested, mutation-proven or enforced by review. It is documented as a
  > CEREMONY in `cloudflare/issuance/README.md`: shell history off, no file, no clipboard manager, no
  > scrollback, `clear` afterwards.

  ⚠ Recorded as a correction rather than quietly fixed, because the original sentence read as a
  guarantee and would have been believed by anyone who did not try to perform it. **After that moment the
  claim holds**: `wrangler secret put` is write-only, and the Worker imports the key as **non-extractable**
  so the runtime — not this document — enforces that production cannot export it.
- **No code path ever exports, logs, or returns it.** The signing function takes data and returns a
  signature; there is no "show key" affordance to be misused later.
- **Access to the Cloudflare account IS access to the commercial model.** Account security (hardware MFA,
  minimal membership) is not IT hygiene here — it is the same asset by another route, and it deserves the
  same seriousness as the key itself.

⚠ **One structural mitigation worth deciding EARLY, because it is cheap now and impossible later** — D4
below: bake a **key SET** rather than a single public key, so a future rotation is a set-membership change
rather than a format change. It does not remove the upgrade migration; it removes the *format* migration on
top of it.

# 4. ⭐ THE PAYMENT SEAM — DOCUMENTED, NOT BUILT

**FOUNDER-RULED: leave payments open as a path; build none of it.**

⛔ **A webhook handler with no provider is dormant machinery, and this repo has already reduced that class
once by removal** (S8.4 round-3 HALT — the resolver release-rider, ripped out precisely because it was
dormant until a later story). **So there is no handler, no route, and no schema for it.**

What exists instead is **one paragraph describing one insertion point**:

> **WHERE:** a provider webhook would arrive at the Worker as a new authenticated route, verified by the
> provider's signature, carrying an order reference and the purchaser's email/domain.
>
> **WHAT IT WOULD TRIGGER:** it would mark the matching `requests` row as paid — and **nothing else.** The
> row still lands in the same admin queue and a human still signs it.
>
> ⭐ **THE SEAM DELIBERATELY DOES NOT BYPASS §1.** Payment answers "should this person get a key"; it does
> not answer "is this key correct". Automating issuance on payment would reintroduce exactly the
> unrevocable-mistake problem the manual ruling exists to prevent. **When payment lands, the human stays.**

⚠ **That is the entire seam.** If a future reader finds themselves adding a table or a route "ready for
payments", they have left the seam and started the machinery.

# 5. DECIDE-ITEMS

## ⛔ D1 — PAYMENT PROVIDER. HELD. RESEARCH INCOMPLETE AND MARKED AS SUCH

**Lemon Squeezy is a Merchant of Record** — they sell in their own name and handle VAT/GST and invoicing.
That is the property that matters, because it moves the tax-collection burden to them.

⚠ **What has been read:** their identity-verification page asks for personal information and a government
ID, and **does not mention business registration on that page.**

⛔ **What has NOT been read, and both must be before this becomes a plan:**

1. **Is India a supported country** for sellers?
2. **Do payouts reach an Indian bank account?**

⚠ **And their page also says additional information may be requested** — so "no business registration
mentioned" is not "no business registration required". **Absence of a requirement on one page is not the
absence of the requirement.**

> ## ⛔ **THE STANDING FACT: TAKING PAYMENT IN INDIA GENERALLY REQUIRES A REGISTERED ENTITY. A MERCHANT OF
> ## RECORD MAY MOVE THAT BURDEN — IT DOES NOT OBVIOUSLY REMOVE IT.**

**Neither of us is qualified to rule that**, and it is the same shape as the relicensing-ordering question
(`S12.1-licensing-decisions.md` §1a): a legal question that wants a professional, recorded so the answer is
chosen rather than assumed.

## ⚠ D2 — TRIAL GATING: `domain → trial_issued_at` IS GAMEABLE, AND THE ARCHITECTURE DOC SAYS SO

The founder specified `domain → trial_issued_at`, which keys on the **email domain**. That stops the
honest repeat and not the determined one: subdomains, look-alike domains, and a second corporate domain all
defeat it.

`architecture-licensing.md` §8 recorded this as an open decision with a recommendation — **DNS-TXT
domain-ownership proof, reusing the S2.5 domain-capture verifier**, which makes "one trial per company"
real rather than nominal.

✅ **RULED: ship `domain → trial_issued_at` now, and record DNS-TXT as the upgrade.**

⛔ **THE TABLE'S EXISTENCE MUST NOT READ AS THE CONTROL BEING IMPLEMENTED. It stops accidents, not
adversaries.**

The reason it is sufficient today is §1's human review — **and that reason is TRUE ONLY WHILE THE VOLUME IS
SMALL.** A person reads every request now, so a determined trial-farmer is caught by a human noticing, not
by the table. **At the volume where nobody reads every request, this control is unimplemented and the table
will still be there looking like it works.**

> ⚠ **RE-READ THIS ROW WHEN REQUEST VOLUME OUTGROWS INDIVIDUAL REVIEW.** That is the trigger — a named
> event, not a date — and it is the same event that reopens §1's manual-issuance ruling from the other
> side.

## D3 — WHERE THE DATA LIVES

D1 (the database) holds company, contact email, domain, band, term. ⚠ `architecture-licensing.md` §6 flags
**Indian customers' billing data under DPDP** as a scoped legal question. Cloudflare D1's region is a choice
with a compliance consequence, and it is cheaper to choose now than to migrate later. **Held, and it is a
lawyer's question, not a session's.**

## ✅ D4 — RULED: BAKE A PUBLIC-KEY **SET**, NOT A SINGLE KEY

**Founder-ruled 2026-08-06.** Every signed key carries a **`kid`**; the product verifies against a SET of
trusted public keys and picks by `kid`.

**The reason is the ruling: cheap now, impossible later.** Adding `kid` to the format before a single key
exists costs a field. Adding it afterwards is a format migration performed on an installed base that
verifies offline — i.e. the thing you would need rotation for in order to do.

### ⛔ AND WHAT A SET DOES **NOT** BUY — stated so nobody reads this as a rotation story

| | |
| --- | --- |
| Keys already minted by an attacker | ⛔ **still run to their own expiry.** Unchanged |
| The installed base | ⛔ **still has to upgrade** to stop trusting the old key |
| Detection of the compromise | ⛔ **still impossible** (§3.2) |

> ## ⭐ **A KEY SET MAKES ROTATION POSSIBLE TO EXPRESS. IT DOES NOT MAKE IT CHEAP.**

What it removes is the **format** migration stacked on top of the upgrade migration — and that second one is
the part that would make rotation *unthinkable* rather than merely expensive. **Expensive-and-possible is a
different category from impossible**, and this ruling buys exactly that difference and nothing more.

### ⛔ THE ONE REFACTOR THAT SILENTLY UN-BUYS D4 — NAMED, SO IT MEETS THE REASON FIRST

**An unknown `kid` must be a REFUSAL. It must never fall back to "the only key we have."**

```js
const key = keySet[payload.kid] ?? Object.values(keySet)[0];   // ⛔ NEVER
```

That line looks like defensive coding and reads like a sensible default. **It turns a key set back into a
single key**, and it does so while **every other test stays green** — signing works, verification works,
multi-kid verification works, and a key signed by a **retired, possibly compromised** kid is accepted
anyway.

> ## ⛔ **IT UN-BUYS THE EXACT PROPERTY D4 WAS RULED FOR: THE ABILITY TO RETIRE A KEY. WITHOUT REFUSAL,
> ## DROPPING A kid FROM THE SET STOPS NOTHING.**

⚠ **Recorded here rather than only in a code comment** because the person who writes that line will be
reading the verifier, not this paper — and the test that catches it
(`cloudflare/issuance/test/licence.test.js`, *"an unknown kid is refused, never fallen back from"*) is the
thing that will actually stop them. **It is mutation-proven: planting that exact fallback fails the
suite.**

## 6.1 ⛔ REGISTER ROW — THE CLOUDFLARE ACCOUNT IS THE SAME ASSET AS THE SIGNING KEY

| item | owner | why it is a register row and not a note |
| --- | --- | --- |
| **Cloudflare account security** | ⛔ **THE FOUNDER'S** | **Access to that account is access to the commercial model by another route** |

Whoever can reach the account can set a new signing secret, read what the Worker does with it, or deploy
code that exports it. **The key's protection is not the key's storage — it is the account boundary.**

> ## ⛔ **IT IS THE SAME ASSET AS THE SIGNING KEY AND MUST BE SECURED AS ONE — NOT AS IT HYGIENE.**

prose paragraph and gets the attention boilerplate gets.**

built so that it does not wait on it: **manual issuance works without an entity, right up to the moment
money changes hands.**

# 6.2 ⛔ TWO OF THIS PAPER'S DECISIONS WERE SOLVED BETTER IN A REPO I HAD NOT READ

**Recorded because the correction is the useful part, not the conclusion.** When the service moved to
`tunnex-web`, two things designed here turned out to already exist there in stronger form:

| this paper proposed | `tunnex-web` already had | why theirs is stronger |
| --- | --- | --- |
| a `trial_domains` table keyed on `domain` | **`trials.domain TEXT UNIQUE`** | a **constraint the database enforces**, not a row a code path is supposed to check |
| an advisory trial verdict recorded at submit | **email verification** (`trial_requests.token_hash` / `consumed_at`) | it **proves control of the mailbox**; mine recorded an opinion about a string |
| `domainOf()` splitting on `@` | **`deriveTrialDomain()` via `psl`** (eTLD+1) | collapses `a@mail.gmail.com` and `a@gmail.com`, and `a@eng.acme.com` with `a@acme.com` — mine treated a subdomain as a different company |

⚠ **AND MY VERSION SHIPPED A DEFECT THEIRS COULD NOT HAVE HAD:** `domainOf` trimmed the domain segment
before checking for whitespace, so `ana@ acme.com` normalised to `acme.com` — an invalid address silently
attributed to a real company. Caught by a test, but the whole function was unnecessary.

> ## ⛔ **I DESIGNED THREE CONTROLS AGAINST A PROBLEM THAT WAS ALREADY SOLVED, IN A REPO I HAD NOT OPENED.**

**The lesson is about ordering, not about these three items.** The founder's instruction named the
destination repo; reading it *first* would have made most of §2 unnecessary. **A design produced without
reading the destination is a design for an imagined codebase** — and it will look complete, because
nothing in it can contradict a repo it never consulted.
