# S10.3b — Kubernetes connector reliability walk

## Purpose

This task closes only defects found while proving private Kubernetes Service
access through a selected Tunnex connector. It applies to any Kubernetes
distribution whose connector uses `hostNetwork`; EKS is the live proof
environment. Public or private LoadBalancer provisioning is explicitly out of
scope for this walk.

## Evidence already obtained

- A Tunnex client resolved an exposed Service name to a synthetic VIP and
  reached its ready NGINX endpoint over HTTP.
- The same proof passed for a `ClusterIP` Service and a `NodePort` Service.
- On the EKS worker that hosts the connector, `table ip tunnex` has a
  forward-hook chain with `policy drop`; unrelated pod-to-CoreDNS, pod-to-API,
  and pod-to-AWS traffic reaches `tunnex_default_drop`.

## Classified findings

1. **P0 — native Kubernetes forwarding is incorrectly captured.** The
   host-network connector must enforce traffic that enters or leaves one of its
   tunnel interfaces, but must not decide ordinary CNI/native node forwarding.
   This is a product defect and is shared by EKS, AKS and on-prem Kubernetes.
   The fix is a native-only pass-through before the overlay policy rules; it
   must not create a tunnel-to-native, native-to-tunnel, or native-to-synthetic
   Service-VIP bypass.
2. **P1 — persistence was disabled for the live demo.** The chart supports a
   PVC, but the current connector intentionally uses `emptyDir`; its enrolled
   identity will not survive a restart. This is a deployment configuration
   limitation, not a chart defect. EBS CSI is an EKS-specific provisioning
   prerequisite; other platforms use their own dynamic StorageClass.
3. **P2 — selected connector has no automatic failover.** This is an explicit
   S10.3a non-goal, not a regression. Multi-connector failover needs a separate
   decision/story and is not silently added here.
4. **Verification outstanding, not a bug:** endpoint churn, UDP, private TLS,
   multi-port exposure and Windows client proof. NodePort and ClusterIP are
   already proven; LoadBalancer is excluded by this task.

## Locked execution order

1. Patch and regression-test the native-forwarding boundary.
2. Release only after the exact revision is green; upgrade the CP with a
   backup, then prove the connector does not break ordinary CNI traffic.
3. Finish the EBS CSI/StorageClass proof and create a PVC.
4. Before converting the live connector from `emptyDir`, mint a new enrollment
   token and perform an explicit re-enrollment/rebind plan. Credentials are
   never copied out of the running pod.
5. Walk endpoint churn, UDP, TLS and Windows as separate evidence legs. A
   failure becomes a new classified finding rather than an unreviewed patch.

## Acceptance for P0

- Native CNI forwarding works with the connector present (DNS, API and HTTPS
  egress are enough to prove the three affected paths).
- A native packet is accepted only when neither interface is a Tunnex tunnel
  interface and its original destination is not an active synthetic Service
  VIP.
- Every packet entering or leaving a Tunnex tunnel remains subject to the
  existing default-deny/explicit-grant policy.
- The rendered nft ruleset remains valid and focused node-agent tests pass.
