# Runtime adapter and dedicated API/UI contract

Decision paper before the next slice. Preserve distinct sandbox domain, creator policy bounds and normal agents.

- Runtime adapter has structured create/inspect/start/stop/delete methods keyed by sandbox UUID and immutable image digest. No shell interpolation, published ports, runtime sockets, host-path mounts, automatic pulls or package installation. Podman rootless capability/preloaded-image admission precedes create. Enforce owned-resource labels before lifecycle actions. A provider start is not Ready.
- Runtime enrollment and policy/SSH readiness are still unfinished. Keep the public create gate closed unless a qualified provisioner is supplied explicitly. The API can deliver real sandbox/template inventory and lifecycle intent, and the dedicated UI can show availability accurately; never create a misleading working sandbox when the runtime is absent.
- API uses generated OpenAPI routes under /organizations/{orgId}/sandboxes, /sandbox-templates and /sandbox-skills. Separate list/detail/create/actions. Current read projections are nonsecret. Action generations preserve CAS. Authenticated human-only handlers plus current store membership/RBAC checks, with no implicit AI Agent authority.
- Proposed template selector remains explicitly an approved runtime configuration selector. Separate image, resources and network scope internally. Skills section initially exposes only approved instruction-only content until a versioned install lifecycle is available; arbitrary package/tool installs are unavailable. Secrets are not accepted by this first instruction-only catalog.
- The selected current template's permitted scope is a ceiling, never the creating user's grant. The creation API rechecks creator scope and returns specific permission/scope/quota/capacity errors. Duplicate create intent uses an idempotency key.
- UI must show disabled/unavailable capacity, actual lifecycle state and unfinished readiness honestly. Separate Sandboxes navigation/list/detail/create; no AI Agent relabeling. Template/skills details and TTL/retention labels remain explicit proposed defaults. Full runtime/user-serviceable product completion still requires enrollment, reconciler, connection readiness and cleanup.
