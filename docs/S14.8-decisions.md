# 1.2 ⛔ THE SCREEN CENSUS CANNOT FIRE ON THIS SLICE, AND THAT IS A COVERAGE BOUNDARY

At S14.7 the census earned its place: it caught `RoutedRanges.tsx` **by name**, and both exact counts refused

**Not a defect. A boundary, and it should be stated rather than left to be assumed away.** What each layer
actually covers:

| layer | question it answers | does it fire on a redesign? |
|---|---|---|
| **screen census** | *is every screen accounted for?* | ❌ counts screens; a redesigned screen is still one screen |
| **component tier** | *does the wiring still make the right decision?* | ⚠ partly — only for the decisions someone wrote a test for |
| **visual leg** | *did the pixels move?* | ❌ **ADVISORY for all of EPIC 14, founder-ruled**; no baseline for this screen |
| **typecheck / build** | *does it compile?* | ❌ silent on deletion |

> ## **NOTHING MECHANICAL ASKS "DID THIS SCREEN KEEP THE PANELS IT HAD."**

That question has exactly one answer today: **the founder looking at it.** Which is the Human Gate Limit
Law's precondition — *the founder can only accept what he can see* — and **§1 says the data will not be
there.** The two findings are the same finding from opposite ends: the only check that covers a redesign is a
human review, and the review is blind until slice 1 lands.

**This is the argument for D1 that does not depend on taste.** It is not "fixtures are nice"; it is that
removing a panel in a redesign is currently caught by nothing else.

**A CANDIDATE, NOT A PROPOSAL** (it would need its own ruling): a per-screen PANEL CENSUS — an exact-count
assertion of the panel titles a screen renders, in the same `toBe` form the screen census uses, so a dropped
panel fails BY NAME instead of being noticed four screens later. It would have caught the four silent drops
on Gateways. **Not built, not assumed; recorded so the boundary has a named remedy.**

## 2.2 ⛔ TWO THINGS THE DESIGN SHOWS THAT WE DO NOT SERVE

**`STATE` IS NOT A SERVED FIELD.** `K8sService` carries `id, cluster_id, name, namespace, protocol,
port_low, port_high, vip, fqdn, managed_by_operator` — **no state, no readiness.** So `LIVE`, `NO READY POD`
and `VANISHED` are three values of a column that does not exist:

- **`VANISHED`** is derivable *for a rule* (`dst_k8s_service_vanished`), but that flag lives on `PolicyRule`,
  not on the Service — and a Service that is unexposed is simply absent from the list.
- **`NO READY POD`** is per-Service readiness from an EndpointSlice watch. **Nothing serves it.** The closest
  thing is `k8s_endpoints_unavailable`, which is a **node-level** health kind — the gateway cannot see
  endpoints *at all* — not a per-Service verdict.

**Same class as the gateway `PEERS` count and the routed-range device count**: a designed column with no
field behind it. **Registered as a decide-item (D5), not silently dropped and not invented.**

**AND THE HANDOFF'S VIP RANGES ARE `100.64.x` (CGNAT space), NOT RFC1918.** `100.64.0.0/10` is a defensible
convention for synthetic VIPs — it cannot collide with a customer LAN. But **the S14.7 address-space map
draws only the three RFC1918 blocks**, so a `100.64` VIP range lands in its `offMap` list rather than on a
grid. That is honest (it is named, not dropped) but it is a **cross-screen consequence worth ruling**: if
`100.64/10` is the house convention for VIP ranges, the map should probably draw it as a fourth block.
**Registered, not assumed.**
