# SA-0 authority and feasibility contract

2026-10-05; local `feature/browser-access`, base `435b4d53`. **SA-0a and SA-0b technically accepted for the authorized local, single-control-plane Linux POC.** This freezes the contracts below; it does not accept the full epic or production capacity/recovery. Native spike evidence and later product evidence remain separately identified.

## Explicit human decisions

The human review authorized proceeding with the recommendations and adding bounded admin configuration. Server Access must be available in **Community edition**. Recording ON/OFF belongs to each server's registration/edit configuration. The latest human decision makes encrypted PostgreSQL the default and recommended recording store for all new recordings. Retention defaults to 30 days and is admin configurable. The initial 4 MiB/session and 64 MiB/org limits are testing defaults, **not production capacity acceptance**. Required capture failure closes the session before unrecorded output continues. Active MFA freshness expiry closes the session; a new connection requires current verified MFA. Existing App Access name/location stays unchanged. Terminal should reuse App Access UI patterns as far as applicable.

The user separately authorized the isolated local API, real gateway enrollment, Linux SSH fixtures, temporary normal admin/member identities, grants/MFA and testing. No commit, push, PR, AWS, remote deployment or publication is authorized by this record.

## Identity, certificates and host trust

The CP owns organization, actor, parent login/credential epoch, server, existing Linux account, gateway identity/serial, supporting grant, configuration authority and session deadlines. Admin management does not grant shell content access. An explicit time-bounded same-org user/group/account grant is required, including for admins. Use named `server_access:view/manage/grant/use/session_manage/replay` permissions; no VPN/App Access permission implies shell or recording access. Installation capability defaults OFF; there is no enterprise entitlement gate.

Use an Ed25519 SSH user CA per organization. Its private material is sealed under the existing installation master key in PostgreSQL, with authenticated org binding checked on open and public/private key matching. The gateway receives only its freshly issued certificate; ephemeral private session keys remain in gateway memory and are cleared after use. The browser receives neither SSH private key nor CA key. Existing enrolled gateway mTLS authenticates transport, not signing authority.

The principal is `tunnex:<org UUID>:<server UUID>:<existing Linux account>`. Each host installs its independently delivered public user CA and root-owned account-specific AuthorizedPrincipalsFile; never map a bare username or reuse a server UUID on another host. Certificate key ID/serial correlate actor/session, but are not OpenSSH actor authorization. Linux permissions/sudo remain unchanged; Tunnex creates no OS users. Independent admin verification pins an SSH SHA256 host fingerprint; mismatch refuses access, with no insecure-ignore fallback.

Issue <=5-minute certificates, bounded by the admitted session lifetime, with only permit-pty and no forwarding extensions. Certificates remain reusable during validity, and expiry does not close an authenticated shell: native probes explicitly demonstrated both. CP single redemption and gateway/broker authority enforce the application lifecycle. A compromised gateway with a live private session key remains in the credential threat boundary. The gateway opens one PTY/shell only, never exec/SFTP/subsystems/forwarding/extra channels. Shells may spawn surviving background work; no confinement or process-kill guarantee is claimed.

Signing-key recovery/rotation proposal: back up sealed CA/recording rows and the installation master key as a matched, access-controlled encrypted backup set; a database backup alone cannot decrypt them. Master-key changes require authenticated decrypt/reseal with integrity checks and transactional replacement, not overwriting a key file. User-CA rotation requires separately authorized host trust distribution, overlapping old/new public trust, short-cert drain and qualified rollback before old trust removal. These are concrete SA-8 implementation/restore qualification requirements, not claims that key rotation or production recovery already works. A separate signer service is a future production option, not a POC prerequisite.

## Terminal transport and continuous authority

Browser HTTPS/WebSocket → CP broker → purpose/version `server_access_terminal_v1` outbound enrolled-gateway mTLS stream → exact registered private IP/port SSH/PTY. Existing apptransport lease/capacity patterns are reused; App Access HTTP purposes do not admit terminal streams. Reject CP/gateway-own destinations, special IPs, unknown purpose/frames, changed gateway serial or unsupported capability.

Admission and each renewal recheck current active/verified user, credential epoch, exact parent login/logout, org membership, verified MFA, enabled feature/server, gateway identity, account allowlist and the original supporting grant/group membership. Overlapping grants never extend or replace existing session authority. Browser Origin/actor/parent/session are bound; atomic claiming is single-use, has a 30-second pending/connecting limit, and never automatically reconnects or replays input.

Default maximum session is one hour, input idle 15 minutes and MFA freshness 15 minutes. Server editors can restrict idle to 60–900 seconds and maximum to 60–3600 seconds; idle cannot exceed maximum. Admin MFA freshness is 60–900 seconds. A session ends at the earliest parent/grant/session/MFA/input-idle deadline. Genuine input/paste resets idle; output, heartbeat, resize and replay do not. Shortening MFA freshness affects active authority; increasing it does not extend the session's originally admitted deadline.

Broker and gateway renew every second with independent finite <=4-second authority and 50 ms deadline watchdogs; target SSH/PTY teardown <=5 seconds. Renewal RPC, SSH dial/handshake and slow-writer budgets are bounded (1-second CP validation/capture, 2-second gateway RPC/dial/writes). No dependency call controls the independent watchdog. CP/Redis failure denies new access and expires ongoing authority. Push is optional acceleration; there is no resume, broker failover or HA claim. Closing a session means withdrawing authority and closing browser/channel/SSH/PTY, not killing unrelated background jobs.

Bound activity to 128 global, 4/user and 16/gateway sessions. Wire frames <=64 KiB, data <=16 KiB, resize 1–400 rows/columns and browser frame rate <=100/sec. Slow output/capture backpressures the existing stream synchronously; no unbounded queue or recording worker backlog is introduced. These POC bounds require production load qualification before capacity claims.

## Recording contract, storage and replay

Snapshot recording ON/OFF, retention and recording quotas at admission. OFF creates no manifest, key or payload chunks, while emitting the same ordinary lifecycle audit evidence. Toggling affects new sessions and never deletes prior recordings or changes an active session's snapshot. ON creates its encrypted manifest/key in the admission transaction before shell start. Each output or resize event must commit with PostgreSQL synchronous_commit ON before forwarding. Capture failure/quota/deadline closes transport immediately and marks retained content incomplete; there is no unrecorded fallback.

Use a versioned internal event envelope: `seq`, monotonic elapsed `millis`, `type=output|resize`, exact output bytes (JSON base64), and dimensions for resize. Raw input is excluded; echoed output can still contain secrets. Do not normalize UTF-8: preserve split/invalid bytes and feed them to xterm's streaming decoder, which displays invalid sequences according to its pinned decoder. There is no asciicast export promise; any future text export needs an explicit invalid-byte policy and qualification.

Generate a 256-bit per-session data key, wrap its org/session-bound envelope with the installation Sealer, and encrypt each chunk with AES-256-GCM using a fresh nonce and AAD `tunnex:ssh-recording:v1:<org>:<session>:<sequence>`. Replay verifies AAD, contiguous count/order, authenticated event sequence/time and bounded dimensions/data before returning content. Tampered, swapped, truncated or reordered content is refused.

Store encrypted chunks in separate tenant/session-keyed PostgreSQL tables, never ordinary audit rows. Defaults: 30 days, 4 MiB/session encrypted payload, 64 MiB/org retained encrypted payload, <=4096 events/session and <=16 KiB/event. Admin bounds: retention 1–3650 days, session quota 64 KiB–16 MiB, org quota >=session quota and <=1 GiB. Limits plus bounded event count bound ciphertext/metadata overhead. The org admission/capture lock serializes quota accounting. No queued output is forwarded on failed commit, ENOSPC/quota or the one-second capture deadline. PostgreSQL's actual configured volume/durability and backup set remain operational qualification responsibilities.

Retention rechecks finite expiry, removes encrypted chunks and wrapped data key transactionally, retains an expired manifest and ordinary audit metadata, and never runs on a recording toggle. This policy is independently separate from access/audit-log retention.

Replay is available from the corresponding Terminal session and ordinary Observer Audit Log session evidence. Every content/metadata request checks current human parent, user/epoch, same-org membership, separate replay permission and own-session or scoped session-management authority. No public blob/signed URL. Metadata-only rechecks run every five seconds in the mounted player; loss of authority clears its terminal content. Already delivered client data cannot be recalled. Expose disabled/capturing/available/incomplete/failed/expired honestly. Playback offers keyboard play/pause/restart/seek and read-only xterm, with screen-reader mode. Explicit OSC52 clipboard/OSC8 links are suppressed; no HTML interpretation or automatic browser-link action is permitted.

## Historical storage expansion and compatibility

An earlier customer-storage requirement introduced external payload destinations. The latest PostgreSQL-first decision below supersedes this admission behavior for new recordings. PostgreSQL retains manifests, ordered chunk indexes, encrypted data-key envelopes and safe audit metadata. Encrypted payloads can instead use a customer-configured mounted dedicated volume (EFS/EBS/local filesystem), S3-compatible bucket, Azure Blob container, or Google Cloud Storage bucket through its authenticated XML API. Existing external recordings retain these original destination snapshots; legacy configuration and adapters remain under Advanced compatibility controls.

The administration UI supports validated configuration, separately reported write/read/delete connection tests, and write-only credentials. Secrets are sealed in the control plane and never returned or audited. Every admitted recording snapshots the sealed tenant-bound destination; settings changes do not redirect older replay or cleanup. Capture durably uploads encrypted chunks before committing its ordered PostgreSQL index and before terminal forwarding. Upload, quota, manifest or index failures close required-recording sessions. Retention keeps the key and snapshot until external deletion succeeds and resumes durable bounded progress after failure. Dedicated storage must already exist; Tunnex does not provision cloud buckets or mount volumes.

S3/GCS use explicit HMAC credentials and bounded signed requests. GCS uses the documented XML API AWS-signature interoperability ([Google signature reference](https://docs.cloud.google.com/storage/docs/authentication/signatures)); Azure uses Shared Key ([Microsoft reference](https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)). HTTPS is required except an explicit local-development flag permitting literal loopback HTTP emulator endpoints. No ambient cloud credential chain or redirect forwarding is used.

Local emulator and filesystem evidence qualifies implementation behavior, not customer-cloud deployment, IAM configuration, EFS durability characteristics, recovery, capacity or performance. A mounted filesystem call blocked in the kernel cannot be cancelled by a Go context; independent terminal authority watchdogs still close the channel, but filesystem stall/resource exhaustion needs operational qualification.

## Latest approved PostgreSQL-first lifecycle

All new recordings use encrypted PostgreSQL output, timing and resize events regardless of legacy storage configuration. The 30-day default applies to new admissions; existing expiry and provider snapshots remain unchanged. Retention can be increased up to 3650 days. Without an archive, expiry deletes ciphertext and the wrapped data key while retaining audit metadata.

A separately saved S3 connection supports manual Export to S3 even when automatic archival is OFF. Automatic archival applies at expiry when enabled. Export writes ordered encrypted chunks plus an encrypted versioned manifest containing the wrapped key, count, integrity digest and incomplete flag. Upload/readback verification must finish before any PostgreSQL source release. Failures retain the source and show retry state. Deterministic object names and durable progress make retries idempotent. Manual export before expiry preserves PostgreSQL through retention; expiry rechecks the complete archive before releasing payload. Archived replay remains subject to the same current human, parent, tenant and replay authority checks.

Manual Download explicitly returns the authorized recording JSON containing output, timing and resize events. It is a browser action and is never an unattended retention destination. S3 connection setup is adjacent to Export; write-only secrets reuse existing storage sealing, testing and adapter code. The UI reuses App Access workspace/shared controls, the existing recording form and generated client rather than introducing a separate settings infrastructure.

### Encrypted archive portability within the installation

New S3 archives include `recording-v2.tunnex-recording`, a verified self-contained encrypted package. Sessions → Import recording accepts this package and authorized Manual download JSON. Package upload requires explicit confirmation and current organization Replay permission plus original owner or SessionManage authority. It can replay after original session/recording deletion without restoring audit identity. The originating installation master remains necessary; no key is exported or plaintext silently substituted. Raw historical chunks/manifests remain server-replay formats and are not import files. Limits are 32 MiB per import package, 4096 events and 16 MiB captured encrypted payload; ordinary HTTP/chunk limits remain unchanged.
