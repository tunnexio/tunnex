# S2S-2 runtime delivery and exact cleanup contract

Status: implementation in progress, 2026-09-24, after explicit user approval of retained safety guards and range reservations. The approved [P3 lifecycle](S-S2S-2-persistence-contract.md#p3--desired-intent-is-separate-from-gateway-evidence) remains authoritative. This paper specifies its delivery and acknowledgement mechanics. It does not approve a daemon, ownership allocator, force-cleanup operation, secret export or production capability change. The user has requested completion of the remaining S2S-2 work; avoid reopening already-approved foundation/all-tier/permission decisions.

## Current boundary and required changes

Migration158 permits only disabled and fully finalized deleted records; its parent trigger requires every update to advance desired revision, rejects all updates after deleted intent, and its deferred child checks require exactly two live tunnels/secrets or zero finalized children. Migration159 makes provider configuration immutable and seals it; its completeness trigger assumes disabled means complete and deleted means all provider children removed. The current `ConnectionStore.Delete` removes provider children, immediately finalizes the parent, then deletes tunnel secrets/tunnels atomically. These are correct only for never-delivered records. Merely expanding the desired-intent enum would bypass lifecycle safety.

Replace those narrow checks together in the next unused migration, keeping159 data and ownership constraints. Existing disabled records remain never delivered and existing finalized tombstones remain terminal. No WireGuard backfill or shared policy/transport change. Keep create-only provider configuration, two immutable tunnel identities and per-tunnel secret revision1; reassign, edit/rotate credentials and profile changes remain separate contracts.

## Durable records

Keep `ipsec_connections.desired_revision` as the human intent CAS revision and expand intent to `disabled|enabled|deleted`. Assignment/history fields remain immutable. Deleted intent is terminal, but `finalized_at` may initially be NULL. Pending deletion retains live Site/gateway references and complete tunnel/provider/secret children. `deleted_at` records intent time; `finalized_at` records cleanup completion time. Acknowledgement/finalization is evidence, not a new desired revision.

Add a one-to-one `ipsec_runtime_state` row lazily on the first runtime intent transition, with composite connection/org owner FK and immutable historical assigned node/Site:

- `last_potentially_delivered_revision bigint NULL`: monotone high-water mark, advanced only by committed apply-delivery creation.
- `last_cleaned_delivery_revision bigint NULL`: monotone coverage high-water mark established only by an accepted exact cleanup acknowledgement.
- `current_cleanup_id uuid NULL`: references the current immutable cleanup command when cleanup is owed.
- `applied_revision bigint NULL`: exact acknowledged application revision, never interpreted as traffic evidence.
- No plaintext, ciphertext copies, PSK-derived hashes, raw engine output or human authority assertions.

Add append-only `ipsec_runtime_deliveries`:

- UUID `id`, connection/org, assigned node/Site, positive desired revision, kind `apply|cleanup`, server `created_at`; UNIQUE(connection, desired_revision, kind).
- For apply: immutable provider configuration revision and authoritative nonsecret ownership-manifest digest. Secret revision bindings are selected from immutable tunnel rows, not supplied by a request. The digest excludes every credential and derives only from the approved runtime ownership manifest.
- For cleanup: `covers_delivery_revision` equals the last potentially delivered revision at cleanup intent creation, plus the complete nonsecret ownership lineage to withdraw. It covers every earlier apply/rekey-owned object in that lineage, not merely the currently observed SA.
- Store the certificate serial used for the original successful authorization only as internal provenance; it does not let an old serial authenticate later. Do not pin future cleanup to an expired serial when the same assigned node legitimately renews.

Add append-only `ipsec_runtime_acknowledgements`, one row per delivery UUID, including composite owner/node binding, exact desired revision, kind/result (`applied|cleaned`), expected manifest digest and CP receipt timestamp. A unique delivery acknowledgement makes exact duplicate requests idempotent. Store only a closed, bounded result shape. Failures are not successful acknowledgements; future error observations must remain a separate bounded status channel and cannot advance cleanup.

Rows retain historical identities after finalization. Foreign keys to connection/org stay live; runtime evidence must not introduce a permanent live-node FK after the approved assignment references are released. No evidence TTL or GC in this increment.

## State transitions

| Current state and action | Transactional result |
| --- | --- |
| Never-delivered disabled → enable | Require exact current CAS, live opt-in, current assignment, fresh qualified capability, complete immutable configuration, qualified enforcement/ownership contract. Advance desired revision, enabled; application pending. Merely enabling does not mark delivery. |
| Enabled → apply material fetch | Recheck all authority and intent gates; create/reuse exact apply delivery and advance potentially-delivered high-water before material leaves CP. Desired revision stays unchanged. |
| Enabled → disable, no material ever delivered | Disabled successor; no host cleanup obligation. Keep provider configuration/secrets for later enable. |
| Enabled → disable after any possibly delivered material not yet cleaned | Disabled successor, new exact cleanup UUID covering delivered high-water; retain all resources and reservations. Reject apply delivery immediately at the next serialized check. |
| Disabled cleanup-pending → enable | Conflict; prior cleanup must complete first. |
| Disabled cleanup-complete → enable | Recheck all enable gates and advance to a new enabled revision. Old apply receipts are not reused. |
| Any nondeleted → delete, never delivered or already clean | Deleted successor and immediate finalization, preserving current never-delivered behavior and shared resources. |
| Any nondeleted → delete with cleanup owed | Deleted successor, new exact cleanup UUID, retained children/references/reservations, finalized_at NULL. A prior disabled-cleanup command becomes stale; the new command covers the same complete high-water. |
| Exact current cleanup acknowledgement for disabled | Atomically record evidence and clear owed cleanup; retain CP configuration/secrets/reservations for re-enable. |
| Exact current cleanup acknowledgement for deleted | Atomically record evidence and finalize only under the retained-refusal disposition below. Remove owned secret/configuration children and release only ownership explicitly permitted by that disposition. |
| Repeated same-intent human operation / already deleted |409; no silent replay, no revision/audit change. User recovers using GET. |

Overflow refuses before writes. Pure application receipt does not advance desired state, release references, enable a disabled connection, or prove packet delivery. A stale application receipt after disable/delete cannot replace cleanup. Disabled cleanup state remains visible even when capability is lost or opt-in is off.

## Authentication, delivery and transaction ordering

Use the existing `AgentChannel.authenticateAgent` seam: TLS peer certificate serial → `nodes.Service.AuthenticateCert` → node principal. Never accept caller-provided org/node IDs as authority. The current seam checks node active status and may mark first certificate delivery; it is not the final delivery authorization because its row can change before the new service transaction.

Pass authenticated node identity AND the actual peer-certificate serial to the delivery/ack service. Re-fetch and lock the exact node row inside the transaction, requiring current active status, revoked_at NULL, matching current cert serial, matching org, and current stored assignment. Current API lookup alone cannot close revocation or certificate-rotation races. Cleanup does not require fresh IPsec capability, opt-in or reachable data plane; it still requires the existing valid active certificate. Revoked certificates get no cleanup exception and no manager impersonation.

Order: existing organization range advisory lock → live organization/version → settings → selected Site → approved subnets in UUID order when needed → gateway → connection → runtime state/delivery rows → tunnel slots. Reuse the existing organization serialization for settings and soft deletion. Revocation keeps its existing security path; the common gateway-row lock provides the delivery/revoke serialization point. Audit existing revocation/rekey paths for incompatible lock order and classify deadlock/serialization as retry-conflict, never an authorization fallback. Post-commit wake-ups are best effort; polling recovers missed notifications.

For apply fetch, validate/decrypt bounded secrets under authoritative bindings, create the immutable delivery and potentially-delivered marker, then COMMIT before writing response bytes. A failed commit exposes no material. A lost response, timeout after commit or crash before first response byte still owes cleanup. Do not roll the delivery marker back when network writing fails. Keep plaintext only in request-local memory; clear byte buffers where practical without claiming complete Go memory erasure.

There is no atomic transaction between PostgreSQL commit and socket delivery. If delivery commits before disable/revoke, bytes may arrive after that later operation commits; the checkpoint deliberately retains cleanup. If disable/revoke wins the row lock, the fetch refuses. Never claim that revocation retracts bytes already authorized. Node serialized command handling must reject stale desired revisions and restore refusal before adopting any old delivery after reconnect/restart. The enforcement/journal contract must define any bounded authorization lease required for disconnected runtime shutdown; this paper does not invent a timeout as cleanup proof.

Acknowledgement processing locks the same authority/assignment/current revision and expected delivery. Validate all bindings, current intent and expected ownership digest before inserting evidence. Exact existing acknowledgement duplicates return success with no new audit/version effects; a differing body for the same delivery conflicts. Stale revision, wrong node/org, wrong coverage/digest, old certificate and unsolicited delivery UUID refuse. Finalization and ack insert share one transaction; injected child-removal/audit failure rolls both back. A duplicate after resources have finalized uses immutable retained assignment evidence, while still authenticating the current node certificate; if that node was subsequently deleted, authentication legitimately fails.

## API shape

Human operations remain existing verified HUMAN `ipsec:manage`, across all licence tiers, with authority before body/header parsing:

- Proposed `PUT /api/v1/organizations/{orgId}/ipsec/connections/{connectionId}/intent`, strict positive quoted `If-Match`, body `{intent: enabled|disabled}`. Return200 redacted connection + desired ETag. Enable remains unavailable until runtime qualification; no optimistic connected state.
- Existing DELETE keeps strict If-Match and200 redacted response, but can now return terminal desired intent with `finalized_at:null` and `cleanup_state:pending`. UI must distinguish requested deletion from completed cleanup; no hidden immediate-finalization promise.
- Existing list/detail add bounded `application_state` and `cleanup_state` projections separate from intent, plus CP receipt times where useful; no SA/raw diagnostic payload in these records. Desired ETag remains the intent revision, not an observation version. Set no-store on lifecycle reads.
- Configuration GET remains explicit credential-free projection. While deletion is pending it may return retained nonsecret configuration; after finalization it returns retained profile/revision only. Disabled records preserve redacted configuration throughout cleanup.
- Settings opt-out checks enabled connections OR outstanding cleanup and returns409, with no settings revision change. Mirror this in the database trigger so direct SQL cannot strand obligations.

Private agent-channel operations, all no-store and authenticated before input processing:

- GET `/agent/ipsec/pending?after=<UUID>`: bounded IDs/current desired revisions and command kinds assigned to this authenticated node; no credentials, no delivery checkpoint.
- POST `/agent/ipsec/connections/{connectionId}/material` with `{desired_revision}`: explicit potentially-delivered transaction; return exact apply delivery UUID, org/connection/node/Site bindings, immutable configuration revision, typed runtime intent and the two write-only PSKs. This is the only secret-bearing read path and is unavailable to human sessions/API tokens. POST avoids accidental cache/prefetch semantics for the checkpoint.
- GET `/agent/ipsec/connections/{connectionId}/cleanup?desired_revision=<n>`: current cleanup UUID, coverage and exact nonsecret ownership manifest. No PSK, even when sealed CP rows are retained.
- POST `/agent/ipsec/connections/{connectionId}/acknowledgements`: bounded exact `{delivery_id,desired_revision,kind,result,ownership_digest}` and the agreed cleanup evidence contract. No raw kernel/daemon output or arbitrary message. Success204; conflicting/stale409; unavailable503; malformed400; common authentication401; scoped missing404.

Material and acknowledgement DTOs are private channel contracts mirrored in node code, not manager/OpenAPI models that could accidentally make credentials downloadable. Secret-bearing responses, requests, errors and traces must never log bodies. Use static typed errors, bounded JSON, unique keys, reject unknown fields and trailing JSON. A delivery UUID is correlation, never a bearer authorization token.

## Finalization and retained refusal — unresolved disposition

P3 approves acknowledged cleanup and release of live references, but the runtime plan also requires preventing protected payload fallback after routes/SAs are removed. A safety-only denial object may therefore need to survive cleanup. It must not be silently forgotten or deleted when a new connection reuses the same ranges.

The enforcement/journal lane recommends retaining an exact nonsecret refusal manifest with namespace/node/connection lineage and its ownership until authoritative supersession. This means either:

1. Cleanup may finalize with retained safety-only guards, and CP retains separate nonsecret guard/range ownership until an exact successor transfer replaces them; shared resource/reference release must respect that retained ownership. No force-forget/deprotection API is implied.
2. Final cleanup requires zero retained connection-owned objects; then the implementation must prove an independent durable refusal mechanism prevents fallback before releasing the old guard and every reservation.

These are materially different lifecycle/resource-reuse behaviors. Root must disposition this point jointly with journal/enforcement before finalization schema/code. The new schema must not accept a boolean `cleaned` while this meaning remains unresolved. Similarly, allocator ownership identifiers, normalized cleanup-manifest format, runtime lease semantics and production qualification are cross-lane dependencies, not accidental service defaults. Foundation authority, all-tier access, exact acknowledgements, pending offline/revoked cleanup and absence of force-cleanup are already decided and need no repeat approval.

## Migration and rollback

Reserve the next unused number at implementation. In one transactional migration add tables, expand constraints and replace parent/child/provider completeness and settings/soft-delete guards together. Live/disabled/enabled/pending-deleted records retain exactly two tunnels/secrets and complete sealed provider configuration; only finalized deletion requires zero owned children. `withdrawal_started` means final configuration removal, not ordinary disable. Keep provider configuration immutable during delivery/cleanup.

Backfill no delivery claims: existing disabled rows have no runtime history, existing deleted tombstones stay finalized. Add indexes for assigned-node pending commands and connection revision. Enforce same-org ownership and legal transitions with direct-SQL tests; matching HTTP checks alone are insufficient. Finalize-at-same-desired-revision is the sole evidence-driven parent transition and requires the exact accepted cleanup record (or structural proof of never-delivered) in the same transaction. Update org-delete/resource guards to test unfinished lifecycle, including deleted-intent/finalized_at NULL.

Down migration refuses if ANY runtime state/delivery/ack row exists, any enabled intent, any pending deletion/cleanup or retained refusal ownership exists. Do not discard history to force159 compatibility. With none present, restore159 trigger/check definitions and preserve all legacy disabled/tombstone/provider data byte-for-byte. Test transactional failed-down leaves schema/data unchanged, empty/new-feature-free down/up, and populated legacy159 preservation. No default database or live review CP migration as part of this design lane.

## Regression and qualification plan

Write regressions before migration/store/HTTP implementation after contract review:

1. Legacy159 preservation, legal/illegal direct-SQL transitions, exact children at pending versus finalized deletion, no forced finalization, immutable delivery/ack identity and monotone high-water, revision overflow.
2. Material transaction commits checkpoint before a fake response writer receives bytes; encryption/commit/audit failures expose zero material. Simulated lost response retains obligation; duplicate fetch reuses exact delivery without new revision/audit.
3. Observed-lock races, both winners: revoke/renew versus material; disable/delete versus material; opt-out versus enable; delete versus application ack; delete versus cleanup ack; re-enable versus cleanup; two exact/conflicting acknowledgements. No sleep-only timing claims.
4. Wrong/current/renewed certificate, foreign-org/foreign-node/wrong-Site assignment, revoked node, missing/stale capability for apply; cleanup remains available without capability/opt-in but never to revoked identity. Auth precedes all request parsing.
5. Disable retention and re-enable only after exact cleanup. Pending deletion retains provider/tunnel/envelope and range dependencies; finalization atomically deletes only owned resources after agreed proof. Shared Sites/subnets/policies/cloud remain untouched.
6. Exact duplicate ack idempotency versus conflicting/stale rejection, no duplicate audit/version effects; failed finalization rolls back acknowledgement and every child deletion. Tombstone cannot resurrect; no TTL or administrator completion.
7. Synthetic secret markers absent from every human response, private error, audit/log sink, trace, cursor and digest. Agent material only reaches exact authenticated assignment; all ordinary readers remain credential-free.
8. Approved-prefix reservation/reuse and retained-refusal transfer according to the disposition above; offline/revoked pending remains honestly visible.
9. Mutation-test each critical checkpoint, node/serial binding, current-revision check, cleanup coverage and finalization proof. Run isolated scratch PostgreSQL races, route/auth censuses, deterministic generators, both API builds and node tests. Keep current production capability0 until independent engine/enforcement/packet qualification completes.

## Ephemeral permit authority lease — proposed implementation contract

A successful apply acknowledgement is historical evidence, not indefinite permission to forward. A failed nftables replacement, blocked child process or node process crash can leave old permit rules in the kernel. Each connection therefore needs kernel-enforced expiring permit membership in addition to its permanent refusal guard. This lease is separate from delivery checkpoints, acknowledgement state and cleanup proof. It introduces no new persisted lifecycle state and does not replace the separately approved retained-guard ownership contract.

Proposed private operation: POST `/agent/ipsec/connections/{connectionId}/permit-lease`, authenticated by the existing agent certificate channel before parsing. A bounded, unique-key JSON request carries exact `delivery_id`, `desired_revision`, `policy_revision` (the authoritative compiled-policy identity), and a fresh unpredictable request nonce. The response echoes those identities and nonce and returns a positive integer `ttl_ms`, with a proposed fixed maximum of 60000ms. It contains no PSKs or runtime credentials and is no-store. The node accepts only the currently outstanding request in its serialized connection lane. Delivery identity and nonce are correlation, never authentication.

Issuance repeats current certificate serial, active/unrevoked node, exact organization/Site/node assignment, enabled desired revision, matching committed apply delivery and current authoritative policy identity under the established lock order. Disabled/deleted/stale-policy/revoked/wrong-assignment requests receive a static refusal and no lease. The compiled policy and policy identity must describe one coherent snapshot; merely accepting a node-supplied hash is insufficient. Existing policy revision/invalidation infrastructure must be inspected and reused during implementation; if it cannot serialize policy revocation against issuance, that seam must be completed before this endpoint qualifies. Renewal follows exactly the same checks and is not authorized by a previous lease, cached material, daemon state or historical acknowledgement.

Issuance linearizes while those checks are locked. A revoke, disable or policy change that wins first prevents issuance; one that follows an already authorized response can leave residual forwarding only until that response's original bounded lease deadline. Network delivery cannot be atomic with a later revocation. The advertised guarantee is bounded residual authority, not instantaneous revocation. A request authenticated before certificate rotation still fails the transactional serial recheck if rotation wins first.

The node records a monotonic `requestStart` before sending each attempt and computes `deadline = requestStart + ttl`. It never starts the TTL at response receipt, uses a serialized wall-clock `NotAfter` as forwarding authority, or restores a lease from disk. Validate nonce, exact identity, TTL bound and current local generation before accepting the reply. Deduct elapsed request time and a bounded installation budget before calculating the kernel element timeout; reject when no positive budget remains. Retry is a new authenticated request with a new nonce; an installation retry of the same reply can only shorten its remaining original deadline. Timeout encoding rounds downward and must not be reset to the original TTL on retries.

Installation has a bounded deadline. Check remaining authority before mutation, after mutation/readback and before reporting success. A timeout or failed readback leaves the permanent refusal path installed and must not report readiness. Kernel timeout behavior under command delay, suspend/resume and the actual qualified platform clock must be demonstrated: if the kernel timer can preserve membership beyond the selected elapsed-time bound, the proposed bound is not yet proven. No wall-clock adjustment may extend authority. The concrete installation budget and renewal cadence are qualification parameters; they must leave room within the maximum lease and must not be silently tied to the existing 30-second capability-report cycle.

All forwarding permits associated with this connection must require unexpired membership, including ingress, reply, output, postrouting and any established-connection fast path. Conntrack state must not bypass the expiration check. Refusal guards and retained ownership never expire with the permit. Failed refresh or process death therefore stops payload permits in the kernel even when userspace cannot delete stale rules. Restart restores refusal before adoption, discards in-memory lease authority and requests fresh authority before permitting any traffic. Journal replay may restore safety ownership but cannot recreate or renew permit membership.

Lease expiration, elapsed wall time, failed renewals and successful daemon shutdown are never cleanup acknowledgements. They do not prove SAs, routes, addresses, credentials or owned kernel objects absent and do not release CP reservations or authorize final deletion. Cleanup still requires the exact agreed evidence and coverage. A delayed old lease response is refused by local generation/nonce checks after cleanup or intent change; if a process crashes before observing a change, the original kernel deadline still bounds the old permit.

Reusable source patterns: `apps/node/internal/ownershiplease/lifecycle.go:applyExactBefore` bounds application using a context timeout, and its startup/renewal paths recheck expiry before and after apply and before success. Reuse those checks conceptually, not its persisted wall-clock `LeaseExpiresAt` or startup replay semantics. The connectivity session/relay credential TTLs belong to different authorization scopes and must not be reused as IPsec forwarding authority. Existing agent certificate authentication, node row locking and typed static response errors remain the shared transport/security seams.

Required regressions before implementation: both-winner revoke/disable/policy-change races; fresh versus stale certificate and assignment; delayed response and mismatched/replayed nonce; oversized/zero/overflow TTL; slow request and bounded apply consuming the lease; failed nft refresh preserving old objects while kernel permits expire; process crash with no userspace cleanup; established traffic denied after expiry; restart/journal unable to renew; wall-clock changes unable to extend authority; platform suspend behavior; exact cleanup still pending after expiry. A renderer test alone cannot establish kernel expiration or packet denial: qualify these in the isolated Linux packet lab with observed expiration and continuing traffic.

## Native XFRM second-pass postrouting — bounded integration proposal

The isolated native lab observed that valid XFRM output revisits postrouting on the physical interface while selectors still expose the inner protected destination. The first-pass XFRM-interface permit is insufficient: the permanent remote-prefix fallback correctly refuses this unmatched second pass. Do not fix this with generic `ipsec out exists`, a physical-interface bypass, or an unbounded SA permit.

Proposed renderer input is an explicit per-connection encrypted-egress tuple: owned tunnel interface index, installed CHILD-SA reqid, exact outer IPv4 peer and independently observed physical output interface index. Bind its tunnel index to one of the existing two immutable namespace/XFRM ownership tuples and to the currently permitted path; require nonzero, unambiguous reqids and exclude all owned XFRM indices from physical outputs. Production discovery must establish the actual underlay route and identity; a hardcoded lab `eth0` is not general route qualification.

A dedicated per-connection expiring reqid set uses the same remaining in-memory lease duration as its interface permit set. A second-pass permit must conjunctively match the protected destination, exact physical output index, `ipsec out reqid` equal to the observed reqid and membership in the expiring reqid set, and `ipsec out ip daddr` equal to the exact assigned peer. The permanent denial remains after these narrow permits. Neither installed SA status nor journal state can populate an unleased member. Renderer readback must check the reqid set type, contents, configured timeout and bounded observed expiration, alongside the existing interface set.

Current daemon readback exposes IKE local/remote addresses and installed CHILD-SA reqid, XFRM IDs, SPIs and selectors. Existing kernel inventory independently verifies namespace and XFRM interface identity but does not yet establish a physical underlay route or full kernel SA identity. The packet lab may combine exact daemon evidence with independently read physical interface identity to validate this narrow rule; that evidence must not be advertised as complete production activation qualification.

Original-tuple NAT protection is a separate prerequisite: global pre-permit refusals classify both conntrack original and current protected source/destination and deny observed DNAT/SNAT. They prevent a destination rewrite from escaping protection or entering an otherwise granted tuple. A postrouting90 check still cannot prove absence of a newly applied SNAT99/100 transformation; coexistence and the later transformation path require separate proof. New regressions must include unleased/wrong reqid, wrong peer, wrong physical interface, wrong tunnel binding, expiry and a valid two-pass encrypted flow. No generic tunnel-set or CNI-hook relaxation is included.

Native grammar correction: declare the reqid set using `typeof ipsec out reqid`, with JSON `type: {"typeof":{"ipsec":{"dir":"out","key":"reqid"}}}`. Bare `type integer` lacks a key width and is rejected by the qualified nft version. Conntrack IPv4 selectors use JSON keys `ip saddr`/`ip daddr` with `dir: original`; a separate `family` property on that expression did not establish its type in the actual native parser. These corrections preserve the exact predicates. See the [upstream nft expression and set documentation](https://netfilter.org/projects/nftables/manpage.html) and [shipped libnftables JSON schema](https://sources.debian.org/src/nftables/1.1.3-1/doc/libnftables-json.5/). Native grammar and semantic readback remain required gates alongside pure tests.

### Implemented private transport and startup boundary

The existing mutually authenticated agent channel exposes `GET /agent/ipsec/pending` (bounded UUID pagination), `POST /agent/ipsec/connections/{id}/material` with `desired_revision`, `GET /agent/ipsec/connections/{id}/cleanup?desired_revision=...`, `POST /agent/ipsec/connections/{id}/acknowledgements`, and `POST /agent/ipsec/connections/{id}/permit-lease`. Pending responses include the authenticated `org_id`, `node_id`, and current `ipsec_enabled` setting (missing settings mean false); these discover a new installation's identity over its trusted control channel. Acknowledgements return 204. All responses carry `Cache-Control: no-store`. Request bodies are bounded to 128 KiB and reject duplicate keys, extra fields, trailing JSON, and invalid structural identities before entering the service.

The node private client requires HTTPS, reuses its existing mTLS transport, refuses redirects, bounds each request to 15 seconds and each response to 1 MiB, and emits static errors without response bodies. Its serialized polling pass obtains current material or cleanup, checks the requested connection/revision, invokes the controller, and acknowledges only a successful exact delivery. Enabled connections remain in pending discovery even after an apply acknowledgement, so subsequent polls refresh policy and permit authority. Polling retains no PSKs, grants, or leases on disk.

On restart, a securely read journal identity permits restoring nonsecret refusal ownership without waiting for the control plane. Existing journal corruption or failure to restore refusal stops startup before WireGuard forwarding. A brand-new installation discovers opt-in in the background and starts no IPsec daemon or port listener while opt-in is false. Unsupported installations leave WireGuard available and advertise no IPsec support. Existing journal refusal is restored before attempting daemon startup, so stale daemon artifacts cannot prevent safety restoration. After bootstrap, every pending response must match the journal's organization and gateway identity. No configuration switch grants production capability; full controller/platform qualification remains required.

Local proof includes a real isolated database response writer that checks committed delivery state using another database connection before its first byte, including a broken response retaining the cleanup obligation. A real blocked policy writer proves lease issuance serializes with rule deletion; after deletion commits, the old policy hash cannot renew. These proofs do not substitute for native controller packet and restart qualification.

Runtime history admission is bounded before new material exposure: at most 64 apply generations per connection and a conservative 480 KiB full cleanup lineage budget under the 512 KiB persisted envelope. Enable and material admission enforce this bound; the delivery trigger independently enforces it for direct SQL. Capacity refusal does not erase history or release retained reservations. The final already-delivered generation remains cleanable and deletable, verified through 64 actual enable/material/disable/acknowledgement cycles in an isolated database.

The initial environment adapter supports independently observed physical IPv4 underlays, main-table local ingress routes, standard local/main/default IPv4 rules and exact destination-scoped priority100 main-table return rules. It rejects unqualified policy routing, CNI/Kubernetes hooks, flowtables, arbitrary NAT/mark rewrites and unknown NFT tables. The known Tunnex forward/filter and source-scoped disjoint masquerade99 forms are admitted; MSS adjustment is limited to TCP maxseg from route MTU. The controller separately verifies the owned refusal table. These restrictions are qualification boundaries, not automatic host modifications.

Conntrack cleanup uses the existing netlink dependency on a locked OS thread with independently verified thread network namespace, deadline and cancellation close. It checks a 4096-flow supported workload before and after the dump, removes only bidirectional local/remote payload tuples, then independently dumps again to establish absence. The dependency allocates the complete dump before returning, so concurrent kernel growth is not a strict preallocation memory bound. The adapter never lowers host conntrack limits. Native exact-drain and full controller qualification remain separate gates.

The initial environment profile requires all approved local prefixes to resolve to one independently observed physical ingress interface. Multiple prefixes on that same interface are supported. More than one local ingress interface refuses activation until renderer grants bind each source prefix to its own interface; a union of interfaces must not widen source identity.

The runtime platform probe performs actual bounded observations: the supervised daemon's exact 6.1.0 engine/algorithm/seven-plugin inventory, current kernel and no-key XFRM readers, effective CAP_NET_ADMIN, current route-rule and NFT composition, and kernel check-mode validation of the complete rendered timed interface/reqid rules. Its unique check-only NFT table is never installed. A successful probe is a process-local prerequisite receipt, not proof of packet enforcement, image publication or authorization to advertise capability. Actual guard apply/readback and native composition proof remain separate.

The probe receipt binds network namespace and a Linux CLOCK_BOOTTIME/CLOCK_MONOTONIC baseline. Namespace change, daemon loss, clock regression or detected suspend offset change invalidates it permanently; authority must be withdrawn and reacquired after requalification. Existing nft set expiration uses kernel jiffies ([upstream implementation](https://github.com/torvalds/linux/blob/master/include/net/netfilter/nf_tables.h)); normal userspace-independent expiration is qualified in running-kernel elapsed time. No wall-clock 60-second bound across host suspend or arbitrary hypervisor pause is asserted. A resume detector does not prove that no packet can run before userspace observes resume, so any stronger wall-time guarantee requires a separately qualified kernel enforcement design.
