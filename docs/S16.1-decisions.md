# S16.1 — Complete installs and UI-managed control-plane upgrades

Status: decisions locked; implementation complete pending committed box-walk evidence.

## Goal

A control plane installed with `curl -fsSL https://get.tunnex.io | sh` has every
file and local service required to perform a verified upgrade. A deployment
administrator can approve that upgrade in the web UI, follow backup, preflight,
apply, and health-check progress there, and return after the brief control-plane
restart to see the final result.

This story amends S16's read-only UI decision. It does not weaken S16's signed
release, forward-only, preflight, backup, health, or air-gap contracts.

## Observable acceptance

1. A fresh public install contains `tunnex.yml`, `.env`, `release.json`, the
   executable `upgrade.sh`, the fixed-purpose host runner, and its enabled
   service. Installation fails before starting the stack if a required asset
   cannot be installed.
2. Re-running the installer repairs a missing managed upgrade asset without
   replacing operator-owned secrets or silently applying an upgrade.
3. Only a verified deployment administrator (`cp_admin`) can request a host
   upgrade. Organization owner/admin membership alone is insufficient because
   an upgrade affects every tenant on the deployment.
4. One click plus an explicit confirmation requests the exact signed release
   shown in the UI. Duplicate clicks converge on the same request; a second
   upgrade cannot run concurrently.
5. Before any image or deployment mutation, the runner creates a real PostgreSQL
   custom-format dump and its keyed `backupctl` manifest, verifies the manifest,
   and runs the existing fail-closed preflight.
6. The UI reports the durable stages `requested`, `verifying`, `backing_up`,
   `preflight`, `pulling`, `restarting`, `health_check`, `healthy`, and `failed`,
   including sanitized failure guidance and the retained backup filenames.
7. The API process receives neither the Docker socket nor a general host command
   surface. The runner accepts only the fixed upgrade request schema and invokes
   the repository's existing `upgrade.sh`.
8. Disabling online update checks keeps the UI action unavailable. Air-gapped
   upgrades continue through the explicit host helper; this story does not add
   browser upload of release bundles.

## Decisions

### D1 — The installer owns a complete, all-or-fail payload — LOCKED

`deploy/install.sh` installs every required file from the same immutable
`SOURCE_REF` before it starts or changes the Compose stack. Managed executable
files are installed with explicit modes. A missing download is a failed install,
not a successful control plane with a broken future workflow.

The installer remains idempotent. It may repair its managed helper and unit
files, but it preserves `.env` secrets, the database volume, retained backups,
and operator configuration according to the existing installer contract.

### D2 — A fixed-purpose host runner bridges UI intent to Docker — LOCKED

The public installer registers a systemd service on the Docker host. The service
runs the shipped runner and watches a deployment-local request directory shared
read/write with the unprivileged API container. The API writes a bounded request;
the runner writes bounded status. Neither side interprets request content as a
shell command.

The runner is the only new privilege boundary. It can invoke only
`upgrade.sh --apply` for the install directory configured in its unit. It does
not expose a TCP listener, accept arbitrary arguments, or provide a general
remote-execution mechanism. The API container is not given `/var/run/docker.sock`
and remains non-root.

### D3 — Deployment administration, not organization role, authorizes — LOCKED

The request and detailed-status endpoints use the existing `requireCPAdmin`
gate, including verified-email and forced-password-change walls. This is a
deployment mutation. The current UI's owner/admin inference is removed from the
upgrade action rather than being treated as authorization.

Requests are attributed to the authenticated deployment administrator in the
audit log. The unauthenticated `/meta` response may continue to advertise a
verified available release, but it cannot request an upgrade or expose detailed
host output.

### D4 — The request pins the release the operator approved — LOCKED

The API records a random request id plus the verified catalog's source SHA and
monotonic sequence. `upgrade.sh` gains expected-source and expected-sequence
checks after signature verification and before backup or mutation. If discovery
moves between the click and execution, the request refuses instead of silently
installing a release the operator did not approve.

Only one request may be active. Repeating the same request is idempotent;
requesting a different release while one is active returns a conflict.

### D5 — Backup means database dump plus key-bound manifest — LOCKED

The current helper emits only a `backupctl manifest`; that is not a database
backup and the UI must not label it one. The runner creates a timestamped
PostgreSQL custom-format dump in the deployment backup directory, creates the
matching manifest, verifies that manifest against the live control-plane master
key, and refuses before mutation if any step fails.

Backups remain on the host with restrictive permissions. The UI receives
filenames and verification state, never database contents, `.env`, or key
material. Automatic retention/deletion is excluded because deleting recovery
artifacts needs its own policy and operator decision.

### D6 — Progress is a small durable state machine — LOCKED

The runner atomically replaces one bounded status file at stage boundaries. The
API validates it before serving it and fails closed to `unknown` on malformed or
missing state. Browser polling reconnects naturally across the API container
restart; no WebSocket, queue, or new database table is required.

Only stable stages, timestamps, target version/source, backup filenames, and a
sanitized reason cross into the UI. Raw command output remains in the local
service journal and is not returned to browsers because it can contain host
paths or operator configuration.

### D7 — Existing verified upgrade logic stays authoritative — LOCKED

The runner does not duplicate release verification, preflight, Compose update,
or health logic. It calls `upgrade.sh`, and that helper remains usable directly
for recovery and air-gapped operation. The UI path adds orchestration and
observation around the same fail-closed mechanism.

The old copy-command fallback remains visible only when the host runner is not
installed or not reporting. A fresh public install reports `host_updater`; older
deployments remain operable and repairable instead of seeing a dead button.

### D8 — No phone-home promise is unchanged — LOCKED

The browser talks only to its own control plane. The local API and runner
communicate through host-local files. Release discovery and artifact downloads
remain the explicit, disable-able outbound checks already documented by S16;
the UI action introduces no Tunnex telemetry, callback, hosted control channel,
or customer-data upload.

### D9 — Story-end review dispositions — LOCKED

All story-end review findings are accepted as must-fix in S16.1. The root runner
and helper live in a root-owned, non-user-writable directory and are published
only after the signed release has been verified. A request is snapshotted in a
root-owned work directory before it is interpreted; crash leftovers cannot
permanently block future work. Every post-request failure writes a terminal,
bounded `failed` status.

The database dump is validated as a PostgreSQL custom archive and its SHA-256 is
recorded in the keyed manifest before mutation. The UI compares durable status
with the current verified catalog target, so a completed earlier upgrade cannot
hide a later one or advertise an absent update. Old installs get an installer
repair instruction, never a command for a missing helper.

Repair preserves existing `.env` values except server-verified release fields;
staged managed assets are published only after verification. Upgrade assets are
updated from the same signed source snapshot as the Compose file. Public
installer compatibility is maintained across the `main`-before-tag interval.

## Non-goals

- Giving the API container Docker or root capability.
- Kubernetes/Helm upgrades; this story owns the public single-host Docker install.
- Downgrade, automatic rollback, or unattended/scheduled upgrades.
- Uploading air-gap bundles through the browser.
- Backup retention or deletion policy.
- Streaming raw host logs to the browser.
- Changing desktop-client auto-update behavior.

## Slices and stop condition

1. Installer completeness: install and repair the helper/runner/unit, with a
   contract test proving no required file can be omitted.
2. Host execution seam: pinned request validation, real backup, stage status,
   concurrency refusal, and focused shell tests.
3. API contract: CP-admin request/status endpoints, audit attribution, bounded
   filesystem adapter, OpenAPI generation, and authorization tests.
4. UI: explicit confirmation, direct request, reconnecting progress, backup
   facts, final health/failure state, and rendered authorization tests.
5. Box-walk: fresh `get.tunnex.io` install, real upgrade, API restart/reconnect,
   retained verified backup, and negative non-admin/concurrent-request legs.

Stop when those acceptance conditions pass. Do not add scheduling, rollback
automation, retention, Kubernetes support, or a general host-command framework.
