# S20.5 node timing and startup decision proposal

Status: **PROPOSED / HOLD — user disposition required before implementation.**

This document records the remaining review of findings 6, 7, and 29 against the
current AWS integration worktree. It proposes one bounded correction for manager
timing and one explicit startup transition for the node agent. It does not
authorize product edits, deployment, or qualification, and it is not a PLAN
checkpoint. The original ranked findings remain preserved.

The governing records are `S20.5-aws-reentry-decisions.md`, the locked D3/D4/D5,
D10/D10a–c and D11/D11a decisions in
`S20.5-kubernetes-zero-touch-lifecycle-decisions.md`, and the already documented
cleanup repair in `S20.5-node-cleanup-review-fix.md`. The node's existing HA
lease, durable fence, exact readback, and expiry requirements remain binding.

## Ranked current failure witnesses

| Rank | Finding | Current witness | Established consequence |
|---|---|---|---|
| P1 | 7 | `hostposture.Manager.ReconcileOnce` captures `now` before `OwnerSource.List` and all kernel work; `HeartbeatFreshness` and default API timeout are both 10 seconds | A completed attempt can publish an already-stale heartbeat. Both `--live` and `--ready` reject it because identity/freshness validation precedes the live-only distinction. |
| P1 | 29 | `hostposture.realCommandRunner.RunInput` calls `exec.CommandContext` with the process-lifetime context supplied by the manager | An `ip`/`nft` command can indefinitely stall the pass and heartbeat. The rtnetlink mutation timeout does not bound these subprocesses or their cumulative work. |
| P1 | 6 | `cmd/agent/main.go` returns on every `submitDesiredStateCommand(..., "desired_state_startup_base")` error, before `StartupReconcile`; deferred `backend.Close` drains the Kubernetes data plane | A transient initial desired-state GET failure, or an ACK transport failure after a successful apply, causes process exit and backend teardown. The continuing desired-state producer tolerates transport errors. |

The manager accepts API timeouts and reconcile intervals up to 30 seconds today.
Those settings make the 10-second heartbeat mismatch larger. Its startup probe
also invokes `--ready`: even a freshly reported API refusal cannot complete
startup, and repeated startup failures can restart a functioning blocked manager.
The existing `TestCheckManagerHeartbeatRejectsStaleAndBlockedReadinessButKeepsBlockedLiveness`
proves only an instantaneous fresh blocked heartbeat, not these delayed paths.

Finding 6 is broader than an initial GET: the current helper returns a single
error for fetch, apply, authority preparation, ACK transport, and durable ACK
checkpoint failures. These do not carry the same recovery authority.

Readiness and traffic preservation are separate claims. A restarted gateway has
not earned readiness, and an HA overlay cannot outlive its lease. Avoiding a
process exit removes destructive churn and permits recovery; it does not prove
uninterrupted LoadBalancer traffic or authorize serving from old observations.

## Proposed manager model: progress is not admission

**Decision M1 — recommended, HELD.** Keep the existing admission heartbeat and
its 10-second evidence freshness. Add one separate, bounded, atomically published
manager-progress record used only by `--live` and the startup probe. Do not add
fields to the existing strict heartbeat JSON: old readers reject unknown fields,
so an apparently additive change would break gateway admission compatibility.

The progress record contains only its own closed schema/contract, exact node,
manager Pod UID, manager boot ID, advancing sequence, publication time, and a
finite outcome (`started`, `completed`, or `blocked`). It contains no owners,
link receipts, or serving authority. The manager is its sole writer. The local
probe must match the expected exact Pod/node identity and reject invalid,
future, or expired timestamps. The writer advances sequence within a boot;
a stateless probe cannot independently prove advancement from one file read.
An otherwise valid recent record can therefore preserve liveness for at most
the progress freshness bound after its writer stops. It never establishes
owner admission. A fresh boot may publish `started` once, permitting one bounded
initial attempt. It cannot continually refresh `started` to hide a stalled
attempt.

The existing admission heartbeat remains the only input to gateway `--wait`:
two advancing active heartbeats from the same manager boot, both containing the
exact Pod UID, with successful current owner and kernel proof. Retain the
conservative owner-observation timestamp from the beginning of the successful
owner read. If its age exceeds 10 seconds by publication, publish blocked
admission instead of relabelling old proof as current. `--ready` continues to
require fresh successful idle/active evidence.

On API failure, the manager may enforce only the existing journal's retained
ownership as already permitted by D10/D11. It publishes blocked admission and
records a completed blocked attempt as progress. It never substitutes cached
owners for a new successful owner observation. Teardown still requires a
successful exact-node empty owner read and durable `restoring` intent.

| Event | Progress/liveness | Admission/readiness | Mutation authority |
|---|---|---|---|
| New manager process | Publish one exact `started` record | No new admission evidence | Existing journal and normal owner validation only |
| Bounded attempt running | Prior progress may remain fresh | Prior admission evidence expires normally; no refresh by a timer | Only the current serialized pass |
| Fresh owner read and exact kernel proof succeed | Publish completed progress after the attempt | Publish fresh active/idle heartbeat; active owner still requires two advancing proofs | Existing D10/D11 receipts |
| API/readback/timeout failure | Publish blocked progress after the attempt | Block; do not refresh successful owner evidence | Existing retained-enforcement or exact cleanup-retry rules only |
| Worker or durable I/O stops returning | No completion-driven progress refresh | Existing evidence expires | No background worker may claim successful completion |
| Manager process exits | Progress ages out | Admission ages out | Replacement re-enters from the durable journal |

The progress writer runs at attempt boundaries, not as an unconditional timer
goroutine. Successful progress publication cannot repair a failed journal or
admission-heartbeat write. Such a failure remains blocked even if the process
is alive. Independent files need no atomic joint success: progress conveys no
admission authority, and admission still requires its own exact readback.

**Decision M2 — recommended concrete budget, HELD.** Bound one attempt's API and
kernel work with a 40-second total deadline. Preserve the configured API timeout
of 1–30 seconds within that deadline; give all kernel operations together a
10-second sub-budget within the remaining attempt budget. No subprocess or
rtnetlink operation receives a fresh full budget after the shared deadline.
Command cancellation must terminate the invocation and bound output-pipe wait;
returning while an owned command continues mutating is not a completed attempt.

Keep the 2-second default interval, but validate the supported interval as
500 milliseconds–5 seconds in both chart/runtime validation. Use a fixed
60-second progress freshness bound: 40 seconds of API/kernel work plus at most
5 seconds between attempts leaves margin for ordinary publication and scheduling.
These are proposed product limits, not measured performance guarantees. A
successful pass whose owner evidence is older than 10 seconds is still blocked.

This intentionally tightens today's accepted 30-second reconcile interval and
allows a hung manager longer to fail its liveness check. Both effects require
explicit disposition. Local filesystem operations such as fsync are not made
cancellable by a context; a stuck durable write stops progress and is detected
by liveness expiry. Do not claim that the 40-second API/kernel budget proves a
hard wall-clock bound on filesystem I/O or an uninterruptible kernel process.

**Decision M3 — recommended, HELD.** Change the manager startup probe to `--live`.
Keep its readiness probe at `--ready`, and gateway initialization at `--wait`.
An API outage can then leave the manager running and visibly blocked while it
retries. It cannot make the DaemonSet ready or admit a gateway. The separate
progress file preserves old gateway heartbeat readers; regression must still
exercise old/new manager/gateway rollout and rollback combinations, including
absence of a progress file. Do not silently fall back from missing progress to
an unlimited liveness success.

## Proposed agent startup model: bounded base acquisition under lease authority

**Decision S1 — recommended, HELD.** Keep base-before-overlay replay on a
successful restart, but establish the durable lease guard before the first
network wait. Add a narrow startup-authority preflight in the existing lifecycle
owner; it strictly reads the durable lease/fence, classifies its state, and
registers the existing absolute expiry without replaying the overlay or issuing
a serving acknowledgement. It cannot extend a deadline, mint an authority,
erase corrupt evidence, or infer authority from surviving kernel state.

This is an explicit state-model change requiring independent review. Today
`Lifecycle.current` is nil until `StartupReconcile` loads it, so `LeaseDeadline`
and `Check` provide no expiry guard during an unbounded earlier retry. Simply
ignoring the initial error or looping before `StartupReconcile` is rejected.

| Startup state | Required transition | Permitted serving claim |
|---|---|---|
| `unverified` | Strict local lease/fence preflight before any base fetch | None |
| `withdrawal_required` | Absent, expired, corrupt, or clock-invalid authority enters the existing exact withdrawal path; retain evidence and block on uncertain cleanup | None |
| `base_pending_guarded` | A validated unexpired lease installs its existing expiry guard; make one bounded base acquisition attempt, capped at 5 seconds and the remaining lease lifetime | None; retained authority is never extended |
| `base_applied` | Apply the authenticated base through existing fences, then run the existing exact startup replay/withdrawal and readback | None until all existing readiness conditions pass |
| `withdrawn_retryable` | Base transport failed or its attempt budget expired; prove the existing scoped withdrawal, then retry base acquisition in-process with backoff | None until a later complete base/authority transition succeeds |
| `running` | Start/retain ordinary producers and lease watchdog under the same serialized mutation owner | Only existing current endpoint, data-plane, CNI, watch, and lease evidence |
| `blocked` | Invalid authority or unproved cleanup retains the existing fail-closed handling and evidence | None |

The guard must operate during both read-only fetch waits and serialized apply
work. Expiry cancels normal work and schedules exact withdrawal; a new attempt
never resets it. The startup preflight and replay must share the lifecycle's
identity/generation authority so an earlier preflight cannot authorize replay
of a subsequently changed checkpoint. The preflight is not a second writer of
lease state and must not checkpoint a lease as successfully replayed.

If the first bounded base transport attempt fails, the recommendation favors
prompt exact withdrawal followed by a live retrying process. A valid old lease
may be cleared only after the existing withdrawal readback succeeds, as the
current lifecycle already requires; recovery then waits for fresh control-plane
authority. Preserving that overlay across multiple unavailable-base attempts is
not proposed. Cleanup timeout/failure must not be relabelled as a safe retryable
transport failure. Do not bypass the existing shutdown/fail-closed path when
cleanup cannot be proved.

**Decision S2 — recommended, HELD.** Separate the helper's phase outcomes so a
base ACK transport failure after successful base application is pending
reporting, not a reason to destroy the process before startup lease handling.
Retry the exact ACK through the existing idempotent path after the lifecycle
guard/replay is established. An ACK HTTP success with failed durable checkpoint,
invalid desired authority, or failed substrate readback retains its existing
strict failure classification. No serving receipt is invented from a network
attempt, and successful desired application alone does not override readiness.

## Finding 4 is a separate serving-readiness decision

**Decision E1 — recommend retaining current fail-closed behavior; HELD.**
LoadBalancer discovery currently clears reportability after an uncertain API
read, and that generation change retracts readiness. Keeping old endpoint bytes
would not by itself preserve readiness or LoadBalancer traffic. D5 defines
successful Service truth and initial readiness, but no grace period for serving
from an old endpoint during an uncertain read.

Changing this requires a separate decision covering eligible failures
(transport/5xx versus 403/404/invalid Service truth), maximum last-good age,
Service/port/ingress identity changes, reporting versus serving readiness, and
recovery races. Do not bundle it into manager liveness or startup retry fixes.
The independent EndpointSlice/Service watch must retain its existing
fail-closed stale-Pod-IP rule; relaxing it is not an implied consequence of E1.
The current early-EOF withdrawal is explicitly tested and follows S10.3 WF-K5.

## Required regression matrix before a dispositioned implementation is accepted

| Surface | Injected witness | Required proof |
|---|---|---|
| Manager timing | Owner success/error consumes the configured API timeout | Completed blocked progress is live; stale/failed owner evidence never admits a Pod |
| Manager timing | Kernel runner waits for cancellation; several commands consume one budget | Shared deadlines bound total API/kernel work; no post-timeout mutations or unconditional progress refresh |
| Manager timing | Default, boundary, and rejected interval/timeout values | Runtime/chart agree; the proposed 5-second interval maximum is explicit; admission remains 10 seconds |
| Manager probes | Initial API outage exceeds the previous startup window | Process remains live while startup can finish; readiness and gateway wait remain blocked |
| Manager authority | API error with retained owners or durable `restoring` | No fabricated empty-owner proof, new owner admission, or wrong-direction mutation |
| Manager cleanup | Cancellation after an exact primitive and before final journal publication | Durable `restoring` survives; retry performs only old epoch cleanup and never recreates an active missing link |
| Manager persistence | Admission/progress publication fails independently; prior-process or foreign-Pod record remains | Progress cannot authorize admission; foreign-Pod/expired records fail liveness; recent prior-process progress expires within the stated bound; unknown durable state stays blocked |
| Manager rollout | Old/new heartbeat reader and manager combinations, including rollback | Existing admission JSON remains readable; new progress checks fail closed on missing/invalid evidence |
| Agent startup | Initial GET fails once then recovers | Exact withdrawal precedes retry where required; transport failure alone does not repeatedly close/reopen the backend |
| Agent startup | Valid lease expires during base fetch/apply | Original expiry controls cancellation/withdrawal; no pre-startup retry window extends authority |
| Agent startup | Missing/corrupt/expired checkpoint or backward wall clock | No base wait postpones required fail-closed handling; no corrupt evidence is silently overwritten |
| Agent startup | Base application succeeds; ACK transport fails then succeeds | Lease handling runs and exact ACK retries without process teardown or fabricated delivered checkpoint |
| Agent startup | ACK checkpoint, substrate readback, or withdrawal fails | Failure remains distinct from transient transport; no readiness, success receipt, or unproved safe-retry claim |
| Agent lifecycle | Shutdown during fetch, retry, or a command | Cancellation is bounded; legitimate shutdown still performs existing drain and exact cleanup |
| Readiness | Process progress remains healthy while owner, endpoint, CNI, or watch proof is blocked | Liveness does not set `/readyz`, admit a gateway, or promise traffic continuity |

Tests should use injected clocks, fake API/command seams, temporary durable
stores, and actual state-machine composition. They must not execute host
networking or cloud actions. Feature-sized lifecycle/timing changes require
fresh independent review. Unit evidence is a substitute, not the required live
qualification proof.

## Disposition requested and boundaries

The concrete recommendations needing disposition are M1 (separate progress
authority), M2 (40/10/5/60-second work/interval/liveness limits), M3 (startup
uses liveness), S1 (guarded single base attempt, then exact withdrawal and
in-process retry), S2 (phase-aware ACK transport recovery), and E1 (retain the
current endpoint fail-closed policy pending a separate choice). Approval of one
does not silently approve a conflicting alternative for another.

No proposed change resets committed link receipts, recaptures a post-reboot
baseline, or creates a new host ownership epoch after ordinary reboot. S20.6
host-reboot rebootstrap remains deferred. S20.5.1 Windows terminal-uninstall
recovery and S20.5.2 private rollout recovery remain unchanged. There is no
provider-specific networking remedy, new CNI adapter, or automatic cloud change
in this proposal.
