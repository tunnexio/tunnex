# 1. ⛔ THE FINDING — **THE SPEC DESCRIBES THE SHAPE OF A REQUEST, NOT THE EXISTENCE OF A CAPABILITY**

Every idp-sync path enumerates `provider: [microsoft, google]`. The **server answers Google with
`400 provider_not_supported`** — *"directory sync currently supports microsoft only"*.

It is deliberate and documented: `supportedProvider` (`enterprise/idpsync/service.go:83`) rejects at CONFIG
time on purpose, and its comment says the enum keeps google **for forward-compat** while the capability gate
lives in the service.

> ## **FOUND BY READING THE SERVED PAYLOAD. The spec, the handler signature and the generated schema all**
> ## **read as though Google works — only `curl` disagreed.**

**The cost of missing it is a dead end that looks like a bug in our product:** without a fourth arm, a non-404
falls into `unknown`, so Google renders *"status unknown"* with a **Retry that can never succeed**, above a
**Configure form for a credential the server refuses to store.** That is "never imply an action it did not
perform", produced entirely by trusting the contract over the response.

**Fourth instance of `edition.ts`'s lesson in a new costume:** a generated artifact describes what is
*expressible*, never what is *implemented*.

---

# 2. ⛔ CHECK 7b — THE UN-MAP BLAST RADIUS, one screen over from S14.12's cascade

`UnmapGroup` (`enterprise/idpsync/service.go:276`) does three things and the **204 mentions none of them**:

1. unbinds the group from the directory,
2. **`DeleteGroupMembersByGroup` — deletes every member row**,
3. `PushOrgNodes` — re-pushes org-wide, so access changes immediately.

⛔ **THE GROUP SURVIVES**, as an empty manual group. So policy rules referencing it are **not**
cascade-deleted the way S14.12's group-delete cascade works — **they stay, still look enforced, and match
nobody.** That is the quietest possible failure mode, and it is the opposite shape from the cascade: there,
deleting a group destroyed rules silently; here, un-mapping *preserves* rules and empties them.

**Typed confirm + four named consequences. NO COUNT** — the server serves no preview and the 204 has no body,
so a client-computed member count would be a second source of truth about what the server is about to do.

---

# 3. ⛔ FAIL-STATIC, SAID OUT LOUD — the thing a health badge cannot carry

The reconciler is fail-static (S7.5.2): a failing poll does **not** empty the groups, it keeps the last good
membership. **Safe for availability, unsafe for deprovisioning** — a user removed in the directory **keeps
their access here** for as long as sync is broken.

"Degraded" implies the opposite to most readers. The panel says it in words.

Tiers are MEASURED from `ClassifySyncHealth`, not invented: the ceiling is **3× the 10-minute poll interval =
30 minutes**, anchored on the last SUCCESSFUL sync — or on creation, so a credential that is wrong from birth
still escalates. **An unrecognised tier fails toward ESCALATED**, never toward ok.

# 6. ⛔ AND S14.12's SCREEN WAS OFFERING AN ACTION THE SERVER ALWAYS REFUSES

`AddGroupMember` answers **`409 idp_managed_group`** — *"this group is managed by directory sync; members
cannot be edited manually"* (`enterprise/policy/service.go:125`). **The web read `origin` NOWHERE**, so
Access's `GroupRow` gated Add/Remove on `canManage` alone and rendered them on synced groups too.

**Every use of those controls was a guaranteed 409**, and the only place that fact was written down was a
server error string nobody could reach without clicking. Now: a `DIRECTORY` badge, the controls withheld, and
a note naming where membership CAN be changed.

⚠ **The DELETE control stays.** Deleting a synced group is genuinely allowed; only MEMBERSHIP is the
reconciler's. Hiding the wrong verb trades one wrong affordance for another.

# 7. FOUR THINGS FROM THIS PASS

1. ⛔ **The `operator` role — the type was right and my justification was wrong.** I asserted `operator`
   distinguishes `policy:manage` from `org:update`; TypeScript refused the value. **The reflex there is to
   widen the type.** Measured instead: `memberships` CHECKs `role IN (owner, admin, member)` — `operator` is
   a MACHINE role that never renders a UI. The generated type was correct and the test I was writing was
   about a session that cannot exist.
2. **Tightened the open-edition SSO test from a proxy string to the property** — the IdP upsell legitimately
   contains "Microsoft Entra", so the matcher had become ambiguous. It now asserts *no configuration surface
   in open* (no credential inputs, no Configure/Sync control) plus that the degradation is still an
   Enterprise sentence. **Fourth instance of measure-the-property-not-the-proxy.**
3. **`seed`'s `docker run` never passed `TUNNEX_SEED_FORCE` through**, so the one-command switch could not
   re-seed an accumulated database. **The guard was correct and the plumbing was not** — the open DB held
   **71 real orgs** left by a Go test run pointed at it while diagnosing the long-lived-dev-DB class. Fixed
   the target.
4. ⛔ **A MUTATION SURVIVED AND THE HONEST ANSWER IS THAT IT SHOULD HAVE.** Swapping the gate to `org:update`
   changed nothing, because both permissions are held by exactly owner+admin among user-assignable roles.
   **No behavioural test can distinguish them today.** So the test pins the PREMISE instead — if the mirror
   ever splits them for a human role, it fails loudly. *Recording a survivor as unfixable-and-why is a
   different claim from a survivor left unexplained.*

# 8. REGISTERED — **ranked**

## ⛔⛔ #1 — THE INVITATION WORKFLOW. **THE ONLY WRITE-ONLY STATE THAT IS ITSELF AN ACCESS GRANT.**

Ranked ABOVE the rest of the write-only-state register, and the reason is a category difference, not a
severity guess:

> ## **THE OTHER THREE ARE CONFIGURATION, WHOSE EFFECT IS VISIBLE SOMEWHERE ELSE ON THE SCREEN.**
> ## **A PENDING INVITATION IS INVISIBLE *AND GRANTS ORG MEMBERSHIP WHEN ACCEPTED*.**

`POST /domains`, `PUT /pool-cidr` and `PUT /idp-sync/{provider}` all write settings you can infer from
behaviour: a pool has an address range, sync has a health tier, a domain either captures signups or does not.
**An outstanding invitation has no observable effect until the moment it becomes a member** — and by then the
grant has already happened.

Measured in §10: there is **no `GET …/invitations`**, and `resendInvitation` / `revokeInvitation` are keyed by
**`EmailRequest`** — an address, not an id. **So an invitation cannot be listed, and can only be revoked by
someone who already knows the exact address they typed.** A mistyped or mistaken invite is, in practice,
unrevokable.

**Next server story. All three verbs together** — the read plus both mutations — so the workflow lands whole
rather than as two buttons keyed by a string nobody can recall.

# 10. ⛔ AND THE INVITATION WORKFLOW IS THE WORST WRITE-ONLY STATE IN THE PRODUCT

**MEASURED, and it is not "two missing buttons":**

- There is **NO `GET …/invitations`**. Only `POST` create, `POST` resend, `POST` revoke (`openapi.yaml:1638`,
  `:1662`, `:1686`). An operator **cannot list pending invitations at all.**
- Both mutations are keyed by **`EmailRequest` — an email address, not an invitation id.**

Put together:

> ## **YOU CANNOT REVOKE AN INVITATION YOU CANNOT LIST. The only way to revoke or resend one is to already**
> ## **know the exact address you typed — which the product never shows you again.**

**This is the fourth write-only-state instance and the most consequential.** The other three are
CONFIGURATION whose effect is visible somewhere else on the screen. A pending invitation is invisible **and
grants org membership when accepted** — so a typo'd or mistaken invite is, in practice, **unrevokable**, and
nothing in the UI will ever show that it is outstanding.

**It is also why S14.11's `listInvitations` note was ranked as a broken workflow rather than a missing
column** — that ranking is now measured rather than asserted.

**NOT BUILT HERE, and the reason is the D3 precedent, not scope fatigue:** the fix needs a **read that does
not exist**, and this register has ruled twice that we name write-only state rather than invent GETs. Adding
`GET /invitations` is a spec change plus a handler — **a server story, and it should carry the two mutations
with it** so the workflow lands whole instead of as two buttons keyed by a string nobody can recall.

**Registered as the recommended next story.** Everything needed to scope it is above.
