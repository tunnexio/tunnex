# Parent integration contract

Branch `story/sandbox-agent-delegation` starts at committed sandbox foundation `9b5d17d`. Migration0180 is reserved;0180 can be tested without0179, but merge after saved keys0179 and before optional runner0181.

The parent owns OpenAPI/router/generation. Merge the maps in `S-sandbox-agent-delegation-openapi.yaml`, update the existing lifecycle operation descriptions to explain owned machine delegation, then `make generate`. `sandbox:delegate_manage` is owner/admin-only and mutating; regenerate the RBAC mirror. No node role or machine operator role gains a general sandbox permission.

The tested independent adapter `RegisterSandboxDelegationRoutes` is for routers whose OpenAPI operation dispatch is coordinated manually. On the normal generated strict router, implement the three generated apiServer methods using the existing `sandboxDelegationRepository` assertion on `s.sandboxes`, `authorize(ctx, org, rbac.PermSandboxDelegateManage)` and an explicit `!p.IsMachine() && !p.IsAgent()` human check before body parsing. Then call `SetDelegationEnabled`, `IssueDelegation`, `RevokeDelegation`. Derive grant OrgID and OwnerID from the path and authenticated human; never accept request owner fields. Convert selected network tuples exactly as existing sandbox create does. Return204,201,204 respectively; map store errors through sandboxError except IssueDelegation ErrConflict ->409 sandbox_delegation_conflict and ErrDisabled ->403 sandbox_delegation_disabled, as the independent adapter does. Do not register raw routes and generated dispatch for the same paths.

No router/OpenAPI/generated artifact changes are committed here to avoid collision with the saved-key worker. Parent integration is required before human grant API endpoints become reachable. Existing create/get/action handlers already call the transactional store seam; without explicit organization opt-in and a grant they deny machines.

CLI: `TUNNEX_SERVER=https://...` and `TUNNEX_MACHINE_TOKEN` must be supplied through the existing secret environment. `tunnex sandbox create --org UUID --request request.json --idempotency-key stable-key`; `get --org UUID --id UUID`; `start|stop|delete --org UUID --id UUID --generation N`. JSON uses the existing SandboxCreate schema. It reads no human credential store, accepts no cookie, and retries nothing automatically. Read generation with get and retain the same key after uncertain creation. The machine can only read/act on grant-created instances, not the human inventory. No terminal/bootstrap/enrollment endpoint is delegated.

Grant revocation, expiry, organization opt-out, credential revocation/reassignment and current human membership are checked for lifecycle/readback and runtime credential authentication. Explicit grant revoke atomically audits and requests deletion with one new generation for each retained grant-created instance; it does not touch human-created or other-grant instances. Existing orchestrator/qualification/cleanup inventory batches sweep invalid delegation authority for expiry, opt-out, credential revocation/reassignment and owner offboarding. Human owners/admins retain existing cleanup. Revocation is pending cleanup until the existing reconciler verifies network/provider removal; existing SSH sessions are not asserted closed by a database update. An offline runner receives withdrawal when connectivity returns; its absolute local TTL remains the hard bound. Current runtime binding, per-user/org quotas, resources and900second cap remain authoritative. No grant activates a worker, changes routing, expands resource caps or provisions cloud infrastructure. Separate live approval is required to select an existing credential, enable organization delegation and issue a concrete grant; activation also depends on separately qualified/approved runtime configuration.
